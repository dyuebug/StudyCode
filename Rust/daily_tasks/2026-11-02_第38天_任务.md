## 📝 具体任务

1. [ ] 补任务单条接口（预计 60 分钟）
   - `GET /tasks/{id}`（含标签）、`PATCH /tasks/{id}`、`DELETE /tasks/{id}`
   - `PATCH` 用 `Option<Option<T>>` + `deserialize_some` 实现三态
   - **动手 A（必做）**：先删掉 `deserialize_with = "deserialize_some"`，
     跑 `patch_due_at_is_three_state`，观察"显式 null"那一步失败的样子：
     `left: "2026-11-30"`（没清掉）。这就是"不报错的 bug"。

2. [ ] 状态机（预计 50 分钟）
   - `models.rs` 加 `TaskStatus`：`as_str` / `parse` / `can_transition_to`
   - `PATCH /tasks/{id}/status`，非法跃迁 409，未知值 400，同值幂等
   - **动手 B（必做）**：把 `can_transition_to` 里 `(Todo, Done)` 加上，
     看哪条用例变红，说明"为什么这条规则必须由代码而不是文档来保证"

3. [ ] 标签多对多（预计 60 分钟）
   - `POST /tasks/{id}/tags`、`DELETE /tasks/{id}/tags/{name}`
   - 三步写入放进一个事务：`INSERT tags` → `SELECT tag_id` → `INSERT task_tags`
   - **动手 C（必做）**：把中间表的 `PRIMARY KEY (task_id, tag_id)` 去掉，
     重复贴同一个标签，观察 POST 返回里出现两个一样名字——
     这就是"数据库约束才是最终去重手段"的证据

4. [ ] 条件查询 + 执行计划（预计 60 分钟）
   - `GET /projects/{id}/tasks?status=&priority=&limit=&offset=`
   - 新增 `examples/explain_plan.rs`，造 2000 行，对比三种写法：
     1. 只有 `project_id`
     2. `project_id + status`
     3. `project_id AND (? IS NULL OR status = ?)`
   - **动手 D（必做）**：把 `ORDER BY priority, id` 去掉再跑一次，
     说明 `USE TEMP B-TREE FOR ORDER BY` 这一行是**谁**产生的

## 💡 学习建议

1. 先写"非法输入"的断言，再写实现——反过来的话你会想不出该断言什么
2. 三态、级联、状态机这三条都是**静默失败**型的 bug：
   不写断言，代码"看起来对"，运行也"看起来对"
3. `EXPLAIN QUERY PLAN` 不要只看有没有 `USING INDEX`，
   要看**用了索引的哪几列**——`(project_id=?)` 和 `(project_id=? AND status=?)` 差别很大
