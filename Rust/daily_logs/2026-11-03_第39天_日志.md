### 2. 真 500：JSON 响应 + 日志留真因

做法：`DROP TABLE tasks` 之后请求 `GET /projects/1/tasks`。

```
客户端看到：{"success":false,"code":"internal","message":"服务器内部错误，请稍后重试或联系管理员"}

服务端日志：[ERR] 内部错误: error returned from database: (code: 1) no such table: tasks
```

用例断言了 body 里**不含** `no such table` / `tasks` / `SELECT` / `sqlx` / `sqlite`。
这条断言才是"不泄漏"的证据；只写一句"我们做了统一错误层"是没有意义的。

### 3. 错误形状一致（实测 key 集合）

```
404 → ["code", "message", "success"]
400 → ["code", "message", "success"]
409 → ["code", "message", "success"]
```

三种状态码，同一个形状。这条用例锁的是**形状**而不是字段值——
形状不一致时客户端不会报错，只会在 `unwrap()` 上 panic（第 38 天踩过）。

### 6. 【修正】"没撞上"不等于"撞不上"

自然压测一次 BUSY 都没撞出来，这个结果**不能**得出"并发没问题"。
写事务只有几十微秒，撞锁概率本来就低。所以补了一个确定性实验：

`examples/hold_lock.rs` 用 `BEGIN IMMEDIATE` 抢住写锁并睡 3 秒，
期间发写请求：

| `busy_timeout` | 客户端看到 | 耗时 | 服务端日志 |
|---|---|---|---|
| `0` | `500 {"code":"internal"}` | **0.0013 s** | `[ERR] 内部错误: ... (code: 5) database is locked` |
| `5000` | `201 Created` | **3.045 s** | `[LOG] #2 POST ... → 201 Created (3045 ms, >=1s)` |

结论比"busy_timeout 很重要"精确得多：

- `busy_timeout=0` 时失败是**几乎立即**的（1.3 ms），它不是"稍后重试"，是"根本不等"
- `busy_timeout=5000` 时请求**成功了**，代价是 3 秒延迟——
  而这 3 秒只有耗时分桶才捞得出来
- `busy_timeout` 决定的是**失败前等多久**，不是**会不会失败**

### 7. 压测里踩的两个坑（都是"尺子坏了"）

**坑 1：并发追加同一个文件会丢行。**
第一版脚本让 20 个进程 `>> "$OUT/codes.txt"`，200 个请求只记到 **105 行**。
服务端日志却显示 200 个请求全部 201。丢的是**测量数据**，不是请求。
改成"每个请求写自己的文件，最后合并"，同一场景立刻变成 200/200。

> 这个坑值得单独记：如果只看脚本输出，结论会是"服务丢了一半请求"。
> **测量工具本身没有测试，它坏掉时也会给出很像真的数字。**

**坑 2：Git Bash 里 curl 发中文 → 100 个请求全 400。**

```

```

`description` 写了中文，终端按本地代码页（GBK）编码发出去，服务端收到非法 UTF-8。
单发一次 ASCII 请求就正常 201。**先怀疑请求本身是否合法**，再去怀疑服务端逻辑。

## 📖 学到的知识点

### 1. `ResponseError` + `From<sqlx::Error>` 让 `?` 变成错误策略

```rust
impl ResponseError for ApiError { fn status_code(&self) ... ; fn error_response(&self) ... }
impl From<sqlx::Error> for ApiError { fn from(e: sqlx::Error) -> Self { Self::Internal(e) } }
```

于是 handler 里只剩 `sqlx::query(...).await?;`。
**关键不是少写几个字符，是"漏写"变得不可能**：18 个出口，
每个都手写 `map_err` 时漏一个不会报错，只会在某天开始返回纯文本。

### 2. 一个错误类型里要区分"给谁看"

`ApiError` 四个变体里只有 `Internal` 装了下层错误：

- `Display`（进日志）→ 带 `sqlx::Error`，运维要看真因
- `error_response`（给客户端）→ 固定文案，客户端拿 SQL 片段没用，攻击者有用

**同一份错误，两套文案**，这不是重复，是受众不同。

### 3. `From<sqlx::Error>` 不等于"所有错误都该自动 500"

`corrupted_data`（库里出现枚举外的状态值）**没有**走 `ApiError::Internal`：
它不是"下层炸了"，而是我们自己判断出数据坏了，文案已经决定好给客户端看。
硬塞进 `Internal(_)` 反而要造一个假错误。这是 `From` 转换的边界。

### 4. 请求 ID：进程内 `AtomicU64` 就够，UUID 是下一个层级的事

单进程多线程用计数器即可；跨进程/跨服务才需要 UUID 或 trace id。
`Ordering::Relaxed` 足够——这里只要求"不重复"，不要求跨线程的 happens-before。

### 5. 耗时分桶 = 手工版 histogram

`<10ms / <100ms / <1s / ≥1s` 让日志可聚合：`grep '≥1s'` 直接筛慢请求。
真上监控时换成 `metrics::histogram!`，**桶边界不用重想**——
分桶这件事本来就是监控系统的第一等公民，只是先用手工版理解它。

### 6. `BEGIN IMMEDIATE` vs `BEGIN`（DEFERRED）

`BEGIN` 只拿读锁，第一次写才升级；升级失败拿到的 `SQLITE_BUSY`
**不能靠重试解决**（snapshot 已过期）。`BEGIN IMMEDIATE` 一上来就抢写锁，
是 SQLite 官方推荐的多写者模式。做复现实验时这一点尤其重要：
用 DEFERRED 可能根本占不住写锁，实验就"成功"了但什么也没证明。

### 7. 4 worker ≠ 4 个写者

4 个 worker 是 4 个**线程**，各有 App 实例，但共享同一个连接池；
而 SQLite 的写锁是**文件级**的，同一时刻只有一个写事务。
所以"加 worker"提高的是并发处理能力，不是写入吞吐——
这条在 §5.9 的实验里变成可看见的事实。

### 8. 证据分级不是形式主义

今天有三处原本可以"写得很好看"的结论，最后都降级或改写了：

| 想写的 | 实际的 |
|---|---|
| "并发 200 全部成功，性能良好" | 只有成功率与耗时极值，没有 TPS/延迟分位 |
| "并发下没有 SQLITE_BUSY" | 短事务撞不上，不能代表高并发安全 |
| "busy_timeout 解决了锁争用" | 只是把失败推迟；5 秒也会被吃完 |

## 💭 今日心得

今天最值钱的不是错误层，是**那个只记到 105 行的压测脚本**。

它差一点让我得出"服务丢了近一半请求"的结论——而且这个错结论**有数字支撑**，
比凭感觉的猜测更有说服力，也更危险。真正救回来的动作是"去对一下服务端日志"：
服务端说 200 个全成功，脚本说只收到 105 个，两边不一致 → 一定是**其中一边的观测坏了**。
测量工具和被测系统**必须能互相验证**，这是今天最实在的一条工程习惯。

第二件事是 `busy_timeout`。一天里我对它的理解变了三次：

1. 一开始（第 37 天）："设 5 秒，防止数据库锁住" —— 当开关用
2. 压测没撞出 BUSY 时："看来并发没问题" —— 把'没观测到'当成'不存在'
3. 做完 `hold_lock` 实验才明白：它决定的是**失败前等多久**，不是会不会失败；
   而成功但慢 3 秒的请求，如果没有耗时桶，日志里看起来和正常请求一模一样

这三步里，第 2 步是最容易停下来的地方——因为那一步已经有"跑过压测"的形式了。
**形式上的验证比没有验证更危险**，它会让人提前结束思考。

第三个感受：`ResponseError` 那三行代码是今天最简单的部分，
但它是唯一一个"写对之后永远不会退步"的部分——
因为它把"不许泄漏"从**人的自觉**变成了**类型系统**。
