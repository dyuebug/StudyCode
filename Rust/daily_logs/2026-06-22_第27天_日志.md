## 📖 学到的知识点

### 1. 原子写入模式（atomic write）

```rust
// 序列化 → 写临时文件 → 原子重命名
let json = serde_json::to_string_pretty(todos)?;
fs::write(tmp_path, json)?;
fs::rename(tmp_path, self.file_path)?;
```

**为什么不能直接写目标文件？**
直接 `fs::write("todos.json", ...)` 在写入中途崩溃（断电、panic、kill -9）会留下**半截 JSON**，下次启动反序列化直接失败，数据永久损坏。

**三步法保证什么？**
- 写 `.tmp` 失败 → 原文件完好
- rename 失败 → 原文件完好
- rename 成功 → 要么旧内容、要么新内容，**不存在中间态**

关键前提：`fs::rename` 在同分区内是原子操作，这是 POSIX 和 Windows `MoveFileEx` 的保证。**跨分区 rename 退化为复制，不再原子**。

### 2. `AppState` 从类型别名改为结构体

```rust
// 旧：单一类型，无法扩展
pub type AppState = Arc<Mutex<Vec<Todo>>>;

// 新：可组合多字段
#[derive(Clone)]
pub struct AppState {
    pub todos: Arc<Mutex<Vec<Todo>>>,
    pub persistence: Arc<Mutex<PersistenceManager>>,
}
```

**问题**：改成结构体后，原来 `state.lock()` 的所有调用点全部失效，需要改成 `state.todos.lock()`。这是**破坏性重构**，但比继续堆 `Arc<Mutex<(Vec<Todo>, PersistenceManager)>>` 元组要清晰得多。

### 3. 锁的持有时间最小化

```rust
// 先克隆数据，立即释放锁
let todos = self.todos.lock()?.clone();

// 再拿另一个锁做 I/O
let persistence = self.persistence.lock()?;
persistence.save(&todos)?;
```

**为什么克隆？** 文件 I/O 可能耗时几十毫秒，如果一直持有 `todos` 锁，期间所有读请求（GET /todos）全部阻塞。先克隆后放锁，把锁的临界区压缩到「复制一个 Vec」，I/O 在锁外完成。

**代价**：每次保存克隆整个 Vec。数据量大时（上万条）应改用 `Arc<Vec<Todo>>` 或分页。

### 4. 两个独立 Mutex 的加锁顺序

`save_to_file()` 固定按 `todos → persistence` 顺序加锁。**若其他地方按相反顺序加锁，会死锁**。当前代码只有这一处同时持两把锁，安全；一旦新增路径必须沿用同一顺序，或改用单一锁。

### 5. 优雅降级：保存失败不阻断 HTTP 响应

```rust
if let Err(e) = state.save_to_file().await {
    eprintln!("保存失败: {}", e);
}
// 仍然返回成功响应
```

内存中的数据**已经提交**，HTTP 响应如实说明"操作成功"；保存失败是持久化层问题，记录日志而非回滚。这是**写后缓存（write-behind）**的简化形态。代价：崩溃时丢失最后一次未落盘的修改。

### 6. 首次运行视为正常情况

```rust
pub fn load(&self) -> Result<Vec<Todo>, String> {
    if !Path::new(&self.file_path).exists() {
        return Ok(vec![]);  // 不是错误
    }
    // ...
}
```

文件不存在 = 第一次启动，返回空数组而不是 `Err`。**把预期内的状态建模成正常分支，而不是错误分支**，避免启动时刷一堆无意义的红色日志。

## 💭 今日心得（推定）

第 26 天完成 CRUD 时，`todo-api` 只是个"演示品"——重启即失忆。加上持久化后，它第一次具备了**真实软件的属性**：状态跨进程存活。

真正有意思的不是 `serde_json` 的用法（那是第 19 天学的），而是**原子写入这个模式**。它把"文件写入"从「一次操作」重新理解为「两个操作 + 一个原子切换点」。这个思路在数据库（WAL、双写缓冲）、Git（对象先写后改 ref）、配置中心都是同一个形状。**理解了 rename 的原子性，就理解了几乎所有本地持久化方案的底层假设。**

另一个收获是**降级策略的设计取舍**：保存失败该不该让请求失败？这里选了"不回滚、只记日志"，因为它假设"内存是对的，磁盘迟早会追上"。换成金融场景就必须反过来——**这不是对错问题，是数据重要性决定的设计选择**。
