### 3. 【修正】"`OR` 会让 SQLite 放弃索引" —— 这句话说过头了

原判断：`WHERE project_id = ? AND (? IS NULL OR status = ?)` 会导致 SQLite
**放弃索引、全表扫描**。

实测：**没有全表扫描**。它用的是 `idx_tasks_project (project_id=?)`，
也就是复合索引的**前缀**；真正的损失是 `status` 那一列用不上——
`idx_tasks_project_status` 的第二个列白建了，且每行多判一次 `OR`。

正确的说法是：**`OR` 让复合索引的后半段失效**，不是"索引全部失效"。
这类"听起来很有道理"的性能断言，必须用执行计划验证。

### 4. 三条与"排序"有关的结论

| 查询 | 是否用索引 | 是否额外排序 |
|---|---|---|
| `WHERE project_id=?` | `idx_tasks_project` | **是**（TEMP B-TREE） |
| `WHERE project_id=? AND status=?` | `idx_tasks_project_status` 两列 | **是** |
| JOIN 按 `t.id` 定位 | `INTEGER PRIMARY KEY (rowid)` | 否 |
| JOIN 校验归属 | `idx_projects_owner` 覆盖索引 | 否 |

`ORDER BY priority` 永远要临时 B-Tree——**没有任何索引以 `priority` 起始**。
想省掉这次排序得建 `(project_id, priority)`，代价是多一份写放大；
2000 行量级不值得，先记下来不动手。

### 5. 一次"六个接口同时 500"的真实排查

刚接完 `/tasks/*` 路由，六个用例一起红：

```
[LOG] PATCH /tasks/1 → 500 Internal Server Error (1 ms)
[LOG] DELETE /tasks/2 → 500 Internal Server Error (1 ms)
[LOG] POST /tasks/1/tags → 500 Internal Server Error (1 ms)
```

`GET /tasks/{id}` 却正常。原因：归属校验用的 JOIN 里，
列清单常量是 `id, project_id, title, ...`，而 `tasks` 和 `projects` **都有 `id`**
→ SQLite 运行时报 `ambiguous column name: id`。

**这是运行时错误，编译期看不出来**，而且只影响走 JOIN 的那组接口。
修法：给 JOIN 单独一份带 `t.` 前缀的列清单（`TASK_COLUMNS_ALIASED`）。

> 排查范式：**"一组接口同时挂、另一组正常"** → 先找这组共用的那条 SQL，
> 再看有没有裸列名 / 拼错的表别名。

### 6. `error[E0716]`：临时值在借用期间被释放

```rust
let mut q = sqlx::query(&format!("EXPLAIN QUERY PLAN {sql}"));   // ❌
// error[E0716]: temporary value dropped while borrowed
```

`sqlx::query` 返回的 `Query<'_>` 借用了那段字符串，而 `format!` 的临时值
在这条语句结束就被释放。改成先 `let full_sql = format!(...)` 再借用即可。
**`&format!(...)` 几乎总是一个错误**——它的生命周期只到语句末尾。

### 7. 两条"测试假设错了，而不是代码错了"

| 失败断言 | 我以为 | 实际 |
|---|---|---|
| `重复贴同一标签不应产生第二行` → `left: 2` | 任务 1 没有标签 | 种子数据里任务 1 已挂 `rust` |
| `body_json(resp)["data"]["tags"].as_array().unwrap()` → panic | 贴/撕标签返回 `{task, tags}` | 返回的是 `data: [...]` 本身 |

第二条尤其典型：形状不对时**不会报"形状不对"**，只会在 `unwrap()` 上 panic，
错误信息完全指不到真正的原因。断言前先确认响应形状。

### 8. 失败用例会留下临时目录

8 个失败跑留下了 8 个 `$TEMP/task-manager-test-*`，已按字面名逐个删除。
原因：`cleanup()`（真正 `pool.close()`）在断言失败后不执行，
而 `Drop` 只能删文件、关不了异步连接池。目录名带 pid + 序号，能定位是哪次跑的。
**这不是 bug，是"清理依赖正常退出"的固有局限**，已写进 README。

## 📖 学到的知识点

### 1. `Option<Option<T>>` 的三态必须靠 `deserialize_with` 才能成立

- 字段缺失 → `None` → 不改
- `null` → `Some(None)` → 清空
- 有值 → `Some(Some(v))` → 写入

serde 默认把 `null` 也解析成外层 `None`，与"缺失"无法区分。
不加 `deserialize_some` 的后果是"清空"永久失效，**且不报错**。

### 2. 一条 UPDATE 优于"读-改-写"

`COALESCE(?, col)` 处理"没给就保留"，
`CASE WHEN ? = 1 THEN ? ELSE col END` 处理"给了就写（含 NULL）"。
好处不只是少一次往返，而是**避免丢失更新**：并发改不同字段互不覆盖。

### 3. 状态机必须有唯一入口

`PATCH /tasks/{id}` 不接受 `status`，只能走 `/status`。
未知值 400（客户端写错）、非法跃迁 409（形状对、语义错）、同值 200（幂等）。
枚举的穷尽 `match` 在这里才有价值——第 37 天用 `String` 是对的，今天换成枚举也是对的，
**取决于"是否需要判断迁移合法性"**。

### 4. 多对多：删的是边，不是点

`DELETE /tasks/{id}/tags/{name}` 只删 `task_tags` 关联行。
标签是全局共享资源，删点会波及别的任务。

### 5. `ON DELETE CASCADE` 的前提是 `foreign_keys(true)`

写在迁移里不等于生效。`delete_project_cascades_tasks` 这条用例
真正验证的是 `db.rs` 里那个开关，而不是 SQL 语法。

### 6. 复合索引：第二列只在"确定条件"下有用

`(project_id, status)` 在 `WHERE project_id=? AND status=?` 时两列都用上；
写成 `? IS NULL OR status=?` 就只用上前缀。
**索引不是"建了就生效"，是"条件形状匹配才生效"。**

### 7. `JOIN` 的列名歧义是运行时错误

`tasks`/`projects` 都有 `id` 时，`SELECT id` 会报 `ambiguous column name`。
编译期无感知 → 表现为一组接口 500。
解决办法：JOIN 用带别名的列清单常量。

### 8. `&format!(...)` 借用不到临时值

`error[E0716]`。凡是要把字符串借给某个结构体（含 `Query<'_>`），
先 `let` 出来。

## 💭 今日心得

今天所有的时间几乎都花在**同一种 bug** 上：**静默失败**。

- `Option<Option<T>>` 不加 `deserialize_with` → 清空功能失效，不报错
- 不写 `foreign_keys(true)` → 级联删除不生效，不报错
- `can_transition_to` 少一条规则 → 非法跃迁通过，不报错
- `SELECT id` 含糊 → 报 500，但**编译期毫无征兆**

共同点：**它们都不会在"写代码的时候"暴露自己**。只有断言能暴露。
所以第 36 天那句"测试的价值 = 它会不会自己说不"，今天得到了具体的样子：
这 17 条用例里真正值钱的是那 4 条**证明型**的（三态、非法跃迁、级联、越权），
其余 13 条只是"没写坏"的兜底。

第二个心得：**性能断言必须实测**。"OR 会让索引失效"这句话我原先写得很肯定，
执行计划一看是"只用了前缀"。差别的确存在，但结论从"完全失效"变成"白建一列"，
修复优先级完全不同（前者必须改，后者可以先记着）。
**过度概括的结论最危险，因为它听起来有道理，所以没人去验。**
