## 📖 知识点摘要（来自材料，非学习心得）

### 1. unsafe 只解锁五项，必须有清单感
| # | 能力 | 常见用途 |
|---|---|---|
| 1 | 解引用裸指针 `*const T` / `*mut T` | 手写容器、`split_at_mut` |
| 2 | 调用 `unsafe fn`（含 FFI） | `get_unchecked`、libc 调用 |
| 3 | 访问/修改 `static mut` | 全局可变状态（**几乎都该换掉**） |
| 4 | 实现 `unsafe trait`（`Send` / `Sync`） | 极少数手写并发原语 |
| 5 | 访问 `union` 字段 | C 对接、位级类型双关 |

**不在清单里的，一概不解锁**：借用检查、类型检查、生命周期、可变性规则全部照旧。

### 2. unsafe 块的编译器警告是一堂课
不含危险操作的 `unsafe {}` 会触发 `warning: unnecessary unsafe block`——
这个警告证明 unsafe 只是"声明"，不改变块内代码的受检程度。

### 3. `my_split_at_mut`：签名借 vs 实现绕
```rust
fn my_split_at_mut(v: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32])
```
- **实现**用 `from_raw_parts_mut` + `ptr.add(mid)` 绕过了借用检查
- **签名**的 `&mut v` 却一点没松动：调用方在 left/right 存活期间不能再借 `v`
- 现象：`data` 必须写在花括号外才能打印。这不矛盾，而是同一件事的两面

### 4. SAFETY 注释要覆盖具体前提
合格版本（材料 §2.2）：
```
SAFETY:
1. ptr 来自 v，有效且对齐
2. [ptr, ptr+mid) 与 [ptr+mid, ptr+len) 不相交
3. 两段长度和 == 原长度，不越界
4. 原可变借用被消耗，不存在重叠可变引用
```
"这里我知道没问题"不是 SAFETY 注释，它没有信息量。

### 5. `into_raw` 必须配 `from_raw`
`Box::into_raw` 是"放弃所有权"。没有配对的 `Box::from_raw`，
编译器不报错，结果是内存泄漏；配对两次就是 double free。
`Counter` 的 `Drop` 就是这个配对的唯一收口点。

### 6. UB 的五种典型形态
1. 解引用悬垂指针
2. 越界读写
3. 同时存在两个 `&mut` 指向同一数据
4. 读取未初始化内存
5. 破坏类型不变量（构造非法 `&str`）

**UB ≠ 崩溃**。优化器会假设 UB 不发生，直接删掉它认为不可能的分支——
所以典型症状是"debug 版正常，release 版出错"。

### 7. 最具欺骗性的一条：悬垂裸指针
```rust
let p = v.as_mut_ptr();
v.push(4);          // 可能重新分配，p 立即失效
unsafe { *p = 99; } // 编译器完全不报错
```
来源看起来完全合法的指针，一次 `push` 之后就是悬垂的。
这是"unsafe 审查必须看控制流，不能只看指针创建处"的原因。
