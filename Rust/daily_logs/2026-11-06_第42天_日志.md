## 📖 学到的知识点

### 1. `strip` 在 Windows/MSVC 上一点体积都没省

实测两行数字完全相同：

```
-O                        210,944 B
-O -C strip=symbols       210,944 B
```

原因：MSVC 目标把调试信息放在**外部 `.pdb`** 里，PE 文件本来就没有符号表可删。
网上那句"`strip` 能让二进制小一半"是 **ELF（Linux/macOS）**世界的经验。

连带的第二个发现：**debug 与 release 只差 15%**（247 KB → 211 KB），
因为大头在 `.pdb`（1.4 MB），而两者的 `.pdb` 只差 33 KB。

**教训**：别人给的百分比，换一个目标平台就可能完全失效。数字必须自己量。

---

### 2. release 改的是**行为**，不只是速度

```rust
let x: u8 = 255;
let y = x + 1;   // debug: panic；release: 静默变成 0
```

`debug-assertions` 与 `overflow-checks` 在 release 下关闭。
所以"本机测试通过"推不出"上线没问题"——**测试必须用要上线的那个 profile 跑**：

```bash
cargo test --release
```

本文件用 `cfg!(debug_assertions)` 把它变成了可见的输出：
同一份源码编出两种二进制，启动时自己报出身份。

### 3. 多阶段构建省掉的是"整套编译器"

实测证据不是"镜像变小了"这种模糊说法，而是：

运行镜像里**根本没有 Rust 工具链**——阶段 1 编完就被丢掉了。
镜像 123 MB 里，大头是 `debian:bookworm-slim` 基础层，业务二进制只占 7 MB。

### 4. "编译只花了 0.4 秒"——stub 二进制陷阱（今天最大的坑）

第一次 `docker run` 的现象：

```
$ docker ps -a
chat42   Exited (0)
$ docker logs chat42
（完全空白）
```

**退出码 0、日志一行没有**，比崩溃难查得多。

回到构建日志找答案：

```
#12 DONE 279.6s     ← 依赖编译
#15 DONE 0.4s       ← "真源码"编译，0.4 秒
```

0.4 秒编完一个 actix-web 应用是不可能的——**它根本没编**。

原因：Docker 的 `COPY` **保留构建上下文文件的原始 mtime**。
宿主机 `src/main.rs` 的 mtime 早于上一步刚 `echo` 出来的占位文件，
cargo 指纹判定"源码没变过"，直接把 `fn main() {}` 的产物留在镜像里。

修法两条，缺一不可：

```dockerfile
COPY src ./src
RUN set -e; \
    touch src/main.rs src/lib.rs;          # 1) 让 mtime 变新
    cargo build --release --locked; \
    if ! grep -aq "聊天服务" /app/target/release/realtime-chat; then   # 2) 断言不是 stub
      echo "构建产物是 stub 二进制：源码没被重编"; exit 1; \
    fi
```

修完：`#13 0.360 Compiling realtime-chat` → `Finished in 1.28s`，二进制层从 446 KB 变成 7 MB。

**通用规律**：分层构建里，"这一步很快就完成"永远值得怀疑。
`grep -a` 查一个只有真二进制才有的字符串，等于给构建加了一条"产物正确性断言"——
把**静默失败**变成了**构建失败**。

---

### 5. 依赖层缓存到底省了多少（实测两个数字）

| 场景 | 耗时 |
|---|---|
| 首次完整构建（编全部依赖） | **279.6 s** |
| 改源码后重建（依赖层 CACHED） | **3.755 s** |

**74 倍**。这就是"为什么 `Cargo.toml` 和 `src/` 要分成两层 COPY"的全部理由：
依赖不变时，那 279 秒被完整跳过。

顺带说明为什么 `.dockerignore` 要排除 `target/`：
构建上下文是**整包发给守护进程**的，`target/` 动辄几百 MB。

### 6. 容器里的 127.0.0.1 是容器自己的回环

程序自身默认 `BIND_ADDR=127.0.0.1:8090`（本机开发友好），
但容器里绑这个地址，宿主机永远访问不到——而日志会显示"已监听"，非常迷惑。

修法是在镜像里把默认值改成 `0.0.0.0`：

```dockerfile
ENV BIND_ADDR=0.0.0.0:8090
```

实测对照（同一个二进制）：

```
本机：BIND_ADDR 默认 127.0.0.1 → 打印 ⚠️ 绑定在 127.0.0.1：容器外/宿主机将无法访问
容器：ENV 0.0.0.0:8090       → 启动日志 http://0.0.0.0:8090（4 个 worker），无警告
```

`0.0.0.0` 的含义是"监听本机所有网卡"，不是"任何地址都能访问"——
真正的可达性还取决于 `-p` 映射与网络策略。

### 7. 健康检查要"敢说不"，所以真的发了个 HTTP 请求

容器里没有 curl（不想为一次检查装 5 MB 的东西），用 bash 的 `/dev/tcp` 直说 HTTP：

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD bash -c 'exec 3<>/dev/tcp/127.0.0.1/8090 && printf "GET /health HTTP/1.0\r\n\r\n" >&3 && head -1 <&3 | grep -q " 200 "'
```

为什么不满足于"端口能连上"：**端口开着不等于服务健康**（重启中的进程也可能连着）。
实测容器状态 `healthy`，`docker inspect .State.Health.Log[0].ExitCode = 0`。

### 8. 本机"零警告"不等于真的没有警告（两个原因叠加）

构建镜像时冒出一条本机从来没出现过的警告：

```
warning: use of deprecated method `Atomic::<usize>::fetch_update`:
         renamed to `try_update` for consistency
  --> src/room.rs:84:14
```

两个原因：

1. **缓存**：本机 `cargo build` 认为 `room.rs` 没变 → 不重编 → 不重新报警告
2. **工具链版本**：镜像里 `rust:1-slim-bookworm` 是 **rustc 1.99.1**，本机 **1.92.0**

而"按编译器建议改"这条路走不通，实测：

| 工具链 | `try_update` |
|---|---|
| 本机 1.92.0 | ❌ `E0658: use of unstable library feature 'atomic_try_update'`（issue #135894） |
| 镜像 1.99.1 | ✅ 编译通过，运行输出 `Ok(1)` |

**结论：保留 `fetch_update`**，等本机升到 1.99+ 再迁移。
这是"编译器给的建议不一定是当下能用的建议"的一个具体例子。

### 9. 我自己犯的错：`; echo $?` 吃掉了退出码

第一次构建我用的是：

```bash
docker build ... > log 2>&1; echo "退出码=$?"
```

命令整体返回 0（`echo` 成功），于是我汇报"构建成功"。
实际日志里写着 `#12 ERROR ... exit code: 101`。

`cmd; echo $?` 与 `cmd` 的成败语义完全不同：前者永远成功。
要看真实退出码，就不要在后面接命令；或者用 `set -e` / `&&`。

| # | 问题 | 现象 | 原因 | 解决 |
|---|---|---|---|---|
| 1 | 构建失败 | `transfer too slow ... 30s` | 容器内到 crates.io 吞吐极低，触发 cargo 放弃阈值 | 加 `CARGO_NET_RETRY`/`CARGO_HTTP_TIMEOUT`/`CARGO_HTTP_LOW_SPEED_LIMIT=1`/关闭 multiplexing |

## 💭 今日心得

今天最值钱的不是"部署成功了"，而是**三次"看起来成功、其实没做事"**。

第一次：`docker build ... ; echo $?` 返回 0 —— 我差点就这么汇报了。
第二次：容器 `Exited (0)`、日志空白 —— 一个"成功退出"其实是 stub 程序跑完了。
第三次：本机的"零警告"—— 靠的是缓存，不是代码干净。

三次的共同点：**信号都在，只是我没去看产生信号的那一层。**
- 退出码被 shell 语法改写了 → 要看日志
- 二进制没编 → 要看构建每步的耗时
- 警告没出现 → 要看是否重新编译过

`0.4 秒`这个数字是今天的"31.05 秒"。上次它告诉我停机 grace 在偷偷等着，
这次它告诉我**根本没编译**。同一个方法：**先怀疑"太快/太慢"的那个数字，别急着解释业务逻辑。**

第二个收获是"实测能推翻常识"。`strip` 小一半、debug 比 release 大一倍，
这两个说法在 MSVC 上都不成立。如果我按"常识"写完材料就收工，
交出去的会是一份**看起来专业、实际错一半**的笔记。

第三个是工具链版本差。镜像里 1.99.1 给出的建议，本机 1.92.0 用不了。
"跟着编译器提示改"是本能，但提示的正确性是有**前提版本**的。
