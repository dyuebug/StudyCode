## 📖 学到的知识点

### 1. WebSocket 握手就是一次 HTTP 协议升级

`GET /ws/lobby` 带 `Upgrade: websocket` + `Connection: Upgrade` + `Sec-WebSocket-Key`，
服务端回 `101 Switching Protocols`，之后同一条 TCP 上跑的就是帧，不再是 HTTP 报文。
所以 WebSocket 和普通接口**共用同一个端口、同一个 worker 池**，不是第二个服务。

`actix_ws::handle(&req, payload)` 一次做完三件事，返回三元组：

| 返回 | 类型 | 用途 |
|---|---|---|
| response | `HttpResponse` | 101 响应，**立刻**返回给客户端 |
| session | `Session` | 写端：`text` / `binary` / `ping` / `pong` / `close` |
| stream | `MessageStream` | 读端：`Stream<Item = Result<Message, ProtocolError>>` |

读写端分离是刻意的设计：逼你明确区分"我要发"和"我要收"，
一个任务同时处理两者就写成 `select!`，而不是共享可变状态。

**顺带验证了两个失败路径**（实测）：

```
curl -o /dev/null -w '%{http_code}' http://127.0.0.1:8091/ws/lobby
400                     # 没有 Upgrade 头，handle 直接拒绝

curl http://127.0.0.1:8091/ws/a.b
{"code":"invalid_room","message":"房间名需 1~32 个字符，只允许字母、数字、- 和 _","success":false}
```

### 2. `Rooms` 必须在 `HttpServer::new` 外面创建

`HttpServer::new` 的闭包**每个 worker 调用一次**。写在闭包里就是 4 份注册表：

```rust
HttpServer::new(move || {
    let rooms = Rooms::new();   // ❌ A 连 worker1、B 连 worker2，永远看不见对方
    realtime_chat::app(rooms)
})
```

最坏的地方是**它不报错**：两个客户端都能连上，都能收到自己的 join，
就是收不到对方的。像给两组人各发了一块白板。
正确写法是外面建一份，`Rooms: Clone`（内部 `Arc`）后 clone 进闭包。

### 3. 广播为什么用 `broadcast` 而不是 `Arc<Mutex<Vec<Session>>>`

官方示例的写法可行，但两个代价：

1. 发包时**持锁**，所有连接的发包排在同一个锁后面
2. 慢客户端没有背压信号——你只能等它，或者靠超时硬断

`broadcast` 给每个订阅者一个独立 `Receiver`，慢的那个自己落后，
恢复时拿到 `RecvError::Lagged(n)`：明确告诉你"你丢了 n 条"。
容量的含义也很清楚：**单个客户端最多能落后多少条**（本项目 64）。

```rust
pub fn publish(&self, msg: impl Into<String>) -> usize {
    self.tx.send(msg.into()).unwrap_or(0)   // 没人在听 = Err，不是失败
}
```

### 4. `actix_ws::Session` 是一个容量 32 的有界队列 —— 这才是关键

读源码确认（`actix-ws-0.3.1/src/session.rs`）：

```rust
pub struct Session { inner: Option<Sender<Message>> }   // tokio::sync::mpsc::Sender
// lib.rs: let (tx, rx) = channel(32);
pub async fn text(&mut self, msg: impl Into<ByteString>) -> Result<(), Closed> {
    inner.send(Message::Text(msg.into())).await         // 满了就挂起，这是真背压
}
```

这个事实决定了整个"慢客户端"策略的形状——
**写不进去不是返回错误，而是永远等待**。

---

### 5. 两道闸门：`Lagged` 管"读得慢"，写超时管"根本不读"

这是今天最重要的发现，也是必须实测才能得到的结论。

| 客户端状态 | 数据流向 | 服务端看到什么 |
|---|---|---|
| 读得慢（在收，但跟不上） | 缓冲撑爆，旧的被丢弃 | `rx.recv()` 返回 `Lagged(n)` |
| **根本不读** | TCP 缓冲填满 → 发送缓冲填满 → mpsc 32 槽填满 | `session.text().await` **永久挂起** |

"永久挂起"要命的地方在于：挂住的正是我们自己的连接任务，
它再也走不到 `rx.recv()`，所以 **`Lagged` 永远不会出现**。
不加写超时，这个连接就是个僵尸，直到操作系统级 TCP 超时（可能十几分钟）才回收。

实测（`lazy_reader` + `flood` 200 条 × 8 KB）：

```
[WS] 成员 1 加入 slow，当前 1
[WS] 成员 2 加入 slow，当前 2
[WS] 成员 1 写超时 10s（对端不读），主动断开
[WS] 成员 1 离开 slow，剩余 1
[WS] 成员 2 离开 slow，剩余 0
```

灌消息的那个客户端看到的事件流：

```
{"count":2,"member":2,"type":"join"}
{"count":1,"member":1,"type":"leave"}    ← 不读的那个被踢了
```

`GET /rooms/slow/members`：灌之前 `1`，灌之后 `0`。

**一个容易犯的实验错误**：灌消息的客户端必须**边灌边读**。
服务端把消息广播给所有人（含发送者），只写不读的话它会先撑爆自己，
结果变成"两个客户端互相把对方踢了"，什么也证明不了。

### 6. `close()` 也是一次写，收尾同样会被堵

第一次跑上面的实验，日志顺序是错的：

```
[WS] 成员 1 写超时 10s（对端不读），主动断开
[WS] 成员 2 离开 slow，剩余 0     ← 2 先打印
[WS] 成员 1 离开 slow，剩余 0     ← 1 晚了 10 秒
```

原因：收尾里的 `session.close(None).await` 进的是**同一个有界队列**，
对端不读，它又卡满了一个 `SEND_TIMEOUT`。

修法：记住"写通道已经堵死"（`writer_blocked`），这种情况下不发 close——
反正对端收不到，再等一个超时只是白白多挂 10 秒。修完顺序恢复正常。

**这条比"加超时"更有价值**：它说明"加个超时"不是终点，
每一处**写**都要问一句"这里堵住了会怎样"。

---

### 7. 收尾顺序：先减在线数，再广播 leave

```rust
room.leave();                                    // 1. 先减
room.publish(json!({ "type": "leave", "member": member, "count": room.online() }));  // 2. 再发
```

反过来的话，`leave` 里的 `count` 会多算自己一个。
同理，**进房要先订阅再广播 join**，否则自己收不到"你加入了"那条。

### 8. `include_str!` 把静态页编进二进制

```rust
async fn index() -> HttpResponse {
    HttpResponse::Ok().content_type("text/html; charset=utf-8")
        .body(include_str!("../static/chat.html"))
}
```

好处：部署时只有一个可执行文件，不会出现"程序在跑、静态文件没同步"。
代价：改一行 CSS 也要重新编译。教学项目里这个取舍很划算。

---

### 9. 房间名校验只放在会**产生副作用**的入口

`/ws/{room}` 会 `get_or_create`（往 HashMap 插 key），必须校验；
`/rooms/{room}/members` 是纯读，不校验——查一个非法名字得到 `count: 0` 是合理的答案。

房间名进 HashMap key、日志、JSON，放任任意字符串进来，
就等于给"往日志里注入换行"开了个入口。白名单（字母数字 `-` `_`，1~32 字符）
比转义便宜，也更难写错。

| # | 问题 | 现象 | 原因 | 解决 |
|---|---|---|---|---|
| 1 | `text.as_str()` 编译失败 | `error[E0658]: use of unstable library feature 'str_as_str'` | `ByteString` Deref 到 `str`，`.as_str()` 解析成 `str::as_str`（未稳定） | 改成 `&*text`，得到 `&str` |

| 6 | 被踢的连接晚了 10 秒才收尾 | 日志顺序错乱，`剩余` 数字不对 | `close()` 也是写，同样卡在队列上 | 用 `writer_blocked` 标记，堵死时跳过 close |

## 💭 今日心得

今天最值钱的不是"聊天室跑起来了"，而是**读代码读出来的一个错误结论被实测推翻了**。

看代码时很自然地想：`broadcast` 容量 64，慢了就给 `Lagged`，慢客户端问题解决了。
实测才发现完全不是这样——"慢"和"不读"是两种客户端，走的根本不是同一条路径。
而 `actix-ws` 的 `Session` 是个容量 32 的有界队列这件事，
在文档里只是一句 "Sends text into the WebSocket"，读源码才看见 `Sender<Message>`。

这类"文档没写、但决定了你系统怎么坏"的细节，只有两条路能拿到：
读实现，或者做实验。今天两条都用了，而且互相印证的结论才敢写进 README。

第二个收获是 §5.5 那个日志顺序错误。它属于"功能已经对了，只是慢了 10 秒"，
正常人不会去看。但顺着这个 10 秒能挖出"`close` 也是一次写"，
而这正好解释了为什么有人写的 WebSocket 服务在客户端假死时会堆积任务。
**看起来无关紧要的异常数字，往往是下一条规律的入口。**
