### 2. 教学演示（`cargo run -- --demo-only`）

```
2.1 计算 Sec-WebSocket-Accept
   Key            = dGhlIHNhbXBsZSBub25jZQ==
   Accept         = s3pPLMBiTxaQ9kYGzzhZRbK+xOo=      ← 与 RFC 6455 一致
   一致           = true

2.2 帧编码与解码闭环
   短载荷 5 字节       帧总长     11 字节  头部 7 bit 直接长度
   中载荷 300 字节     帧总长    308 字节  头部 标记 126 + 2 字节长度
   长载荷 70000 字节   帧总长  70014 字节  头部 标记 127 + 8 字节长度

   服务端发出的帧不带掩码，按客户端帧解析 → Err(MissingMask)
   只喂 3 个字节给解码器 → Err(Incomplete)
   声称 2 GiB 载荷的头部 → Err(PayloadTooLarge(2147483648))

1.3 文本帧 "hi" + 掩码键 [01,02,03,04] 的字节：81 82 01 02 03 04 69 6B
```

逐字节解读 `81 82 01 02 03 04 69 6B`：

| 字节 | 含义 |
|---|---|
| `81` | FIN=1 + opcode=0x1（文本） |
| `82` | MASK=1 + len=2 |
| `01 02 03 04` | 4 字节掩码键 |
| `69 6B` | `'h' ^ 0x01 = 0x69`、`'i' ^ 0x02 = 0x6B` |

## 📖 知识点摘要（来自材料，非学习心得）

### 1. 四种"服务端推送"方案
| 方案 | 实时性 | 主要问题 |
|---|---|---|
| 短轮询 | 一个间隔 | 空请求极多 |
| 长轮询 | 近似实时 | 每条消息都要重发 HTTP 请求 |
| SSE | 实时 | **只能单向下行** |
| WebSocket | 实时 | 需要连接状态管理 |

**反直觉的一点**：低频场景用轮询更划算。WebSocket 的成本不在协议，
而在"谁在线、消息发给谁、断线怎么补、多实例怎么广播"。

### 2. 握手的三步计算
```
accept = Base64( SHA1( client_key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )
```
那个固定 GUID 的作用是**让结果不可预测**，从而排除"缓存把一个普通请求误升级"。
SHA-1 在这里**不承担安全职责**——WebSocket 本身不加密，`wss://` 的安全性全部来自 TLS。

### 3. 帧的四种长度情形
- 载荷 < 126 → 1 字节长度
- 126 ~ 65535 → 标记 126 + 2 字节
- \> 65535 → 标记 127 + 8 字节
- 分片消息 → FIN=0 的前若干帧 + FIN=1 的末帧（opcode 0x0）

`126` / `127` 是**逃逸标记**，不是长度值。多花 2 字节，换取短消息永远只占 2 字节头。

### 4. actix-ws 的三个对象
- `HttpResponse`：**必须由你返回**，返回得晚握手就超时
- `Session`：写端，`Clone`，`text/binary/ping/pong/close`；`close()` **消费 self**
- `MessageStream`：读端，`recv()` 返回三层嵌套；`max_frame_size()` / `aggregate_continuations()` 都消费 self

**读写是两个值**，所以同时读写一条连接**不需要锁**——各给一个任务即可。

### 5. 广播的两种实现
| | `Mutex<Vec<Session>>`（官方示例） | `tokio::sync::broadcast`（本项目） |
|---|---|---|
| 发送语义 | 持锁遍历 + `FuturesUnordered` 并发 | 写一次 ring buffer，不等任何人 |
| 慢客户端 | 拖慢发送侧，无背压信号 | 自己 `Lagged(n)`，明确知道丢了几条 |
| 内存 | 无额外缓冲 | 每条消息占 capacity 份 |
| 结论 | 可行，但需要额外技巧 | 隔离性更好，但容量必须设上限 |

### 6. 关闭握手（RFC 6455 §7.1.1）
```
发 Close → 等对端 Close → 再关 TCP
```
直接断 socket 会让对端读到 EOF 而不是关闭帧。实测中第一次就是这么做的，
服务端日志里出现了 `I/O error: payload reached EOF before completing` ——
**一个纯粹由客户端不规范关闭造成的假错误**。加上"等 2 秒关闭响应"之后消失。

### 7. 客户端不能只靠"空闲超时"退出
服务端每 5 秒一个 ping，所以"多久没收到数据"永远不会触发。
实测中第一版客户端用 8 秒空闲超时，结果**永不退出**，一直打印 ping。
改成"12 秒总时限"才正确。

**结论：空闲 ≠ 没收到数据。** 长连接的活性检查必须区分"业务消息"与"协议心跳"。

## ❓ 遇到的问题与解决

### 问题 1：客户端永不退出
**现象**：`--client` 运行超过 60 秒仍在打印 `← ping，回 pong`。

**原因**：退出的条件是"8 秒读不到数据"，但服务端每 5 秒发一次 ping，
读操作永远在 5 秒内返回 → 空闲判断永远不成立。

**解决**：改为整体 12 秒会话时限。**教训**：心跳把"没数据"和"没响应"解耦了，
任何"超时退出"逻辑都必须说明它等的是哪一种。

### 问题 2：服务端日志出现 `payload reached EOF before completing`
**现象**：客户端明明发了 Close 帧，服务端却报 IO 错误。

**原因**：客户端发完 Close 立刻 return，`TcpStream` 被 drop → FIN 到达时
服务端的帧可能还没解完。

**解决**：按 RFC 补上关闭握手——发 Close 后等对端回 Close（最多 2 秒）再关 TCP。
补上之后服务端日志变成 `收到 Close 帧 code: Normal, description: 再见`。

### 问题 3：测试断言写反（`Lagged` 之后是哪一条）
**现象**：`slow_subscriber_gets_lagged` 失败，期望 `"m4"` 实际 `"m3"`。

**原因**：误以为 `Lagged` 会自动跳到队尾。实际上它只是报告跳过了几条，
下一次 `recv()` 拿到的是**缓冲区里最旧**的那条。

**解决**：断言改为 `m3` 再 `m4`，并在测试里写下这条注释，
避免下次再记反。

### 问题 4：`cargo build` 报 "failed to remove target/debug/ws-basics.exe"（os error 5）
**原因**：后台还在运行服务端，可执行文件被占用（Windows 不允许删除运行中的 exe）。

**解决**：先停服务再编译。Windows 上这是常态，Linux 才允许替换正在运行的文件。

### 学习重点

- **`wrap()` 是洋葱模型**：`wrap(A).wrap(B)` → 请求先过 A 再过 B，
  响应先出 B 再出 A。这决定了日志中间件的耗时统计包不包括鉴权
- **中间件拿不到 `web::Json<T>`**：提取器在 handler 阶段才运行。
  要在中间件里读 body，必须自己消费 `Payload` 并放回去
- **鉴权结果怎么传给 handler**：`req.extensions_mut().insert(user_id)`，
  handler 里用 `HttpRequest` 取。不要塞进 `AppState`（那是全局的，会被并发覆盖）
- **超时中间件**：`actix-web` 的 `Timeout` 与 tokio 的 `timeout` 语义不同，
  前者断开连接，后者返回错误
