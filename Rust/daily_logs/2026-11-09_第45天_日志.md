## 📖 学到的知识点

### 1. 过程宏必须至少两个 crate —— 这是 workspace 的第一个真实理由

`proc-macro = true` 的 crate **只能导出过程宏**，不能同时导出 trait、结构体、函数。
而 `#[derive(Validate)]` 生成的 `impl Validate for X` 需要使用者能 `use` 到那个 trait。

所以最小结构必然是：

```
validate-derive   （只能导出宏）
validate-demo     （定义 trait + 使用宏）
```

以前看"为什么用 workspace"，答案总是"多包管理方便"——这只是便利性。
过程宏给出的是一个**硬约束**：不是想不想分，是必须分。
真实库（如 `validator`）还要第三个 crate（共享 trait 与错误类型），
或者提供 `#[validate(crate = path)]` 让使用者指定路径。

### 2. 报错质量由 span 决定，不是由文案决定

同一个"未知属性键"的错误，两种写法天差地别：

```rust
// 差：错误指向整个 derive 调用点，使用者不知道该改哪
syn::Error::new(Span::call_site(), "未知键")

// 好：错误指向用户写的那一行那个词
syn::Error::new_spanned(&meta.path, format!("未知的校验键：{}", ident))
```

用 `unwrap()` 处理 `parse` 结果更糟：panic 的 span 在宏内部，
使用者看到的是 `proc-macro panicked`，而不是自己的代码。

**这一条只有真的去触发一次才知道。** 写完宏不试报错，等于只做了一半。

### 3. thiserror 与 anyhow 的分界线只有一个问题

> **调用方是否需要按变体分支？**

- 需要 → `enum AppError`（thiserror），因为调用方要 `match NotFound / Invalid / Db`
- 不需要 → `anyhow::Result`，因为它只要能打印、能加 context

本项目同时用了两者，并且在同一个文件里对照：
`find_task` 返回 `AppError`（要映射 400/500），
`load_or_default` 返回 `anyhow::Result`（启动失败就一种处理方式）。

选错的代价：把 enum 用在只有 `?` 的地方 → 一堆没人 match 的变体；
把 anyhow 用在服务边界 → handler 里只能 `downcast`，类型系统彻底失效。

### 4. `#[instrument]` 没有输出，不是宏没生效

加了 `#[tracing::instrument]` 后什么也看不到，第一反应是"宏没生效"。
真实原因：**subscriber 默认不打印 span 的生命周期事件**。必须显式开启：

```rust
tracing_subscriber::fmt()
    .with_span_events(FmtSpan::CLOSE)   // 少了这行，只有 INFO 行，没有 close 行
    .init();
```

开启后立刻出现：

```
INFO startup{host=127.0.0.1 port=8080 level=info}: close time.busy=52.5µs time.idle=6.80µs
INFO service.find_task{task.id=7}: close time.busy=700ns time.idle=1.20µs
```

这和第 43–44 天反复撞的「静默失败」是同一族：**该说话的东西没说话，而默认"没说话 = 没问题"。**

### 5. `{}` 与 `{:#}` 的差别是"丢不丢因果链"

同一段 anyhow 错误的两种打印：

```
{}  （只有最外层）：读取配置文件失败：不存在的配置文件.conf
{:#}（完整因果链）：读取配置文件失败：不存在的配置文件.conf: 系统找不到指定的文件。 (os error 2)
```

日志里写 `{}` 等于**永远丢掉根因**。规则：anyhow 进日志一律 `{:#}` 或 `{:?}`。
（`{:#}` 是单行的完整链，`{:?}` 是多行带 backtrace 的形式。）

### 6. 内存序错误无法用运行证明存在

这是今天最重要的一条认知。用 `Relaxed` 写自旋锁（`BrokenLock`），
在 x86_64 Windows 上连跑 5 次，**每次都得 4000，全部「通过」**。

原因两层：
- x86 是 TSO 强内存模型，硬件几乎不重排；
- 但**编译器重排**在任何平台都存在。

所以在 x86 上测不出来，不代表代码正确。换到 ARM 或换编译器版本就可能炸。

因此材料里的措辞必须精确：
「本机跑通」只能标【实测】，**不能**推出「内存序正确」（那是【推定】甚至无法验证）。
这也是我坚持在 `32_atomics_and_ordering.rs` 末尾加一行警告的原因——
一篇教内存序的材料如果暗示"跑通了就行"，那是在教错。

### 7. "零依赖"是被环境逼出来的设计，不是风格偏好

原本给文件管理器规划的是 `clap`。首次 `cargo test --offline` 直接失败：

```
error: failed to download `clap v4.6.1`
```

本机 crates.io 不可达（`curl` 返回 `000`），本地缓存里只有 clap 的传递依赖片段
（anstyle / strsim），**没有 clap 本体**。

于是改成手写 `cli.rs`。这个决定本身不算什么，重要的是**如实记录原因**：
README 与 `src/cli.rs` 头部都写清「本来要用 clap，因本机不可用改为零依赖」，
并列出手写版故意没做的四件事（短选项合并、选项与位置混排、自动 help、类型错误提示）。

否则半年后回看，会以为这是"有意的极简设计"，而不是"一次被迫的降级"。

## 🔧 同日修复：把"跳过"变成"真跑"

上面问题 6 原本被归为"无法解决"。重新想了一遍：`symlink_dir` 确实要特权，
但 Windows 还有第二种目录链接——**junction（`mklink /J`）不需要管理员**。

三步验证：

```
1) 能否创建（Git Bash 里调用 cmd）
   $ cmd //c "mklink /J jt\\link jt\\real"
   exit=0                                   ← 无特权成功

2) std 是否把它当符号链接（这是退路能否成立的前提）
   real     is_symlink=false is_dir=true
   link     is_symlink=true  is_dir=false   ← 是
   f.txt    is_symlink=false is_file=true

3) 测试真的跑起来了吗
   $ cargo test -- --nocapture
   链接创建方式：junction
   test junction_被识别为符号链接 ... ok
   test 符号链接被列出但不展开 ... ok
   test result: ok. 9 passed; 0 failed        ← 集成测试 8 → 9
```

然后做**可证伪验证**（这是本篇唯一一次"故意改坏"）：

```
$ sed -i 's/fs::symlink_metadata(&path)/fs::metadata(&path)/' src/lib.rs
$ cargo test --test file_manager
test 符号链接被列出但不展开 ... FAILED
panicked at tests\file_manager.rs:78:
assertion `left == right` failed           ← symlinks_skipped 断言先红
test result: FAILED. 8 passed; 1 failed
```

换回 `symlink_metadata` 后恢复 9 passed，`fmt=0 clippy=0`。

**这一轮修复真正的收获不是"测试通过了"，而是三个层次的区分**：

| 状态 | 证据 | 之前的标注 |
|---|---|---|
| 代码写了 | 有 `symlink_metadata` | "实现了" |
| 测试跑了 | `9 passed` | — |
| 测试**会红** | 改回 `metadata` → 1 failed | 只有到这一层才算"验证过" |

之前的"跳过"停在第一层却占了第三层的名额；现在它站在第三层。
同时新增 `junction_被识别为符号链接` 单独锁定退路前提——
哪天 std 改了行为，这条先红，而不是让主测试悄悄失去意义。

**仍未覆盖**：Unix 真 `symlink()` 与 `a -> b -> a` 环（junction 构造不出环），
需 WSL/Linux，已写进 `剩余课程规划.md` 的未完成项。

「未验证 / 已知局限」一节，并且把"跑通了"明确标成【实测-本机】而不是【正确】。

第二个收获关于缺口分类本身。分析时我把缺口分成"未落地 / 未验证 / 未接触"，

这说明一件事：**写代码能让"未落地"减少，但不能让"未验证"减少。**
