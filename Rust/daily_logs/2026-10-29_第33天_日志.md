### 4. 实验 2 的答案：id 会复用

实测序列：插入得 `id=3` → 删除 `id=3` → 再插入 → **又拿到 `id=3`**。

原因是 `INTEGER PRIMARY KEY` 是 rowid 的别名，分配规则是 `max(id)+1`，
不是 `AUTOINCREMENT`（后者依赖 `sqlite_sequence` 表，永不复用）。

**工程推论**：不要用 id 大小推断记录新旧。判断新旧要用 `created_at` / `updated_at`。

## 📖 知识点摘要（来自材料，非学习心得）

### 1. 范式判断的三个反例
- 一个字段塞多个值（`"tag1,tag2"`）→ 违反 **1NF**
- 非主属性只依赖复合主键的一部分 → 违反 **2NF**
- 非主属性依赖另一个非主属性（传递依赖）→ 违反 **3NF**

### 2. 只有三类冗余是合法的
反范式的唯一正当理由是"**这份数据可以从源数据重建**"——
统计计数、缓存结果、搜索索引表。**无法重建的冗余就是 bug。**

### 3. 四种主键策略的代价
| 策略 | 代价 |
|---|---|
| 自增整数 | 暴露记录数量；分布式下需要协调 |
| UUID v4 | 随机 → 破坏 B 树局部性 → 写放大约 2–3 倍 |
| UUID v7 / ULID | 时间有序，兼顾分布性与局部性 |
| 业务键 | 业务键会变，一旦变了要改所有外键 |

### 4. 四类字段的标准存法
- 金额 → `BIGINT` 存**分**（浮点数不能表示 0.1）
- 时间 → UTC + `TEXT`（ISO 8601）或原生时间类型，永远不存本地时区
- 布尔 → SQLite 用 `INTEGER 0/1`，`BOOLEAN` 只是别名
- 枚举 → `TEXT` + `CHECK (status IN (...))`，不用魔法数字

### 5. 索引的三个判定标准
建索引前必须满足其一：
1. 该列出现在高频查询的 `WHERE` 中
2. 该列用于 `JOIN` / `ORDER BY` 且无法被现有索引覆盖
3. 实测执行计划显示 `SCAN` 且该表行数已经上量

**不满足就一个都别建**——每个索引都让写变慢。经验上限：每表 ≤ 5 个。

### 6. 最值得记住的设计陷阱：软删除 + UNIQUE
`deleted_at IS NOT NULL` 的软删除 + `title UNIQUE` → 删掉的标题无法再被使用。

三种解法里只有**部分索引**是对的：

```sql
CREATE UNIQUE INDEX idx_tasks_title_active
    ON tasks(title) WHERE deleted_at IS NULL;
```

（另两种是"把标题改成 `标题+时间戳`"和"用触发器"，前者污染数据，后者隐藏逻辑。）

### 7. SQLite 与 PostgreSQL 的关键差异
- SQLite 外键**默认关闭**，PG 默认开启
- SQLite 写操作全局串行（同一时刻只有一个写者），PG 支持行级并发写
- SQLite 类型系统是"存储类"（只有 5 种），PG 是严格类型
- SQLite 无 `ALTER COLUMN`，改列类型要重建表

## 🔍 迁移后：哪些问题消失了，哪些还在

### 消失的问题

| 第 27 天的问题 | 为什么消失 |
|---|---|
| 手工 `iter().max()+1` 生成 ID，并发下重复 | 数据库原子分配 rowid |
| 改一条 = 整体覆写文件 | `UPDATE ... WHERE id = ?` 只碰一行 |
| 锁守卫不能跨 `await` | `SqlitePool` 是 `Send + Sync`，可直接跨 await |
| 两个 `Arc<Mutex<>>` 的加锁顺序问题 | 状态里只剩一个 `pool` |
| "内存已改、磁盘失败"的不一致 | `Ok` 即已落库，`Err` 即没做成 |

### 仍然存在的问题

**"先 SELECT 再 UPDATE"时的丢失更新。**

当前 `PUT` 是**单条原子 UPDATE**，不丢失。但一旦加上业务校验
（"先读出 completed，判断能不能改，再写回"），读-改-写之间就有窗口了。

解法：加 `version` 列做乐观锁（第 32 天已实现过）。
`rows_affected() == 0` → 版本过期 → 返回 409 而不是 404。

**结论：数据库把"内存数据竞争"降级成"逻辑层竞态"——
更好解决，但不是不存在。**

## ❓ 遇到的问题与解决

### 问题 1：`curl -d` 传中文 → `invalid unicode code point`
**现象**：`POST /todos` 返回 `400 Json deserialize error: invalid unicode code point at line 1 column 24`

**原因**：不是服务端 bug，是 Windows Git Bash 命令行传参的编码问题——
中文在传给 `curl` 的过程中字节被破坏。

**解决**：把 JSON 写进文件，用 `--data-binary @file` 发送。
用 `xxd` 确认文件字节是合法 UTF-8（`e8 bf 81` = "迁"），发出去就成功了。

**教训**：**HTTP 客户端测试失败时，先确认发出去的字节是什么**，
不要第一时间怀疑服务端。`xxd` / `curl -v` 是最快的定位手段。

### 问题 2（第 32 天遗留确认）：`cargo build --offline` 失败
加 sqlx 后 Cargo 重新解析依赖，拉取未缓存的传递依赖 → 离线构建失败。
改用普通 `cargo build`（本机有网）解决。

### 学习重点

- **握手是 HTTP，之后才是 WebSocket**：`Upgrade: websocket` + `Sec-WebSocket-Key`
- **广播优先用 channel**：`Mutex<Vec<Session>>` 手写遍历也行（actix-ws 官方示例就是这么做的，
  用 `FuturesUnordered` 让多个发送并发），但它**持锁发送**、且慢客户端没有背压信号；
  `tokio::sync::broadcast` 让每个连接持自己的 Receiver，慢的那个自己收 `Lagged(n)`，
  代价是 ring buffer 的容量上限
- **心跳是应用层的**：WebSocket 协议本身没有自动保活
- **断线是常态，不是异常**：重连必须有退避，否则服务重启时所有客户端同时冲击
