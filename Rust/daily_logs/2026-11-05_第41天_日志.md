## 📖 学到的知识点

### 1. 集成测试的价值是"测协议"，不是"测代码"

`room.rs` 的 3 个单测测的是数据结构：加入、离开、广播对不对。
但那 3 个测试全绿的时候，服务端仍可能是坏的——比如：

- 握手缺 `Upgrade` 头时到底返回 400 还是 500？
- 两个人真的连上了，但到底在不在同一个房间？
- 断开时 `leave` 里的 `count` 减了没有？

这些**只有真的走一遍 TCP** 才能回答。所以 `tests/ws.rs` 里每个用例都
起一个真实服务器、用真实的 WebSocket 客户端连上去。

顺带一个便宜但管用的断言：

```rust
assert_eq!(resp.status().as_u16(), 101, "握手成功必须是 101 Switching Protocols");
```

`connect_async` 成功并不代表协议对——把状态码钉死，才能防止"某天有人把它改成了 200"。

---

### 2. 端口用 0，让操作系统分配

```rust
let srv = HttpServer::new(...).workers(1).bind(("127.0.0.1", 0))?;
let addr = srv.addrs()[0].to_string();   // 拿回真正的端口
```

手写端口（8090、8091……）在并行跑测试时会撞车，而且撞车时间歇性的——
表现为"单独跑能过，整套跑就失败"，是最难查的一类问题。
绑 0 之后 `addrs()` 给出实际端口，再拼成 URL 交给客户端。

**每个用例起独立服务器**也是同一个道理：注册表在内存里，
共享服务器就共享房间，"人数从 0 变 1"的断言会被别的用例污染。

---

### 3. `ServerHandle::stop(true)` 会吃掉 30 秒（今天最大的坑）

第一版测试写完，7 个用例全绿，但整套跑了 **31.05 秒**。
第一反应是"灌消息那个用例数据太多"，于是把 32 KB × 200 改成 8 KB × 200，
结果**还是 31.05 秒**——一个数字都没变，说明猜错了。

真正的 30 秒来自收尾：

```rust
h.stop(true).await;   // 优雅停机：等现有连接自己结束，最长等 30 秒
```

这些用例结束时 WebSocket 连接大多还开着，于是每条用例都在停机处干等。
改成 `h.stop(false)`（直接停）之后：

```
test result: ok. 7 passed; finished in 1.01s
```

31 秒 → 1 秒，**30 倍**。

**教训**：性能问题的第一个假设如果被"改完数字没变"否定，就立刻换方向，
不要在同一个假设上继续微调。

---

### 4. 阻塞 IO 必须放进 `spawn_blocking`

测试里要访问 `GET /rooms/{room}/members`，为了不给项目加 HTTP 客户端依赖，
直接用阻塞的 `std::net::TcpStream` 手写了一个 GET。

但 `#[actix_web::test]` 跑的是**单线程** actix System：
如果在这个线程上阻塞，服务端任务也没机会执行，就变成"自己等自己"的死锁
（表现是 5 秒超时，而不是报错）。所以：

```rust
tokio::task::spawn_blocking(move || { /* 阻塞的 TcpStream */ }).await
```

**判断标准**：这段代码会让线程"停下来等"，就属于阻塞；
在 async 上下文里它必须离开当前线程。

---

### 5. 比较 JSON 要用 `Value`，不要比字符串

```rust
// ❌ 必然失败
assert_eq!(body, r#"{"success":true,"data":{"room":"lobby","count":0}}"#);
```

实际返回是：

```
{"data":{"count":0,"room":"lobby"},"success":true}
```

原因：`serde_json::json!` 默认用 `BTreeMap` 存对象，**键按字母排序**。
（开了 `preserve_order` 特性才会保持插入顺序。）

正确写法：

```rust
assert_eq!(body, serde_json::json!({ "success": true, "data": { "room": "lobby", "count": 0 } }));
```

`Value` 的 `PartialEq` 与键序无关。这条和"别用字符串比 JSON"是同一件事，
只是 `json!` 的排序行为让它变得特别容易踩。

---

### 6. "等一段时间"的行为必须做成参数

第 40 天定的写超时是 10 秒。如果测试要验证"不读的客户端会被踢"，
用默认值这一条用例就得跑 10 秒以上，而测试里还有 200 条消息要灌。

```rust
let cfg = ChatConfig {
    heartbeat: Duration::from_secs(30),
    send_timeout: Duration::from_millis(300),   // 测试里只要 0.3 秒
};
```

**这才是"可测性"的本质**：不是"能不能测"，而是"测一次要多久"。
凡是要等的行为，时间都该是参数；默认值负责生产，参数负责测试。

顺带说明为什么用 `from_env()` 而不是全局 `static mut`：
环境变量在测试里会互相干扰（并行跑时谁都可能改），所以测试走函数参数，
环境变量只给运维用。

---

### 7. 数据量不是瓶颈时，改数据量不会有任何变化

| 改动 | 整套耗时 |
|---|---|
| 32 KB × 200 条 | 31.05 s |
| 8 KB × 200 条 | 31.05 s |

两个数字**一模一样**，这本身就是最强的证据：瓶颈根本不在数据。
真实的因果是"用例数量 × 30 秒停机" = 7 条并行、每条占着一个 worker 等 30 秒。

**方法论**：一次只改一个变量，并且要看"数字有没有动"。
数字纹丝不动，说明改的那个东西和症状没有因果关系。

## ❓ 遇到的问题与解决

| # | 问题 | 现象 | 原因 | 解决 |
|---|---|---|---|---|
| 1 | 整套测试 31 秒 | 全绿但太慢 | `stop(true)` 优雅停机等现有连接，最长 30 秒 | 改 `stop(false)` → 1.01 秒 |
| 2 | 以为瓶颈是数据量 | 32KB→8KB 耗时不变 | 归因错误；真实原因是停机 grace | 见知识点 7 |
| 3 | 两个 HTTP 断言失败 | `left: "{\"data\":..."` vs 期望的键序 | `serde_json` 用 BTreeMap，键按字母排序 | 改比较 `Value` |
| 4 | 文档注释编译失败 | `expected item after doc comment` | 编辑时把注释和 `async fn` 挤到了一行 | 补回换行 |
| 5 | 阻塞 TCP 会不会自锁 | —— | 单线程 System 上阻塞会把服务端一起卡住 | 放进 `spawn_blocking`，并在注释里写明原因 |
| 6 | 测试间互相污染 | —— | 注册表在内存，共享服务器就共享房间 | 每用例独立服务器 + 端口 0 |

**问题 2 值得单独记一笔**：如果我当时没去看"改完数字变没变"，
很可能会继续在数据量上做文章（减少条数、压缩 payload），
最后"测试变快了"但其实只是把用例改弱了。**先确认因果，再优化。**

## 💭 今日心得

今天最值钱的一课是**"31 秒"这个数字**。

如果我只盯着"7 个用例全绿"，收工就结束了。多问一句"为什么这么慢"，
挖出来的是 actix 的一个默认行为（`stop(true)` 的 30 秒 grace），
而这个行为在生产里同样存在——线上重启时如果有一堆长连接，
`stop(true)` 就是会等那么久。测试里踩到，等于提前知道了线上会怎么慢。

第二个收获是"改一个变量，看数字动没动"。
32 KB → 8 KB 耗时**完全没变**的那一眼，比任何日志都有信息量：
它直接否定了我的假设，把注意力逼到正确的地方。

还有一个反复出现的规律：**断言失败时先怀疑自己的假设**。
今天两次失败都不是服务端的问题——一次是 JSON 键序（我以为 `json!` 保持插入顺序），
一次是停机 grace（我以为 `stop(true)` 只是"优雅地"关）。
这和前几天"以为初始状态对、其实不对"是同一个毛病。
