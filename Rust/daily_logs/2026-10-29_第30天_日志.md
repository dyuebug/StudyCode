## 📖 知识点摘要（来自材料，非学习心得）

### 1. ABI 三件套，各管一段
| 设施 | 管什么 | 缺了会怎样 |
|---|---|---|
| `extern "C"` | 二进制调用约定（寄存器、栈清理） | 参数传错位置，行为不可预测 |
| `#[repr(C)]` | 结构体内存布局（顺序 + 对齐 + 补齐） | 字段静默错位，读到垃圾 |
| `#[no_mangle]` | 符号名不做修饰 | C 侧链接期 `undefined reference` |

**三者缺一不可，且互不替代。** 这是 FFI 最容易混淆的地方。

### 2. 为什么 FFI 必然 unsafe
编译器对 C 侧一无所知：会不会返回空指针？会不会保留传入的指针？
会不会有内部静态缓冲区？长度参数是字节还是元素？
签名无法表达这些问题，所以**声明时标 unsafe，证明责任交给调用点**。

### 3. 字符串跨边界的四个数字（本次实测）
输入 `"你好 FFI"`：
| 度量 | 值 | 含义 |
|---|---|---|
| `as_bytes_with_nul().len()` | 11 | UTF-8 字节数 10 + NUL 1 |
| C 侧 `strlen` | 10 | 到 NUL 为止的字节数 |
| Rust `.len()` | 10 | UTF-8 字节数（不是字符数！） |
| `.chars().count()` | 6 | 实际字符数 |

**结论**：`.len()` 是字节数，不是字符数。跨语言传长度时必须明确说的是哪个。

### 4. `CString` 与 `CStr` 的分工
- `CString`：**拥有**，`new()` 时检查内含 NUL 并自动补结尾 NUL，Drop 释放
- `CStr`：**借用**，`from_ptr()` 是 unsafe（信任 NUL 结尾），`to_str()` 做 UTF-8 校验
- `into_raw` / `from_raw`：所有权的交出与收回，**必须成对**

### 5. `#[repr(C)]` 的填充是"可计算"的
`Packet { id: u8, len: u32, flag: u16 }`：
```
offset 0    : id     1 字节
offset 1-3  : 填充   3 字节   ← len 要求 4 字节对齐
offset 4-7  : len    4 字节
offset 8-9  : flag   2 字节
offset 10-11: 尾部填充 2 字节  ← 总大小须为 max_align(4) 的倍数
────────────────────────────
总计 12 字节，而字段和只有 7
```
同样三个字段改序为 `{ u32, u16, u8 }` → 8 字节。**顺序改一改，省 33%。**

### 6. 跨 FFI 边界只能用 POD
`&str`（胖指针）、`String`（ptr+cap+len）、`Vec`、`Option`、`Result`
**全部不能直接过界**。而且写错了**能编译**——错误在 C 侧运行时才暴露，
这是 4.2 被列为"最危险"的原因。

### 7. panic 不能穿过 FFI
C 栈帧里没有 Rust 需要的 landing pad，展开穿过 C 是 UB。
Rust 1.81+ 的应对是**直接 abort 整个进程**（`panic in a function that cannot unwind`）。
正确做法：导出函数内部用 `catch_unwind` 兜住，用错误码表达失败。

### 8. 谁分配谁释放：FFI 头号 bug 来源
导出 `*mut T` 就**必须**导出配对的 `*_free(p: *mut T)`。
这是 API 契约的一部分，要写进头文件注释，而不是靠使用者猜。
