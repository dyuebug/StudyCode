## 📖 学到的知识点

### 1. GitHub 只读**仓库根**的 `.github/workflows/`

计划里原本要写 `realtime-chat/.github/workflows/ci.yml`。
查证后发现：放在子项目目录里的 workflow **不报错、不提示、永远不运行**。
GitHub 的 Actions 发现机制只看仓库根目录。

这属于"静默失败"的又一例：文件在、YAML 格式对、就是没有效果。
和第 42 天那个 stub 二进制是同一类问题——**失败不吭声**。

改法：文件放仓库根 `.github/workflows/rust-realtime-chat.yml`，
用 `paths: ['Rust/realtime-chat/**']` 控制只在子项目变动时触发。

### 2. 五道闸门，按"从快到慢"排序

| 闸门 | 防什么 | 成本 |
|---|---|---|
| `cargo fmt --check` | 格式漂移 | 秒级 |
| `cargo clippy -- -D warnings` | 惯用法错误 | 十秒级 |
| `cargo check` | 类型错误 | 十秒级 |
| `cargo test` | 行为错误 | 分钟级 |
| `cargo build --release` | 只有 release 才暴露的问题 | 分钟级 |

排序不是随意的：`fmt` 3 秒能发现的问题，不该等 3 分钟的测试跑完才说。
CI 的时间成本是"每次推送都要付一次"的税。

另一个常被忽略的点：**CI 里不能用 `cargo fmt`**，只能用 `--check`。
CI 直接改代码会造成"通过的是 CI 改过的版本，不是你提交的版本"这种错觉。

### 3. `-D warnings` 才是门禁的本质

不加它，clippy 照样输出满屏 `warning:`，但任务标绿——因为警告不改变退出码。
**门禁 = 把警告变成退出码。**

第 43 天这条命令第一次真正跑通了：`cargo clippy --all-targets -- -D warnings`
报出三处 `clippy::useless_conversion`，退出码 101：

```
examples/flood.rs:72:49     format! 出来的 String 又 .into()
tests/ws.rs:310:28          vec![1,2,3] 已是 Vec<u8> 又 .into()
tests/ws.rs:365:33          format! 出来的 String 又 .into()
```

**这三处暴露了一个比 lint 本身更重要的结论**：
第 41 天记录的"本地零警告"是**构建缓存**造成的假象——
`tests/` 和 `examples/` 从来没被重新编译过，它们的警告从未出现过。
`cargo build` 看不见的目标，`clippy --all-targets` 看得见。
所以 `--all-targets` 不能省。

### 4. 实测：`cargo test` 在 0 个用例时退出码是 0

在一个空 crate 里把测试文件命名成 `tests/ws.rs.bak`（cargo 只收集 `tests/*.rs`）：

```
running 0 tests
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
cargo test 退出码=0
```

于是"只信退出码"的门禁会把"整个测试目录没被收集"放行。
这是"0 和全部在退出码上长得一模一样"的实证。

### 5. 数量断言不能写成"每行都要有通过"

修这个洞的第一反应是 `grep -Eq "test result: ok\. [1-9][0-9]* passed"`。
但在本项目里这会把**正常情况**判成失败，因为正常输出天然有两段 0：

```
running 3 tests   → 3 passed     src/room.rs 单测
running 0 tests   → 0 passed     src/main.rs 的 bin 单测（main 里没有 #[test]）
running 7 tests   → 7 passed     tests/ws.rs 集成测试
running 0 tests   → 0 passed     doctest（没有文档示例）
```

正确写法是**汇总**，实测 `total = 3 + 0 + 7 + 0 = 10`：

```bash
total=$(grep -Eo 'test result: ok\. [0-9]+ passed' test.log \
        | grep -Eo '[0-9]+' | awk '{s += $1} END {print s + 0}')
[ "$total" -ge 10 ] || exit 1
```

局限也要说清：它证明"**至少**跑了 10 个"，不是"该跑的都跑了"。
摘掉一条老用例、加两条新的，总数仍是 10。

### 6. 实测：`cargo test | tee` 也会吃掉退出码

CI 里要保存测试日志，最自然的写法是 `cargo test 2>&1 | tee log`。
但管道的退出码是**最右侧命令**（`tee`）的，它永远成功。实测：

```
$ bash -c 'false | tee /dev/null >/dev/null; echo $?'
0
$ bash -c 'set -o pipefail; false | tee /dev/null >/dev/null; echo $?'
1
```

这是"退出码被吃掉"的**第二副面孔**。第一副是 `cmd; echo $?`（第 42 天）：
`;` 让你读到的是 `echo` 的退出码。
两副的共同点：**退出码来自你没想到的那条命令。**

### 7. 缓存键必须绑定"输入内容"，不是"运行时间"

三个输入，缺一不可：

| 输入 | 漏掉会怎样 |
|---|---|
| `Cargo.lock` 内容 | 换了依赖版本仍命中旧缓存，产物与源码不符 |
| 工具链版本 | 升级 rustc 后仍命中旧产物，缓存毒化 |
| 操作系统 | 跨系统的 `target/` 不可互换 |

`30_ci_cd.exe --cache-key` 里用 FNV-1a 做了最小实现。实测两次相同
（`3caa44347372a825`），末尾加一个空格就变成 `87f9ea202bd3807f`。

顺带一个坑：**不能用 `DefaultHasher` 做缓存键**——它的算法不保证跨版本稳定，
Rust 升级后同一输入的输出可能不同，缓存会永久失效。
"看起来能用、实际会坏"的典型。

### 8. 三态结果：Pass / Fail / **Unknown**

`Outcome` 用三态而不是 `bool`，因为"通过 / 失败"两态会丢掉一个真实存在的情况：
**不知道**。命令跑了，但看不出结论（0 行输出、没有成功标记也没有失败标记）。

CI 的语义是"没证明通过就是没通过"，所以 `Unknown` 的退出码也是 1。
验收标准是 0/非 0 的世界里，"不知道"必须落在非 0 那一侧。

### 9. "零输出 = 可疑"这条规则本身不成立

`cargo fmt --check` 干净时本来就一句话不说。
所以判断前必须先知道"这条命令成功时该不该说话"——
`Gate` 结构体里加了 `expects_output` 开关（`silent_ok()` 显式声明）。

一刀切的规则只会制造误报，而误报多了，真报警就没人看了。
这是本次写代码时才想明白的：**启发式依赖上下文，不能当公理用。**

### 10. 注释里写 `**/` 会提前结束块注释

在 Rust 块注释里写 GitHub 的递归 glob `**/Cargo.lock`，
其中的 `*/`（第 2、3 个字符）会被当成**结束标记**，后面的 YAML 全被当 Rust 解析：

```
error: prefix `lock` is unknown
   --> 30_ci_cd.rs:618:36
error[E0762]: unterminated character literal
```

Rust 的块注释还**支持嵌套**，所以这个问题更难定位。
文件里已把它写成一个陷阱条目，并把那段 glob 拆开写。

## 💭 今日心得

今天最值钱的不是"学会了写 CI"，而是**又一次撞上同一类问题**：

第 42 天是"构建成功但产物是 stub"，今天有三个同族变种：

1. workflow 放错目录 → 不报错，永远不运行
2. `cargo test` 0 个用例 → 退出码 0，任务标绿
3. `cargo test | tee` → 退出码来自 `tee`，失败也绿

三者形状不同，本质一样：**失败不吭声，成功也是假的**。
自动化检查的全部价值在于"能否失败"——一条永远通过的检查，
比没有检查更危险，因为它会让人以为检查过了。

第二个收获是"通用的规则常常是错的"。
"零输出=可疑"听起来天经地义，但 `cargo fmt --check` 干净时本来就该沉默；
"每行都要有通过用例"听起来合理，但本项目天然有两段合法的 0。
写自动化判断时，**先问"这条规则有没有合法的反例"**，
比直接把它写成 if 更省事。

还有一点关于诚实：workflow 写完了，但本机无法触发 GitHub Actions。
所以 `CI.md` 里必须把"本地手工跑通的三条命令"和"CI 未实测"分开写。
第 42 天已经有一次"看起来成功、实际没做"的教训，
今天如果含糊过去，等于是没学到。
