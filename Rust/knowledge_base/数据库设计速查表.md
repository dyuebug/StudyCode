# 数据库设计速查表

> 生成日期：2026-10-29（第 33 天）
> 适用：SQLite（本地/单机）与 PostgreSQL（生产）
> 定位：**设计决策的判据**，不是语法手册。每条规则都给出"什么时候不适用"。

---

## 一、从需求到 DDL 的四步

```
1. 找名词  → 实体（User / Task / Tag）
2. 找动词  → 关系（User 拥有 Task、Task 属于 Tag）
3. 定基数  → 1:1 / 1:N / N:M（N:M 需要中间表）
4. 加约束  → NOT NULL / UNIQUE / CHECK / FK
```

**跳过第 3 步是最常见的错误**。1:N 和 N:M 的表结构完全不同，
后期从 1:N 改成 N:M 需要数据迁移，代价远高于一开始想清楚。

### 关系判据

| 关系 | 落地方式 | 例子 |
|---|---|---|
| 1:1 | 同表或独立表 + UNIQUE 外键 | user ↔ user_profile |
| 1:N | **子表**加外键列 | user 1—N task（task.user_id） |
| N:M | **中间表**（两张外键 + 联合主键） | task ↔ tag（task_tags） |

## 二、范式：判据，不是教条

### 三条范式的实际含义

| 范式 | 一句话判据 | 违反的症状 |
|---|---|---|
| 1NF | 每个字段是**原子值**，不能是列表 | `tags = "work,urgent"` 存逗号串 |
| 2NF | 非主键列**完全依赖**整个主键 | 中间表里存了只依赖 task_id 的 `task_title` |
| 3NF | 非主键列**不传递依赖**其他非主键列 | `task` 表里存 `user_name`（依赖 user_id → name） |

违反 1NF 的典型后果：`WHERE tags LIKE '%urgent%'` 会误匹配 `not-urgent`，
且无法建索引、无法保证原子性。

### 什么时候**故意**反范式

反范式不是"偷懒"，是**用一致性换读性能**。合法场景只有三个：

1. **计数缓存**：`user.task_count` 避免每次 `COUNT(*)`。
   代价：每次增删要同步更新，需事务保护。
2. **历史快照**：订单里的 `unit_price` 必须存下单时的价格，
   不能 JOIN 商品表取当前价（那会随商品改价而变）。
3. **报表/物化视图**：预聚合表，可定期重建，容忍延迟。

**判据**：如果这份冗余数据**可以被重建**，反范式是安全的；
如果是"唯一真相"，冗余就是未来的 bug 源。

## 三、主键策略

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| `INTEGER AUTOINCREMENT` | 紧凑（8 字节）、索引快、可读 | 可枚举（泄露业务量）、分库难 | 单机/中小型 |
| `UUID v4` | 无中心、不可枚举、可离线生成 | 16 字节、随机分布**破坏 B 树局部性** | 分布式 |
| `UUID v7` / `ULID` | 时间有序 + 不可枚举 | 生态支持较新 | 分布式首选 |
| 业务主键（如 ISBN） | 天然唯一 | 业务规则会变 | 极少数 |

**SQLite 注意**：`INTEGER PRIMARY KEY` 本身就是 rowid 的别名，
**不需要** `AUTOINCREMENT`（后者额外维护 `sqlite_sequence` 表，
只在"绝不复用已删除 id"时才必要）。

**UUID 的性能陷阱**：v4 全随机，每次插入落在 B 树随机位置 →
页分裂、缓存命中率下降。数据量到千万级时插入性能会明显劣化。
**解决：用 UUID v7 或 ULID（时间前缀保证局部性）。**

## 四、类型选择

| 业务 | 不要用 | 应该用 | 原因 |
|---|---|---|---|
| 金额 | `FLOAT` / `REAL` | `BIGINT` 存**分**，或 `DECIMAL(19,4)` | 浮点 `0.1 + 0.2 != 0.3` |
| 时间 | 本地时间字符串 / 时间戳秒 | UTC + 时区类型；SQLite 用 TEXT(ISO 8601) | 夏令时、跨时区比较 |
| 布尔 | `VARCHAR` 存 "yes"/"no" | `BOOLEAN`（PG）/ `INTEGER 0/1`（SQLite） | 一致性与比较效率 |
| 枚举 | `VARCHAR` 无约束 | `CHECK (status IN (...))` 或 PG 的 `ENUM` | 防止脏值 |
| 结构化扩展 | 拆 20 个可空列 | JSON 列（PG `jsonb`） | 只在"结构确实不固定"时用 |
| IP | `VARCHAR(45)` | PG `inet`；SQLite 存 BLOB/INTEGER | 类型化省空间且可比较 |

**核心原则**：类型是**约束**，不是"能装下就行"。
选 `TEXT` 存数字等于放弃了范围校验与索引效率。

### 时间字段三件套

```sql
created_at TEXT NOT NULL,                          -- 创建时刻，永不改
updated_at TEXT NOT NULL,                          -- 每次 UPDATE 都要改
deleted_at TEXT,                                   -- NULL = 未删除（软删除）
```

`updated_at` 的可靠实现**不在数据库**（SQLite 没有 ON UPDATE 触发器语法糖），
必须由应用层每次写操作显式设置。写漏了不会报错，只会让数据静默失真。

## 五、索引策略

### 该不该建：三个依据

1. **慢查询日志里出现过。** 这是唯一硬证据。
   "这个字段看起来重要"不是依据。
2. **选择性高。** 选择性 = 不同值数 / 总行数。
   `completed`（只有 0/1）选择性 ≈ 0，建了优化器也多半不用。
   经验的阈值：选择性 > 0.1 才值得单独建索引。
3. **是查询条件或排序键。** 只出现在 `SELECT` 列表里的列，
   单独建索引没意义（除非要做覆盖索引）。

### 复合索引：最左前缀

建了 `INDEX (a, b, c)`：

| WHERE 条件 | 能否用 |
|---|---|
| `a = ?` | ✅ |
| `a = ? AND b = ?` | ✅ |
| `a = ? AND b = ? AND c = ?` | ✅ |
| `b = ?` | ❌ 跳过最左列 |
| `a = ? AND c = ?` | ⚠️ 只能用 a，c 需回表过滤 |
| `a > ? AND b = ?` | ⚠️ b 用不上（范围条件之后的列失效） |

**列顺序规则**：等值条件在前，范围条件在后，排序列放最后。

### 索引的代价（必须一起记住）

- 每次 INSERT/UPDATE/DELETE 都要维护索引 → **写放大**
- 磁盘占用约为被索引列的 20%–50%
- 索引太多会让优化器选择成本上升

**判据**：一张表的索引数通常不超过 5 个。超过就该问"这些查询真的都要走索引吗"。

### 覆盖索引

若查询的所有列都在索引里，数据库可以**只读索引不回表**：

```sql
CREATE INDEX idx_tasks_list ON tasks (completed, id, title);
SELECT id, title FROM tasks WHERE completed = 0;   -- 不回表
```

在 `EXPLAIN QUERY PLAN` 里表现为没有 `SEARCH tasks` 之外的回表步骤。
代价是索引变宽、写更慢——**只在热查询上做**。

## 六、约束：把业务规则写进数据库

| 约束 | 作用 | 漏写的后果 |
|---|---|---|
| `NOT NULL` | 禁止空值 | 代码里到处 `unwrap_or_default()`，掩盖 bug |
| `UNIQUE` | 唯一性 | 并发下同一邮箱注册两次 |
| `CHECK` | 值域 | `status = 'dnne'` 这类脏值进入系统 |
| `FOREIGN KEY` | 引用完整性 | 删父行后子行成孤儿 |

### 三个必须知道的坑

1. **SQLite 外键默认关闭。**
   必须在**每个连接**上 `PRAGMA foreign_keys = ON`（或用
   `SqliteConnectOptions::foreign_keys(true)`）。
   默认关闭是 2001 年的向后兼容决定，不是 bug。

2. **`UNIQUE` 允许多个 NULL。**
   `UNIQUE(email)` 在 PostgreSQL 与 SQLite 上都允许插入多行 `email = NULL`
   （SQL 标准规定 NULL 不等于任何值）。
   要"强制非空且唯一"必须同时写 `NOT NULL`。

3. **`CHECK` 不能跨表。**
   `CHECK` 只能看当前行。跨表规则只能靠外键、触发器或应用层事务。

## 七、软删除 + 唯一索引：必修的坑

软删除（`deleted_at IS NOT NULL`）与 `UNIQUE` 天然冲突：

```sql
-- 用户删除了 title='买牛奶'，再想新建同名任务 → UNIQUE 冲突
CREATE UNIQUE INDEX idx_tasks_title ON tasks (title);
```

三种解法：

| 方案 | 做法 | 代价 |
|---|---|---|
| **部分索引**（PG/SQLite 都支持） | `CREATE UNIQUE INDEX ... ON tasks(title) WHERE deleted_at IS NULL` | 最干净，推荐 |
| 删除时改值 | `title = title \|\| ' #deleted' \|\| id` | 污染数据，搜索会命中已删项 |
| 应用层检查 | 不建 UNIQUE | 并发下会重复，等于放弃约束 |

**部分索引是正确解。** 它在 SQLite 里同样支持（3.8.0+）。

## 八、task-manager 表结构草案

> 这是第 37–39 天综合项目的设计输入，可直接作为迁移文件的第一版。

```
┌──────────┐        ┌──────────┐        ┌──────────┐
│  users   │1      N│  tasks   │N       M│   tags   │
│──────────│────────│──────────│────────│──────────│
│ id  PK   │        │ id  PK   │        │ id  PK   │
│ email UQ │        │ user_id  │───────┐│ name  UQ │
│ name     │        │ title    │       ││ color    │
│ pwd_hash │        │ status   │       │└──────────┘
│ created  │        │ due_at   │       │      │
└──────────┘        │ created  │       │      │
                    │ deleted  │       │      │
                    └──────────┘       │      │
                          │            │      │
                          └──┬─────────┴──────┘
                             │  task_tags (N:M 中间表)
                             │  (task_id, tag_id) 联合主键
```

```sql
-- 迁移 0001：基础表
CREATE TABLE users (
    id         INTEGER PRIMARY KEY,
    email      TEXT    NOT NULL UNIQUE,
    name       TEXT    NOT NULL,
    pwd_hash   TEXT    NOT NULL,          -- 绝不存明文
    created_at TEXT    NOT NULL
);

CREATE TABLE tasks (
    id         INTEGER PRIMARY KEY,
    user_id    INTEGER NOT NULL REFERENCES users(id),
    title      TEXT    NOT NULL,
    -- status 用 CHECK 限值域，而不是自由文本
    status     TEXT    NOT NULL DEFAULT 'todo'
                       CHECK (status IN ('todo', 'doing', 'done')),
    priority   INTEGER NOT NULL DEFAULT 0 CHECK (priority BETWEEN 0 AND 5),
    due_at     TEXT,                      -- 可空：不是每个任务都有截止日
    version    INTEGER NOT NULL DEFAULT 0,-- 乐观锁
    created_at TEXT    NOT NULL,
    updated_at TEXT    NOT NULL,
    deleted_at TEXT                       -- 软删除
);

CREATE TABLE tags (
    id    INTEGER PRIMARY KEY,
    name  TEXT    NOT NULL UNIQUE,
    color TEXT    NOT NULL DEFAULT '#888888'
);

CREATE TABLE task_tags (
    task_id INTEGER NOT NULL REFERENCES tasks(id),
    tag_id  INTEGER NOT NULL REFERENCES tags(id),
    PRIMARY KEY (task_id, tag_id)         -- 联合主键即唯一约束
);

-- 索引设计（每一条都对应一个具体查询）
-- Q1: 我的未完成任务列表（最高频）
CREATE INDEX idx_tasks_user_status ON tasks (user_id, status, id);
-- Q2: 标题唯一（仅对未删除的行生效 —— 部分索引）
CREATE UNIQUE INDEX idx_tasks_user_title ON tasks (user_id, title)
    WHERE deleted_at IS NULL;
-- Q3: 按截止日排序
CREATE INDEX idx_tasks_due ON tasks (user_id, due_at) WHERE deleted_at IS NULL;
```

### 索引逐条说明

| 索引 | 支撑的查询 | 为什么这个列顺序 |
|---|---|---|
| `(user_id, status, id)` | `WHERE user_id=? AND status=? ORDER BY id` | 等值在前，排序列在后 |
| `(user_id, title) WHERE deleted_at IS NULL` | 部分唯一，避开软删除冲突 | 用户维度隔离 + 只约束存活行 |
| `(user_id, due_at) WHERE deleted_at IS NULL` | 按截止日排序 | 部分索引排除已删行，索引更小 |

**注意 `task_tags` 没有额外索引**：`PRIMARY KEY (task_id, tag_id)` 的 B 树
已经支撑 `WHERE task_id = ?`。反查 `WHERE tag_id = ?` 则**需要**
额外的 `INDEX (tag_id)` —— 这就是"最左前缀决定你要不要建反向索引"。

## 九、SQLite ↔ PostgreSQL 差异速查

| 项目 | SQLite | PostgreSQL |
|---|---|---|
| 参数占位 | `?` / `?1` | `$1` |
| 自增 | `INTEGER PRIMARY KEY` | `GENERATED ALWAYS AS IDENTITY` / `SERIAL` |
| 布尔 | `INTEGER 0/1` | `BOOLEAN` |
| 时间 | `TEXT`（ISO 8601） | `TIMESTAMPTZ` |
| JSON | `TEXT` + `json_*` 函数 | `jsonb`（可索引） |
| 外键 | **默认关闭** | 默认开启 |
| 大小写敏感 | `LIKE` 默认不敏感（ASCII） | `LIKE` 敏感，需 `ILIKE` |
| 并发 | 单写者 | 多写者（MVCC） |
| 部分索引 | 支持 | 支持 |
| 改列类型 | **不支持**，需建新表迁移 | `ALTER TABLE ... TYPE` |
| `RETURNING` | 3.35+ | 支持 |

**迁移到 PostgreSQL 时最容易漏的三处**：占位符、时间类型、`LIKE` 大小写。

## 十、反模式清单

| 反模式 | 症状 | 修法 |
|---|---|---|
| 逗号分隔的多值字段 | `tags = "a,b,c"` | 建关联表（1NF） |
| 万能 `VARCHAR(255)` | 全表都是字符串 | 按语义选类型 |
| 无主键表 | 无法定位单行、无法做关联 | 加代理主键 |
| 存派生数据不维护 | `task_count` 与实际不符 | 去规范化必须有同步机制 |
| `SELECT *` | 传输多余列、破坏覆盖索引 | 显式列名 |
| 在 SQL 里做业务计算 | 逻辑分散在代码和 SQL 两处 | 计算放应用层，SQL 只取数据 |
| 用 `LIKE '%x%'` 做搜索 | 无法走索引，全表扫描 | 前缀匹配 `LIKE 'x%'` 或全文索引 |
| 时间存本地时间 | 跨时区排序错误 | 统一 UTC |
| 用浮点存金额 | 0.01 累加出 0.0099999 | 整数分 |
| 每张表都加 `is_active/flag1/flag2` | 语义丢失 | 用状态机 + CHECK 约束 |

## 十一、设计评审 checklist

写完 DDL 后逐条自问：

- [ ] 每张表都有主键？
- [ ] 每个 `FOREIGN KEY` 对应的列都建了索引？（否则删父行时子表全表扫描）
- [ ] 每个 `UNIQUE` 都考虑了软删除吗？
- [ ] 每个可空列都真的应该可空吗？（能 `NOT NULL DEFAULT` 就别留空）
- [ ] 每个索引都能说出它支撑哪条具体查询吗？
- [ ] 时间字段全部是 UTC 吗？
- [ ] 金额字段是整数分或 DECIMAL 吗？
- [ ] 状态字段有 `CHECK` 约束吗？
- [ ] 有没有"看起来像列表"的文本字段？（1NF 检查）
- [ ] 复合索引的列顺序符合"等值→范围→排序"吗？
- [ ] `updated_at` 有明确的写入点吗？
- [ ] 破坏性变更是否已拆成"加新列 → 双写 → 切换 → 删旧列"？
