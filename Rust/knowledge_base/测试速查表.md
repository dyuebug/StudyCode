# Rust 测试速查表

> 对应材料：`rust_basics/28_testing.rs`（第 36 天）、`todo-api/tests/`、`task-manager/tests/`、
> `realtime-chat/tests/ws.rs`（第 41 天）

---

## 1. 一句话

测试 = 一段**会自己判断对错**的代码。
它的价值不是"证明代码对"，而是**在你改坏它的时候立刻告诉你**。

---

## 2. 属性速查

| 属性 | 作用 |
|---|---|
| `#[test]` | 标记一个测试函数 |
| `#[cfg(test)] mod tests { ... }` | 单元测试模块，正常构建时整体剔除，**不进二进制** |
| `#[should_panic]` | 期望 panic 才算通过 |
| `#[should_panic(expected = "子串")]` | 还要求 panic 信息包含该子串 |
| `#[ignore]` | 默认跳过，`cargo test -- --ignored` 单独跑 |
| `#[tokio::test]` | 把 `async fn` 变成 tokio 运行时下的测试 |
| `#[actix_web::test]` | 同上，但用 actix 的 `System`，能起服务器 |

```rust
#[cfg(test)]
mod tests {
    use super::*;                    // 拿到父模块的私有项

    #[test]
    fn adds() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    #[should_panic(expected = "不能为 0")]
    fn rejects_zero() {
        divide(1, 0);
    }

    #[test]
    fn returns_result() -> Result<(), String> {   // 也可以用 ? ；返回 Err 即失败
        let v = parse("42").map_err(|e| e.to_string())?;
        assert_eq!(v, 42);
        Ok(())
    }
}
```

## 3. `cargo test` 常用参数

| 命令 | 作用 |
|---|---|
| `cargo test` | 跑全部（单测 + 集成 + doctest） |
| `cargo test 名字子串` | 只跑名字含该子串的用例 |
| `cargo test --test ws` | 只跑 `tests/ws.rs` 这个集成测试 |
| `cargo test --lib` | 只跑 `src/` 里的单元测试 |
| `cargo test -- --nocapture` | 不吞 `println!` 输出（调试必用） |
| `cargo test -- --test-threads=1` | 串行执行（共享外部资源时） |
| `cargo test -- --ignored` | 只跑被 `#[ignore]` 的 |
| `cargo test --release` | 用 release 编译并测试（见 §6 的重要说明） |

## 4. 单元测试 vs 集成测试

| | 单元测试 | 集成测试 |
|---|---|---|
| 位置 | `src/` 里的 `#[cfg(test)] mod tests` | `tests/*.rs` |
| 能否访问私有项 | **能**（同 crate） | **不能**（独立 crate，只能 `use` 公开 API） |
| 适合测什么 | 纯逻辑、边界条件 | 协议、HTTP 端点、真实 TCP |
| 数量原则 | 多 | 少而关键 |

### 4.1 集成测试是**独立 crate**，这会逼出一次重构

第 36 天实测：`todo-api` 加上 `tests/api.rs` 之后发现——
测试要构造应用，但装配代码在 `main.rs` 里，测试够不着。

解法（值得记住的模板）：

```
src/lib.rs      pub fn configure(cfg: &mut web::ServiceConfig) { ... }  ← 装配收敛到一处
src/main.rs     let app = App::new().configure(todo_api::configure);    ← 复用同一份装配
tests/api.rs    let app = test::init_service(App::new().configure(todo_api::configure));
```

好处不只是"测试能跑"：`main.rs` 与测试**共用同一份路由装配**，
不会出现"测试通过的配置和线上跑的不是一份"这种最坏的偏差。

### 4.2 每个测试一个独立资源

测试**默认并行**，共享资源就会互相污染：

```rust
// 每个测试一个临时 SQLite 文件 + 一个 Drop 守卫
struct TempDirGuard(PathBuf);
impl Drop for TempDirGuard {
    fn drop(&mut self) { let _ = std::fs::remove_dir_all(&self.0); }
}
```

Windows 上文件占用会导致删除失败——守卫里要允许重试，
不能因为清理失败就让测试红（那是清理的锅，不是被测代码的锅）。

端口同理：`bind(("127.0.0.1", 0))` 让操作系统分配，别手写端口。

## 5. ⭐ 零用例陷阱（第 43 天实测）

```bash
cargo test
running 0 tests
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
# 退出码 = 0
```

**0 个用例和全部通过，在退出码上长得一模一样。**

`realtime-chat` 正常输出里还天然有两段合法的 0（bin 单测、doctest），
所以断言不能写成"每行都要有通过"，必须**汇总**：

```bash
set -o pipefail                      # 不加这个，`| tee` 会吞掉 cargo 的退出码
cargo test 2>&1 | tee /tmp/test.log
total=$(grep -Eo 'test result: ok\. [0-9]+ passed' /tmp/test.log \
        | grep -Eo '[0-9]+' | awk '{s += $1} END {print s + 0}')
[ "$total" -ge 10 ] || { echo "通过用例总数 $total < 10"; exit 1; }
```

实测：`realtime-chat` 汇总 **10 = 3 + 0 + 7 + 0**。

局限：它证明"**至少**跑了 10 个"，不证明"该跑的都跑了"。

## 6. `--release` 测的**不是同一个程序**

`-O`（release）会同时关掉 `debug-assertions` 与 `overflow-checks`：

```rust
let x: u8 = 255;
println!("{}", x + 1);
// debug   → panic: attempt to add with overflow
// release → 输出 0（静默回绕）
```

所以：
- 平时用 debug 跑测试，快，且能抓到溢出
- **发布前必须** `cargo test --release` 跑一遍——它测的是真的要发出去的那个程序
- 依赖 release 才暴露的 bug，debug 测试永远抓不到

## 7. 踩过的坑

### 7.1 假测试：永远为真

```rust
#[test]
fn check() {
    let x = compute();
    assert!(x >= 0 || x < 0);      // 恒真，永远通过
}
```

判断办法：**把实现改坏，测试必须变红**。不会红的测试等于没有测试。

### 7.2 测试之间共享 `static mut`

第 36 天实测：`static mut` 在多线程测试下数据竞争，
且 `--edition 2024` 下直接编译失败：

```
error: creating a shared reference to mutable static is discouraged
note: `#[deny(static_mut_refs)]` on by default
```

用 `AtomicU32` / `Mutex` / 每测试独立 fixture。

### 7.3 `stop(true)` 让每条用例白等 30 秒

第 41 天实测：`realtime-chat` 整套测试 **31.05 s**。
真相不是"数据太多"，是每条用例结束时都在等优雅停机（默认最长 30 s）。
改成 `stop(false)` → **1.01 s**。

教训：**测试慢到没人愿意跑，就等于没有测试。**

### 7.4 阻塞调用把服务端一起卡住

测试跑在单线程 `System` 上，直接 `TcpStream::read` 会死锁。
必须 `tokio::task::spawn_blocking`。

### 7.5 用字符串比对 JSON

`serde_json` 的对象按字母排序，`assert_eq!(body, "...")` 必然失败。
解析成 `Value` 再比。

## 9. 检查清单（加测试前）

- [ ] 这个用例**改坏实现就会红**吗？（不会红 → 删掉重写）
- [ ] 它跑在独立资源上吗？（临时文件、端口 0、独立内存状态）
- [ ] 用了外部依赖吗？超时设了吗？（没超时的等待迟早挂住 CI）
- [ ] 断言比的是结构化数据还是字符串？（JSON 一律比 `Value`）
- [ ] 收尾走的是"直接停"还是"优雅停机"？（测试用直接停）
- [ ] 新增用例后，门禁里的**数量阈值**要不要调？
