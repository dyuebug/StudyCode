# Actix-web 中间件速查表

> 对应材料：`web/middleware/`（第 35 天）、`task-manager/`（第 37–39 天的日志/请求 ID/耗时中间件）
> 本表结论以"本项目实测过"为准，未实测的会标注。

---

## 1. 一句话

中间件 = 包在路由树外面的**一层服务**。请求穿过它进来，响应穿过它出去，
两头都能插一手，也可以直接短路（不叫内层）。

它的价值不只是"少写代码"，而是**不能被绕过**：handler 就算写错了，
也逃不出中间件那一层。

---

## 2. 洋葱模型：`wrap` 的调用顺序决定内外层

```rust
App::new()
    .wrap(A)          // 最外层
    .wrap(B)          // 次外层
    .service(web::resource("/x").to(handler))
```

请求方向：**A → B → handler**
响应方向：**handler → B → A**

也就是说：**先 `wrap` 的是外层**。
日志中间件应放在最外层（要看到所有请求，包括被鉴权拒掉的），
鉴权放在内一层（日志要能记录"401 是谁被拒了"）。

---

## 3. 三个 trait 的分工

| trait | 是什么 | 谁写 |
|---|---|---|
| `Service` | 能处理请求的东西（`call` → `Future<Response>`） | 中间件实现它 |
| `Transform<S, Req>` | "把服务 S 包成新服务"的工厂 | 中间件实现它 |
| `ServiceFactory<Req>` | App 内部使用的构造器 | **用户几乎从不直接写** |

骨架：

```rust
pub struct Logging;                                   // 中间件本体（配置）

impl<S, B> Transform<S, ServiceRequest> for Logging
where
    S: Service<ServiceRequest, Response = ServiceResponse<B>, Error = actix_web::Error>,
{
    type Response = ServiceResponse<B>;
    type Error = actix_web::Error;
    type Transform = LoggingMiddleware<S>;
    type InitError = ();
    type Future = Ready<Result<Self::Transform, Self::InitError>>;

    fn new_transform(&self, service: S) -> Self::Future {
        ready(Ok(LoggingMiddleware { service }))
    }
}

pub struct LoggingMiddleware<S> { service: S }

impl<S, B> Service<ServiceRequest> for LoggingMiddleware<S> /* + 同样的 where */ {
    type Response = ServiceResponse<B>;
    type Error = actix_web::Error;
    type Future = LocalBoxFuture<'static, Result<Self::Response, Self::Error>>;

    fn poll_ready(&self, cx: &mut Context<'_>) -> Poll<Result<(), Self::Error>> {
        self.service.poll_ready(cx)
    }

    fn call(&self, req: ServiceRequest) -> Self::Future {
        let start = std::time::Instant::now();
        let fut = self.service.call(req);
        Box::pin(async move {
            let res = fut.await?;
            println!("status={} 耗时={:?}", res.status(), start.elapsed());
            Ok(res)
        })
    }
}
```

## 4. 短路：不调内层，直接返回

```rust
fn call(&self, req: ServiceRequest) -> Self::Future {
    let ok = req.headers().get("authorization").is_some();
    if !ok {
        // 直接构造响应，**不调用 self.service.call(req)**
        let (req, _payload) = req.into_parts();
        let res = HttpResponse::Unauthorized()
            .json(serde_json::json!({ "success": false, "code": "unauthorized" }));
        return Box::pin(async move { Ok(ServiceResponse::new(req, res)) });
    }
    self.service.call(req)
}
```

短路是把双刃剑：省了内层开销，但**内层日志/请求 ID 全都不会执行**。
所以请求 ID 中间件必须在外层，否则被拒的请求没有 ID，排查时对不上。

## 5. 不要消费 body

中间件要读 body 就得先取出来，但取出来之后 handler 就拿不到了。
正确姿势是"读、然后放回去"：

```rust
let (req, mut payload) = req.into_parts();
let bytes = payload.read_to_end(...).await?;   // 读
// ... 处理 ...
let payload = Payload::from(bytes);            // 放回
let req = ServiceRequest::from_parts(req, payload);
Ok(self.service.call(req).await)
```

如果只是要"读一眼"，更省事的做法是**不读 body**，只记 header / 路径 / 状态码。

## 6. 往上传递数据：`extensions`

鉴权中间件验完 token，需要把"当前用户"交给 handler：

```rust
// 中间件：写入
req.extensions_mut().insert(UserId(42));

// handler：取出（提取器）
impl FromRequest for UserId {
    type Error = actix_web::Error;
    type Future = Ready<Result<Self, Self::Error>>;

    fn from_request(req: &HttpRequest, _: &mut Payload) -> Self::Future {
        let v = req.extensions().get::<UserId>().copied()
            .ok_or_else(|| actix_web::error::ErrorUnauthorized("缺少用户上下文"))?;
        ready(Ok(v))
    }
}
```

要点：
- `extensions` 是**类型索引的 map**，同一个类型只能存一个值（要区分就包一层 newtype）
- 提取器找不到值 → 返回 401，而不是 `unwrap` panic
- 提取器的错误也是响应，要符合项目的统一错误格式

## 7. 作用域：`App::wrap` vs `Scope::wrap`

| 挂在哪 | 影响范围 | 典型用途 |
|---|---|---|
| `App::wrap` | 整个应用 | 日志、请求 ID、panic 兜底、CORS |
| `Scope::wrap` | 只包那棵子树 | 管理接口的鉴权、某个 API 版本的限流 |

**本项目实测的坑**：把鉴权挂在 `Scope("/admin")` 上，
以为"非 admin 路径也受保护"——实际是**只有 `/admin` 受保护**，
其他接口完全裸奔。判断依据只能是"用不带 token 的请求逐个打这 8 个端点"，
而不是读代码猜。

## 8. 踩过的坑（每条都实测报错过）

### 8.1 `App<T, B>` → `App<T>`（E0107）

第 37 天实测：给 `App` 显式标注了泛型参数，加了中间件之后报

```
error[E0107]: struct takes 1 generic argument but 2 were given
```

原因是 actix-web 4 里 `App` 的第二个参数（body 类型）已经从公开签名里拿掉了。
**结论**：不要手写 `App` 的返回类型，用 `impl ServiceFactory<ServiceRequest>`
或干脆让编译器推断。版本升级后这类"签名漂移"最先炸的就是手写的泛型。

### 8.2 `ServiceFactory<Request>` → `ServiceFactory<ServiceRequest>`（E0277）

第 37 天实测：

```
error[E0277]: the trait bound `...: ServiceFactory<Request>` is not satisfied
help: the trait `ServiceFactory<ServiceRequest>` is implemented for ...
```

写 `App` 的泛型约束时，参数类型是 **`ServiceRequest`**，不是 `&HttpRequest`。
这是 actix-web 4 与 3 最重要的差异之一——
旧教程里到处都是 `ServiceFactory<Request>`，照抄必炸。

### 8.3 中间件里 `unwrap` 了 header

```rust
let token = req.headers().get("authorization").unwrap();   // ❌ 缺头就 500
```
缺 header 是**正常情况**（匿名请求），应当是 401，不是 500。

### 8.4 以为中间件能看见 body 而不付代价

每次 `read_to_end` 都是真的把 body 读进内存。
健康检查、静态资源这类大流量路径上读 body 会显著抬高内存峰值。

## 9. 检查清单（新增一个中间件前）

- [ ] 它要防的**具体**回归是什么？（写不出来就别加）
- [ ] 放外层还是内层？被它拒绝的请求，日志里能看到吗？
- [ ] 会短路吗？短路的响应格式与项目统一错误格式一致吗？
- [ ] 需要读 body 吗？能不读就别读
- [ ] 往上传递的数据用 `extensions` 还是重新解析？
- [ ] `App` 级还是 `Scope` 级？**用不带凭证的请求实测一遍**
