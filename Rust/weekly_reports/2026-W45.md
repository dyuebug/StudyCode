## 二、本周核心认知（截至目前）

### 【实测】1. 复合索引的第二列只在"确定条件"下才生效

```
WHERE project_id = ? AND status = ?
  → SEARCH tasks USING INDEX idx_tasks_project_status (project_id=? AND status=?)

WHERE project_id = ? AND (? IS NULL OR status = ?)
  → SEARCH tasks USING INDEX idx_tasks_project (project_id=?)
```

`OR` 写法**没有**导致全表扫描，只是退化为用索引前缀。
"条件可选就要拼 SQL，不要用 `OR`" 依然成立，但理由要改成
"复合索引后半段白建"而不是"索引完全失效"。

### 【实测】2. `ORDER BY priority` 永远要临时 B-Tree

三种查询都出现 `USE TEMP B-TREE FOR ORDER BY`——因为没有索引以 `priority` 起始。
想省掉得建 `(project_id, priority)`，代价是写放大；2000 行量级不值得。

### 【实测】3. "静默失败"是这类系统的主要风险

今天遇到的四个问题，只有一个是"会报错"的：

| 问题 | 会报错吗 |
|---|---|
| `Option<Option<T>>` 不加 `deserialize_with` | ❌ 清空功能失效 |
| 迁移里写了 `CASCADE` 但没开 `foreign_keys` | ❌ 外键不生效 |
| 状态机少一条规则 | ❌ 非法跃迁通过 |
| JOIN 里 `SELECT id` 列名歧义 | ✅ 运行时 500 |

前三个只能靠"证明型断言"发现，第四个才靠日志。

### 【实测】4. 归属校验要"穿过"资源关系

任务表没有 `owner_id`，越权判断必须 `tasks JOIN projects`。
由此产生的 `ambiguous column name: id` 是**运行时**错误——
表现为"一组接口同时 500、另一组正常"。

### 【实测】5. 第 39 天："没观测到" ≠ "不存在"

自然压测（4 worker，P=20/50，事务写）**一次 `SQLITE_BUSY` 都没撞出来**。
原因不是"并发安全"，而是写事务只有几十微秒，撞锁概率太低。

改成确定性实验（`BEGIN IMMEDIATE` 占锁 3 秒）：

| `busy_timeout` | 客户端 | 耗时 |
|---|---|---|
| `0` | `500 {"code":"internal"}` | 0.0013 s |
| `5000` | `201 Created` | 3.045 s |

两句话概括：

- `busy_timeout` 决定的是**失败前等多久**，不是**会不会失败**
- "成功但慢 3 秒"的请求，没有耗时桶的话在日志里和正常请求完全一样

### 【实测】6. 测量工具本身也会坏，而且坏得像真的

第一版压测脚本用 20 个进程 `>>` 追加同一个文件，200 个请求只记到 **105 行**。
单看脚本会得出"服务丢了一半请求"；对一下服务端日志（200 个全 201）就知道
是**尺子坏了**。

→ 结论：测量工具和被测系统必须能**互相验证**。
一个没有测试的脚本，坏掉时给的是"有数字支撑的错结论"——比感觉更危险。

### 【实测】7. 错误层写对之后不会再退步

`ApiError` + `ResponseError` + `From<sqlx::Error>` 之后，handler 里只剩 `?`。
18 个错误出口，"漏写一个"从**可能**变成**不可能**。

500 的实测响应体：

```json
{"success":false,"code":"internal","message":"服务器内部错误，请稍后重试或联系管理员"}
```

同一时刻服务端日志里是 `no such table: tasks`——**日志给人看，响应体给客户端看**。
用例 `internal_error_is_json_and_hides_sql` 断言 body 里不含 SQL 片段。

### 【实测】8. 慢客户端有两条完全不同的路径，只有一条会被 `Lagged` 抓住

`tokio::sync::broadcast` 的 `RecvError::Lagged(n)` 只能抓住"**读得慢**"；
抓不住"**根本不读**"——后者的连接任务卡在 `Session` 内部的容量 32 的 mpsc 上，
**再也走不到 `rx.recv()`**，所以 `Lagged` 永远不会出现。

实测（`lazy_reader` 只连不读 + `flood` 灌 200×8 KB）：

```
服务端：[WS] 成员 1 写超时 10s（对端不读），主动断开
对端：  {"count":1,"member":1,"type":"leave"}
```

结论：**必须再加一道写超时闸门**，否则僵尸连接会挂到操作系统级 TCP 超时。
只有"两道闸门"才覆盖全部慢客户端。

### 【实测】9. 31.05 s → 1.01 s：瓶颈是停机 grace，不是数据量

7 个集成用例全绿但整套跑了 31.05 秒。第一个假设是"灌的消息太多"，
把 32 KB×200 改成 8 KB×200 —— **耗时一个数字都没变**。

这个"没变"才是关键证据：瓶颈不在数据。真因是收尾的
`ServerHandle::stop(true)`（优雅停机，等现有连接，最长 30 秒），
而用例结束时 WebSocket 大多还开着。改成 `stop(false)` 后 **1.01 s**。

同一个行为在生产里也存在：**线上重启时若有长连接，优雅停机就是会等满**。
测试里提前知道了线上会怎么慢。

### 【实测】10. `strip` 在 MSVC 上省了 0 字节

```
-O                      210,944 B
-O -C strip=symbols     210,944 B    ← 完全相同
```

MSVC 把调试信息放在**外部 `.pdb`**（1.4 MB），PE 里没有符号表可删。
顺带推翻了另一个常识：debug 与 release 只差 **15%**（247 KB → 211 KB），
不是"一半"——因为大头在 `.pdb`，而两者的 `.pdb` 只差 33 KB。

→ 平台一换，百分比就失效。**别人给的比例不能当结论用。**

### 【实测】11. "0.4 秒编完 actix-web" 意味着根本没编

容器 `Exited (0)`、`docker logs` **完全空白**——一个"成功退出"的故障。
回到构建日志：

```
#12 DONE 279.6s     ← 依赖
#15 DONE 0.4s       ← "真源码"，不可能
```

原因：Docker 的 `COPY` **保留构建上下文文件的原始 mtime**，
cargo 判定"源码没变"，把上一步 `fn main() {}` 的 stub 留在了镜像里。

修法：`touch src/*.rs` + `grep -aq "聊天服务" 二进制` 产物断言。
修完 `Compiling realtime-chat` 出现，二进制层 446 KB → 7 MB。

**通用规律**：分层构建里"这一步很快就完成"永远值得怀疑；
给构建加一条"产物正确性断言"，能把**静默失败**变成**构建失败**。

### 【实测】12. 放在子项目目录里的 workflow 永远不运行

计划里要把 workflow 写在 `realtime-chat/.github/workflows/ci.yml`。
查证后发现：GitHub 的 Actions 发现机制**只读仓库根** `.github/workflows/`。
子目录里的同名文件不报错、不提示、永远不运行。

这是【实测】11 的同族第三例：
第 42 天是"容器退出 0 但二进制是 stub"，
第 43 天先是"workflow 放错目录"，再是下面第 13 条。

改法：放仓库根，用 `paths: ['Rust/realtime-chat/**']` 只对子项目触发。

### 【实测】13. `cargo test` 在 0 个用例时退出码仍是 0

空 crate 里把测试文件命名成 `tests/ws.rs.bak`（cargo 只收集 `tests/*.rs`）：

```
running 0 tests
test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
cargo test 退出码 = 0
```

只信退出码的门禁会放行"整个测试目录没被收集"这种事。
而且断言**不能**写成"每行都要有通过"——`realtime-chat` 正常输出天然有两段 0
（bin 单测、doctest），那样会把正常情况判成失败。

正确写法是汇总：`total = 3 + 0 + 7 + 0 = 10`，断言 `total ≥ 10`。

### 【实测】14. `cargo test | tee` 也会吃掉退出码

CI 里保存测试日志最自然的写法就是加 `| tee`，但管道的退出码取**最右侧命令**：

```
$ bash -c 'false | tee /dev/null >/dev/null; echo $?'                  → 0
$ bash -c 'set -o pipefail; false | tee /dev/null >/dev/null; echo $?' → 1
```

这是"退出码被吃掉"的第二副面孔（第一副是本报告坑 #13 的 `cmd; echo $?`）。
共同点：**退出码来自你没想到的那条命令。**

### 【实测】15. "本地零警告"是构建缓存造成的假象

`cargo clippy --all-targets -- -D warnings` 首次跑出 3 个 `useless_conversion`，
退出码 101：

```
examples/flood.rs:72:49
tests/ws.rs:310:28
tests/ws.rs:365:33
```

第 41 天记录的"零警告"来自 `cargo build`——而 `cargo build` **不编译**
`tests/` 和 `examples/` 里从未被触碰的目标。`--all-targets` 才看得见。

教训：**"没输出"要先确认"它到底跑没跑"**，这与【实测】11 是同一类判断。

第 44 天收口时一次核对揪出三处不一致，**每一处都曾经是对的**：
