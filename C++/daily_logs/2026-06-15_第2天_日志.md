## 📖 学到的知识点

### 1. 面向对象思想

**过程论 vs 对象论**：
- **过程论（C语言）**：数据和逻辑分离，世界是过程的总和
- **对象论（C++）**：数据和逻辑相互依存，世界由对象组成
- **优势**：对象论更适合大规模复杂系统

**关键理解**：
- 类是对对象的抽象（蓝图）
- 对象是类的实例（房子）
- 由对象抽象出类，由类实例化出对象

---

### 2. 类的定义

**类的组成**：
```cpp
class ClassName {
private:
    // 数据成员（属性）
    int _data;
    
public:
    // 成员函数（行为）
    void setData(int d);
};  // 注意分号！
```

**两个部分**：
1. 数据成员：相当于现实世界的属性
2. 成员函数：相当于现实世界的行为

---

### 3. 访问控制符（封装）⭐⭐⭐⭐⭐

**三种访问权限**：

| 访问控制符 | 说明 | 访问范围 |
|-----------|------|---------|
| **public** | 公有的 | 类内、类外（通过对象） |
| **private** | 私有的 | 仅类内 |
| **protected** | 保护的 | 类内、派生类 |

**默认访问权限**：
- `class`：默认 `private`
- `struct`：默认 `public`

**封装的意义**：
- 数据隐藏：保护敏感数据（private）
- 接口暴露：提供公有函数访问私有数据（public）
- 控制访问：防止非法修改，保证数据合法性

**实践验证**：
```cpp
class GoodStudent {
private:
    int _age;
public:
    void setAge(int age) {
        if (age < 0 || age > 150) {
            cout << "年龄无效！" << endl;
            return;
        }
        _age = age;
    }
};
```

**核心理解**：封装不是"藏起来"，而是"控制访问"！

---

### 4. 构造函数（Constructor）⭐⭐⭐⭐⭐

**定义**：
- 对象创建时**自动调用**
- 用于初始化数据成员
- **没有返回类型**（连 void 都不要）
- **函数名与类名相同**

**对象创建规则**：
1. 没有构造函数：编译器自动生成默认构造函数（但不初始化数据）
2. 提供了构造函数：编译器不再生成默认构造函数
3. 构造函数可以重载：提供多种创建对象的方式
4. 想要默认构造：必须手动提供空参构造函数

**示例**：
```cpp
class Point {
public:
    // 默认构造函数
    Point() {
        _x = 0;
        _y = 0;
    }
    
    // 带参数的构造函数
    Point(int x, int y) {
        _x = x;
        _y = y;
    }
private:
    int _x;
    int _y;
};

Point pt1;          // 调用默认构造函数
Point pt2(10, 20);  // 调用带参数的构造函数
```

**验证结果**：
```
调用默认构造函数 Student()
调用构造函数 Student(string, int, string)
```

---

### 5. 初始化列表 ⭐⭐⭐⭐⭐（推荐）

**语法**：
```cpp
Rectangle(int width = 0, int height = 0)
: _width(width)    // 初始化列表
, _height(height)
{
    // 构造函数体
}
```

**为什么推荐**：
- 直接初始化，而不是先默认初始化再赋值
- 效率更高
- 某些成员（const、引用）只能用初始化列表

**注意事项**：
- 初始化顺序由成员**声明顺序**决定，不是初始化列表的顺序
- 可以设置默认参数：`Point(int x = 0, int y = 0)`

**实践验证**：
```
创建矩形：宽=0, 高=0
创建矩形：宽=10, 高=0
创建矩形：宽=10, 高=20
```

---

### 6. 析构函数（Destructor）⭐⭐⭐⭐⭐

**定义**：
- 对象销毁时**自动调用**
- 用于清理资源（如释放动态内存）
- **没有返回类型**
- **函数名为 `~类名`**
- **没有参数，不能重载**

**语法**：
```cpp
~ClassName() {
    // 清理资源
    cout << "析构函数被调用" << endl;
}
```

**析构函数调用时机** ⭐⭐⭐⭐⭐（重点）：

| 对象类型 | 析构调用时机 |
|---------|-------------|
| **局部对象** | 离开作用域时 |
| **全局对象** | 程序结束时 |
| **静态对象** | 程序结束时 |
| **堆对象** | delete 时 |

**验证结果**：
```
1. 全局对象创建：程序开始
2. 堆对象销毁：delete 时
3. 局部对象销毁：离开作用域时
4. 静态对象销毁：程序结束时
5. 全局对象销毁：程序结束时（最后）
```

**关键理解**：
- 局部对象：后创建的先销毁（栈的特性）
- 不建议手动调用析构函数
- 调用析构函数 ≠ 对象被销毁
- 对象销毁一定会调用析构函数

---

### 7. struct vs class

**C语言 struct**：
- 只能有数据成员
- 没有成员函数
- 没有访问控制
- 不能继承

**C++ struct**：
- 基本等同于 class
- 默认访问权限是 `public`

**C++ class**：
- 默认访问权限是 `private`

## ❓ 遇到的问题与解决

**问题1**：为什么析构函数的调用顺序是"后创建的先销毁"？

**解决**：
- 局部对象存储在栈上
- 栈的特性：后进先出（LIFO）
- 对象的创建和销毁遵循栈的规律

**理解**：
```
创建顺序：A → B → C
销毁顺序：C → B → A（栈的后进先出）
```

---

**问题2**：初始化列表和在构造函数体中赋值有什么区别？

**解决**：
- **初始化列表**：直接初始化成员变量
- **构造函数体赋值**：先默认初始化，再赋值

**示例**：
```cpp
// 初始化列表（推荐）
Point(int x, int y) : _x(x), _y(y) {
    // _x 和 _y 已经初始化
}

// 构造函数体赋值
Point(int x, int y) {
    // _x 和 _y 先默认初始化（随机值）
    _x = x;  // 再赋值
    _y = y;
}
```

**结论**：初始化列表更高效，是推荐做法

---

**问题3**：封装的真正意义是什么？

**解决**：
通过实践对比 BadStudent 和 GoodStudent，深刻理解了封装的价值：

**不封装的问题**：
```cpp
BadStudent bs;
bs.age = -10;  // ❌ 可以设置非法值
```

**封装的好处**：
```cpp
GoodStudent gs("李四", 20);
gs.setAge(-10);  // ✅ 被拒绝："年龄无效！"
```

**核心理解**：
- 封装不是"隐藏"，而是"控制"
- 通过接口控制数据访问
- 保证数据的合法性和一致性

## 💭 今日心得

### 1. 面向对象的核心是封装

今天学习了面向对象的第一个核心概念：封装。通过实践，我深刻理解了：
- **封装不是藏起来，而是控制访问**
- private 成员保护数据
- public 接口控制访问
- 可以在接口中加入数据合法性检查

这种设计思想在大型项目中非常重要！

### 2. 构造和析构成对出现

构造函数和析构函数是一对：
- **构造函数**：对象创建时，初始化资源
- **析构函数**：对象销毁时，清理资源

这种"成对出现"的设计思想，后续会学到更深入的 RAII 原则。

### 3. 对象的生命周期

通过练习4，我清楚地看到了对象的完整生命周期：
```
创建对象 → 构造函数自动调用
    ↓
使用对象
    ↓
对象销毁 → 析构函数自动调用
```

不同类型的对象，析构时机不同：
- 局部对象：离开作用域立即销毁
- 堆对象：delete 时销毁
- 静态/全局对象：程序结束时销毁

### 4. 初始化列表是最佳实践

虽然在构造函数体中赋值也能工作，但初始化列表是更好的选择：
- 直接初始化，不是先默认初始化再赋值
- 效率更高
- 某些成员（const、引用）只能用初始化列表

**记住**：推荐使用初始化列表！

### 5. 类的设计需要考虑完整性

设计一个类时，需要考虑：
1. 哪些数据应该是私有的？（敏感数据）
2. 需要提供哪些公有接口？（外界如何使用）
3. 需要哪些构造函数？（创建对象的方式）
4. 需要析构函数吗？（是否有资源需要清理）

这是一种**系统化的设计思维**。
