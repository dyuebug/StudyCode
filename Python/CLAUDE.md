## 1. 总控原则

### 1.1 事实优先级

当不同文件中的描述发生冲突时，按照以下优先级判断，不再依据旧统计数字或文件修改时间猜测进度：

1. 实际存在且可运行的源码、页面、配置和测试文件。
2. `daily_logs/` 中明确标记为已完成的学习日志。
3. `daily_tasks/` 中的任务计划。任务只能证明“计划过”，不能证明“完成了”。
4. 阶段总结、项目 README 和知识库文档。
5. 本文件中的汇总数字。汇总数字必须根据前四项重新核对。

### 1.2 已完成、计划中、待核验的含义

- **已完成**：有学习日志中的完成记录，或有实际项目文件和可验证功能。
- **计划中**：出现在任务清单或路线图中，但没有完成日志或可验证产物。
- **待核验**：文档声称完成，但缺少对应文件、测试结果或实现证据。
- **历史记录异常**：日期、天数、文件数量或项目数量与其他资料冲突时，保留原始记录，不擅自改写历史；在汇总中明确标注异常。

### 1.3 不制造学习记录

Claude 不得：

- 把任务清单当成完成日志。
- 根据文件修改时间推断学习日期。
- 为了让天数连续而补造日志、项目或学习时长。
- 把示例代码、设计思路或扩展建议描述为已经实现。
- 在没有用户确认时填写“遇到的问题”“学习心得”或完成度。

## 4. 进度与文件命名规则

### 4.1 学习序号规则

- 学习序号表示学习会话，不表示自然日。
- 新建任务或日志前，先读取 `daily_logs/` 和 `daily_tasks/`，找出最大的已使用序号。
- 新序号必须唯一，默认使用“最大已确认完成序号 + 1”。
- 如果存在同序号旧文件，不覆盖、不删除，先在新任务中说明冲突。
- 文件名使用真实生成日期：`YYYY-MM-DD_第X天_任务.md` 或 `YYYY-MM-DD_第X天_日志.md`。
- 记录正文同时写明“记录日期”和“学习序号”，不要用文件名推断另一项。
- 历史错序只记录为异常，不为了连续性批量重命名历史文件。

### 4.2 每日任务与日志的对应关系

每个学习序号最多有一份当前任务和一份完成日志。任务可以没有日志，日志不能没有对应任务或明确说明是补记。

- 任务文件：记录计划、资源、预计时长和成功标准。
- 日志文件：记录实际完成情况、实际时长、问题、验证结果和下一步。
- 任务中的 `[ ]` 不得在没有用户确认时改成 `[x]`。
- 日志中的完成度应根据逐项完成情况计算，不使用预设的 100%。

### 4.3 统计规则

每次更新统计时说明统计口径：

- “已完成学习天数”：只统计有完成日志的唯一序号。
- “累计时长”：只累加完成日志中的明确时长；无法确认的数字标记为自报或待核算。
- “完成文件数”：只统计实际文件，不把文档中估算的文件数当作事实。
- “完成项目数”：必须列出项目名称和路径，不能只写一个总数。
- “掌握技能数”：不再使用不可复核的“720+”等数字，改用主题清单和文件路径说明。

## 5. 每天开始学习流程

触发语：“开始学习”“今天开始学习”“准备学习”。

1. 读取 `daily_logs/` 中按学习序号排序的最后一份完成日志，不以文件修改时间为唯一依据。
2. 读取该日志的“明天计划”，同时检查是否存在重复序号、未完成任务或日期冲突。
3. 读取本文件的当前待办重点，确定今天只推进一个主要主题。
4. 判断是否已有今日任务：
   - 有且内容有效：复用并补充，不重复创建。
   - 有但序号或日期冲突：创建前先在任务中写明冲突。
   - 没有：按命名规则创建新的任务文件。
5. 任务文件必须包含：
   - 记录日期、学习序号、阶段。
   - 昨日实际完成内容和遗留问题。
   - 今日学习目标和具体任务。
   - 预计时长、学习资源和成功标准。
   - 工程化任务时必须包含运行验证或测试任务。
6. 向用户汇报时只陈述已核对的事实，并明确“计划”和“已完成”的区别。

## 9. 学习材料规范

### 9.1 教学原则

- 零基础友好，但不牺牲概念准确性。
- 先解释“是什么、为什么、如何判断”，再给代码。
- 采用项目驱动和循序渐进方式。
- 遇到问题先教分析方法，再给结论。
- 示例必须说明运行方式、输入、输出和边界情况。

### 9.2 Python 学习文件推荐结构

1. 核心概念简介。
2. 核心概念详解。
3. 函数卡片：作用、语法、参数、返回值和最小示例。
4. 基础操作实践。
5. 深入理解（可选，并标明可以跳过）。
6. 常见错误和陷阱。
7. 练习题和思考提示。
8. 运行方式与成功标准。

### 9.3 注释和练习题规则

- 注释解释关键原因、参数约束和非直观行为，不重复描述显而易见的代码。
- 新函数在第一次使用前应有函数卡片；综合项目可在文件开头集中说明。
- 练习题默认不提供答案；只有用户明确索要答案时才提供，并优先给思路和验证方法。
- 教学示例可以详细，项目代码应逐步向模块化、可测试和可维护靠拢。

## 10. 项目工程化质量门禁

任何标记为“项目完成”的内容，至少满足以下检查：

### 10.1 运行和依赖

- 有明确启动命令和运行目录。
- 使用的第三方库记录在 `requirements.txt` 或 `pyproject.toml`。
- 不把 `.venv`、缓存或 IDE 配置作为项目依赖提交。
- 路径使用跨平台方式，避免依赖当前工作目录。
- 配置和密钥不硬编码；`.pem`、`.env`、令牌和数据库凭据不得进入提交内容。

### 10.2 测试和验证

- Python 逻辑优先补充 `pytest` 测试。
- Flask API 至少验证正常请求、参数错误、资源不存在和持久化结果。
- 前端项目至少执行 `TEST.md` 中的手工用例；增加自动化测试后，记录工具和命令。
- 每次完成项目都记录实际验证命令和结果，而不是只写“无 bug”。

### 10.3 文档同步

代码发生以下变化时，同步检查 README、计划、总结和测试文档：

- 文件数量或目录结构变化。
- API、数据结构或启动方式变化。
- 新增依赖、测试或安全处理。
- 功能从计划变为实际实现，或实际实现被延期。

### 10.4 质量检查

- 优先拆分超过 500 行的项目文件。
- 关注重复逻辑、硬编码路径、过长函数、异常吞掉和缺失资源关闭。
- 变更后运行适用的语法检查、测试或 lint。
- 只修复与本次任务相关的明确问题，避免无目标地重写学习示例。
