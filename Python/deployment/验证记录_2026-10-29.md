## 5. 命名卷持久化

向容器内数据库写入一条用户与帖子，然后重启容器再次查询：

```bash
docker exec forum-test python -c "
import sqlite3
c = sqlite3.connect('/data/forum.db')
c.execute(\"INSERT INTO users (username, password_hash) VALUES ('persist_user', 'x')\")
uid = c.execute(\"SELECT id FROM users WHERE username='persist_user'\").fetchone()[0]
cid = c.execute('SELECT id FROM categories LIMIT 1').fetchone()[0]
c.execute('INSERT INTO posts (user_id, category_id, title, content) VALUES (?,?,?,?)',
          (uid, cid, 'Docker 持久化验证', '写入命名卷'))
c.commit(); c.close()
"
docker restart forum-test
curl -sS http://127.0.0.1:8000/api/posts
```

```json
{"items":[{"category":"database","created_at":"2026-10-29 15:19:12","id":1,
"title":"Docker 持久化验证","username":"persist_user"}],
"page":1,"per_page":10,"status":"success"}
```

## 7. Nginx 配置语法与反向代理

真实 `forum.conf` 依赖 Let's Encrypt 证书路径，因此使用**临时自签证书**做语法与行为验证：

```bash
openssl req -x509 -nodes -newkey rsa:2048 -days 1 \
  -subj "//CN=forum.example.com" \
  -keyout privkey.pem -out fullchain.pem
docker cp fullchain.pem nginx-proxy-test:/etc/letsencrypt/live/forum.example.com/fullchain.pem
docker cp privkey.pem   nginx-proxy-test:/etc/letsencrypt/live/forum.example.com/privkey.pem
docker exec nginx-proxy-test nginx -t
```

**语法检查结果**：

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

> 说明：容器内上游地址临时由 `127.0.0.1:8000` 改为 `host.docker.internal:8000`，仅用于跨容器访问宿主机端口；仓库中的配置未修改。

| 验证项 | 命令要点 | 结果 |
|---|---|---|
| HTTPS 反代到 Flask | `curl -sk --resolve forum.example.com:18443:127.0.0.1 https://forum.example.com:18443/api/posts` | `HTTP:200` |
| 80 端口跳转 HTTPS | `curl -H "Host: forum.example.com" http://127.0.0.1:18088/` | `HTTP:301`，`Location: https://forum.example.com/` |
| 静态资源不存在 | 请求 `/static/missing.css` | `HTTP:404` |
| 后端停机 | 停止后端容器后再请求 | `HTTP:502` |
| 限流 | 连续 40 次请求 | `503` 出现 6 次，说明 `limit_req` 生效 |

> 限流验证时后端已停机，因此其余请求为 502；503 只可能来自 Nginx 限流。

## 8. 部署脚本语法

```bash
for f in deployment/scripts/*.sh; do bash -n "$f"; done
```

**结果**：

```text
deployment/scripts/backup.sh: syntax ok

deployment/scripts/healthcheck.sh: syntax ok
```

### 8.1 发现并修复 CRLF 换行

`file deployment/scripts/*.sh` 显示三个脚本均为 **CRLF**。在 Linux 容器中直接执行时：

```text
/scripts/backup.sh: line 4: $'\r': command not found
/scripts/backup.sh: line 5: set: pipefail: invalid option name
```

**修复**：

```bash
sed -i 's/\r$//' deployment/scripts/backup.sh deployment/scripts/deploy.sh deployment/scripts/healthcheck.sh
```

新增 `.gitattributes` 强制 `*.sh`、`*.py`、`*.conf`、`*.service`、`*.yml`、`*.md` 使用 LF，并在 `tests/test_project_layout.py` 增加回归测试 `test_deployment_scripts_use_lf_line_endings`。

```bash
DB_PATH=/data/forum.db BACKUP_DIR=/backups bash deployment/scripts/backup.sh
gunzip -c /backups/*.gz > /tmp/restored.db
```

**结果**：

### 8.5 `systemd/forum.service` 静态校验

Docker 内安装 systemd 因网络 TLS 中断失败后，改用本机 WSL Ubuntu（systemd 259）执行：

```bash
wsl -d Ubuntu -- bash -lc \
  'systemd-analyze verify /mnt/e/.../deployment/systemd/forum.service; echo EXIT=$?'
```

**结果**：

```text
Configuration file .../forum.service is marked executable. Please remove executable permission bits. Proceeding anyway.
Configuration file .../forum.service is marked world-writable. Please remove world writability permission bits. Proceeding anyway.
forum.service: Command /opt/study-forum/.venv/bin/gunicorn is not executable: No such file or directory
EXIT=0
```

**结论**：单元文件语法通过。两条权限警告来自 Windows 挂载视图，不是仓库文件权限；`gunicorn` 路径不存在是因为未在 WSL 安装应用。**真实启停、开机自启与 `journalctl` 收集仍未验证。**
