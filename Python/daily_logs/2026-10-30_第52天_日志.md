## 📖 学到的知识点

### 一、触发条件与权限

```yaml
on:
  push:
    branches: [master, main]
  pull_request:

permissions:
  contents: read
```

- `push` 限定分支，避免任意分支都消耗 CI 额度。
- `pull_request` 让外部贡献在合并前接受检查；来自 fork 的 PR 默认拿不到写权限。
- `permissions: contents: read` 是最小权限原则：工作流只需要读代码，不需要写仓库。
- 若后续要上传构建产物或创建 Release，需要单独增加 `actions: write` 或 `contents: write`，不能图省事给全量权限。

### 二、依赖缓存

```yaml
- uses: actions/setup-python@v5
  with:
    python-version: ${{ matrix.python-version }}
    cache: pip
```

- `cache: pip` 缓存的是 pip 下载的 wheel 与源码包，键通常由依赖文件哈希决定。
- 依赖文件不变时命中缓存，安装更快；依赖变更后缓存失效，保证环境正确。
- 缓存不是依赖锁：仍需 `requirements.txt` 或锁文件固定版本，否则同一提交在不同时间可能装到不同版本。

### 三、流水线步骤与失败影响

| 步骤 | 作用 | 失败意味着 |
|---|---|---|
| 检出代码 | 获取仓库内容 | 工作流立即失败 |
| 安装 Python | 固定解释器版本 | 环境与本地不一致 |
| 安装依赖 | 还原依赖 | 后续步骤无法执行 |
| 语法检查 | `compileall` | 存在语法错误，不能发布 |
| 运行测试 | `pytest -q` | 行为不符合预期，不能发布 |
| 依赖漏洞扫描 | `pip-audit` | 有已知漏洞，需要评估 |

`compileall` 只检查语法，不检查导入路径、类型或运行逻辑；测试通过也不等于功能完整。两者是互补关系。

### 四、`continue-on-error` 的取舍

```yaml
- name: 依赖漏洞扫描
  run: |
    pip install pip-audit
    pip-audit
  continue-on-error: true
```

- 漏洞扫描受外部漏洞库、网络和版本影响，失败原因可能是基础设施而不是代码。
- 设为 `continue-on-error` 可以避免阻塞主流程，但**风险是漏洞被忽略**。
- 更稳妥的做法：单独任务 + 定时运行 + 失败通知；修复期限按漏洞等级约定。
- 学习项目可以宽容，生产项目不应长期忽略依赖漏洞。

### 五、本地复现 CI

```bash
python -m compileall -q forum_project python_basics
python -m pytest -q
python -m pip_audit
cd web_projects/todo_app && npm test
```

- 本地复现的价值是缩短反馈环：不必等 CI 排队就能发现大部分问题。
- 本地与 CI 的差异：操作系统、Python 补丁版本、依赖缓存、环境变量、文件权限、换行符。
- 部署脚本的 CRLF 问题就是典型例子：Windows 本地能执行，Linux 报 `$'\r': command not found`。

4. **无构建产物与部署阶段**：当前只做检查，没有发布、回滚或环境区分。

7. **漏洞扫描不阻塞**：已知漏洞不会让流水线变红。

### 七、可回滚的发布流程

```text
1. 记录当前版本：git rev-parse --short HEAD，写入发布记录。
2. 在 CI 通过后构建不可变产物（镜像 digest 或带版本号的压缩包）。
3. 备份当前数据库：备份脚本 + 完整性校验。
4. 部署新版本，保留旧版本目录或旧镜像。
5. 健康检查：连续 N 次成功才判定发布成功。
6. 失败处理：切回旧版本 → 恢复服务 → 保留日志与现场。
7. 发布后观察：错误率、响应时间、关键接口。
```

- 回滚必须是**演练过的操作**，不能只写在文档里。
- 数据库迁移要向前兼容：先加列、再写代码、最后清理旧列，避免回滚后结构不匹配。
- 发布记录至少包含：版本、时间、操作人、变更内容、验证结果、回滚点。

## ⚠️ 遇到的问题与解决

**问题1**：本地 `pytest` 全部通过，CI 却在安装依赖时失败。

- 现象：CI 日志显示某个间接依赖版本找不到。
- 原因：`requirements.txt` 只固定了直接依赖，间接依赖随索引变化。
- 解决：生成锁定文件，或在 CI 中固定索引与版本；本地用同一份依赖清单重建虚拟环境验证。
- 可复用的经验：**“本地能跑”不等于“环境可复现”**。

**问题2**：前端测试在本地通过，但 CI 没有执行，合并后才发现回归。

- 原因：工作流只运行 Python 测试，没有 Node 步骤。
- 解决：增加 Node 环境与 `npm ci && npm test`；`npm ci` 依据锁文件安装，比 `npm install` 更适合 CI。
- 可复用的经验：**流水线覆盖范围要与项目实际组成一致**。
