## 📖 学到的知识点

### 一、目录结构与文件定位

- 部署相关的四类文件应分离：
  - 代码：`/opt/study-forum`
  - 数据：`/var/lib/study-forum`
  - 配置：`/etc/study-forum`
  - 日志：`/var/log`
- `/etc` 放配置，`/var` 放运行时变化的数据；把数据库放在代码目录会导致升级覆盖数据。
- `find /srv/app -type f` 只列文件；`-maxdepth` 限制深度；`-name` 按名称过滤。
- `ls -l` 第一列 10 位：类型（`-` 文件、`d` 目录、`l` 链接）+ 属主/属组/其他人权限。

### 二、权限模型

- 三位八进制分别对应属主、属组、其他人：`rwx` = 7，`rw-` = 6，`r--` = 4，`---` = 0。
- 目录的执行位 `x` 表示“可进入/可遍历”，没有 `x` 时即使有 `r` 也无法访问目录内文件。
- `chmod 640 file` 表示属主读写、属组只读、其他人无权限，适合配置文件。
- `chown forum:forum file` 同时改属主和属组；`-R` 递归，但不应无差别用于整个系统目录。
- 最小权限原则：应用用户只拥有数据目录写权限，代码目录只读。

### 三、进程与端口

- `ps aux` 显示所有用户进程；`ps -ef` 使用另一套字段风格，两者都能看到 PID、用户和完整命令。
- `ss -lntp`：`-l` 监听、`-n` 数字端口、`-t` TCP、`-p` 显示进程。定位“端口被谁占用”用它，而不是盲猜。
- `kill <PID>` 发送 `SIGTERM`，允许进程清理后退出；`kill -9` 发送 `SIGKILL`，无法被捕获，应作为最后手段。
- 服务重启失败时排查顺序：进程是否存在 → 端口是否被旧进程占用 → 日志是否有权限或配置错误。

### 四、日志定位

- `tail -n 100 file` 看最近 100 行；`tail -f file` 持续跟踪。
- `less +F file` 兼具跟踪与回看，适合排查启动失败。
- `command > out.log 2>&1` 把标准输出和标准错误写入同一文件；顺序不能颠倒，否则 stderr 仍指向原终端。
- 容器内的日志默认写到 stdout/stderr，由 `docker logs` 收集；这与宿主机 `journalctl` 是两套机制。

## ⚠️ 遇到的问题与解决

**问题1**：最小 Ubuntu 容器里执行 `ps aux` 提示 `command not found`。

- 现象：`ps: command not found`；`ss` 同样缺失。
- 原因：`ubuntu:24.04` 精简镜像默认不安装 `procps` 与 `iproute2`。
- 解决：

  ```bash
  apt-get update
  apt-get install -y procps iproute2 curl less
  ```

- 可复用的经验：**镜像精简不等于命令一定存在**，部署文档应写明依赖包。

**问题2**：`chmod 640` 后应用仍无法写入数据目录。

- 现象：读取数据库正常，写入时报 `unable to open database file`。
- 定位过程：`ls -ld /srv/app/data` 发现目录属主是 `root`，应用用户只有读和执行权限。
- 原因：文件权限正确，但目录缺少写权限；创建数据库文件需要在目录内写。
- 解决：`chown -R forum:forum /srv/app/data && chmod 750 /srv/app/data`。
- 可复用的经验：**数据库错误先看目录权限，不只看文件权限**。
