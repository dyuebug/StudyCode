## 📖 学到的知识点

### 一、镜像分层与缓存

- 每条 `RUN`、`COPY`、`ADD` 生成一层；层内容不变时可复用缓存。
- 先 `COPY requirements.txt` 再 `RUN pip install`，最后 `COPY forum_project`：只改业务代码时依赖层命中缓存，避免每次重装依赖。
- `RUN` 内的命令应合并并清理缓存，否则中间产物留在镜像层中，体积不会因为后面的 `rm` 而变小。
- 基础镜像未固定 digest 时，重新构建可能拿到新版本，导致“代码没变但环境变了”。

### 二、运行时行为

- `PYTHONUNBUFFERED=1` 让 stdout/stderr 不缓冲，日志立即出现在 `docker logs`；否则容器内日志可能延迟或丢失。
- `PYTHONDONTWRITEBYTECODE=1` 禁止生成 `.pyc`，保持镜像与卷干净。
- `WORKDIR /app` 后续的 `COPY`、`RUN`、`CMD` 都相对该目录执行。
- 非 root 用户通过 `groupadd`/`useradd` 创建，`chown` 代码与数据目录，再用 `USER app` 切换；容器内 root 与宿主机 root 的隔离程度取决于用户命名空间配置，不应默认可信。

### 三、健康检查

- `HEALTHCHECK` 命令在容器内执行，退出码 0 为健康，1 为不健康。
- `python:3.12-slim` 默认没有 `curl`，用 `urllib.request.urlopen` 发一个只读请求，避免为了健康检查额外安装工具。
- `--start-period=10s` 给应用启动留出宽限期，此期间的失败不计入重试次数。
- `--interval`、`--timeout`、`--retries` 共同决定状态从 `starting` 变为 `unhealthy` 的时间。
- 健康检查应请求无副作用的只读接口，不能触发写操作。

### 四、端口与网络

- `-p 127.0.0.1:8000:8000` 只把端口绑定到宿主机回环地址，公网无法直连，由宿主机 Nginx 转发。
- 写成 `-p 8000:8000` 等价于绑定 `0.0.0.0`，会暴露到所有网卡。
- 容器之间通过 compose 服务名解析，不通过 `localhost`；`localhost` 在容器内指容器自身。

### 五、数据卷与 Compose

- 命名卷由 Docker 管理，删除容器后仍存在；`docker compose down -v` 才会删除卷。
- 绑定挂载整个 `/app` 会覆盖镜像内代码，开发时可用，生产环境应只挂载数据目录。
- `${SECRET_KEY:?请在 .env 中设置 SECRET_KEY}`：变量缺失时 Compose 直接报错退出，避免用默认密钥启动。
- `restart: unless-stopped` 在进程崩溃和宿主机重启后恢复，但手动 `docker stop` 后不会自动拉起。

## ⚠️ 遇到的问题与解决

**问题1**：`docker compose up` 直接失败，提示缺少 `SECRET_KEY`。

- 现象：`required variable SECRET_KEY is missing a value`。
- 原因：compose 文件使用了 `:?` 语法，未设置变量时按设计拒绝启动。
- 解决：在 `.env` 或命令环境中设置 `SECRET_KEY`；生产环境使用随机值，且 `.env` 不提交。
- 可复用的经验：**这是保护机制，不要改成默认值绕过**。

**问题2**：容器健康检查一直 `unhealthy`，但手动 `curl` 正常。

- 现象：`docker inspect` 显示 `unhealthy`，日志无异常。
- 定位过程：`docker inspect --format '{{json .State.Health}}'` 查看最近一次检查的输出。
- 原因：健康检查使用的 `127.0.0.1:8000` 与 gunicorn 实际监听地址不一致，或 `start-period` 太短。
- 解决：确认 gunicorn 监听 `0.0.0.0:8000`（容器内），适当增加 `start-period`。
- 可复用的经验：**先看 Health.Log，再看应用日志**；健康检查失败不等于应用崩溃。

**问题3**：修改代码后重新构建仍然很慢。

- 原因：`COPY forum_project /app/forum_project` 放在依赖安装之前，导致依赖层缓存失效。
- 解决：调整 Dockerfile 顺序，把变化频率低的依赖清单放前面。
- 可复用的经验：**缓存命中的关键是层的顺序，不是层的数量**。
