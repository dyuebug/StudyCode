## 1. 为什么学习项目也需要测试

手工点页面能证明“这次能用”，不能证明：

- 改一个功能后旧功能仍然可用；
- 参数错误时返回的是 400 而不是 500；
- 权限判断没有在重构中被删掉；
- 统计数字与日志一致。

测试的最小目标不是覆盖率，而是**锁住已经确认的行为**。当前仓库的测试分三类：

| 类型 | 位置 | 作用 |
|---|---|---|
| API 测试 | `forum_project/tests/`、`python_basics/留言板项目/test_app_v4_sqlite.py` | 验证路由、状态码、数据库结果 |
| 结构回归测试 | `tests/test_project_layout.py` | 验证关键文件存在、日志序号唯一、时长统计口径 |
| 前端单元测试 | `web_projects/todo_app/tests/` | 验证 LocalStorage 封装的读写与异常分支 |

## 2. pytest 基础

### 2.1 发现规则

`pytest.ini`：

```ini
[pytest]
testpaths =
    forum_project/tests
    python_basics/留言板项目
    tests
python_files = test_*.py
addopts = -q
```

- `testpaths` 限定搜索范围，避免扫描 `.venv`。
- `python_files = test_*.py` 只收集以 `test_` 开头的文件。
- 测试函数也必须以 `test_` 开头。

运行：

```bash
# 全部
python_basics/.venv/Scripts/python.exe -m pytest

# 单个文件
python_basics/.venv/Scripts/python.exe -m pytest forum_project/tests/test_forum.py -q

# 单个用例，显示完整输出
python_basics/.venv/Scripts/python.exe -m pytest forum_project/tests/test_forum.py::test_create_post -vv -s
```

### 2.2 fixture

fixture 提供测试所需的准备数据，并在用例结束后清理。

```python
import pytest
from forum_project import create_app


@pytest.fixture()
def app(tmp_path):
    application = create_app(
        {
            "TESTING": True,
            "DATABASE": str(tmp_path / "test.sqlite"),
            "SECRET_KEY": "test-secret",
        }
    )
    yield application


@pytest.fixture()
def client(app):
    return app.test_client()
```

要点：

- `tmp_path` 是 pytest 内置 fixture，每个用例得到独立目录，测试之间不共享数据库。
- `yield` 之前是准备，之后是清理；本例中临时目录由 pytest 自动删除。
- fixture 可以依赖 fixture（`client` 依赖 `app`）。

### 2.3 Flask 测试客户端

```python
def test_index(client):
    response = client.get("/")
    assert response.status_code == 200
    assert "论坛".encode() in response.data
```

测试客户端不需要启动服务器，直接调用 WSGI 应用，速度快且可断言状态码、响应头和正文。

### 2.4 会话与 CSRF

论坛项目所有 POST 都要带 CSRF token。测试中先读取会话里的 token：

```python
def fetch_csrf_token(client):
    with client.session_transaction() as session:
        return session["_csrf_token"]
```

`session_transaction()` 直接操作测试会话，不经过 HTTP。拿到 token 后作为表单字段提交：

```python
response = client.post(
    "/post/new",
    data={"title": "标题", "content": "正文", "category": "general", "csrf_token": token},
)
```

### 2.5 参数化

```python
@pytest.mark.parametrize(
    ("title", "content", "expected"),
    [
        ("", "正文", 400),
        ("ab", "正文", 400),
        ("正常标题", "", 400),
        ("正常标题", "正文", 302),
    ],
)
def test_create_post_validation(client, token, title, content, expected):
    response = client.post("/post/new", data={...})
    assert response.status_code == expected
```

一个用例覆盖多组输入，失败时 pytest 会指出具体参数组合。

### 2.6 monkeypatch

用于替换环境变量、当前目录或模块属性：

```python
def test_load_messages(tmp_path, monkeypatch):
    monkeypatch.chdir(tmp_path)
    (tmp_path / "messages.json").write_text("[]", encoding="utf-8")
    module = importlib.import_module("app_v2_持久化版")
    module.load_messages()
    assert module.messages == []
```

`monkeypatch` 会在用例结束后自动还原，不需要手写 `try/finally`。

### 2.7 断言异常

```python
with pytest.raises(ValueError, match="标题"):
    validate_post("", "正文")
```

`match` 使用正则匹配异常消息，避免只断言“抛了异常”而不知道原因。

## 3. 测试隔离的三个坑

### 3.1 模块级全局状态

留言板 v1～v3 使用全局 `messages` 列表。若同一进程内多个用例共享，前一个用例的写入会污染后一个。

处理方式：

- 每个用例开始前重置全局变量；
- 或每次用 `importlib.reload()` 重新加载模块；
- 涉及文件时用 `monkeypatch.chdir(tmp_path)` 隔离工作目录。

### 3.2 固定数据库路径

若应用硬编码 `sqlite:///forum.db`，测试会写到真实文件。

处理方式：通过 `test_config` 注入 `DATABASE`，并确保 `create_app` 在初始化前完成配置覆盖。论坛项目把 `init_database(application)` 放在 `test_config` 之后，正是为此。

### 3.3 时间与顺序

分页、排序测试不要依赖“当前时间”。使用固定数据并断言 ID 顺序，或显式插入已知时间戳。

## 5. 依赖管理

### 5.1 记录什么

`requirements.txt` 记录**直接依赖**，不记录 `.venv` 中的全部包。当前分组：

```text
# Web 应用
Flask>=3.1,<4.0
Werkzeug>=3.1,<4.0
Jinja2>=3.1,<4.0
gunicorn>=22.0,<24.0 ; sys_platform != "win32"
```

- 使用兼容范围而不是精确锁定，学习项目便于升级。
- 生产项目建议用 `pip freeze` 生成锁定文件，或使用 `pip-tools` / `uv` 管理。
- `gunicorn` 加平台标记，Windows 本地安装不会失败。
- 不把 `.venv/` 提交到仓库；它包含平台相关的二进制文件。

### 5.2 虚拟环境

```bash
# 创建
python -m venv python_basics/.venv

# 安装
python_basics/.venv/Scripts/python.exe -m pip install -r requirements.txt
```

Windows 使用 `Scripts/`，Linux/macOS 使用 `bin/`。文档中给出完整路径，避免依赖“当前已激活”。

### 5.3 依赖漏洞扫描

CI 中执行：

```bash
pip install pip-audit
pip-audit
```

当前配置为 `continue-on-error: true`，即发现问题不会阻断构建。这是学习仓库的折中；生产项目应改为阻断并定期升级。

## 6. CI 流程

`.github/workflows/ci.yml` 的步骤：

1. 检出代码。
2. 安装 Python 3.12，启用 pip 缓存。
3. 安装 `requirements.txt`。
4. `python -m compileall -q forum_project python_basics`：语法检查，能发现缩进、拼写导致的语法错误。
5. `python -m pytest -q`：运行全部测试。

触发条件：推送到 `master` / `main`，以及所有 Pull Request。

- 只在 Ubuntu 上运行，未覆盖 Windows 路径差异。

## 7. Node 端测试（Todo App）

`storage.js` 是纯逻辑模块，可以用 Node 内置测试运行器验证，不需要浏览器。

```bash
cd web_projects/todo_app
node --test tests/
```

测试通过 `node:vm` 在沙箱中加载 `storage.js`，注入一个假的 `localStorage`：

```js
const sandbox = { localStorage: createFakeStorage(), console };
vm.createContext(sandbox);
vm.runInContext(source + "\n;globalThis.__Storage = Storage;", sandbox);
const Storage = sandbox.__Storage;
```

覆盖场景：

- 保存后读取，数据一致；
- 空存储返回空数组；
- 损坏 JSON 返回空数组，不抛异常；
- 非数组 JSON 返回空数组；
- `setItem` 抛异常时 `saveTasks` 返回 `false`；
- `clearStorage` 后读取为空；
- `isStorageAvailable` 在可用/不可用两种环境下返回正确布尔值。

局限：这是单元测试，不验证真实浏览器行为；UI 交互仍需按 `TEST.md` 手工验证。
