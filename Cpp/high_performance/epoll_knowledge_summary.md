## 🗺️ epoll 知识地图

```
epoll 高性能 I/O 多路复用
│
├─ 第一层：基础原理（第70天）
│  │
│  ├─ 为什么需要 epoll？
│  │  └─ select 的三大缺陷
│  │     ├─ O(n) 轮询：性能随连接数线性下降
│  │     ├─ 1024 限制：FD_SETSIZE 硬编码
│  │     └─ 重复设置：每次调用都要重设 fd_set
│  │
│  ├─ epoll 的三大改进
│  │  ├─ 事件通知：O(1) 获取就绪 fd
│  │  ├─ 无数量限制：受限于系统资源
│  │  └─ 状态维护：内核维护，不需重设
│  │
│  ├─ epoll 内部原理
│  │  ├─ 红黑树（RB-Tree）
│  │  │  ├─ 存储所有监听的 fd
│  │  │  ├─ fd 作为 key，event 作为 value
│  │  │  └─ 插入/删除/查找：O(log n)
│  │  │
│  │  └─ 就绪列表（Ready List）
│  │     ├─ 双向链表，存储已就绪的 fd
│  │     ├─ epoll_wait 直接返回此列表
│  │     └─ 时间复杂度：O(1)
│  │
│  └─ epoll 三大 API
│     ├─ epoll_create1(flags)：创建 epoll 实例
│     ├─ epoll_ctl(epfd, op, fd, event)：管理监听的 fd
│     └─ epoll_wait(epfd, events, maxevents, timeout)：等待事件
│
├─ 第二层：LT vs ET（第71天）
│  │
│  ├─ LT（水平触发，Level Triggered）
│  │  ├─ 触发条件：只要 fd 就绪就通知
│  │  ├─ 行为特点：持续通知（像水龙头）
│  │  ├─ 编程难度：简单，不容易丢数据
│  │  ├─ 性能特点：系统调用多
│  │  ├─ 是否需要非阻塞：可选
│  │  ├─ 是否需要循环读：可选
│  │  └─ 适用场景：开发阶段、低并发（<100）
│  │
│  ├─ ET（边缘触发，Edge Triggered）
│  │  ├─ 触发条件：状态变化时通知一次
│  │  ├─ 行为特点：通知一次（像门铃）
│  │  ├─ 编程难度：复杂，容易丢数据
│  │  ├─ 性能特点：系统调用少（提升 10 倍）
│  │  ├─ 是否需要非阻塞：必须
│  │  ├─ 是否需要循环读：必须
│  │  └─ 适用场景：高并发（>1000）、生产环境
│  │
│  ├─ 性能对比
│  │  ├─ 场景：1000 连接，每个 10KB 数据
│  │  ├─ LT：10000 次 epoll_wait
│  │  └─ ET：1000 次 epoll_wait（快 10 倍）
│  │
│  ├─ ET 的两大要求
│  │  ├─ 必须非阻塞 I/O
│  │  │  └─ 原因：循环读取，避免最后一次阻塞
│  │  └─ 必须循环读取
│  │     └─ 原因：ET 只通知一次，不读完会丢数据
│  │
│  └─ EAGAIN 的正确理解
│     ├─ 不是错误：表示"暂时没有数据"
│     ├─ ET 模式下：表示"数据读完了"
│     └─ 处理方式：break 退出循环（不关闭连接）
│
└─ 第三层：多线程架构（第72天）
   │
   ├─ 单线程 epoll 的瓶颈
   │  ├─ 问题：业务逻辑慢会阻塞 epoll_wait
   │  └─ 结果：其他就绪的 fd 无法处理
   │
   ├─ epoll + 线程池架构
   │  ├─ 职责分离
   │  │  ├─ 主线程：epoll_wait（快）
   │  │  └─ 工作线程：处理业务（可以慢）
   │  ├─ 任务队列：连接主线程和工作线程
   │  └─ 性能提升：充分利用多核（4 线程 = 4 倍）
   │
   ├─ 竞态问题
   │  ├─ 场景：同一 fd 被多个线程同时处理
   │  ├─ 原因：epoll 不知道 fd 正在被处理
   │  └─ 后果：数据乱序、程序崩溃
   │
   ├─ EPOLLONESHOT 解决方案
   │  ├─ 含义：One Shot = 一次性触发
   │  ├─ 行为：触发后自动移除，处理完手动注册
   │  ├─ 保证：同一时刻只有一个线程持有 fd
   │  └─ 类比：借书（借出移除，还回上架）
   │
   ├─ EPOLLONESHOT 关键点
   │  ├─ 注册时：EPOLLIN | EPOLLET | EPOLLONESHOT
   │  ├─ 处理完：EPOLL_CTL_MOD 重新注册
   │  ├─ 连接关闭：EPOLL_CTL_DEL（不重新注册）
   │  └─ listen_fd：不需要 EPOLLONESHOT
   │
   └─ 最佳实践（10+ 陷阱）
      ├─ ET 陷阱：忘记循环读取、使用阻塞 I/O
      ├─ EAGAIN 陷阱：当作错误处理
      ├─ EPOLLONESHOT 陷阱：忘记重新注册
      └─ 通用陷阱：忘记检查返回值、主线程处理业务
```

## 📊 核心概念对比

### select vs epoll 对比

| 维度 | select | epoll |
|------|--------|-------|
| **时间复杂度** | O(n) | O(1) |
| **最大连接数** | 1024（FD_SETSIZE） | 无限制（系统资源） |
| **监听方式** | 轮询 | 事件通知 |
| **fd_set 处理** | 每次重设 | 内核维护 |
| **跨平台** | 支持 | Linux 独有 |
| **适用场景** | <100 连接、跨平台 | 高并发、Linux |

---

### LT vs ET 对比

| 维度 | LT（水平触发） | ET（边缘触发） |
|------|---------------|---------------|
| **触发条件** | 只要就绪就通知 | 状态变化时通知一次 |
| **通知次数** | 多次（持续） | 一次 |
| **类比** | 水龙头（持续流） | 门铃（响一次） |
| **性能** | 较低（系统调用多） | 更高（系统调用少） |
| **编程难度** | 简单 | 复杂 |
| **非阻塞要求** | 可选 | 必须 |
| **循环读取** | 可选 | 必须 |
| **数据安全** | 高（不易丢） | 低（易丢） |
| **适用场景** | 开发、<100 连接 | 生产、>1000 连接 |

---

### 单线程 vs 多线程 epoll 对比

| 维度 | 单线程 epoll | epoll + 线程池 |
|------|-------------|---------------|
| **架构** | 主线程处理一切 | 主线程监听、工作线程处理 |
| **瓶颈** | 业务逻辑慢阻塞 | 无阻塞 |
| **性能** | 基准 | 4 线程 = 4 倍 |
| **复杂度** | 简单 | 复杂 |
| **竞态问题** | 无 | 有（需 EPOLLONESHOT） |
| **多核利用** | 低（单核） | 高（多核） |
| **适用场景** | I/O 密集 | CPU 密集 + I/O 密集 |

## 💡 核心经验总结

### 1. 性能优化的本质

**三个层次的性能提升**：
- **select → epoll**：轮询 → 事件通知（基础提升）
- **LT → ET**：持续通知 → 通知一次（减少系统调用 10 倍）
- **单线程 → 多线程**：串行 → 并行（充分利用多核 4 倍）

**总性能提升**：select 单线程 → epoll ET 多线程 = **40 倍+**

---

### 2. 编程复杂度的权衡

**复杂度递增**：
```
select（最简单）
  ↓ +红黑树、就绪列表
epoll LT
  ↓ +非阻塞、循环读取
epoll ET
  ↓ +线程池、EPOLLONESHOT
epoll ET + 线程池（最复杂）
```

**经验**：
- 开发阶段：用 LT 模式（简单、易调试）
- 生产环境：用 ET + 线程池（复杂但高性能）

---

### 3. 常见陷阱的规律

**ET 模式陷阱**（最多）：
- 忘记循环读取 → 数据丢失
- 使用阻塞 I/O → 程序卡死
- 误解 EAGAIN → 错误关闭连接

**多线程陷阱**：
- 不使用 EPOLLONESHOT → 竞态
- 忘记重新注册 → 连接死掉

**通用陷阱**：
- 忘记检查返回值 → 错误难定位
- 主线程处理业务 → 阻塞其他连接

---

### 4. 学习方法的反思

**有效的学习方法**：
1. **理论 + 实践结合**：先理解原理，再写代码
2. **对比学习**：select vs epoll、LT vs ET
3. **循序渐进**：从简单到复杂（LT → ET → 多线程）
4. **经验沉淀**：总结陷阱和最佳实践

**本周最有价值的学习**：
- 理解"为什么"比记住"怎么做"更重要
- 画图辅助理解（红黑树、就绪列表、竞态场景）
- 用类比简化理解（水龙头 vs 门铃）
