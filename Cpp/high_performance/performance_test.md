### 实验3：理论分析（无需实际测试）

**假设场景**：1000 个连接，100 个活跃

**select 的工作量**：
- 每次 select() 遍历 1000 个 fd
- 时间复杂度：O(1000)
- 即使只有 100 个活跃，也要检查 1000 次

**epoll 的工作量**：
- epoll_wait() 直接返回 100 个就绪 fd
- 时间复杂度：O(100)
- 工作量只与活跃连接数相关

**结论**：
- 连接数 1000，活跃 100：epoll 快 10 倍
- 连接数 10000，活跃 100：epoll 快 100 倍
- 连接数越多，epoll 优势越明显

## 🎓 知识总结

### select 适用场景

✅ 适合：
- 连接数 < 100
- 跨平台需求（Windows 也支持 select）
- 简单的小型服务器

❌ 不适合：
- 高并发（>1000 连接）
- 性能要求高的场景

---

### epoll 适用场景

✅ 适合：
- 高并发（1000+ 连接）
- 长连接场景（WebSocket、推送服务）
- 性能敏感的服务器（Nginx、Redis）

❌ 不适合：
- 少量连接（<10）
- 需要跨平台（epoll 是 Linux 独有）

---

### 核心理解

**select 的问题**：
```
连接数 ↑ → 性能 ↓（线性下降）
```

**epoll 的优势**：
```
连接数 ↑ → 性能稳定（只与活跃连接数相关）
```

**本质区别**：
- select：主动轮询（你去问每个 fd）
- epoll：被动通知（fd 就绪时告诉你）
