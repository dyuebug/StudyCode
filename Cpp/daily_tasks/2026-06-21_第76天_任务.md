### 任务1：主从 Reactor 理论学习（预计60分钟）

#### 1.1 单 Reactor + 线程池的瓶颈

**问题场景**：
```
单 Reactor + 线程池：
  主线程（Reactor）：
    - epoll_wait 监听所有 fd
    - accept 新连接
    - recv 接收所有连接的数据
    - 创建任务交给线程池

  工作线程池：
    - 处理业务逻辑
    - send 发送结果
```

**瓶颈**：
- 主线程负责所有 I/O 操作（accept + recv）
- 当连接数很多时（10000+），主线程成为瓶颈
- 即使有多核 CPU，主线程只用 1 个核

**影响**：
- 场景：10000 个连接，每个连接每秒 1 个请求
- 主线程：10000 次 recv/秒
- 假设每次 recv 1ms，主线程需要 10 秒
- 结果：主线程忙不过来，延迟增加

---

#### 1.2 主从 Reactor 架构

**核心思想**：多个 Reactor 并行工作

**架构图**：
```
┌────────────────────────────────────────┐
│     主 Reactor（Main Reactor）          │
│                                        │
│  职责：只负责 accept 新连接             │
│                                        │
│  while (true) {                        │
│    events = epoll_wait(listen_fd);     │
│    client_fd = accept(listen_fd);      │
│    // ⭐ 分发给从 Reactor               │
│    subReactor.addConnection(client_fd);│
│  }                                     │
└────────────────────────────────────────┘
              ↓ 分发连接
┌────────────────────────────────────────┐
│   从 Reactor 1（Sub Reactor 1）        │
│                                        │
│  职责：负责一部分连接的 I/O             │
│                                        │
│  while (true) {                        │
│    events = epoll_wait(...);           │
│    recv(fd, buf, ...);                 │
│    pool.enqueue([buf, fd]() {         │
│      process(buf);                    │
│      send(fd, result, ...);           │
│    });                                │
│  }                                     │
└────────────────────────────────────────┘

┌────────────────────────────────────────┐
│   从 Reactor 2（Sub Reactor 2）        │
│  （同上，负责另一部分连接）             │
└────────────────────────────────────────┘

┌────────────────────────────────────────┐
│   从 Reactor 3（Sub Reactor 3）        │
│  （同上，负责另一部分连接）             │
└────────────────────────────────────────┘

              ↓ 任务队列
┌────────────────────────────────────────┐
│       工作线程池（共享）                │
│                                        │
│  处理所有从 Reactor 的业务逻辑          │
└────────────────────────────────────────┘
```

**职责划分**：

| 组件 | 职责 | 线程 |
|------|------|------|
| **主 Reactor** | 只负责 accept | 1 个线程 |
| **从 Reactor** | 负责各自连接的 I/O（recv） | N 个线程 |
| **工作线程池** | 业务逻辑处理 | M 个线程 |

---

#### 1.3 主从 Reactor 的优势

**1. 职责再分离**：
```
单 Reactor：accept + recv（混在一起）
主从 Reactor：accept（主）+ recv（从）
```

**2. 充分利用多核**：
```
单 Reactor：1 个线程处理所有 I/O
主从 Reactor：1 + N 个线程并行处理 I/O
```

**3. 性能提升**：
```
场景：10000 个连接，4 个从 Reactor

单 Reactor：
  - 主线程：10000 次 recv = 10 秒
  - QPS = 1000

主从 Reactor：
  - 主 Reactor：accept（很快，可忽略）
  - 4 个从 Reactor：10000 次 recv / 4 = 2.5 秒/个
  - QPS = 4000
  - 性能提升 4 倍
```

---

#### 1.4 连接分配策略

**轮询（Round Robin）**：
```cpp
// 轮询分配连接给从 Reactor
int next_sub_reactor = 0;
void onNewConnection(int client_fd) {
    subReactors[next_sub_reactor].addConnection(client_fd);
    next_sub_reactor = (next_sub_reactor + 1) % NUM_SUB_REACTORS;
}
```

**优点**：简单，分配均匀  
**缺点**：不考虑负载

**最少连接（Least Connections）**：
```cpp
// 选择连接数最少的从 Reactor
void onNewConnection(int client_fd) {
    int min_idx = 0;
    int min_connections = subReactors[0].getConnectionCount();
    
    for (int i = 1; i < NUM_SUB_REACTORS; i++) {
        int count = subReactors[i].getConnectionCount();
        if (count < min_connections) {
            min_connections = count;
            min_idx = i;
        }
    }
    
    subReactors[min_idx].addConnection(client_fd);
}
```

**优点**：负载均衡  
**缺点**：需要维护连接计数

---

#### 1.5 主从 Reactor vs 单 Reactor + 线程池

| 维度 | 单 Reactor + 线程池 | 主从 Reactor |
|------|-------------------|-------------|
| **I/O 处理** | 1 个线程 | 1 + N 个线程 |
| **accept** | 主线程 | 主 Reactor |
| **recv** | 主线程 | 从 Reactor（多个） |
| **业务逻辑** | 工作线程池 | 工作线程池 |
| **瓶颈** | 主线程（I/O） | 业务逻辑 |
| **多核利用** | 部分（只工作线程） | 充分（I/O + 业务） |
| **适用连接数** | <1000 | >10000 |
| **复杂度** | 中 | 高 |

#### 1.6 Nginx 的架构

**Nginx 采用主从 Reactor 模式**：

```
┌─────────────────────────────────────┐
│       Master 进程                    │
│  - 管理 Worker 进程                  │
│  - 信号处理                          │
└─────────────────────────────────────┘
              ↓ fork
┌─────────────────────────────────────┐
│     Worker 进程 1（主从 Reactor）    │
│                                     │
│  主 Reactor：accept                 │
│  从 Reactor：epoll 处理 I/O         │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│     Worker 进程 2（主从 Reactor）    │
└─────────────────────────────────────┘

...
```

**特点**：
- 每个 Worker 进程独立运行
- Worker 内部使用主从 Reactor
- Worker 数量 = CPU 核数
- 充分利用多核

### 任务2：主从 Reactor 对比分析（预计60分钟）

**对比三种 Reactor 模型**：

#### 2.1 单线程 Reactor

**架构**：
- 1 个线程
- Reactor + Handler 都在同一线程

**优点**：简单  
**缺点**：业务逻辑慢会阻塞  
**适用**：<100 连接

---

#### 2.2 Reactor + 线程池

**架构**：
- 主线程：Reactor（accept + recv）
- 工作线程：业务逻辑

**优点**：业务逻辑不阻塞  
**缺点**：主线程 I/O 可能成为瓶颈  
**适用**：100-1000 连接

---

#### 2.3 主从 Reactor

**架构**：
- 主 Reactor：accept
- 从 Reactor：recv（多个线程）
- 工作线程：业务逻辑

**优点**：I/O 和业务都充分利用多核  
**缺点**：复杂  
**适用**：>10000 连接

---

### 任务3：架构演进总结（预计30分钟）

**Reactor 演进路线**：
```
单线程 Reactor
  ↓ 问题：业务逻辑慢
Reactor + 线程池
  ↓ 问题：主线程 I/O 瓶颈
主从 Reactor
  ↓ 完美
```

**性能对比**：
```
场景：10000 连接，业务逻辑 100ms

单线程 Reactor：
  - QPS = 10
  
Reactor + 4 线程池：
  - QPS = 40

主从 Reactor（4 从 + 4 线程池）：
  - QPS = 160
  - 性能提升 16 倍
```
