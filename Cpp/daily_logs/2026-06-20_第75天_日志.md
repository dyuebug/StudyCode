## 📖 学到的知识点

### 1. 单线程 Reactor 的瓶颈

**问题场景**：
```cpp
class ReadHandler {
    void handleEvent() {
        recv(fd, buf, sizeof(buf), 0);
        
        // ❌ 业务逻辑（假设需要 100ms）
        processBusinessLogic();  // 阻塞整个 Reactor
        
        send(fd, result, len, 0);
    }
};
```

**问题**：
- 业务逻辑慢（数据库查询、文件操作、复杂计算）
- 阻塞整个 Reactor 事件循环
- 其他就绪的 fd 无法及时处理
- 无法充分利用多核 CPU

**影响**：
- 场景：1000 个连接，业务逻辑 100ms
- 单线程：1000 × 100ms = 100 秒
- QPS = 10（非常低）

**根本原因**：
- 所有工作在单线程中串行执行
- CPU 利用率低（只用 1 个核）

### 2. Reactor + 线程池架构

**解决方案**：职责再分离

**架构设计**：
```
┌────────────────────────────────────┐
│   主线程（Reactor）                 │
│                                    │
│  Reactor 事件循环                   │
│    ↓                               │
│  Handler::handleEvent() {          │
│    recv(fd, buf, ...);  ← I/O（快）│
│                                    │
│    // ✅ 交给线程池处理              │
│    pool.enqueue([buf, fd]() {     │
│      process(buf);                │
│      send(fd, result, ...);       │
│    });                            │
│  }                                │
└────────────────────────────────────┘
              ↓ 任务队列
┌────────────────────────────────────┐
│   工作线程池（4 个线程）            │
│                                    │
│  线程1：处理业务逻辑 1              │
│  线程2：处理业务逻辑 2              │
│  线程3：处理业务逻辑 3              │
│  线程4：空闲，等待任务              │
└────────────────────────────────────┘
```

**职责划分**：

| 组件 | 职责 | 特点 |
|------|------|------|
| **主线程（Reactor）** | I/O 事件处理 | 快速、不阻塞 |
| **工作线程池** | 业务逻辑处理 | 可以慢、并发 |

**主线程**：
- epoll_wait 监听事件
- recv 接收数据
- 创建任务，放入队列
- 立即继续事件循环（不阻塞）

**工作线程**：
- 从队列取任务
- 处理业务逻辑（可以慢）
- send 发送结果

**优势**：
- ✅ Reactor 主线程不阻塞（只负责 I/O）
- ✅ 工作线程并发处理业务逻辑
- ✅ 充分利用多核 CPU

**性能提升**：
- 场景：1000 个连接，业务逻辑 100ms，4 个工作线程
- 多线程：1000 × 100ms / 4 = 25 秒
- QPS = 40
- **性能提升 4 倍**

### 3. Reactor + 线程池 vs epoll + 线程池

**第1周的 epoll + 线程池**（第72天）：
```cpp
// 原始 epoll + 线程池
while (true) {
    events = epoll_wait(...);
    
    for (event in events) {
        if (fd == listen_fd) {
            // 主线程处理 accept
        } else {
            // ❌ 整个事件处理交给线程池
            pool.enqueue([fd]() {
                handleClient(fd);  // recv + 业务 + send
            });
        }
    }
}
```

**今天的 Reactor + 线程池**：
```cpp
// Reactor + 线程池
class ReadHandler {
    void handleEvent() {
        // ✅ 主线程只负责 recv
        recv(fd, buf, sizeof(buf), 0);
        
        // ✅ 只把业务逻辑交给线程池
        pool.enqueue([buf, fd]() {
            processBusinessLogic(buf);
            send(fd, result, len, 0);
        });
    }
};
```

**核心区别对比**：

| 维度 | epoll + 线程池 | Reactor + 线程池 |
|------|---------------|-----------------|
| **架构** | 原始 epoll | Reactor 框架 |
| **主线程** | epoll_wait + 分发 | Reactor 事件循环 |
| **线程池** | recv + 业务 + send | 只处理业务逻辑 |
| **recv** | 工作线程 | 主线程 |
| **send** | 工作线程 | 工作线程 |
| **代码组织** | 混在一起 | Handler 分离 |
| **扩展性** | 低 | 高 |
| **粒度** | 粗粒度 | 细粒度 |

**关键理解**：
- 第1周：整个事件处理交给线程池（粗粒度）
- 今天：只把业务逻辑交给线程池（细粒度）
- Reactor 提供了更清晰的架构
- 细粒度分工更灵活

### 4. 关键代码实现

**ReadHandler 的核心逻辑**：
```cpp
void handleEvent() override {
    // ⭐ 主线程：recv 接收数据
    char buf[1024];
    int len = recv(client_fd, buf, sizeof(buf) - 1, 0);
    
    if (len > 0) {
        // ⭐⭐⭐ 关键：交给线程池处理业务逻辑
        // 捕获必要的变量
        int fd_copy = client_fd;
        string data(buf, len);
        
        reactor->getThreadPool()->enqueue([fd_copy, data]() {
            // ⭐ 工作线程：处理业务逻辑
            cout << "[工作线程] 开始处理" << endl;
            
            // 业务逻辑（可以慢）
            string result = processBusinessLogic(data);
            
            // ⭐ 工作线程：send 发送结果
            send(fd_copy, result.c_str(), result.length(), 0);
            
            cout << "[工作线程] 处理完成" << endl;
        });
    }
}
```

**Lambda 捕获的要点**：
- `[fd_copy, data]()`：值捕获，避免悬垂引用
- fd 必须拷贝，因为工作线程执行时主线程可能已修改
- data 使用 string 管理内存，自动拷贝

### 6. 最优线程数选择

**理论最优**：
- **CPU 密集型**：线程数 = CPU 核数
- **I/O 密集型**：线程数 = CPU 核数 × 2

**我们的场景**（业务逻辑 100ms）：
- 属于 I/O 密集型（等待时间长）
- 最优线程数 = CPU 核数 × 2

**实际建议**：
- 4 核 CPU：8 线程
- 8 核 CPU：16 线程
- 16 核 CPU：32 线程

**线程数过多的问题**：
- 上下文切换开销增加
- 内存占用增加（每个线程需要栈空间）
- 调度开销增加
- 性能反而下降

**实验结果**（4 核 CPU）：
- 4 线程：QPS = 40
- 16 线程：QPS = 38（下降）
- 32 线程：QPS = 30（显著下降）

**结论**：线程数不是越多越好

**单线程**：

## ❓ 遇到的问题与解决

**问题1**：为什么主线程 recv，工作线程 send？

**解决**：
- 主线程负责 I/O 事件监听（epoll_wait）
- recv 是 I/O 操作，应该在主线程（快）
- 业务逻辑可能很慢，应该在工作线程
- send 跟随业务逻辑，在工作线程完成

**问题2**：Lambda 捕获为什么要值捕获？

**解决**：
- 工作线程执行时，主线程可能已经修改了变量
- 引用捕获会导致悬垂引用
- 值捕获确保数据安全
- fd 必须拷贝，data 使用 string 管理

**问题3**：Reactor + 线程池和 epoll + 线程池本质区别是什么？

**解决**：
- **粒度不同**：
  - epoll + 线程池：整个事件处理（粗粒度）
  - Reactor + 线程池：只业务逻辑（细粒度）
- **架构不同**：
  - epoll + 线程池：原始 epoll
  - Reactor + 线程池：Reactor 框架
- **扩展性不同**：
  - epoll + 线程池：难以扩展
  - Reactor + 线程池：易于扩展

### 2. 粗粒度 vs 细粒度的权衡

**粗粒度**（第1周 epoll + 线程池）：
- 整个事件处理交给线程池
- 优点：简单，容易实现
- 缺点：不够灵活，难以优化

**细粒度**（今天 Reactor + 线程池）：
- 只把业务逻辑交给线程池
- 优点：灵活，易于优化
- 缺点：复杂，需要仔细设计

**权衡**：
- 简单场景：粗粒度足够
- 复杂场景：细粒度更优
- 架构设计：从粗到细，逐步演进

### 3. 性能优化的系统思维

**今天学到的性能优化方法**：

**1. 并行化**：
- 单线程 → 多线程
- 性能提升 N 倍（N = 线程数）

**2. 找瓶颈**：
- 单线程：瓶颈在业务逻辑
- 4 线程（4 核）：瓶颈在 CPU 核数
- 16 线程（4 核）：瓶颈在上下文切换

**3. 最优配置**：
- I/O 密集型：线程数 = CPU 核数 × 2
- CPU 密集型：线程数 = CPU 核数
- 过多线程反而降低性能

**系统思维**：
- 不是简单地"加线程"
- 而是分析瓶颈，针对性优化
- 理解系统的整体行为
