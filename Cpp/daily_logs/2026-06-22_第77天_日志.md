### 2. 三种 Reactor 详细对比

| 维度 | 单线程 Reactor | Reactor + 线程池 | 主从 Reactor |
|------|---------------|-----------------|-------------|
| **线程数** | 1 | 1 + M | 1 + N + M |
| **I/O 线程** | 1 | 1 | 1 + N |

### 3. 架构选择决策树

**快速决策方法**：
```
连接数多少？
  ├─ <100
  │   └─→ 单线程 Reactor ✅
  │
  ├─ 100-1000
  │   ├─ 业务逻辑快（<10ms）？
  │   │   └─→ 单线程 Reactor ✅
  │   │
  │   └─ 业务逻辑慢（>100ms）？
  │       └─→ Reactor + 线程池 ✅
  │
  └─ >10000
      ├─ 业务逻辑快（<10ms）？
      │   └─→ 主从 Reactor ✅
      │
      └─ 业务逻辑慢（>100ms）？
          └─→ 主从 Reactor + 线程池 ✅
```

**简化原则**：
- **连接数少** → 单线程
- **业务慢** → 加线程池
- **连接数多 + 业务快** → 主从 Reactor

### 4. 常见问题解答（FAQ）

**Q1：为什么需要 Reactor 模式？**

**A**：
- 原始 epoll：所有逻辑混在事件循环中
- 问题：难以扩展、难以维护
- Reactor：职责分离（事件循环 vs 事件处理）
- 好处：代码清晰、易于扩展、符合开闭原则

---

**Q2：什么时候需要线程池？**

**A**：
- 问题：业务逻辑慢（>100ms）会阻塞 Reactor
- 解决：线程池处理业务逻辑
- 效果：性能提升 N 倍（N = 线程数）

---

**Q3：什么时候需要主从 Reactor？**

**A**：
- 问题：单 Reactor 主线程 I/O 成为瓶颈
- 条件：连接数多（>10000）+ 业务快（<10ms）
- 解决：多个 Reactor 并行处理 I/O
- 效果：性能再提升 N 倍

---

**Q4：Nginx 为什么不用线程池？**

**A**：
- Nginx 的业务逻辑极快（<1ms，只转发）
- 单线程事件循环足够
- 多进程（Worker）已充分利用多核

---

**Q5：Redis 为什么用单线程？**

**A**：
- Redis 的业务逻辑极快（<1微秒，内存操作）
- 连接数不多（通常 <1000）
- 单线程简单、无锁、高效

---

**Q6：如何判断是 I/O 瓶颈还是业务瓶颈？**

**A**：
- 方法：计算各步骤耗时，找到 max
- I/O 瓶颈：recv/send 耗时 > 业务逻辑耗时 → 主从 Reactor
- 业务瓶颈：业务逻辑耗时 > recv/send 耗时 → 线程池

---

**Q7：最优线程数如何选择？**

**A**：
- CPU 密集型：线程数 = CPU 核数
- I/O 密集型：线程数 = CPU 核数 × 2
- 从 Reactor 数量：CPU 核数
- 工作线程池：CPU 核数 × 2（I/O 密集型）

---

**Q8：三种 Reactor 如何演进？**

**A**：
- 每一步都解决上一步的瓶颈
- 单线程 → 线程池：解决业务逻辑慢
- 线程池 → 主从：解决 I/O 瓶颈
