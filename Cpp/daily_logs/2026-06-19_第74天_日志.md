## 📖 学到的知识点

### 1. Reactor 模式核心概念

**定义**：
- Reactor（反应器）= 事件驱动架构模式
- 用于处理并发 I/O 事件
- 核心思想：**事件分离（Separation）+ 事件分发（Dispatching）**

**为什么需要 Reactor？**

**原始 epoll 的问题**：
```cpp
while (true) {
    events = epoll_wait(...);
    for (event in events) {
        if (fd == listen_fd) {
            // ❌ accept 逻辑混在这里
        } else {
            // ❌ recv 逻辑混在这里
        }
    }
}
```

问题：
- 所有逻辑混在事件循环中
- 难以扩展（添加新事件类型要修改事件循环）
- 难以维护（逻辑耦合）
- 难以测试（无法独立测试）

**Reactor 的解决方案**：
```cpp
class Reactor {
    void run() {
        while (true) {
            events = epoll_wait(...);
            for (event in events) {
                Handler* h = getHandler(event.fd);
                h->handleEvent();  // ✅ 分发给具体 Handler
            }
        }
    }
};

class AcceptHandler {  // ✅ 专门处理新连接
    void handleEvent() { /* accept 逻辑 */ }
};

class ReadHandler {    // ✅ 专门处理读事件
    void handleEvent() { /* recv 逻辑 */ }
};
```

优势：
- 事件循环和事件处理分离
- 每种事件有独立的 Handler
- 易于扩展和维护

### 2. Reactor 三大组件

**组件1：Reactor（反应器）**
- 职责：事件循环 + 事件分发
- 核心方法：
  - `registerHandler()`：注册 Handler
  - `removeHandler()`：移除 Handler
  - `run()`：运行事件循环
- 包含：
  - epoll 实例（epfd）
  - Handler 映射表（`map<int, Handler*>`）

**组件2：Demultiplexer（事件分离器）**
- 职责：I/O 多路复用
- 实现：`epoll_wait` / `select` / `poll`
- 作用：监听多个 fd，返回就绪的事件

**组件3：Handler（事件处理器）**
- 职责：处理具体的事件
- 抽象接口：
  ```cpp
  class Handler {
      virtual void handleEvent() = 0;  // 纯虚函数
      virtual int getFd() const = 0;
  };
  ```
- 具体实现：
  - `AcceptHandler`：处理新连接
  - `ReadHandler`：处理读事件
  - `WriteHandler`：处理写事件

### 3. Reactor 工作流程

```
1. 应用启动
   ↓
2. 创建 Reactor
   ↓
3. 注册 Handler
   - AcceptHandler（listen_fd）
   ↓
4. Reactor.run() 启动事件循环
   ↓
5. Demultiplexer.select()（epoll_wait）
   ↓ 返回就绪事件
6. Reactor 分发事件
   - 查找对应的 Handler
   - 调用 Handler.handleEvent()
   ↓
7. Handler 处理事件
   - AcceptHandler：accept + 注册新 ReadHandler
   - ReadHandler：recv + send
   ↓
8. 返回步骤 5（循环）
```

**关键步骤**：
- **事件分离**：epoll_wait 返回就绪事件
- **事件分发**：Reactor 查找 Handler 并调用
- **事件处理**：Handler 执行具体逻辑

### 4. Handler 抽象接口设计

**接口定义**：
```cpp
class Handler {
public:
    virtual ~Handler() = default;
    
    // 纯虚函数：处理事件
    virtual void handleEvent() = 0;
    
    // 获取文件描述符
    virtual int getFd() const = 0;
};
```

**设计意义**：
- 定义统一接口（多态）
- Reactor 只依赖抽象接口（依赖倒置原则）
- 易于扩展（开闭原则）

**具体实现**：
```cpp
class AcceptHandler : public Handler {
    void handleEvent() override {
        // 1. accept 新连接
        // 2. 创建 ReadHandler
        // 3. 注册到 Reactor
    }
};

class ReadHandler : public Handler {
    void handleEvent() override {
        // 1. recv 数据
        // 2. send 回显
        // 3. 如果连接关闭，从 Reactor 移除
    }
};
```

### 5. Reactor 单线程模型

**架构图**：
```
┌────────────────────────────────────┐
│      单线程 Reactor                 │
│                                    │
│  ┌──────────────────────────────┐ │
│  │   Reactor（事件循环）         │ │
│  │                              │ │
│  │  while (true) {              │ │
│  │    events = epoll_wait()     │ │
│  │    dispatch(events)          │ │
│  │  }                           │ │
│  └──────────────────────────────┘ │
│                                    │
│  ┌──────────┐  ┌──────────┐      │
│  │ Accept   │  │  Read    │      │
│  │ Handler  │  │ Handler  │ ...  │
│  └──────────┘  └──────────┘      │
└────────────────────────────────────┘
```

**特点**：
- 所有逻辑在单线程中执行
- Reactor + 所有 Handler 都在同一个线程
- 优点：简单，无竞态问题
- 缺点：业务逻辑慢会阻塞整个 Reactor

### 6. Reactor vs 原始 epoll 对比

| 维度 | 原始 epoll | Reactor 模式 |
|------|-----------|-------------|
| **代码组织** | 所有逻辑混在事件循环中 | 事件循环 + Handler 分离 |
| **职责划分** | 不清晰 | 清晰（Reactor 分发，Handler 处理） |
| **扩展性** | 低（修改事件循环） | 高（添加新 Handler） |
| **可维护性** | 低（逻辑耦合） | 高（职责单一） |
| **可测试性** | 低（无法独立测试） | 高（Handler 可独立测试） |
| **复杂度** | 简单 | 稍复杂（需要设计接口） |
| **性能** | 基准 | 略低（+10ns，可忽略） |

**关键差异**：
- 原始 epoll：直接调用，简单但耦合
- Reactor：分层设计，复杂但清晰

### 7. Reactor 的优缺点

**✅ 优点**：

1. **代码结构清晰**（职责分离）
   - 事件循环和事件处理分离
   - 每个 Handler 职责单一

2. **易于扩展**（开闭原则）
   - 添加新事件类型 → 创建新 Handler
   - 不需要修改 Reactor

3. **易于维护**（单一职责）
   - 修改某种事件 → 只修改对应 Handler
   - Bug 隔离，易于定位

4. **易于测试**（可测试性）
   - Handler 可独立测试
   - Mock Reactor 进行单元测试

**❌ 缺点**：

1. **复杂度增加**
   - 需要设计抽象接口
   - 学习成本较高

2. **性能略有损失**
   - 虚函数调用开销（+5-10ns）
   - Handler 查找开销
   - 相比网络 I/O（毫秒级），可忽略

3. **单线程模型的固有问题**
   - 业务逻辑慢会阻塞整个 Reactor
   - 无法充分利用多核

### 8. 适用场景

**✅ Reactor 单线程适合**：
- I/O 密集型应用
- 业务逻辑简单且快（微秒级）
- 需要清晰的代码结构
- 原型开发和学习

**❌ 不适合的场景**：
- CPU 密集型应用
- 业务逻辑慢的应用（数据库查询、文件操作）
- 需要极致性能的场景（>100万 QPS）

**解决方案**：
- Reactor 多线程模型（明天学习）
- 主从 Reactor（后天学习）

## ❓ 遇到的问题与解决

**问题1**：为什么需要 Handler 抽象接口？

**解决**：
- 统一接口：Reactor 只依赖抽象，不依赖具体
- 多态：可以处理不同类型的事件
- 扩展性：添加新 Handler 不修改 Reactor
- 这是依赖倒置原则（DIP）的体现

**问题2**：Reactor 和原始 epoll 性能差距大吗？

**解决**：
- 理论差距：+10ns（虚函数调用 + Handler 查找）
- 实际影响：网络 I/O 是毫秒级，+10ns 可忽略
- 性能差异 < 0.1%
- 代码质量提升显著

**问题3**：什么时候用 Reactor，什么时候用原始 epoll？

**解决**：
- **原始 epoll**：简单场景、原型验证、追求极致性能
- **Reactor**：生产环境、长期维护、需要扩展性
- 原则：能用 Reactor 就用 Reactor，除非有特殊理由

### 2. "分离"是架构设计的核心

**Reactor 的核心思想**：事件分离与分发

**分离什么**？
- 事件循环 vs 事件处理
- Reactor vs Handler
- 关注点分离

**为什么分离**？
- 职责单一：每个模块只做一件事
- 易于理解：逻辑清晰
- 易于扩展：修改局部，不影响整体

**这让我想起软件设计的金句**：
> "All problems in computer science can be solved by another level of indirection."  
> （计算机科学中的所有问题都可以通过增加一层间接层来解决）

Reactor 就是这样一个"间接层"：
- 原始 epoll：事件 → 直接处理
- Reactor：事件 → Reactor 分发 → Handler 处理

多了一层，但代码质量提升了。

### 3. 设计模式的实践价值

**之前对设计模式的误解**：
- 觉得是"过度设计"
- 觉得增加了复杂度
- 觉得性能有损失

**今天的理解**：
- 设计模式是经验总结
- 复杂度换来了可维护性
- 性能损失可忽略（+10ns）

**Reactor 体现的设计原则**：
- 单一职责原则（SRP）：每个 Handler 职责单一
- 开闭原则（OCP）：添加新 Handler，不修改 Reactor
- 依赖倒置原则（DIP）：Reactor 依赖抽象接口

这些不是空洞的理论，而是实实在在的好处：
- SRP → 易于维护
- OCP → 易于扩展
- DIP → 易于测试

### 4. 对"性能 vs 可维护性"的权衡

**今天学到的权衡**：

**原始 epoll**：
- 性能：100 分（基准）
- 可维护性：60 分

**Reactor**：
- 性能：99.9 分（-0.1%）
- 可维护性：95 分

**结论**：
- 牺牲 0.1% 性能
- 换来 58% 可维护性提升
- 绝对值得！

**这让我明白**：
- 过早优化是万恶之源
- 可维护性比性能更重要（大多数情况下）
- 除非性能是瓶颈，否则优先考虑架构

### 5. 单线程模型的局限性

**今天的 Reactor 单线程模型**：
- 优点：简单，无竞态
- 缺点：业务逻辑慢会阻塞

**这让我理解了架构演进的必然性**：
- 单线程 → 多线程（明天学习）
- 单 Reactor → 主从 Reactor（后天学习）

**架构不是一蹴而就的**：
- 从简单到复杂
- 每一步都解决特定问题
- 逐步演进

这就是"渐进式设计"：
- 不要一开始就追求完美
- 先实现基础功能
- 遇到瓶颈再优化
