## 📖 学到的知识点

### 1. LT（水平触发）vs ET（边缘触发）

**LT（Level Triggered）- 水平触发**：
- **触发条件**：只要 fd 处于"就绪"状态，epoll_wait 就返回
- **行为特点**：持续通知（像水龙头，只要开着就持续流水）
- **编程特点**：安全、简单，不容易丢数据
- **性能特点**：系统调用多，性能较低

**ET（Edge Triggered）- 边缘触发**：
- **触发条件**：只在状态从"未就绪"变为"就绪"时通知一次
- **行为特点**：通知一次（像门铃，按一次响一次）
- **编程特点**：复杂、容易出错，可能丢数据
- **性能特点**：系统调用少，性能更高

**核心区别**：
```
LT：持续通知 → 像水龙头持续流水
ET：通知一次 → 像门铃只响一次
```

### 2. 为什么 ET 模式更快？

**性能提升的本质**：减少 epoll_wait 的返回次数

**LT 模式的工作流程**：
```
1. 数据到达（1000 字节）
2. epoll_wait 返回（第1次通知）
3. 你读了 300 字节
4. 还剩 700 字节
5. epoll_wait 再次返回（第2次通知）← 额外的系统调用
6. 你读了 300 字节
7. 还剩 400 字节
8. epoll_wait 再次返回（第3次通知）← 额外的系统调用
9. 你读完剩余 400 字节
```

**ET 模式的工作流程**：
```
1. 数据到达（1000 字节）
2. epoll_wait 返回（只通知一次）
3. 你循环读取：
   - 读 300 字节
   - 读 300 字节
   - 读 300 字节
   - 读 100 字节
   - recv 返回 EAGAIN（数据读完）
```

**性能对比**：
- **场景**：1000 个连接，每个 10KB 数据，缓冲区 1KB
- **LT 模式**：1000 × 10 = 10000 次 epoll_wait
- **ET 模式**：1000 × 1 = 1000 次 epoll_wait
- **性能提升**：10 倍

### 3. ET 模式的两大要求

**要求1：必须使用非阻塞 I/O**

**为什么？**
- ET 模式下，必须循环读取直到数据读完
- 如果使用阻塞 I/O，最后一次 recv 会永久阻塞
- 因为没有数据时，阻塞 I/O 会等待更多数据到来
- → 整个事件循环卡住
- → 其他连接无法处理

**设置非阻塞的方法**：
```cpp
void setNonBlocking(int fd) {
    int flags = fcntl(fd, F_GETFL, 0);
    fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}
```

**要求2：必须循环读取直到 EAGAIN**

**为什么？**
- ET 模式只通知一次
- 如果不一次性读完，剩余数据不会再通知
- 剩余数据会"卡"在内核缓冲区，永远读不到

**正确的循环读取方式**：
```cpp
while (true) {
    int n = recv(fd, buf, sizeof(buf), 0);
    if (n > 0) {
        // 处理数据
    } else if (n == 0) {
        // 连接关闭
        break;
    } else {
        if (errno == EAGAIN || errno == EWOULDBLOCK) {
            // 数据读完了，正常退出
            break;
        } else {
            // 真正的错误
            perror("recv");
            break;
        }
    }
}
```

### 4. EAGAIN 的正确理解 ⭐⭐⭐⭐⭐

**常见误解**：
- ❌ EAGAIN 是错误，应该关闭连接
- ❌ EAGAIN 表示连接有问题
- ❌ EAGAIN 应该用 perror 打印

**正确理解**：
- ✅ EAGAIN = "暂时没有数据可读"
- ✅ 在非阻塞模式下，这是正常的
- ✅ 在 ET 模式下，EAGAIN 是"数据读完了"的信号
- ✅ 应该 break 退出循环，而不是关闭连接

**errno 的两个值**：
- `EAGAIN`：标准的错误码
- `EWOULDBLOCK`：与 EAGAIN 等价，历史遗留
- 通常写成：`errno == EAGAIN || errno == EWOULDBLOCK`

### 5. ET 模式的关键代码

**设置 ET 模式**：
```cpp
struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET;  // 添加 EPOLLET 标志
ev.data.fd = client_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, client_fd, &ev);
```

**accept 也要循环**（ET 模式下）：
```cpp
// listen_fd 就绪时
while (true) {
    int client_fd = accept(listen_fd, ...);
    if (client_fd < 0) {
        if (errno == EAGAIN) {
            break;  // 所有新连接都处理完了
        }
    }
    // 处理新连接
}
```

**recv 循环读取**：
```cpp
while (true) {
    int n = recv(fd, buf, sizeof(buf), 0);
    if (n > 0) {
        send(fd, buf, n, 0);  // 回显
    } else if (n == 0) {
        // 连接关闭
        break;
    } else if (errno == EAGAIN) {
        // 数据读完，正常
        break;
    }
}
```

## ❓ 遇到的问题与解决

**问题1**：为什么 ET 模式必须配合非阻塞 I/O？

**解决**：
- 因为 ET 模式需要循环读取直到 EAGAIN
- 如果是阻塞 I/O，最后一次 recv 会永久阻塞等待新数据
- 非阻塞 I/O 在没有数据时立即返回 EAGAIN
- 这样才能正常退出循环

**问题2**：EAGAIN 到底是不是错误？

**解决**：
- EAGAIN 不是真正的错误
- 它是非阻塞 I/O 的正常返回值
- 含义："现在没有数据，但连接正常，稍后可能有数据"
- 在 ET 模式下，EAGAIN 表示"数据已经读完了"
- 应该 break 退出循环，而不是关闭连接

**问题3**：ET 模式下为什么 accept 也要循环？

**解决**：
- listen_fd 也是 ET 模式
- 如果有多个新连接同时到达
- epoll_wait 只通知一次
- 必须循环 accept 直到 EAGAIN，否则会漏掉连接

**水龙头 vs 门铃**的类比让我豁然开朗：

这不只是技术差异，更是两种设计哲学：
- **LT**：我帮你记住状态，反复提醒你（安全但低效）
- **ET**：我只告诉你一次，后面你自己负责（高效但危险）

这让我想起生活中的很多场景：
- **安全设计**：汽车的安全带提示，会一直响（LT）
- **高效设计**：门禁卡只刷一次，后面你自己记住关门（ET）

ET 模式能提升 10 倍性能，但代价是什么？

**编程复杂度大幅增加**：
- 必须非阻塞 I/O

- 必须考虑边界情况

这让我理解了软件工程中的一个真理：**没有免费的午餐**。

- 深刻理解 ET 的原理

- 经过大量测试和优化

### 3. EAGAIN 的反直觉理解

今天最大的收获是理解了 EAGAIN。

**直觉反应**：EAGAIN 是 error（错误），应该关闭连接。

**实际含义**：EAGAIN 是 "try again"（稍后再试），表示暂时没数据，但连接正常。

这种反直觉的设计让我意识到：**系统编程需要摆脱常识，用机器的视角思考**。

在非阻塞 I/O 的世界里：
- "暂时没数据"是正常的
- "没有错误"才是错误的（因为应该返回数据或 EAGAIN）

这种思维方式的转变，是系统编程能力提升的标志。

### 4. 对"高并发"的新认识

之前我觉得"高并发"就是"同时处理很多连接"。

今天我理解了：**高并发的核心是减少不必要的系统调用**。

为什么系统调用昂贵？
- 用户态 → 内核态切换
- 上下文保存和恢复
- CPU 缓存失效

ET 模式通过减少 epoll_wait 的返回次数，大幅减少了系统调用。

这就是为什么：
- LT 模式：1000 连接 = 10000 次 epoll_wait
- ET 模式：1000 连接 = 1000 次 epoll_wait

10 倍性能差距，来自对系统调用的优化。
