## 📖 学到的知识点

### 1. select 的三大缺陷

**问题1：O(n) 轮询**
- 每次 select() 都要遍历所有 fd
- 1000 个连接，只有 10 个活跃，也要检查 1000 次
- 连接数越多，性能越差（线性下降）

**问题2：1024 数量限制**
- FD_SETSIZE 硬编码为 1024
- 无法支持高并发（C10K 问题）

**问题3：重复设置 fd_set**
- select 会修改 fd_set，每次调用需要重新设置
- 用户态 ↔ 内核态频繁拷贝

### 2. epoll 的三大改进

**改进1：事件通知机制（O(1) 性能）**
- 内核维护就绪列表，直接返回就绪的 fd
- 不需要遍历，性能与总连接数无关
- 只与活跃连接数相关

**改进2：无数量限制**
- 受限于系统资源，没有硬编码限制
- 可以支持百万级并发

**改进3：内核维护状态**
- fd 状态由内核维护，不需要每次重设
- 减少用户态 ↔ 内核态拷贝

### 3. epoll 内部原理

**核心数据结构1：红黑树（RB-Tree）**
- 存储所有被监听的 fd
- fd 作为 key，epoll_event 作为 value
- 插入/删除/查找：O(log n)

**核心数据结构2：就绪列表（Ready List）**
- 双向链表，存储已就绪的 fd
- epoll_wait 直接返回这个列表
- O(1) 时间复杂度

**工作流程**：
```
1. epoll_create1()  → 创建 epoll 实例（初始化红黑树和就绪列表）
2. epoll_ctl(ADD)   → 将 fd 插入红黑树，注册回调函数
3. fd 就绪          → 内核调用回调，将 fd 加入就绪列表
4. epoll_wait()     → 返回就绪列表中的 fd（O(1)）
```

### 4. epoll 三大 API

**API 1：epoll_create1()**
```cpp
int epfd = epoll_create1(0);  // 创建 epoll 实例
```

**API 2：epoll_ctl()**
```cpp
// 操作类型：EPOLL_CTL_ADD（添加）、MOD（修改）、DEL（删除）
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);  // 添加监听
```

**API 3：epoll_wait()**
```cpp
// 返回就绪的事件数组
int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
```

### 5. epoll 回显服务器实现要点

**关键步骤**：
1. 创建 epoll 实例（epoll_create1）
2. 监听 socket 加入 epoll（EPOLL_CTL_ADD）
3. 事件循环：epoll_wait 等待事件
4. 区分事件类型：
   - listen_fd 就绪 → 新连接（accept + ADD）
   - client_fd 就绪 → 数据到达（recv + send）
5. 连接关闭时从 epoll 删除（EPOLL_CTL_DEL）

**设计要点**：
- 监听 socket 和客户端 socket 都要加入 epoll
- 用 fd 区分是新连接还是数据到达
- 客户端关闭时记得 EPOLL_CTL_DEL
- epoll_wait 返回的是就绪事件数组，不是所有 fd

## ❓ 遇到的问题与解决

**问题1**：如何区分"新连接"和"数据到达"两种事件？

**解决**：
- 用 fd 判断：`if (fd == listen_fd)` 就是新连接
- listen_fd 就绪 → accept() 接受新连接
- client_fd 就绪 → recv() 接收数据

**问题2**：为什么 epoll 没有 fd 数量限制？

**解决**：
- select 用固定大小的 bitmap（FD_SETSIZE=1024）
- epoll 用红黑树动态管理，只受系统资源限制
- 红黑树可以存储任意数量的 fd

**问题3**：epoll 为什么比 select 快？

**解决**：
- select：每次遍历所有 fd（O(n)），主动轮询
- epoll：直接返回就绪 fd（O(1)），被动通知
- 本质区别：select 是"你去问"，epoll 是"它告诉你"

## 💭 今日心得

今天是阶段13的第一天，也是我理解"高性能"本质的重要一天。

### 1. 从 select 到 epoll 的飞跃

在阶段12学习 select 时，我觉得"一个线程处理多个连接"已经很厉害了。但今天学习 epoll，我才明白：**select 只是多路复用的开始，epoll 才是高性能的核心。**

**select 的问题**：就像一个服务员，站在门口不停地问每一桌："需要服务吗？需要服务吗？"1000 桌就要问 1000 次，即使只有 10 桌真正需要。

**epoll 的方案**：服务员在门口等着，哪桌需要服务，那桌举手（回调函数），服务员直接去服务举手的桌子。

这就是"主动轮询"和"被动通知"的区别。这个理解让我豁然开朗。

### 2. 红黑树 + 就绪列表的设计精妙

epoll 的内部设计让我惊叹：
- **红黑树**：管理所有 fd，保证插入/删除/查找的高效（O(log n)）
- **就绪列表**：只存储就绪的 fd，epoll_wait 直接返回（O(1)）

这种设计分离了"管理"和"查询"两个职责：
- 红黑树负责管理（支持大量 fd）
- 就绪列表负责返回（只返回需要的）

这是经典的数据结构应用，也是系统设计的典范。

### 3. 理论与实践的结合

今天的学习让我体会到：**理解原理 → 写代码 → 实验验证**的完整流程。

- **理论**：理解为什么 epoll 快（红黑树、就绪列表、事件通知）
- **实践**：用 epoll API 写出回显服务器
- **验证**：准备对比实验，用数据说话

这种学习方式让我不只是"会用"，而是"理解本质"。

### 4. 对"高性能"的新理解

以前我认为"高性能"就是"快"，但今天我明白了：

**高性能的本质不是单次速度，而是规模扩展能力。**

- select：10 个连接很快，1000 个连接就慢了
- epoll：10 个连接和 1000 个连接性能差不多（只与活跃数相关）

这就是为什么 Nginx、Redis 能支持百万级并发，而传统的多线程服务器只能支持几千并发。
