## 📖 学到的知识点

### 1. epoll + 线程池架构

**单线程 epoll 的瓶颈**：
```
主线程：epoll_wait → recv → 处理业务逻辑（慢）→ send → epoll_wait
                              ↑ 阻塞在这里
```

**问题**：
- 业务逻辑慢（数据库查询、文件操作、复杂计算）
- 阻塞主线程，其他就绪的 fd 无法处理
- CPU 多核利用率低（单线程只用 1 个核）

**解决方案：职责分离**：
```
主线程（只负责监听）：
  epoll_wait → 分发任务到队列 → 立即 epoll_wait（不阻塞）

工作线程池（负责处理）：
  从队列取任务 → 处理业务逻辑（可以慢）→ 完成
```

**优势**：
- 主线程专注监听，响应快
- 工作线程并发处理，吞吐量高
- 充分利用多核 CPU

**性能对比**：
- **场景**：1000 个连接，每个请求 100ms 处理时间
- **单线程 epoll**：1000 × 100ms = 100秒，QPS = 10
- **epoll + 4线程池**：1000 × 100ms / 4 = 25秒，QPS = 40
- **性能提升**：4 倍

### 2. 竞态问题

**问题场景**：同一 fd 被多个线程同时处理

**时间线**：
```
时刻1：epoll_wait 返回 fd=5（数据1到达）
时刻2：主线程将 fd=5 的任务放入队列
时刻3：工作线程 A 从队列取出 fd=5，开始处理数据1
时刻4：客户端又发送数据2到 fd=5
时刻5：epoll_wait 又返回 fd=5（数据2到达）← 问题！
时刻6：主线程又将 fd=5 的任务放入队列
时刻7：工作线程 B 从队列取出 fd=5，开始处理数据2

结果：线程 A 和线程 B 同时处理 fd=5
  → recv 可能读到对方的数据
  → send 可能互相覆盖
  → 数据乱序、程序崩溃
```

**为什么会出现这个问题**？
- epoll 不知道 fd=5 正在被处理
- 只要有新数据到达，epoll_wait 就会再次返回
- 主线程会再次分发任务，导致多个线程同时处理

### 3. EPOLLONESHOT 的解决方案

**含义**：
- One Shot = 一次性触发
- fd 就绪后，epoll_wait 返回一次
- **之后 epoll 自动将该 fd 从监听列表移除**
- 直到你用 EPOLL_CTL_MOD 重新注册

**工作流程**：
```
时刻1：epoll_wait 返回 fd=5
时刻2：epoll 自动移除 fd=5（不再监听）← 关键
时刻3：主线程将 fd=5 的任务放入队列
时刻4：工作线程 A 从队列取出 fd=5，开始处理
时刻5：客户端又发送数据到 fd=5
时刻6：epoll_wait 不会返回 fd=5（已移除）← 避免竞态
时刻7：工作线程 A 处理完成
时刻8：工作线程 A 用 EPOLL_CTL_MOD 重新注册 fd=5
时刻9：epoll_wait 返回 fd=5（新数据就绪）
```

**保证**：
- 同一时刻，只有一个线程处理一个 fd
- 避免竞态条件
- 数据顺序正确

**类比**：
- 像借书：借出后从书架移除，还回后重新上架
- 像排队：被叫到号的人离开队列，办完事再重新排队

### 4. EPOLLONESHOT 的关键代码

**注册时设置 EPOLLONESHOT**：
```cpp
struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET | EPOLLONESHOT;  // 一次性触发
ev.data.fd = client_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, client_fd, &ev);
```

**处理完成后重新注册**：
```cpp
// 工作线程处理完 fd 后
void handleClient(int fd, int epfd) {
    // 循环读取数据...
    
    // ⭐⭐⭐ 关键：重新注册
    struct epoll_event ev;
    ev.events = EPOLLIN | EPOLLET | EPOLLONESHOT;
    ev.data.fd = fd;
    epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev);
}
```

**主线程分发任务**：
```cpp
// 主线程不处理业务逻辑，只分发任务
if (fd != listen_fd) {
    pool.enqueue([fd, epfd]() {
        handleClient(fd, epfd);
    });
}
```

### 5. 注意事项

**listen_fd 不需要 EPOLLONESHOT**：
- 因为 accept 不涉及竞态问题
- 主线程循环 accept 即可
- 只有 client_fd 需要 EPOLLONESHOT

**处理完成后必须重新注册**：
- 否则 fd 永远不会再触发
- 连接"死掉"

**连接关闭时不需要重新注册**：
- 直接 EPOLL_CTL_DEL + close(fd)

### 6. 常见陷阱总结

**陷阱1**：ET 模式忘记循环读取 → 数据丢失

**陷阱2**：ET 模式使用阻塞 I/O → 程序卡死

**陷阱3**：把 EAGAIN 当作错误 → 错误关闭连接

**陷阱4**：忘记设置 listen_fd 为非阻塞 → accept 阻塞

**陷阱5**：EPOLLONESHOT 后忘记重新注册 → 连接死掉

**陷阱6**：多线程不使用 EPOLLONESHOT → 竞态

**陷阱7**：忘记处理 EPOLLHUP 和 EPOLLERR → fd 一直触发

**陷阱8**：epoll_ctl 的 event 参数为 NULL（ADD/MOD 时）

**陷阱9**：忘记检查 epoll_ctl 的返回值

**陷阱10**：在主线程处理耗时业务 → 阻塞其他连接

## ❓ 遇到的问题与解决

**问题1**：为什么需要 epoll + 线程池架构？

**解决**：
- 单线程 epoll 的问题：业务逻辑慢会阻塞主线程
- 其他就绪的 fd 无法及时处理
- 解决方案：主线程只监听（快），工作线程处理业务（可以慢）
- 职责分离，提升性能

**问题2**：为什么会出现竞态问题？

**解决**：
- epoll 不知道 fd 正在被处理
- 只要有新数据，epoll_wait 就会再次返回
- 导致多个线程同时处理同一个 fd
- 解决方案：EPOLLONESHOT 触发后自动移除，处理完再重新注册

**问题3**：EPOLLONESHOT 的本质是什么？

**解决**：
- 触发后自动"下线"（从 epoll 监听列表移除）
- 处理完成后手动"上线"（EPOLL_CTL_MOD 重新注册）
- 保证同一时刻只有一个线程持有 fd
- 类似"借书"或"排队"的机制

即使 epoll 的 I/O 很快，但如果业务逻辑慢（数据库查询 100ms、文件操作 50ms），整个系统就慢了。

**epoll + 线程池**的解决方案很优雅：
- **主线程**：专心做自己擅长的事（监听 I/O）
- **工作线程**：处理耗时的业务逻辑
- **任务队列**：连接两者，解耦合

这就是"职责分离"的精髓。
