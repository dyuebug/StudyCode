## 📖 学到的知识点

### 1. 单 Reactor + 线程池的瓶颈

**架构回顾**（第75天）：
```
主线程（单 Reactor）：
  - epoll_wait 监听所有 fd
  - accept 新连接
  - recv 接收所有连接的数据
  - 创建任务交给线程池

工作线程池：
  - 处理业务逻辑
  - send 发送结果
```

**瓶颈场景**：
- 场景：10000 个并发连接
- 每个连接每秒 1 个请求
- 每次 recv 耗时 1ms

**性能分析**：
- 主线程：10000 × 1ms = 10 秒
- 结果：主线程需要 10 秒才能处理完所有 recv
- 即使有 4 个工作线程，主线程依然忙不过来

**瓶颈**：
- ❌ 主线程成为瓶颈（所有 I/O 操作在单线程）
- ❌ 即使有多核 CPU，主线程只用 1 个核
- ❌ 工作线程可能空闲，无法帮助处理 I/O

**根本原因**：
- 单个 Reactor 无法充分利用多核
- 所有 I/O 操作串行执行

### 2. 主从 Reactor 架构

**核心思想**：职责再分离 + 多 Reactor 并行

**架构设计**：
```
┌────────────────────────────────────────┐
│   主 Reactor（Main Reactor）            │
│   线程：主线程                          │
│                                        │
│   职责：只负责 accept 新连接            │
│                                        │
│   while (true) {                       │
│     events = epoll_wait(listen_fd);    │
│     client_fd = accept(listen_fd);     │
│     // ⭐ 分发给从 Reactor              │
│     subReactors[idx].addConnection(    │
│         client_fd);                    │
│   }                                    │
└────────────────────────────────────────┘
              ↓ 轮询分配
┌────────────────────────────────────────┐
│   从 Reactor 1（Sub Reactor 1）        │
│   线程：工作线程 1                      │
│   管理：2500 个连接（假设总共 10000）   │
│                                        │
│   while (true) {                       │
│     events = epoll_wait(...);          │
│     recv(fd, buf, ...);                │
│     pool.enqueue([buf]() {            │
│       process(buf);                   │
│       send(fd, result, ...);          │
│     });                               │
│   }                                    │
└────────────────────────────────────────┘

从 Reactor 2、3、4（同上，各管理 2500 个连接）

              ↓ 任务队列
┌────────────────────────────────────────┐
│       工作线程池（共享）                │
│   处理所有从 Reactor 的业务逻辑         │
└────────────────────────────────────────┘
```

**职责划分**：

| 组件 | 职责 | 线程数 | 处理内容 |
|------|------|--------|---------|
| **主 Reactor** | accept 新连接 | 1 | listen_fd |
| **从 Reactor** | recv 数据 | N（如 4） | 各自管理的 client_fd |
| **工作线程池** | 业务逻辑 | M（如 4） | 共享的业务处理 |

**总线程数**：1 + N + M = 1 + 4 + 4 = 9

**关键设计**：
- 主 Reactor 只负责 accept（很快）
- 从 Reactor 分担 recv（并行）
- 工作线程池处理业务逻辑

### 3. 性能提升分析

**场景设置**：
- 10000 个并发连接
- 每个连接每秒 1 个请求
- recv 耗时：1ms
- 业务逻辑耗时：1ms（极快）
- 4 个从 Reactor
- 4 个工作线程

**单 Reactor + 线程池**：
- 主线程：10000 × 1ms = 10 秒（recv）← 瓶颈
- 工作线程：10000 × 1ms / 4 = 2.5 秒
- 总时间：max(10, 2.5) = 10 秒
- **QPS = 10000 / 10 = 1000**

**主从 Reactor + 线程池**：
- 主 Reactor：10000 × 0.1ms = 1 秒（accept）
- 从 Reactor：10000 × 1ms / 4 = 2.5 秒（recv，并行）← 瓶颈
- 工作线程：10000 × 1ms / 4 = 2.5 秒
- 总时间：max(1, 2.5, 2.5) = 2.5 秒
- **QPS = 10000 / 2.5 = 4000**

**性能提升**：4 倍！

**关键结论**：
- 主从 Reactor 的优势在于 I/O 成为瓶颈时
- 当业务逻辑极快（<10ms），主从 Reactor 优势明显
- 当业务逻辑慢（>100ms），业务逻辑依然是瓶颈

### 4. 连接分配策略

**1. 轮询（Round Robin）**：
```cpp
int nextIndex = 0;
void onNewConnection(int client_fd) {
    subReactors[nextIndex]->addConnection(client_fd);
    nextIndex = (nextIndex + 1) % subReactors.size();
}
```

- 优点：简单易实现、分配均匀
- 缺点：不考虑实际负载

**2. 最少连接（Least Connections）**：
```cpp
void onNewConnection(int client_fd) {
    int minIdx = 0;
    int minCount = subReactors[0]->getConnectionCount();
    
    for (int i = 1; i < subReactors.size(); i++) {
        int count = subReactors[i]->getConnectionCount();
        if (count < minCount) {
            minCount = count;
            minIdx = i;
        }
    }
    
    subReactors[minIdx]->addConnection(client_fd);
}
```

- 优点：负载均衡
- 缺点：需要维护连接计数

**3. 哈希（Hash）**：
```cpp
void onNewConnection(int client_fd) {
    int idx = client_fd % subReactors.size();
    subReactors[idx]->addConnection(client_fd);
}
```

- 优点：同一 fd 总是分配到同一 Reactor，缓存局部性好
- 缺点：可能分配不均匀

### 5. 三种 Reactor 模型对比

**详细对比表**：

| 维度 | 单线程 Reactor | Reactor + 线程池 | 主从 Reactor |
|------|---------------|-----------------|-------------|
| **线程数** | 1 | 1 + M | 1 + N + M |
| **I/O 线程** | 1 | 1 | 1 + N |
| **accept** | 主线程 | 主线程 | 主 Reactor |
| **recv** | 主线程 | 主线程 | 从 Reactor（多个） |
| **业务逻辑** | 主线程 | 工作线程 | 工作线程 |
| **I/O 瓶颈** | ✅ 存在 | ✅ 存在 | ❌ 不存在 |
| **业务瓶颈** | ✅ 存在 | ❌ 不存在 | ❌ 不存在 |
| **多核利用** | ❌ 差 | ⚠️ 部分 | ✅ 充分 |
| **适用连接数** | <100 | 100-1000 | >10000 |
| **复杂度** | 低 | 中 | 高 |
| **代表项目** | Redis | - | Nginx, muduo |

**演进路线**：
```
单线程 Reactor
  ↓ 问题：业务逻辑慢会阻塞
  ↓ 解决：引入线程池
Reactor + 线程池
  ↓ 问题：主线程 I/O 瓶颈
  ↓ 解决：多个 Reactor 并行
主从 Reactor
  ↓ 完美（工业级标准）
```

**性能对比**（业务逻辑 1ms）：

| 模型 | QPS | 性能提升 |
|------|-----|---------|
| 单线程 Reactor | 100 | 基准 |
| Reactor + 4 线程池 | 400 | 4 倍 |
| 主从 Reactor（4 从 + 4 线程） | 4000 | 40 倍 |

### 6. 工业级实现：Nginx

**Nginx 架构**：
```
Master 进程：
  - 读取配置文件
  - 管理 Worker 进程
  - 信号处理（reload, stop）
    ↓ fork
Worker 进程 1, 2, ..., N（N = CPU 核数）：
  - 主从 Reactor 模型
  - 主 Reactor：accept
  - 从 Reactor：epoll 处理 I/O
  - 业务逻辑：在同一线程（极快，只转发）
```

**Nginx 特点**：

**1. 多进程模型**：
- Master + 多个 Worker
- Worker 数量 = CPU 核数
- 进程隔离，稳定性高

**2. 每个 Worker 内部使用 epoll**：
- 单线程事件循环
- 非阻塞 I/O
- 业务逻辑极快（<1ms）

**3. 为什么 Nginx 不用线程池？**：
- Nginx 的业务逻辑极快（只转发、代理）
- 单线程足够，避免线程同步开销
- 多进程已充分利用多核

**其他工业实现**：

**muduo**（C++ 网络库）：
- 主从 Reactor + One Loop Per Thread
- 每个线程一个 Reactor
- 高性能、易用

**Redis**（内存数据库）：
- 单线程 Reactor
- 业务逻辑极快（内存操作）
- 简单、无锁

**Netty**（Java 框架）：
- 主从 Reactor
- Boss Group（主）+ Worker Group（从）
- Java 网络应用标准

### 7. 架构选择指南

**决策树**：
```
连接数多少？
  ├─ <100
  │   └─ 单线程 Reactor
  │
  ├─ 100-1000
  │   ├─ 业务逻辑快（<10ms）
  │   │   └─ 单线程 Reactor
  │   │
  │   └─ 业务逻辑慢（>100ms）
  │       └─ Reactor + 线程池
  │
  └─ >10000
      ├─ 业务逻辑快（<10ms）
      │   └─ 主从 Reactor
      │
      └─ 业务逻辑慢（>100ms）
          └─ 主从 Reactor + 线程池
```

**适用场景总结**：

**主从 Reactor 适合**：
- ✅ 连接数多（>10000）
- ✅ 业务逻辑快（<10ms）
- ✅ I/O 密集型

**Reactor + 线程池 适合**：
- ✅ 连接数中等（100-1000）
- ✅ 业务逻辑慢（>100ms）
- ✅ CPU + I/O 混合

**单线程 Reactor 适合**：
- ✅ 连接数少（<100）
- ✅ 业务逻辑快（<1ms）
- ✅ 简单场景

## ❓ 遇到的问题与解决

**问题1**：为什么需要主从 Reactor？单 Reactor + 线程池不够吗？

**解决**：
- 当连接数多（>10000）且业务逻辑快时
- 单 Reactor 的主线程成为瓶颈（所有 recv 在主线程）
- 主从 Reactor 用多个线程分担 I/O
- 充分利用多核

**问题2**：主从 Reactor 总是比 Reactor + 线程池快吗？

**解决**：
- **不一定**
- 当业务逻辑慢（>100ms）时，业务逻辑是瓶颈
- 此时主从 Reactor 无优势，反而更复杂
- 只有当 I/O 成为瓶颈时，主从 Reactor 才有优势

**问题3**：为什么 Redis 用单线程，Nginx 用主从 Reactor？

**解决**：
- **Redis**：
  - 业务逻辑极快（<1微秒，内存操作）
  - 连接数不多（通常 <1000）
  - 单线程足够，简单无锁
- **Nginx**：
  - 连接数多（>10000）
  - 业务逻辑快（<1ms，只转发）
  - I/O 是瓶颈，需要多 Reactor

**结论**：架构选择取决于场景
