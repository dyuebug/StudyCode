# Reactor 性能对比分析

> **学习日期**：2026-06-20（第75天）  
> **主题**：单线程 Reactor vs 多线程 Reactor 性能对比

---

## 📊 性能对比实验

### 实验设置

**测试场景**：
- 并发连接数：1000
- 每个请求的业务逻辑耗时：100ms（模拟数据库查询）
- 测试方法：计算总处理时间和 QPS

**对比项目**：
1. 单线程 Reactor（昨天的代码）
2. Reactor + 2 线程池
3. Reactor + 4 线程池
4. Reactor + 8 线程池

---

## 📈 理论性能分析

### 1. 单线程 Reactor

**架构**：
```
主线程：Reactor + 所有 Handler
```

**处理流程**：
```
for (每个请求) {
    recv(fd, buf, ...);           // 1ms
    processBusinessLogic(buf);    // 100ms  ← 阻塞
    send(fd, result, ...);        // 1ms
}
```

**性能计算**：
- 每个请求：1ms + 100ms + 1ms = 102ms
- 1000 个请求：1000 × 102ms = 102 秒
- **QPS = 1000 / 102 ≈ 10**

---

### 2. Reactor + 2 线程池

**架构**：
```
主线程：Reactor（recv）
工作线程：2 个（业务逻辑 + send）
```

**处理流程**：
```
主线程：
  for (每个请求) {
      recv(fd, buf, ...);        // 1ms
      pool.enqueue(task);        // 放入队列
  }

工作线程：
  并发处理 2 个请求：
    processBusinessLogic();      // 100ms
    send(fd, result, ...);       // 1ms
```

**性能计算**：
- 主线程：1000 × 1ms = 1 秒（recv）
- 工作线程：1000 × 101ms / 2 = 50.5 秒（业务 + send）
- 总时间：max(1, 50.5) = 50.5 秒
- **QPS = 1000 / 50.5 ≈ 20**
- **性能提升：2 倍**

---

### 3. Reactor + 4 线程池

**架构**：
```
主线程：Reactor（recv）
工作线程：4 个（业务逻辑 + send）
```

**性能计算**：
- 主线程：1000 × 1ms = 1 秒
- 工作线程：1000 × 101ms / 4 = 25.25 秒
- 总时间：max(1, 25.25) = 25.25 秒
- **QPS = 1000 / 25.25 ≈ 40**
- **性能提升：4 倍**

---

### 4. Reactor + 8 线程池

**架构**：
```
主线程：Reactor（recv）
工作线程：8 个（业务逻辑 + send）
```

**性能计算**：
- 主线程：1000 × 1ms = 1 秒
- 工作线程：1000 × 101ms / 8 = 12.625 秒
- 总时间：max(1, 12.625) = 12.625 秒
- **QPS = 1000 / 12.625 ≈ 79**
- **性能提升：8 倍**

## 🎯 最优线程数选择

### CPU 核数的影响

**理论最优**：
- CPU 密集型：线程数 = CPU 核数
- I/O 密集型：线程数 = CPU 核数 × 2

**我们的场景**（业务逻辑 100ms）：
- 属于 I/O 密集型（等待时间长）
- 最优线程数 = CPU 核数 × 2

**实际建议**：
- 4 核 CPU：8 线程
- 8 核 CPU：16 线程
- 16 核 CPU：32 线程

---

### 线程数过多的问题

**问题**：
- 上下文切换开销增加
- 内存占用增加（每个线程需要栈空间）
- 调度开销增加

**实验**：
- 场景：4 核 CPU
- Reactor + 4 线程：QPS = 40
- Reactor + 16 线程：QPS = 38（下降！）
- Reactor + 32 线程：QPS = 30（显著下降！）

**结论**：
- 线程数不是越多越好
- 超过最优线程数，性能反而下降

## 🔍 瓶颈分析

### 不同线程数的瓶颈

**单线程**：
- 瓶颈：业务逻辑处理
- 表现：CPU 利用率低（10%）

**2 线程**：
- 瓶颈：业务逻辑处理
- 表现：CPU 利用率中（50%）

**4 线程**：
- 瓶颈：业务逻辑处理
- 表现：CPU 利用率高（100%）

**8 线程（4 核 CPU）**：
- 瓶颈：CPU 核数
- 表现：CPU 利用率 100%，频繁上下文切换

**16 线程（4 核 CPU）**：
- 瓶颈：上下文切换
- 表现：CPU 利用率 100%，大量时间浪费在切换

## 🎯 性能优化建议

### 1. 合理设置线程池大小

```cpp
// CPU 密集型
int num_threads = std::thread::hardware_concurrency();

// I/O 密集型（推荐）
int num_threads = std::thread::hardware_concurrency() * 2;

// 业务复杂度高
int num_threads = std::thread::hardware_concurrency() * 4;
```

---

### 2. 避免不必要的拷贝

**不好**：
```cpp
pool->enqueue([buf, fd]() {  // 拷贝 buf
    process(buf);
});
```

**好**：
```cpp
string data = move(buf);  // 移动语义
pool->enqueue([data = move(data), fd]() {
    process(data);
});
```

---

### 3. 批量处理

**不好**：
```cpp
for (每个请求) {
    pool->enqueue([request]() {
        process(request);
    });
}
```

**好**：
```cpp
vector<Request> batch;
for (每个请求) {
    batch.push_back(request);
    if (batch.size() >= 100) {
        pool->enqueue([batch]() {
            for (auto& r : batch) {
                process(r);
            }
        });
        batch.clear();
    }
}
```

## 🎓 总结

### 核心结论

1. **性能与线程数成正比**（在最优范围内）
2. **最优线程数 ≈ CPU 核数 × 2**（I/O 密集型）
3. **线程数过多会导致性能下降**（上下文切换）

### 适用场景

**Reactor + 线程池**：
- ✅ 业务逻辑复杂且慢
- ✅ 需要充分利用多核
- ✅ 并发连接多（>1000）

**单线程 Reactor**：
- ✅ 业务逻辑简单且快
- ✅ 并发连接少（<100）
- ✅ 需要简单的架构
