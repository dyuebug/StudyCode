## 📊 四种模型详细对比

### 1. 原始 epoll

**架构**：
```cpp
while (true) {
    events = epoll_wait(...);
    for (event in events) {
        if (fd == listen_fd) {
            // accept 逻辑
        } else {
            // recv + 业务 + send 逻辑
        }
    }
}
```

**特点**：
- 所有逻辑混在一起
- 难以扩展和维护

**性能**：QPS = 10（业务逻辑 100ms）

**适用**：学习、原型

---

### 2. 单线程 Reactor

**架构**：
```
Reactor（事件循环 + 分发）
  ↓
Handler（事件处理）
  - AcceptHandler
  - ReadHandler
```

**特点**：
- 职责分离（事件循环 vs 事件处理）
- 易于扩展（添加新 Handler）
- 单线程，无竞态

**性能**：QPS = 10（业务逻辑依然阻塞）

**适用**：<100 连接，业务逻辑快

---

### 3. Reactor + 线程池

**架构**：
```
主线程（Reactor）：
  - epoll_wait
  - accept
  - recv
  - 分发任务到线程池

工作线程池：
  - 处理业务逻辑
  - send
```

**特点**：
- 职责再分离（I/O vs 业务逻辑）
- 业务逻辑不阻塞主线程
- 充分利用多核（工作线程）

**性能**：QPS = 40（4 工作线程）

**适用**：100-1000 连接，业务逻辑慢

---

### 4. 主从 Reactor

**架构**：
```
主 Reactor（1 线程）：
  - accept

从 Reactor（N 线程）：
  - recv
  - 分发任务到线程池

工作线程池（M 线程）：
  - 处理业务逻辑
  - send
```

**特点**：
- 职责再分离（accept vs recv）
- 多个 Reactor 并行处理 I/O
- 充分利用多核（I/O + 业务）

**性能**：QPS = 4000（4 从 Reactor + 4 工作线程，业务逻辑快）

**适用**：>10000 连接，I/O 密集型

## 📈 性能对比

### 场景1：业务逻辑慢（100ms）

| 模型 | QPS | 提升 | 瓶颈 |
|------|-----|------|------|
| 原始 epoll | 10 | 基准 | 业务逻辑 |
| 单线程 Reactor | 10 | 1x | 业务逻辑 |
| Reactor + 4 线程池 | 40 | 4x | 业务逻辑 |
| 主从 Reactor（4+4） | 40 | 4x | 业务逻辑 |

**结论**：业务逻辑慢时，线程池是关键，主从 Reactor 无优势

---

### 场景2：业务逻辑快（1ms）

| 模型 | QPS | 提升 | 瓶颈 |
|------|-----|------|------|
| 原始 epoll | 100 | 基准 | I/O |
| 单线程 Reactor | 100 | 1x | I/O |
| Reactor + 4 线程池 | 400 | 4x | 主线程 I/O |
| 主从 Reactor（4+4） | 4000 | 40x | - |

**结论**：业务逻辑快时，主从 Reactor 优势明显

## 🎯 职责分离的演进

### 第一次分离：事件循环 vs 事件处理

**原始 epoll → 单线程 Reactor**

```
混在一起：
  while (true) {
      events = epoll_wait(...);
      // 所有处理逻辑
  }

分离后：
  Reactor：事件循环 + 分发
  Handler：事件处理
```

**好处**：
- 代码结构清晰
- 易于扩展（添加新 Handler）
- 符合开闭原则

---

### 第二次分离：I/O vs 业务逻辑

**单线程 Reactor → Reactor + 线程池**

```
混在一起：
  Handler：recv + 业务 + send

分离后：
  主线程（Handler）：recv
  工作线程：业务 + send
```

**好处**：
- 业务逻辑不阻塞 I/O
- 充分利用多核
- 性能提升 4 倍

---

### 第三次分离：accept vs recv

**Reactor + 线程池 → 主从 Reactor**

```
混在一起：
  主线程：accept + recv

分离后：
  主 Reactor：accept
  从 Reactor：recv
```

**好处**：
- I/O 充分利用多核
- 高并发时无瓶颈
- 性能再提升 4 倍

## 🏆 工业级实现对比

### Nginx

**模型**：多进程 + 主从 Reactor

**架构**：
- Master 进程：管理
- Worker 进程：每个 Worker 独立运行
- Worker 内部：主从 Reactor（但业务逻辑极快，不需要线程池）

**特点**：
- 进程隔离，稳定性高
- Worker 数量 = CPU 核数
- 业务逻辑极快（只转发）

**适用**：代理、负载均衡、静态资源

---

### muduo

**模型**：主从 Reactor + One Loop Per Thread

**架构**：
- 主 Reactor：accept
- 从 Reactor：每个线程一个 Reactor
- 业务逻辑：在 Reactor 线程或线程池

**特点**：
- C++ 网络库
- 高性能、易用
- Reactor 和线程一一对应

**适用**：高性能 C++ 网络应用

---

### Redis

**模型**：单线程 Reactor

**架构**：
- 单线程事件循环
- 非阻塞 I/O
- 业务逻辑极快（内存操作）

**特点**：
- 简单、无锁
- 业务逻辑快（<1微秒）
- 单线程足够

**适用**：内存数据库

---

### Netty（Java）

**模型**：主从 Reactor

**架构**：
- Boss Group（主 Reactor）：accept
- Worker Group（从 Reactor）：I/O
- 业务线程池：业务逻辑

**特点**：
- Java NIO 框架
- 高性能、易用
- 工业级标准

**适用**：Java 网络应用

## 🎓 架构选择指南

### 决策树

```
连接数多少？
  ├─ <100
  │   └─ 单线程 Reactor
  │
  ├─ 100-1000
  │   ├─ 业务逻辑快（<10ms）
  │   │   └─ 单线程 Reactor
  │   │
  │   └─ 业务逻辑慢（>100ms）
  │       └─ Reactor + 线程池
  │
  └─ >10000
      ├─ 业务逻辑快（<10ms）
      │   └─ 主从 Reactor
      │
      └─ 业务逻辑慢（>100ms）
          └─ 主从 Reactor + 线程池
```

---

### 选择建议

**单线程 Reactor**：
- ✅ 连接数少
- ✅ 业务逻辑快
- ✅ 需要简单架构
- 例如：Redis

**Reactor + 线程池**：
- ✅ 连接数中等
- ✅ 业务逻辑慢
- ✅ CPU + I/O 混合
- 例如：Web 应用服务器

**主从 Reactor**：
- ✅ 连接数多
- ✅ 业务逻辑快
- ✅ I/O 密集型
- 例如：Nginx

**主从 Reactor + 线程池**：
- ✅ 连接数多
- ✅ 业务逻辑慢
- ✅ 需要最高性能
- 例如：Netty

## 💡 核心经验

### 1. 没有银弹

- 不是越复杂越好
- 选择适合场景的架构
- 过度设计反而降低性能

### 2. 职责分离是核心

- 每次分离都解决特定问题
- 分离带来清晰和灵活
- 但也增加复杂度

### 3. 找到瓶颈是关键

- 业务逻辑慢 → 线程池
- I/O 慢 → 多 Reactor
- 不同瓶颈，不同方案

### 4. 架构是渐进式的

- 从简单开始
- 遇到瓶颈再优化
- 逐步演进

### 5. 理论联系实践

- 理论分析性能
- 实践验证理论
- 两者结合才能深刻理解
