# 主从 Reactor 模式详解

> **学习日期**：2026-06-21（第76天）  
> **主题**：主从 Reactor 模式（Master-Slave Reactor）

---

## 🎯 核心概念

**主从 Reactor**（Master-Slave Reactor）：
- 多个 Reactor 并行工作
- 主 Reactor：负责 accept 新连接
- 从 Reactor：负责已建立连接的 I/O
- 充分利用多核 CPU

---

## 📊 单 Reactor + 线程池的瓶颈

### 瓶颈分析

**架构回顾**（第75天）：
```
主线程（单 Reactor）：
  - epoll_wait 监听所有 fd
  - accept 新连接
  - recv 接收所有连接的数据
  - 创建任务交给线程池

工作线程池：
  - 处理业务逻辑
  - send 发送结果
```

**问题场景**：
- 场景：10000 个并发连接
- 每个连接每秒 1 个请求
- 每次 recv 耗时 1ms

**性能计算**：
- 主线程：10000 次 recv/秒 × 1ms = 10 秒
- 结果：主线程需要 10 秒才能处理完所有 recv
- QPS = 10000 / 10 = 1000

**瓶颈**：
- ❌ 主线程成为瓶颈（所有 I/O 操作）
- ❌ 即使有多核 CPU，主线程只用 1 个核
- ❌ 工作线程空闲，无法帮助处理 I/O

**图示**：
```
主线程（100% 忙）：
  [accept][recv1][recv2][recv3]...[recv10000]
  ↑ 瓶颈：单线程处理所有 I/O

工作线程 1（50% 闲）：[业务1]   [业务2]
工作线程 2（50% 闲）：  [业务3]   [业务4]
工作线程 3（50% 闲）：    [业务5]   [业务6]
工作线程 4（50% 闲）：      [业务7]   [业务8]
```

**结论**：
- 单个 Reactor 无法充分利用多核
- 需要多个 Reactor 并行处理 I/O

## 🏗️ 主从 Reactor 架构

### 架构设计

**核心思想**：职责再分离 + 多 Reactor 并行

```
┌────────────────────────────────────────┐
│   主 Reactor（Main Reactor）            │
│   线程：主线程                          │
│                                        │
│   职责：只负责 accept 新连接            │
│                                        │
│   while (true) {                       │
│     events = epoll_wait(listen_fd);    │
│     client_fd = accept(listen_fd);     │
│                                        │
│     // ⭐ 分发给从 Reactor              │
│     int idx = nextSubReactor();        │
│     subReactors[idx].addConnection(    │
│         client_fd);                    │
│   }                                    │
└────────────────────────────────────────┘
              ↓ 轮询分配
┌────────────────────────────────────────┐
│   从 Reactor 1（Sub Reactor 1）        │
│   线程：工作线程 1                      │
│                                        │
│   职责：负责 1/N 连接的 I/O             │
│   管理：2500 个连接（假设总共 10000）   │
│                                        │
│   while (true) {                       │
│     events = epoll_wait(...);          │
│     for (event in events) {            │
│       recv(fd, buf, ...);              │
│       pool.enqueue([buf, fd]() {      │
│         process(buf);                 │
│         send(fd, result, ...);        │
│       });                             │
│     }                                 │
│   }                                    │
└────────────────────────────────────────┘

┌────────────────────────────────────────┐
│   从 Reactor 2（Sub Reactor 2）        │
│   管理：2500 个连接                     │
└────────────────────────────────────────┘

┌────────────────────────────────────────┐
│   从 Reactor 3（Sub Reactor 3）        │
│   管理：2500 个连接                     │
└────────────────────────────────────────┘

┌────────────────────────────────────────┐
│   从 Reactor 4（Sub Reactor 4）        │
│   管理：2500 个连接                     │
└────────────────────────────────────────┘
              ↓ 任务队列
┌────────────────────────────────────────┐
│       工作线程池（共享）                │
│                                        │
│   处理所有从 Reactor 的业务逻辑         │
│                                        │
│   线程 1：[业务1][业务2][业务3]...      │
│   线程 2：[业务4][业务5][业务6]...      │
│   线程 3：[业务7][业务8][业务9]...      │
│   线程 4：[业务10][业务11][业务12]...   │
└────────────────────────────────────────┘
```

### 职责划分

| 组件 | 职责 | 线程数 | 处理内容 |
|------|------|--------|---------|
| **主 Reactor** | accept 新连接 | 1 | listen_fd |
| **从 Reactor** | recv 数据 | N（如 4） | 各自管理的 client_fd |
| **工作线程池** | 业务逻辑 | M（如 4） | 共享的业务处理 |

**总线程数**：1 + N + M = 1 + 4 + 4 = 9

## 🚀 性能提升分析

### 理论性能

**场景设置**：
- 10000 个并发连接
- 每个连接每秒 1 个请求
- recv 耗时：1ms
- 业务逻辑耗时：100ms
- 4 个从 Reactor
- 4 个工作线程

**单 Reactor + 线程池**：
- 主线程：10000 × 1ms = 10 秒（recv）
- 工作线程：10000 × 100ms / 4 = 250 秒（业务）
- 总时间：max(10, 250) = 250 秒
- **QPS = 10000 / 250 = 40**

**主从 Reactor + 线程池**：
- 主 Reactor：10000 × 0.1ms = 1 秒（accept，很快）
- 从 Reactor：10000 × 1ms / 4 = 2.5 秒（recv，并行）
- 工作线程：10000 × 100ms / 4 = 250 秒（业务）
- 总时间：max(1, 2.5, 250) = 250 秒
- **QPS = 10000 / 250 = 40**

**等等，QPS 相同？**

问题：业务逻辑太慢（100ms），成为瓶颈！

**重新设定**：业务逻辑只需 10ms

**单 Reactor + 线程池**：
- 主线程：10 秒（recv）
- 工作线程：10000 × 10ms / 4 = 25 秒
- 总时间：max(10, 25) = 25 秒
- **QPS = 10000 / 25 = 400**

**主从 Reactor + 线程池**：
- 主 Reactor：1 秒（accept）
- 从 Reactor：2.5 秒（recv，并行）
- 工作线程：25 秒（业务）
- 总时间：max(1, 2.5, 25) = 25 秒
- **QPS = 10000 / 25 = 400**

**还是相同？**

问题：业务逻辑依然是瓶颈（25 秒 > 2.5 秒）

**再调整**：业务逻辑只需 1ms（极快）

**单 Reactor + 线程池**：
- 主线程：10 秒（recv）← 瓶颈
- 工作线程：10000 × 1ms / 4 = 2.5 秒
- **QPS = 10000 / 10 = 1000**

**主从 Reactor + 线程池**：
- 从 Reactor：2.5 秒（recv）← 瓶颈
- 工作线程：2.5 秒
- **QPS = 10000 / 2.5 = 4000**

**性能提升：4 倍！**

### 关键结论

**主从 Reactor 的优势在于**：
- 当 I/O 操作成为瓶颈时
- 多个 Reactor 并行处理 I/O
- 充分利用多核

**适用场景**：
- ✅ 连接数多（>10000）
- ✅ 业务逻辑快（<10ms）
- ✅ I/O 密集型
- ❌ 业务逻辑慢（>100ms）→ 业务逻辑依然是瓶颈

## 🔄 连接分配策略

### 1. 轮询（Round Robin）

```cpp
class MainReactor {
private:
    vector<SubReactor*> subReactors;
    int nextIndex = 0;

public:
    void onNewConnection(int client_fd) {
        // 轮询分配
        subReactors[nextIndex]->addConnection(client_fd);
        nextIndex = (nextIndex + 1) % subReactors.size();
    }
};
```

**优点**：
- 简单易实现
- 分配均匀（假设所有连接负载相同）

**缺点**：
- 不考虑实际负载
- 某些连接可能更活跃

---

### 2. 最少连接（Least Connections）

```cpp
void onNewConnection(int client_fd) {
    // 找到连接数最少的从 Reactor
    int minIdx = 0;
    int minCount = subReactors[0]->getConnectionCount();

    for (int i = 1; i < subReactors.size(); i++) {
        int count = subReactors[i]->getConnectionCount();
        if (count < minCount) {
            minCount = count;
            minIdx = i;
        }
    }

    subReactors[minIdx]->addConnection(client_fd);
}
```

**优点**：
- 负载均衡
- 考虑实际连接数

**缺点**：
- 需要维护连接计数
- 不考虑连接活跃度

---

### 3. 哈希（Hash）

```cpp
void onNewConnection(int client_fd) {
    // 根据 fd 哈希
    int idx = client_fd % subReactors.size();
    subReactors[idx]->addConnection(client_fd);
}
```

**优点**：
- 同一 fd 总是分配到同一 Reactor
- 有利于缓存局部性

**缺点**：
- 可能分配不均匀

## 📊 三种 Reactor 模型对比

### 对比表

| 维度 | 单线程 Reactor | Reactor + 线程池 | 主从 Reactor |
|------|---------------|-----------------|-------------|
| **线程数** | 1 | 1 + M | 1 + N + M |
| **I/O 线程** | 1 | 1 | 1 + N |
| **accept** | 主线程 | 主线程 | 主 Reactor |
| **recv** | 主线程 | 主线程 | 从 Reactor（多个） |
| **业务逻辑** | 主线程 | 工作线程 | 工作线程 |
| **I/O 瓶颈** | ✅ 存在 | ✅ 存在 | ❌ 不存在 |
| **业务瓶颈** | ✅ 存在 | ❌ 不存在 | ❌ 不存在 |
| **多核利用** | ❌ 差 | ⚠️ 部分 | ✅ 充分 |
| **适用连接数** | <100 | 100-1000 | >10000 |
| **复杂度** | 低 | 中 | 高 |
| **代表项目** | Redis | - | Nginx, muduo |

---

### 演进路线

```
单线程 Reactor
  ↓
  问题：业务逻辑慢会阻塞整个 Reactor
  解决：引入线程池
  ↓
Reactor + 线程池
  ↓
  问题：主线程 I/O 成为瓶颈（高并发时）
  解决：多个 Reactor 并行处理 I/O
  ↓
主从 Reactor
  ↓
  完美（当前工业级方案）
```

**关键**：当 I/O 成为瓶颈时，主从 Reactor 优势明显

## 🏢 工业级实现：Nginx

### Nginx 架构

```
┌─────────────────────────────────────┐
│       Master 进程                    │
│                                     │
│   职责：                             │
│   - 读取配置文件                     │
│   - 管理 Worker 进程                 │
│   - 信号处理（reload, stop）         │
└─────────────────────────────────────┘
              ↓ fork
┌─────────────────────────────────────┐
│     Worker 进程 1                    │
│                                     │
│   主从 Reactor 模型：                │
│   - 主 Reactor：accept              │
│   - 从 Reactor：epoll 处理 I/O      │
│   - 业务逻辑：在同一线程（快）       │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│     Worker 进程 2                    │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│     Worker 进程 N                    │
│   （N = CPU 核数）                   │
└─────────────────────────────────────┘
```

### Nginx 特点

**1. 多进程模型**：
- Master 进程 + 多个 Worker 进程
- Worker 数量 = CPU 核数
- 进程隔离，稳定性高

**2. 每个 Worker 内部使用 epoll**：
- 单线程事件循环
- 非阻塞 I/O
- 业务逻辑极快（只转发，不处理）

**3. 为什么 Nginx 不用线程池？**：
- Nginx 的业务逻辑极快（<1ms）
- 主要是转发、代理，不需要复杂计算
- 单线程足够，避免线程同步开销

## 🎓 总结

### 核心思想

**主从 Reactor = 职责分离 + 多核并行**：
```
职责分离：accept（主）vs recv（从）
多核并行：多个从 Reactor 并行处理 I/O
```

### 何时使用

**主从 Reactor 适合**：
- ✅ 连接数多（>10000）
- ✅ 业务逻辑快（<10ms）
- ✅ I/O 密集型

**Reactor + 线程池 适合**：
- ✅ 连接数中等（100-1000）
- ✅ 业务逻辑慢（>100ms）
- ✅ CPU + I/O 混合

**单线程 Reactor 适合**：
- ✅ 连接数少（<100）
- ✅ 业务逻辑快（<1ms）
- ✅ 简单场景

### 架构演进的智慧

**每一步都解决特定问题**：
- 单线程 → 线程池：解决业务逻辑慢
- 线程池 → 主从：解决 I/O 瓶颈

**没有银弹**：
- 不是越复杂越好
- 选择适合场景的架构
