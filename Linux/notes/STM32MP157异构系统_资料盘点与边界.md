## 2. 读到的源码事实：`rpmsg_client_sample.c`（107 行）

这是 **Linux 内核自带的样例驱动**（TI/Google，2011，GPL v2），课程只把两处日志改成了 `printk` 便于观察。
它不是教学原创代码，因此"读它"等于读内核样例，结论的适用面比课程本身更广。

### 2.1 模型：一个 `rpmsg_driver` 就是一条通道的一端

```c
static struct rpmsg_device_id rpmsg_driver_sample_id_table[] = {
    { .name = "rpmsg-client-sample" },   /* 按「通道名」匹配，不是模块名 */
    { },
};
static struct rpmsg_driver rpmsg_sample_client = {
    .drv.name  = KBUILD_MODNAME,          /* 这里是模块名 */
    .id_table  = rpmsg_driver_sample_id_table,
    .probe     = rpmsg_sample_probe,      /* 通道出现时调用 */
    .callback  = rpmsg_sample_cb,         /* 收到消息时调用 */
    .remove    = rpmsg_sample_remove,
};
module_rpmsg_driver(rpmsg_sample_client);
```

四个环节：

1. **注册** `module_rpmsg_driver()`——模块加载即注册，内核在 RPMsg 总线上按 `id_table` 匹配。
2. **匹配**：对端（M4）创建通道并注册名字 `rpmsg-client-sample`，名字对上就 `probe`。
3. **`probe`** 拿到 `rpdev`（含 `src`/`dst` 地址对），`devm_kzalloc` 分配私有数据并 `dev_set_drvdata` 挂上，
   随即发第一条消息（"A7 → M4"）。
4. **`callback`** 收到任意消息 → 打印 → **回发一条**（`rpmsg_send`）→ 形成乒乓；
   计到 `MSG_LIMIT 100` 次就停手（源码注释：*samples should not live forever*）。

### 2.2 五个会踩的坑（源码级）

| 坑 | 依据 | 后果 |
| --- | --- | --- |
| **匹配名 ≠ 模块名** | `id_table` 是 `"rpmsg-client-sample"`，`drv.name` 是 `KBUILD_MODNAME` | 改了模块名不影响匹配；改了 `id_table` 的字符串而 M4 侧不改，`probe` 永不触发，**且无任何报错** |
| `rpmsg_send` 失败只打日志、不重试 | `:51-54`、`:75-80` | 对端未就绪时消息**静默丢失**——"发了但没收到"的第一嫌疑 |
| `rx_count` 无任何锁保护 | `:35`、`:40`、`:44` | 当前实现下回调是串行的所以没事；但它不是内核保证的契约，换用法就可能变成竞争 |
| `printk(KERN_DEBUG ...)` 默认看不见 | `:40`、`:54`、`:80` | 默认 `console_loglevel=7`，KERN_DEBUG 是 7，需要 `dmesg -n 8` 才上控制台——**"程序没输出"经常只是日志等级** |
| 预编译 `.ko` 与内核树必须配对 | `Makefile` 的 `KERN_DIR = ~/stm32mp157/V2/stm32mp15xc-kernel/` | vermagic 不符直接加载失败。这与 Day05 的 `KERN_DIR` 教训**同源**：内核模块不能跨内核树复用 |

### 2.3 与已有知识的接点

- `devm_kzalloc` / `dev_set_drvdata`：与 `notes/驱动入门/` 里 platform 驱动的"资源生命周期绑定设备"是同一套机制，
  只是总线从 platform 换成 rpmsg。
- `probe`/`remove`/`id_table` 的结构：与 `DShanMCU-F103` 驱动的 `Init`/`Test` 风格完全不同，
  是**内核风格**（回调驱动），这正好是"什么时候该接入内核子系统而不是写私有字符设备"（教材 §11 的问题）的实例。
- **不可迁移的部分**：M4 侧的启动、`openamp` 的 remoteproc 配置、共享内存地址与 `vring`——一个字都没看到。

## 4. 结论：现在该做什么、不该做什么

### 不该做

1. **不要写"STM32MP157 讲义"**。没有 CM4 侧源码，写出来必然是转述视频内容，不符合本仓库"每条结论有证据路径"的纪律。
2. **不要用 QEMU 假装验证**。`qemu-system-arm` 没有 MP157 的 A7+M4 异构模型；能跑的那部分（A7 侧 Linux）
   与"异构通信"这个主题无关。
3. **不要把 `.ko` 当成能用的产物**。它是为特定内核树编的，本机没有那个内核树。

### 可以做（按性价比排序）

1. ✅ **已完成（本条）**：把 107 行内核样例驱动读透，产出 §2.2 那张坑表。这是唯一有实体源码的部分，读完是净收益。
2. **补 CM4 侧源码**：需要从课程资料/视频里找 `22`/`23` 例程的 CM4 源文件（当前只有骨架）。
   没有它，这一块就到此为止——**这是硬前置，不是时间问题**。
3. **把 §2.1 的模型画进 `knowledge_base/`**：RPMSG 的"驱动注册 → 按通道名匹配 → probe → callback 乒乓"
   这四步值得一张速查表；但**必须标注"仅 A7 侧、未验证"**，且只在第 2 条有了进展后再写。
4. **`21_FreeRTOS` 一项单独看**：CM4 上的 FreeRTOS 与 F103 的 FreeRTOS 是同一内核不同移植层，
   也许能作为"移植层差异"的对照素材——但同样要先解决"资料不入库"的问题。

### 前置条件（满足任一再推进）

- 拿到 `22`/`23` 例程的 **CM4 侧源码**；
- 或拿到 MP157 开发板 + 可启动的官方镜像；
- 或确认能把该资料目录纳入版本管理（至少把关键源码摘出来入库），否则所有引用都不可复核。
