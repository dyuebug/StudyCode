## 核心概念

### 1. 三个模块的转换对象不同，但都落在同一个函数上

| 模块 | 物理量 → 电信号 | 驱动读的是什么 | 精度受限于 |
| --- | --- | --- | --- |
| 红外避障 | 反射光强 → 数字电平 | `HAL_GPIO_ReadPin` 一次 | 无关（只有 0/1） |
| 超声波 SR04 | 声波往返时间 → 高电平宽度 | `system_get_ns()` 两次之差 | **`system_get_ns()`** |
| 旋转编码器 | 转角 → 两路正交脉冲的相位与间隔 | 中断时刻差 `system_get_ns()` | **`system_get_ns()`** |

前一个模块是"读状态"，后两个是"测时间"。**测时间的两个模块，精度全押在一个函数上**——而那个函数在本工程里是坏的（§6）。这是本篇的主线：不是两个驱动各自写错，而是它们共用的地基先塌了。

### 2. 红外避障：为什么"低电平 = 有障碍物"

教材 §11.10.1（`ch11_drivers.txt:903`）只有一句：

> 读取 PB13 引脚，如果是低电平，则表示即将碰到障碍物。

驱动 `driver_ir_obstacle.c:68-74` 与之一致：

```c
int IRObstacle_Read(void)
{
    if (GPIO_PIN_RESET == HAL_GPIO_ReadPin(IROBSTACLE_GPIO_GROUP, IROBSTACLE_GPIO_PIN))
        return 0;      /* 低电平 → 0 → 碰到障碍物 */
    else
        return 1;
}
```

**返回值语义与电平语义反着**——"低电平"被编码成"返回 0"，而 0 在 C 里通常表示"成功"。调用方若按 `if (IRObstacle_Read())` 写成"成功分支"，就完全反了。教材的 `IRObstacle_Test` 用 `if (0 == IRObstacle_Read())` 才是对的语义。

模块的 LM393 是**开集输出**（`lab_pins.c:92-94` 的注释记录了这一判断），板上若没有外部上拉，不加上拉会读到悬空值。本工程因此在 `lab_pins.c:96-97` 补了 `GPIO_MODE_INPUT + GPIO_PULLUP`。**这是工程推断，不是实测**——教材只说"配置为输入引脚"。

### 3. 超声波：声呐方程

教材 §11.11.2（`ch11_drivers.txt:950`）给出的公式：

```
测试距离 = (高电平时间 × 声速 340 m/s) / 2
```

除以 2 是因为声波走的是**往返**：模块发出去、碰到障碍物、再回来。设距离 $d$、往返用时 $t$：

$$t = \frac{2d}{c}, \qquad c = 340\ \text{m/s}$$

反过来就是驱动要算的：

$$d = \frac{c \cdot t}{2}$$

代入 cm 与 ns：$d(\text{cm}) = \dfrac{340 \times 100}{2} \times t(\text{s}) = 17000 \times \dfrac{t(\text{ns})}{10^9} = t \times 1.7\times10^{-5} = t \times \dfrac{17}{10^6}$

**这就是 `17` 的来历**：$340 \times 100 / 2 / 10^4 = 17$。驱动 `:108` 的行尾注释 `// time /1000000000 * 340 * 100 / 2` 是原始公式，`* 17 / 1000000` 是它的整数优化形式。

### 4. 常量是对的，误差来自截断

先确认常量本身没有精度损失：

$$\frac{10^6}{17} = 58823.5294117647\ldots$$
$$\frac{2 \times 10^9}{34000} = 58823.5294117647\ldots$$

两式**恒等**。所以驱动没有把 340 m/s 写错，也没有把 /2 漏掉。误差全部来自两处整数截断：

1. `system_get_ns()` 返回的 `uint64_t` 把 ns 截成整数（丢 < 1 ns）；
2. `time * 17 / 1000000` 再截一次。

第 2 步的影响是**系统性的**：常量本身没错，但 `CM_TO_ECHO_NS(d)` 先把 `d × 58823.5294` 向下取整成 `d × 58823`（丢掉的 0.5294 ns/cm 在 d < 1000 时累积不到 1 ns，问题不在这里），随后乘 17 除以 10⁶ 又截一次。两步截断的方向一致，都向下。

E4 实测（`lab_motion/logs/lab_motion_timing.log`）：

```
  距离cm Echo(ns)     驱动读数 偏差
  1      58823        0        -1
  2      117647       1        -1
  3      176470       2        -1
  ...
  10     588235       9        -1
```

**1–10 cm 全部偏小 1 cm**。这不是随机误差，是截断的固定方向。

> 附带一个反直觉现象：真实运行时 `system_get_ns()` 用的是 `cnt * 1000000 / 999`，1 tick = 1000 ns 却被算成 1001 ns，**高报了 0.1%**。这个正偏差恰好抵消了 -1 cm 的负偏差，于是 10 cm 读出来还是 10。两个错误互相掩盖，**不能证明其中任何一个是对的**。

### 5. `while (timeout--)` 的后置自减陷阱

这是本篇最重要的一条。驱动 `driver_ultrasonic_sr04.c:85-92`：

```c
while (timeout-- && (HAL_GPIO_ReadPin(...) == GPIO_PIN_RESET))
{
    udelay(1);
}
if (!timeout)
{
    return -1;
}
```

`timeout--` 是**后置**自减：先把旧值交给条件判断，再把 `timeout` 减 1。于是退出循环时 `timeout` 的终值有三种：

| 退出原因 | 退出时 `timeout` 旧值 | 减 1 后 `timeout` | `!timeout` | 结果 |
| --- | --- | --- | --- | --- |
| 条件为假（Echo 早已变高） | k ≥ 2 | k−1 ≥ 1 | 0 | 正常继续 |
| **超时耗尽** | **0** | **0xFFFFFFFF** | **0** | **不返回 −1，继续往下算** |
| 恰好最后一次条件为假 | 1 | 0 | 1 | **成功被误判为失败** |

中间那一行是要害：`uint32_t` 从 0 减 1 回绕到 `0xFFFFFFFF`，`!timeout` 为假，`return -1` 一次也不会执行。

E7 实测：

```
  超时耗尽：退出时 timeout=0xFFFFFFFF，!timeout=0
  PASS  耗尽退出时 timeout 回绕为 0xFFFFFFFF ⇒ `if (!timeout)` 为假 ⇒ 失败分支是死代码
  PASS  `!timeout` = 0 ⇒ 不会 return -1，函数继续往下算出垃圾距离并 return 0
  正常回波：退出时 timeout=19499，!timeout=0
  PASS  正常路径返回 19499 ⇒ `!timeout` 为假，正确不返回 -1
  边界情形（恰好最后一次）：退出时 timeout=0，!timeout=1
  PASS  旧值为 1 时退出 ⇒ timeout=0 ⇒ `!timeout` 为真 ⇒ 成功被误判为失败
  驱动同款判断对耗尽情形返回 0（承诺 `return -1` 的超时情形实际返回 0）⇒ 调用方无从区分
```

后果链：

1. 没有回波（超量程、无反射面）→ 第一个循环耗尽 → 不返回 −1 → `time = system_get_ns()`
2. 第二个循环（等 Echo 变低）同样耗尽 → 同样不返回 −1
3. `time = system_get_ns() - time` → 两次调用相隔约 20 ms，而 `system_get_ns()` 每 1 ms 回绕 ⇒ 差值无意义
4. `*pData = 垃圾`，`return 0`
5. `SR04_Test`（`:135`）只在非 0 时才显示 `"err"` ⇒ **OLED 上永远看不到 err，只会看到乱跳的数字**

正确的写法有两种，都只需改一行：

```c
/* 写法 A：不用后置自减 */
while (timeout > 0 && cond) { timeout--; udelay(1); }
if (timeout == 0) return -1;

/* 写法 B：保留原结构，但把判断改成"回绕值" */
while (timeout-- && cond) { udelay(1); }
if (timeout == 0xFFFFFFFFu) return -1;
```

写法 B 保留了"最后一次恰好退出"时误判失败的缺陷，所以只推荐 A。

### 6. `system_get_ns()` 依赖 `HAL_GetTick()`：本工程 `uwTick` 恒 0

`driver_timer.c:135`：

```c
uint64_t system_get_ns(void)
{
    extern TIM_HandleTypeDef htim4;
    TIM_HandleTypeDef *hHalTim = &htim4;
    uint64_t ns = HAL_GetTick();          /* ← 毫秒部分 */
    cnt = __HAL_TIM_GET_COUNTER(hHalTim); /* ← 亚毫秒部分 */
    reload = __HAL_TIM_GET_AUTORELOAD(hHalTim);
    ns *= 1000000;
    ns += cnt * 1000000 / reload;
    return ns;
}
```

量纲是对的：TIM4 的 `Period = 999`、计数时钟 1 MHz，一个周期正好 1 ms = 10⁶ ns，所以 `cnt/reload × 10⁶` 就是纳秒。**问题不在算术，在 `HAL_GetTick()`。**

完整调用链（逐行核实）：

```
HAL_Init()                                    stm32f1xx_hal.c
  └─ HAL_InitTick(TickPriority)               ← 本工程强定义在
     stm32f1xx_hal_timebase_tim.c:42
       ├─ __HAL_RCC_TIM4_CLK_ENABLE()         :52
       ├─ Prescaler → 1 MHz 计数              :70
       ├─ Period = 1000000/1000 - 1 = 999     :82   （1 ms 更新）
       ├─ HAL_TIM_Base_Init(&htim4)
       ├─ HAL_TIM_Base_Start_IT(&htim4)       :92
       └─ HAL_NVIC_EnableIRQ(TIM4_IRQn)       :96

每 1 ms：TIM4_IRQn
  └─ TIM4_IRQHandler()                        stm32f1xx_it.c:165
       └─ HAL_TIM_IRQHandler(&htim4)          :170
            └─ htim->PeriodElapsedCallback(htim)   stm32f1xx_hal_tim.c:3956
                 ↑ 在 HAL_TIM_Base_Init 里被赋为 HAL_TIM_PeriodElapsedCallback  (:6151)
                   而它只有 __weak 定义                                            (:5652)
                   ⇒ 空函数
  ✗ HAL_IncTick() 从未被调用
```

`grep -rn "HAL_IncTick" Core Drivers` 的结果只有两行：

```
Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal.h:295:void HAL_IncTick(void);
Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal.c:293:__weak void HAL_IncTick(void)
```

`grep -rn "HAL_TIM_PeriodElapsedCallback" Core Drivers` 里没有任何 `Core/` 下的强定义，也没有 `SysTick_Handler`、没有 `SysTick_Config`。

**结论**：`uwTick` 从复位起恒为 0，`HAL_GetTick()` 恒返回 0，`system_get_ns()` 只剩后半截：

$$\text{system\_get\_ns}() \in [0,\ 10^6]\ \text{ns},\qquad \text{每 1 ms 回绕一次}$$

E1 实测：10 ms 内 `min=0`、`max=1000000`、回绕 10 次。

> 这一条修正了 Day14 缺陷①的表述。Day14 写的是"`stm32f1xx_it.c` 也没有 `SysTick_Handler`"——事实正确，但漏了 TIM4 这条路：本工程**确实**把 HAL 时基重定向到了 TIM4 并且**确实**使能了中断，只是中断服务函数里调用的用户回调没人实现。断点比"没配时基"更隐蔽：中断在跑，`htim4` 的计数器在动，只有 `uwTick` 不动。

### 7. 1 ms 回绕如何毁掉 SR04

`SR04_Read` 用 `system_get_ns()` 的两次调用之差计时。既然返回值每 1 ms 回绕，差值就只有两种可能：

- Echo 高电平**没有跨越** 1 ms 边界 → 差值 = 真实时长（但整数毫秒已被丢掉）
- Echo 高电平**跨越**了 1 ms 边界 → 差值为负 → `uint64_t` 下溢 → 天文数字

是否跨越，取决于 Echo 上升沿落在 1 ms 窗口的哪个位置——**这是随机的，与距离无关**。

E2 相位扫描（相位取 0/100/300/500/700/900 µs，各跑一次）：

```
  距离cm Echo(us)   六相位读数                                          正确
  5       294.1      5          5          5          5          5          4154504673  5/6
  10      588.2      10         10         10         4154504678 4154504678 4154504678  3/6
  17      1000.0     0          0          0          0          0          0           0/6
  20      1176.5     2          2          2          2          2          4154504671  0/6
  100     5882.4     15         15         4154504683 4154504683 4154504683 4154504683  0/6
```

读法：

- **5 cm**：Echo 只有 294 µs，只要不跨边界就对，跨了就得到 `4154504673`。6 个相位里 5 个碰巧没跨。
- **10 cm**：588 µs，跨边界的概率更高，3/6。
- **17 cm**：Echo 恰好 1000 µs = 一个完整周期，两端 `system_get_ns()` 都返回 0，差值 `0 - 0 = 0` ⇒ **无论相位如何，恒定输出 0**。
- **20 cm / 100 cm**：Echo ≥ 1 ms，整数毫秒被丢弃，`dt` 只剩小数部分 ⇒ 20 cm 读成 2、100 cm 读成 15，**必然错**。

同一距离、不同相位的差值：

```
同样 5 cm：相位 100 us ⇒ 5，相位 900 us ⇒ 4154504673（差 -4154504668）
```

**这条判据的意义**：不是"某个距离读不准"，而是"同一个距离在两次测量之间会给出完全不同的值"。现场表现会是数字乱跳，而工程师第一反应通常去查传感器或接线——方向错了。

### 8. 修复这一层的方式

`system_get_ns()` 本身不需要改，需要补的是**它依赖的那一环**。三种改法，代价递增：

| 改法 | 改动量 | 说明 |
| --- | --- | --- |
| 在 `Core/` 里加一个 `void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) { if (htim->Instance == TIM4) HAL_IncTick(); }` | 一行 | 最小改动，恢复 `HAL_GetTick()` 与所有 HAL 超时 |
| 同上，但把 `HAL_IncTick` 直接改成强定义 | 一行 | 等价；改 HAL 库文件不利于升级，不推荐 |
| SR04 内部改用 `__HAL_TIM_GET_COUNTER` 直接算差值并处理回绕 | 十余行 | 不依赖 `uwTick`，但只解决 SR04 一个模块 |

第一种改法同时修复了 Day14 记录的**所有** `HAL_Delay`/HAL 超时失效问题，性价比最高。**但本篇不做这个修改**——按 Day14 的规矩，源码级缺陷先记录、先写出可证伪的板上预测，验证之后再动手；修改本身需要真板回归。

可证伪的预测（真板可验）：

1. 修好之前：`LAB_TEST=8`（SR04）时，OLED 上距离数字**不随物体远近单调变化**，且快速抖动。
2. 修好之后：同一物体固定在 10 cm 处，读数稳定在 9–10 cm 之间（-1 cm 的系统偏差仍在，见 §4）。
3. 修好之前：把物体移到 60 cm 以外，OLED **不会**显示 `err`（因为 §5 的死代码），而是显示某个不相关的小数字。
4. 修好之后：60 cm 处应稳定读到 59–60 cm（`SR04_TIMEOUT` 够用，见 §9）。

### 9. `SR04_TIMEOUT` 决定了实际量程，不是教材写的 450 cm

驱动 `:46`：`#define SR04_TIMEOUT 20000 // us`

两个等待循环各用一次这个值，每次迭代 `udelay(1)`。**若** `udelay(1)` 真的等 1 µs，单个电平段的等待上限就是 20 ms，把它代回声呐方程（这是**名义值**，真实值见本节末的修正）：

$$d_{\max} = \frac{340 \times 20\times10^{-3}}{2} \times 100 = 340\ \text{cm}$$

教材 §11.11.2 写模块"探测距离约 2 cm ~ 450 cm"（原文 `2cm450cm`，破折号在抽取时丢失）。450 cm 需要：

$$t = \frac{2 \times 4.5}{340} = 26.5\ \text{ms} = 26471\ \mu s$$

**超出超时 1.3 倍。** 也就是说，3.4 m 以外的物体，模块可能测得出，驱动等不到——而按 §5，等不到时也不会返回 −1，而是返回一个垃圾距离。

E3 实测三条（按名义 20 ms 建模）：340 < 450、340 > 300（3 m 内不受影响）、26471 > 20000（差 1.3 倍）。

> 想覆盖到 450 cm，把 `SR04_TIMEOUT` 提到 `30000` 即可。但**先修 §5**，否则提高超时只是让垃圾距离来得更晚。

#### 补充（2026-10-30）：实际量程只有上表的一半

上面 340 cm 的前提是"每次 `udelay(1)` 等 1 µs"。**这个前提不成立**，见 Day19 §8 与 `lab_ir` 的 C1 判据。

`udelay`（`driver_timer.c:53`）把微秒换算成 TIM4 的 tick：

```c
uint32_t reload = __HAL_TIM_GET_AUTORELOAD(hHalTim);   /* 999 */
ticks = us * reload / 1000;                            /* 1 * 999 / 1000 = 0 */
```

`udelay(1)` 的 `ticks` 是 **0**，于是 `while (1)` 里第一次看到计数器变化（`tnow != told`）就 `tcnt >= 0` 成立、立刻 `break`。等待时长等于**一个计数器 tick（0 或 1 µs，均匀分布，均值 0.5 µs）**，不是 1 µs。

| 项 | 名义 | 实测/复算 | 依据 |
| --- | --- | --- | --- |
| `udelay(1)` 一次迭代 | 1 µs | **0.5 µs（均值）** | `lab_ir` C1：`udelay(1) = 0` tick |
| `udelay(9000)` | 9000 µs | 8991 µs | 误差 −0.1%，越长越准 |
| 20000 次轮询 | 20000 µs | **≈ 10000 µs** | 20000 × 0.5 µs |
| 单段最大距离 | 340 cm | **≈ 170 cm** | 10000 µs × 340 m/s ÷ 2 |

**两条必须一起说的修正范围**：

1. `≈ 170 cm` 是**点估计**，忽略了 `HAL_GPIO_ReadPin` 与循环体的开销（真值略大，但远到不了 20000 µs）。要精确值必须用示波器量 Echo 超时波形，或读 `DWT->CYCCNT`。
2. 这个修正**不改变结论方向**，只是把"3.4 m 以内够用"收紧成"约 1.7 m 以内才够用"。§5 的死代码问题反而更严重：驱动更早放弃等待，更早开始返回垃圾距离。

`lab_ir` 的 C1 判据只锁住了 `udelay(1) = 0 tick` 这一条算术，**"每次迭代 0.5 µs"这个推论没有机器判据**——它依赖"轮询循环在两次计数器变化之间不额外等待"的假设。这一点记在 Day19 的「本篇没有验证的东西」第 10 条。

### 10. Trig 脉冲宽度：教材自己给了两个数

教材 §11.11.2 的操作说明（`ch11_drivers.txt:948`）：

> 向 Trig（脉冲触发引脚）发出一个大约 **10us** 的高电平。

教材 §11.11.3 给出的核心代码（`ch11_drivers.txt:1006`）：

```c
HAL_GPIO_WritePin(SR04_TRIG_GPIO_GROUP, SR04_TRIG_GPIO_PIN, GPIO_PIN_SET);
udelay(20);
HAL_GPIO_WritePin(SR04_TRIG_GPIO_GROUP, SR04_TRIG_GPIO_PIN, GPIO_PIN_RESET);
```

仓库驱动 `:81` 同样是 `udelay(20)`。**教材的散文与它自己上一页的代码差了 2 倍。**

这不算错误——HC-SR04 规格要求 Trig 高电平 ≥ 10 µs，20 µs 满足要求，只是多等 10 µs。真正要注意的是 `udelay` 本身：

```c
void udelay(int us)                      /* driver_timer.c:46 */
{
#if 0
    /* SysTick 版本，已禁用 */
#else
    extern TIM_HandleTypeDef htim4;
    uint32_t reload = __HAL_TIM_GET_AUTORELOAD(hHalTim);   /* = 999 */
    ticks = us * reload / 1000;                            /* ≈ us */
    told = __HAL_TIM_GET_COUNTER(hHalTim);
    while (1) { tnow = ...; if (tnow != told) { tcnt += ...; if (tcnt >= ticks) break; } }
#endif
}
```

TIM4 计数器每 1 µs +1，`reload = 999`，所以 `ticks = us × 999 / 1000`——比 `us` 少 0.1%。`udelay(20)` 实际是 19.98 µs，不影响功能。

关键在 `#if 0` 那一支：SysTick 版本的 `udelay` 被禁用了。如果哪天有人把它改回来，**所有在中断里调用 `mdelay`/`udelay` 的地方都会死锁**（§13）。目前轮询 TIM4 计数器，不依赖任何中断，所以安全。这是一个"幸好当时选了另一条路"的例子。

### 11. 旋转编码器：S1 / S2 正交信号与方向判定

EC11 这类增量式编码器输出两路相位差 90° 的方波 S1、S2。转一下，两路电平变化的**先后顺序**告诉你方向；单位时间内的边沿数告诉你速度。

教材 §11.12.2（`ch11_drivers.txt:1054`）原文：

> 可以设置 S1 位上升沿触发中断，在中断函数里读取 S2 的电平：**S2 为低电平则表示正转**，否则表示反转。

驱动 `driver_rotary_encoder.c:140-143`：

```c
if (RotaryEncoder_Get_S2())      /* S2 为高 */
{
    g_count++;                   /* 正转 / 顺时针 */
}
else
{
    g_count--;
    g_speed = 0 - g_speed;
}
```

驱动自己在 `:137` 的注释：

```c
/* S1上升沿触发中断
 * S2为0表示逆时针转, 为1表示顺时针转
 */
```

**三方对齐结果**：

| 来源 | S2 低电平 | S2 高电平 |
| --- | --- | --- |
| 教材 §11.12.2 | **正转** | 反转 |
| 驱动注释 `:137` | 逆时针 | **顺时针** |
| 驱动代码 `:140` | `g_count--` | `g_count++` |

驱动代码与驱动注释一致（高 = 顺时针 = 计数加），**教材散文与二者相反**。

这属于"正转"这个词本身的歧义——顺时针算正转还是逆时针算正转，没有国际标准。教材的"正转"可能指逆时针。但作为教材，它在同一页的代码里没有说清这一点，而读者通常会把散文当规格。

**该信哪一个**：代码的行为是确定的（高电平 → `g_count++`），散文的"正转"是不确定的。所以按"高电平 → 计数增加"来记，方向标签自己定。

### 12. 编码器测速的数学

驱动 `:139`：

```c
g_speed = (uint64_t)1000000000 / (time - pre_time);
```

`time` 与 `pre_time` 都是 ns，所以 `10⁹ / Δt(ns)` = **每秒脉冲数**。驱动 `:54` 的注释："单位:每秒转动次数"——严格说这是"每秒脉冲数"，只有编码器每转输出 1 个脉冲时才等于每秒转数。EC11 典型是每转 20 个定位点（20 脉冲/转），所以真实转数 = `g_speed / 20`。驱动没有做这个换算，注释也没提。

若脉冲间隔是 10 ms，`g_speed = 10⁹/10⁷ = 100`（每秒 100 个脉冲 = 5 转/秒 = 300 rpm，按 20 脉冲/转算）。

### 13. ISR 里 `mdelay(2)` 的代价

`driver_rotary_encoder.c:132`：

```c
time = system_get_ns();      /* ① 记录中断时刻 */
mdelay(2);                   /* ② 阻塞 2 ms 做防抖 */
if (!RotaryEncoder_Get_S1()) /* ③ 复查 S1 是否仍为高 */
    return;
```

三个问题叠在一起：

**① 不死锁，但阻塞 2 ms。** `mdelay` → `udelay` 走的是轮询 TIM4 计数器的分支（§10），不依赖任何中断，所以**不会死锁**。代价是这段时间 CPU 全被这个 ISR 占住。

**② 2 ms 的防抖窗口设死了可分辨的最高频率。** 两个脉冲间隔小于 2 ms（即 > 500 脉冲/秒）时，第二个脉冲到来时 S1 已经因为机械回弹回到低电平，`③` 直接 return，**事件被丢弃**。手转 EC11 通常 20–100 脉冲/秒，够用；电动或快速拧就丢。

**③ 用"睡 2 ms 再看一眼"做防抖，本质是有损的。** 更好的做法是软件计数器防抖（连续 N 次采样同值才认）或 RC 硬件滤波，都不需要阻塞。

### 14. 首次中断的 `pre_time = 0` 与整数毫秒的除零

`static uint64_t pre_time = 0;`（`:124`）是**静态**变量，初值 0。第一次中断时：

```c
g_speed = 1000000000 / (time - 0) = 1000000000 / time;
```

`time` 是 `system_get_ns()` 的返回值。按 §6 它落在 [0, 10⁶]。两种极端：

- `time` 很大（接近 10⁶）⇒ `g_speed ≈ 1000`
- `time` 很小（接近 0）⇒ `g_speed` 巨大甚至溢出
- **`time` 恰为 0** ⇒ **除零**

E5 实测首次中断的情形：真实已开机 3 秒，`system_get_ns()` 返回 **0 ns** ⇒ `g_speed = 1e9/0`。

**Cortex-M3 上除零是什么结果？** ARMv7-M 的 `UDIV`/`SDIV` 规定：除数为 0 时商为 0。若 `SCB->CCR` 的 `DIV_0_TRP` 位为 1，则触发 UsageFault；复位后该位为 0。所以**不触发异常，`g_speed = 0`**。

更普遍的问题是整数毫秒的间隔。因为 `system_get_ns()` 只保留 1 ms 周期内位置，**间隔若是整数毫秒，两端返回值完全相同 ⇒ `Δt = 0`**：

```
间隔取 {1,5,10,20,100} ms：5/5 次 dt=0（驱动处为除零）
```

而非整数毫秒时，`Δt` 只等于**小数部分**，与真实间隔无关：

```
真实间隔 10.3 ms ⇒ g_speed=3330；20.3 ms ⇒ g_speed=3330
（正确应约 97 与 49，比值 2:1）
```

**间隔翻了一倍，读数一模一样。** 这比"误差大"严重得多：读数与所测物理量之间不存在单调关系。

### 15. 非 `volatile` 的共享变量

```c
static int32_t g_count = 0;      /* :53 */
static int32_t g_speed = 0;      /* :54 */
```

`g_count`/`g_speed` 在中断里写（`RotaryEncoder_IRQ_Callback`）、在主循环里读（`RotaryEncoder_Read`），但都没加 `volatile`。

编译器在 `-O2` 下允许把 `g_count` 的值缓存在寄存器里——如果 `RotaryEncoder_Read` 被内联进一个循环，读一次就再也不重读，`*pCnt` 永远是旧值。本工程 `LAB_TEST` 只调用一次，风险被掩盖；一旦放进 `while(1)` 循环就暴露。

教材 §11.12.3 的版本用 `xQueueSendFromISR(g_xQueueRotary, ...)` 把数据递给任务，队列本身有内存屏障语义，绕开了这个问题。**仓库这份裸机版删掉了队列**（`lab_pins.c` 注释也写明"本工程是裸机、没有 RTOS"），于是 `volatile` 从"可有可无"变成"必须有"——而它没有。

### 18. 5 V 回响电平直接进 3.3 V GPIO

教材 §11.11.2：**"SR04 采用 5V 电压"**。HC-SR04 的 Echo 是 5 V 推挽输出，而 PB8 所在 MCU 的 I/O 是 3.3 V 域。教材既没提电平转换，也没说 PB8 是否 5 V 容忍（FT）。

三种可能：

1. PB8 是 FT 引脚（5 V tolerant）⇒ 直连可接受，但边沿更快、功耗略增；
2. PB8 非 FT ⇒ 长期直连会经 ESD 二极管把电流灌进 3.3 V 轨，属超规格使用；
3. 模块实际由 3.3 V 供电 ⇒ 输出电压降到 3.3 V，问题消失，但模块是否在 3.3 V 下可靠工作又成新问题。

**三者都在本机无法区分**，需要真板 + 万用表/示波器。记在这里是因为它是一条**可能烧引脚**的接线，而不是"读数不准"这种软故障。

## 系统调用/接口卡片

> 裸机环境下"线程/进程安全"一栏改写为**可重入性与中断安全**：能否在中断里调用、是否操作共享状态。

### `int IRObstacle_Read(void)`

**作用**：读取红外避障模块的数字输出，判断是否检测到障碍物。

**原型**：`int IRObstacle_Read(void);`（`driver_ir_obstacle.h:60`，实现 `driver_ir_obstacle.c:68`）

**参数**：无。引脚固定为 PB13（`:38-39` 的宏），不可配置。

**返回值和错误**：

| 返回 | 含义 |
| --- | --- |
| `0` | PB13 低电平 → 检测到障碍物 |
| `1` | PB13 高电平 → 未检测到 |

**没有错误返回值**。无法区分"高电平"与"引脚悬空被上拉读成高"。

**资源所有权**：无资源，无状态。引脚由 `lab_pins.c:95-98` 配置。

**可重入性与中断安全**：只读一次 `IDR`，可在中断中调用。

**最小示例**：

```c
if (0 == IRObstacle_Read()) {     /* 注意：0 才是"碰到" */
    LCD_PrintString(0, 0, "BLOCKED");
}
```

**常见误用**：

- 把返回值当"成功/失败"用（`if (IRObstacle_Read())` 会在**没碰到**时进入分支）。
- 以为模块一定有外部上拉，结果悬空读到 1（永远"无障碍"）。

### `int SR04_Read(uint32_t *pData)`

**作用**：触发一次超声测距，把距离（cm）写入 `*pData`。

**原型**：`int SR04_Read(uint32_t *pData);`（`driver_ultrasonic_sr04.h:60`，实现 `driver_ultrasonic_sr04.c:74`）

**参数**：

- `pData`：输出参数，单位 cm。**函数不检查是否为 NULL**。

**返回值和错误**：

| 返回值 | 文档声称 | 实际行为 |
| --- | --- | --- |
| `0` | 成功 | 成功，**或**超时（§5 死代码） |
| `-1` | 失败 | 仅在"恰好最后一次条件为假"时出现，此时其实**成功** |

**资源所有权**：无资源。执行期间独占 PB9（TRIG）与 PB8（ECHO），**阻塞约 20 ms 至 40 ms**。

**可重入性与中断安全**：**不可重入**。两次并发调用会互相干扰 Trig 脉冲与 Echo 计时。**不可在中断中调用**——它是阻塞轮询，最长 2 × 20 ms。

**最小示例**：

```c
uint32_t cm;
if (0 == SR04_Read(&cm)) {          /* 按 §5，0 不等于"成功" */
    LCD_PrintSignedVal(0, 0, cm);
}
```

**常见误用**：

- 相信 `-1` 的语义（见 §5）。
- 在 RTOS 任务里以高于 25 Hz 的频率调用——单次就有 20 ms 阻塞。
- 与 W25Q64 同时访问：两者共用 PB9（§16）。

### `void RotaryEncoder_Read(int32_t *pCnt, int32_t *pSpeed, int32_t *pKey)`

**作用**：取出旋转编码器的累计计数、转速和按键状态。

**原型**：`void RotaryEncoder_Read(int32_t *pCnt, int32_t *pSpeed, int32_t *pKey);`（`.h:62`，实现 `.c:182`）

**参数**：

- `pCnt`：累计脉冲数（正数 = 顺时针，见 §11）。只增/减，不归零。
- `pSpeed`：每秒脉冲数。**上一次调用以来计数没变时置 0**（`:187-190`）。
- `pKey`：1 = 按下，0 = 松开（PB1 低有效，`:66-72`）。

三个指针**都不检查 NULL**。

**返回值和错误**：`void`，无错误路径。内部可能发生除零（§14），结果为 0。

**资源所有权**：无资源。读取共享静态变量 `g_count`/`g_speed`（非 `volatile`，见 §15）。

**可重入性与中断安全**：**不可重入**（`static int32_t pre_count` 是函数级状态，两次并发调用会互相破坏）。**不可在中断中调用**。

**最小示例**：

```c
int32_t cnt, spd, key;
RotaryEncoder_Read(&cnt, &spd, &key);
/* 每转脉冲数按编码器型号折算，EC11 典型 20 */
printf("cnt=%ld rpm=%ld key=%d\r\n", (long)cnt, (long)(spd / 20), (int)key);
```

**常见误用**：

- 把 `pSpeed` 当"当前转速"直接显示：它每秒最多更新一次（两次调用之间没转就置 0），不是连续值。
- 以为 `pCnt` 是有限范围的："旋转编码器"的 `int32_t` 累加溢出要 2³¹ 次脉冲，实际不会遇到，但没有防护。
- 在主循环里连续两次调用：第二次必然读回 `speed = 0`（`pre_count` 已更新）。

### `uint64_t system_get_ns(void)`

**作用**：返回系统运行的纳秒数，用于亚毫秒计时。

**原型**：`uint64_t system_get_ns(void);`（`driver_timer.h`，实现 `driver_timer.c:135`）

**参数**：无。

**返回值和错误**：无错误路径。**本工程实际只返回 [0, 10⁶] ns，每 1 ms 回绕**（§6）。

**资源所有权**：只读 `htim4` 的计数寄存器与 `uwTick`，无副作用。

**可重入性与中断安全**：可重入、可在中断中调用。**但结果不可用**（除非先修 §8 的 `HAL_IncTick`）。

**最小示例**：

```c
uint64_t t0 = system_get_ns();
/* ... */
uint64_t dt = system_get_ns() - t0;   /* 本工程：dt 无意义，见 §7 */
```

**常见误用**：

- 直接对两次返回值做无符号减法 —— 当 `uwTick` 正常时这是对的（回绕周期 584 年）；当它不正常时，每 1 ms 就下溢一次。
- 用它算超过 1 ms 的间隔 —— 见 §7 的相位扫描。

### `void udelay(int us)` / `void mdelay(int ms)`

**作用**：忙等延时。

**原型**：`void udelay(int us);` `void mdelay(int ms);`（`driver_timer.c:46` / `:119`）

**参数**：`us` 微秒、`ms` 毫秒。`mdelay` 实现为 `for (i = 0; i < ms; i++) udelay(1000);`。

**返回值和错误**：`void`。**不检查 `htim4` 是否已初始化**——`HAL_InitTick` 之前调用会读到 `reload = 0`，`ticks = 0`，`while(1)` 的第一轮就 break，延时失效。

**资源所有权**：独占 CPU，无资源。

**可重入性与中断安全**：**可重入**（只用局部变量 + 读寄存器）。**可在中断中调用**，因为走的是轮询 TIM4 计数器的分支，不依赖任何中断。**代价是全程占用 CPU**：`mdelay(2)` 在中断里就是 2 ms 的高优先级阻塞（§13）。

**最小示例**：

```c
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_9, GPIO_PIN_SET);
udelay(20);                                  /* Trig ≥10 µs */
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_9, GPIO_PIN_RESET);
```

**常见误用**：

- 在 RTOS 任务里用 `mdelay(100)` 当"睡眠"——它不让出 CPU，等价于 `vTaskDelay` 的反面。
- 以为 `mdelay` 在中断里会死锁：本工程的实现不会（§10），但如果 `#if 0` 的 SysTick 分支被启用，就会。
- 用它做严格时序（如 DHT11 的 40 µs 窗口）：误差来自函数调用开销，量级与要测的窗口相当（Day17 §5）。

### 建模过程中被自己推翻的三处

写判据时的第一版有 3 条断言**跑出来就是红的**，全部是我的算式错误而不是驱动的缺陷。按规矩不删记录：

| 错在哪 | 错的原因 | 修正 |
| --- | --- | --- |
| E1 断言 `max < 1e6` | 忘了 `cnt=999` 时 `999×10⁶/999 = 10⁶` 是闭区间上界 | 改为 `max ≤ 1e6 && max < 2e6` |
| E3 算出最大量程 3400 cm | 单位错：`us/1000` 得到的是**毫秒**不是秒，再乘 340 就大了 1000 倍 | 改为 `timeout_us × 1e-6 × 340 × 100 / 2` |
| E5 用 10.3 ms vs 10.13 ms 演示"读数与间隔脱钩" | 起点相位取 890 µs，两次都跨了 1 ms 边界，双双下溢成 0，看起来"相同"其实都是垃圾 | 起点改到相位 0，用 10.3 ms vs 20.3 ms，两次都不跨边界，读数确实都是 3330 |

第三条最有教育意义：**"两次读数相同"有两种成因**——真的算出同一个值，或者两次都溢出成了同一个垃圾。判据若不区分这两者，就会把"模型错了"写成"驱动错了"。这和 Day17 §7 那条"1/256 漏检"是同一类错误：**结论听起来专业，但没被输出验证过**。

## 故障排查方法

按"先排除地基，再查模块"的顺序。**这个顺序很重要**：§6 的 `uwTick` 缺陷会让两个模块同时表现异常，如果先去查传感器，会得出"两个模块都坏了"的错误结论。

### 第一步：确认 `HAL_GetTick()` 是活的

```c
/* 临时插在 main 的循环里 */
static uint32_t last = 0;
if (HAL_GetTick() != last) { last = HAL_GetTick(); }
else { /* 卡住不动 ⇒ 命中 §6 */ }
```

更直接的办法：在 `Core/` 里 `grep`。

```bash
grep -rn "HAL_IncTick" Core      # 无结果 ⇒ uwTick 恒 0
grep -rn "HAL_TIM_PeriodElapsedCallback" Core   # 无结果 ⇒ 同上
```

两条都空 ⇒ 停止排查传感器，先修 §8。

### 第二步：确认引脚真的被配了

```bash
grep -n "GPIO_PIN_8\|GPIO_PIN_9\|GPIO_PIN_12\|GPIO_PIN_13" Core/Src/*.c
```

预期在 `lab_pins.c` 里命中，**不在** `gpio.c` 里命中（本工程的 `MX_GPIO_Init` 只配 PC13）。

### 第三步：SR04 单独复现

1. 固定物体在 10 cm，连续读 20 次，记下读数序列。
2. 若读数在 5–10 之间乱跳 ⇒ §7 的相位效应。
3. 若读数恒定不变 ⇒ 检查是不是某个"必然错"的值（17 的整数倍关系，见 §7）。
4. 把物体移开 2 m，读一次：若**没有**返回 −1（显示的不是 `err`）⇒ §5 的死代码。

### 第四步：编码器单独复现

1. 慢速转一圈，记 `pCnt` 的增量，与编码器规格（EC11 典型 20 脉冲/转）对比。
2. 快速转一圈，增量明显偏小 ⇒ §13 的 2 ms 防抖丢事件。
3. 读 `pSpeed`：若恒为 0 或极值 ⇒ §14。
4. 让主循环空转 1 秒再读一次 `pCnt`：若没变化但实际转过 ⇒ §15 的 `volatile`。

### 第五步：用示波器/逻辑分析仪看（需要硬件）

需要看的四个点：

| 点 | 预期 | 不预期说明什么 |
| --- | --- | --- |
| PB9 Trig | 每次测距一个 ≥10 µs 的高脉冲 | 没有脉冲 ⇒ 驱动没被调用 |
| PB8 Echo | 与距离成正比的宽脉冲（10 cm ≈ 588 µs） | 脉冲宽度正常但读数错 ⇒ 软件问题（§6/§7） |
| PB8 峰值电平 | 3.3 V（若模块 3.3 V 供电）或 5 V（5 V 供电） | 5 V ⇒ §18 |
| PB12 / PB0 相位 | S1 上升沿时 S2 稳定为某电平 | 抖动 ⇒ 需要硬件滤波 |

**这张表全部是"未验证"**——本机没有硬件。

## 练习题
