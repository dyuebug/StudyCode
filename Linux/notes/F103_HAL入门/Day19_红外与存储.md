## 核心概念

### 1. 为什么把这三节放在一起

教材把它们排成三个独立小节，但代码里它们是**同一条链路的三个面向**：

```
        ┌──────────────────────────────────────────┐
        │  时间源（唯一的、被三处共用的）            │
        │  udelay()  → 直接读 TIM4->CNT  ✅ 可用     │
        │  system_get_ns() → 依赖 HAL_GetTick() ❌   │
        └──────────────────────────────────────────┘
                 │                    │
      ┌──────────┘                    └───────────┐
      ▼                                            ▼
  发送 (IRSender_Write)                   接收 (IRReceiver_IRQ_Callback)
  全部延时走 udelay                         全部间隔走 system_get_ns
  ⇒ 波形合规                                ⇒ 计数被打回 0，解码 0 次

  存储 (W25Q64) 不碰时间，但 WaitReady 里
  「后置自减 + 判 0」与 SR04 是同一个 bug 的第二次出现
```

一句话概括本篇：**发送端用对了时间源，接收端用错了；存储驱动不碰时间，却复制了 Day18 的那个陷阱。** 三个模块各自看似独立，实际共用一条被判过死刑的时间基线。

### 2. NEC 帧的边沿记账：68 这个数字是怎么来的

接收头（如 HS0038）输出**低有效**：有 38 kHz 载波时输出低，无载波时输出高。所以"发一个载波段"在接收端表现为"下降沿 + 上升沿"一对。

| 段 | 载波（低） | 间隔（高） | 边沿 |
| --- | --- | --- | --- |
| 引导码 | 9 ms | 4.5 ms | 起点 1 + 结束 2 |
| 32 位数据 | 每位 0.56 ms | '1' 1.6 ms / '0' 0.56 ms | 每位 2 个 |
| 停止位 | 0.56 ms | — | 1 个 |

$$1 + 2 + 32 \times 2 + 1 = 68$$

主机复算 A1 的结果与手算一致：`build_edges()` 生成 68 个时刻，`g_IRReceiverIRQ_Timers[68]` 恰好容得下。

**这不是巧合，是必然。** 发送端 `IRSender_Write()` 一共 34 次 `HAL_TIM_PWM_Start/Stop`（1 引导 + 32 位 + 1 停止），每次产生一对边沿 ⇒ $34 \times 2 = 68$。判据 C4 把这两个数对上了：**发送端数调用次数，接收端数边沿，是同一件事的两面**。

### 3. 解析索引 `m = 3 + 2i` 对齐的是"高电平段"

`IRReceiver_IRQTimes_Parse()` 的关键三行：

```c
for (i = 0; i < 32; i++) {
    m = 3 + i * 2;
    n = m + 1;
    time = Timers[n] - Timers[m];      /* 测的是"间隔"，不是"载波" */
```

下标 0/1/2 是引导码的起点、结束、数据起点。于是 i=0 时 `Timers[4] - Timers[3]`：

| 下标 | 含义 | 时刻 |
| --- | --- | --- |
| 2 | bit0 载波起点 | 13.5 ms |
| 3 | bit0 载波结束（上升沿） | 14.06 ms |
| 4 | bit0 间隔结束（下降沿） | 14.62 ms |

所以 `Timers[4]-Timers[3]` = 0.56 ms ⇒ '0'。**它测的是高电平宽度**，与 1.0 ms 门限配套。如果误以为是测载波宽度就会得出相反结论 —— 这是读这类代码最容易翻的车。

最大下标 `3 + 31*2 + 1 = 66`，容量 68 只多一个（下标 67 = 停止位结束）。判据 A1 的三条断言把"紧配、无溢出、无富余"钉住了。

### 4. 引导码窗口 3.5–55 ms：一个多余的零

```c
time = Timers[2] - Timers[1];
if (time < 3500000 || time > 55000000) return -1;   /* :149 */
```

NEC 的引导码高电平是 4.5 ms。窗口下界 3.5 ms（−22%），上界本应是 5.5 ms（+22%），实际写成了 **55 ms**。

判据 A2 用两个比值把它坐实：

| 写法 | 上界/名义 | 含义 |
| --- | --- | --- |
| `5500000`（应为） | 5.5/4.5 = **1.22** | ±22%，与其他窗口对称 |
| `55000000`（实际） | 55/4.5 = **12.2** | 宽 12 倍，等于没有上界 |

后果不是"偶尔误判"，而是**这道闸门形同虚设**：任何 9 ms 低脉冲之后的长时间空闲都会被当成合法引导码。教材 §11.13 的原文与仓库一字不差 —— 这是**教材与仓库共有的**缺陷，不是抄写错误。

对照 §5 的数据位判据，那里两侧裕度是对称的（78%/69%），说明作者本来懂"窗口要对称"这件事，这一个零更可能是笔误。

### 5. 数据位判据 1.0 ms 的两侧容差

| 位 | 名义高电平 | 判据 | 裕度 |
| --- | --- | --- | --- |
| '0' | 0.56 ms | > 1.0 ms 判 '1' | 到 1.0 还有 +78.6% |
| '1' | 1.69 ms | > 1.0 ms 判 '1' | 到 1.0 只剩 −40.8% |

判据 A3 用"±25% 容差"这条实际工程标准检验：'0' 最坏 0.70 ms、'1' 最坏 1.27 ms，门限 1.0 仍稳稳夹在中间。**这条判据是正确的那一个** —— 也正因如此，B6 的 12/12 往返才能全过。

### 6. 核心：`time - pre_time > 1e8` 在回绕下把计数器打回 0

```c
void IRReceiver_IRQ_Callback(void)                  /* :232 */
{
    time = system_get_ns();                          /* :240 */
    if (time - pre_time > 100000000) {               /* :244 */
        g_IRReceiverIRQ_Cnt = 0;
    }
    pre_time = time;
    g_IRReceiverIRQ_Timers[g_IRReceiverIRQ_Cnt] = time;
    g_IRReceiverIRQ_Cnt++;
    if (g_IRReceiverIRQ_Cnt == 4)  { /* 重复码 */ }
    if (g_IRReceiverIRQ_Cnt == 68) { IRReceiver_IRQTimes_Parse(); g_IRReceiverIRQ_Cnt = 0; }
}
```

`:244` 的本意是"距离上一帧超过 100 ms 就认为换了新帧，丢弃残帧"。这个设计是对的 —— 但它假设 `system_get_ns()` 单调递增。

本工程的实际情况（Day18 §6 已证）：`HAL_GetTick()` 恒 0，`system_get_ns()` 只剩周期内部分，返回值 $\in [0, 10^6)$ ns，**每 1 ms 回绕一次**。于是：

| 两个边沿的先后 | `time - pre_time` | 结果 |
| --- | --- | --- |
| 同一毫秒窗口内，后者偏移更大 | 小数（< 1e6） | 不重置 ✅ |
| 跨过毫秒边界 | `uint64_t` 下溢 ≈ $1.8 \times 10^{19}$ | **重置** ❌ |

一帧 66.54 ms（判据 B1 实测），意味着大约 66 次毫秒边界穿越。数据位的边沿间隔是 0.56–1.69 ms，也就是**每个毫秒窗口最多放得下 2 个边沿**。判据 B3 的读数是决定性的：

```
坏时基：cnt 最大 3，解析触发 0 次，重复码分支 0 次
好时基：cnt 最大 68，解析触发 1 次
```

**注意"最大 3"这个数字的分量。** 它不是说"解码不准"，而是说 `if (cnt == 4)` 和 `if (cnt == 68)` 这两个分支**结构上不可达**。所以：

- `Parse()` 一次都不会被调用；
- `PutKeyToBuf()` 一次都不会被调用；
- `IRReceiver_Read()` 里 `isKeysBufEmpty()` 恒为真 ⇒ **永远返回 -1**。

这就是 B4 的断言：**整帧 68 个边沿走完，解析 0 次**。红外接收在本工程里不是"灵敏度差"，是**完全不通**。

而 B6 做了反向对照：把同一个 `build_edges()` 的输出换成 `ts_fixed()`（`uwTick` 正常时的行为），12 组 `(device, data)` 全部还原。**这排除了"解析算法写错了"这个假设**，把唯一嫌疑锁死在时间源上。

### 7. 为什么发送方向反而是好的

```c
void udelay(int us)                                  /* driver_timer.c:53 */
{
    extern TIM_HandleTypeDef htim4;
    uint32_t reload = __HAL_TIM_GET_AUTORELOAD(hHalTim);   /* = 999 */
    ticks = us * reload / (1000);
    told = __HAL_TIM_GET_COUNTER(hHalTim);                 /* 直接读硬件 */
    while (1) {
        tnow = __HAL_TIM_GET_COUNTER(hHalTim);
        if (tnow != told) { tcnt += ...; told = tnow; if (tcnt >= ticks) break; }
    }
}
```

`udelay` 读的是 `TIM4->CNT` 这个**硬件寄存器**，`HAL_GetTick()` 恒 0 与它无关。TIM4 在 `MX_TIM4` 之外由 `HAL_InitTick` 配成 1 MHz 计数 + ARR 999，硬件本身在正常跑 —— 坏掉的只是"累加到 64 位秒级"的那一步。

所以 `IRSender_Write()` 的 34 段延时全部合规：

| 调用 | 名义 | tick 数 | 实际 |
| --- | --- | --- | --- |
| `udelay(9000)` | 9000 µs | 8991 | 8991 µs（−0.1%） |
| `udelay(1600)` | 1600 µs | 1598 | 1598 µs |
| `udelay(560)` | 560 µs | 559 | 559 µs |
| `mdelay(1)` | 1000 µs | 999 | 999 µs |

接收端的引导码窗口是 8–10 ms，8991 µs 落在正中。**发送端时序合规、接收端一条也解不出**，这个组合恰恰是现场最难查的一类故障：示波器看波形完全正常，代码逻辑也看不出错，只有把两个时间源分开看才发现问题在另一边。

### 8. `udelay(1)` 算出 0 个 tick：对 Day18 量程的修正

`ticks = us * reload / 1000 = 1 * 999 / 1000 = 0`。循环条件变成"计数器变化一次就退出"，即耗时 **0–1 µs、均值 0.5 µs**。

这直接影响所有用 `while (timeout--) { ...; udelay(1); }` 写的超时循环 —— 典型就是 `SR04_Read()`：

| 项 | Day18 的说法 | 按 0 tick 修正 |
| --- | --- | --- |
| 20000 次 `udelay(1)` | 名义 20000 µs | ≈ 10000 µs |
| 对应最大距离 | 340 cm | ≈ **170 cm** |

判据 C3 把这条算了出来。**结论方向不变**（"远程测不到"更成立），但绝对数值要改。同时这也解释了 Day18 "本篇没有验证的东西"第 6 条里"真实上限会略小于 20 ms"——不是"略小"，是"约一半"。

> 需要说清的边界：0.5 µs/次是**仅算 `udelay` 自身**的结果。实际上每轮还有一次 `HAL_GPIO_ReadPin`（APB2 读，约几十 ns）和循环开销，真实值会略大于 10000 µs，但仍远小于 20000。精确值必须示波器或 `DWT->CYCCNT` 测，本篇没有测。

### 9. `isRepeatedKey()` 的双重失效

```c
static int isRepeatedKey(void)                       /* :202 */
{
    time = Timers[1] - Timers[0];
    if (time < 8000000 || time > 10000000) return 0;   /* 9 ms 引导码 */
    time = Timers[2] - Timers[1];
    if (time < 2000000 || time > 2500000) return 0;    /* 2.25 ms */
    return 1;
}
```

NEC 的重复码是「9 ms 载波 + 2.25 ms 间隔 + 0.56 ms 停止」，只有 4 个边沿 —— 所以 `if (cnt == 4)` 这个分支的记账是**对的**（判据 A1 的 68 分解也隐含了它）。

但坏时基下 `Timers[1] - Timers[0]` 实测为 **0**（判据 B5：真实 9000000 ns，坏时基算得 0 ns），`< 8000000` 恒真 ⇒ 直接 `return 0`。

所以红外接收有**两条**出口，两条都被同一个函数堵死：

| 出口 | 触发条件 | 状态 |
| --- | --- | --- |
| 正常按键（68 边沿） | `cnt == 68` | 不可达（cnt 最大 3） |
| 长按重复码（4 边沿） | `cnt == 4` | 可达，但 `isRepeatedKey()` 恒为假 |

这解释了为什么"长按遥控器没反应"和"单击也没反应"是**同一个根因的两个现象** —— 现场很容易误判成"两个独立问题"。

### 10. 中断与主循环共享的三个变量缺 `volatile`

```c
static unsigned char g_KeysBuf[BUF_LEN];      /* :41 */
static int g_KeysBuf_R, g_KeysBuf_W;          /* :42 */
static int g_IRReceiverIRQ_Cnt = 0;           /* :45 */
```

跨上下文访问关系：

| 变量 | 写方 | 读方 | 保护 |
| --- | --- | --- | --- |
| `g_KeysBuf_W` | ISR（`PutKeyToBuf`） | 主循环（`isKeysBufEmpty` 读 W）与 ISR（`isKeysBufFull`） | 无 |
| `g_KeysBuf_R` | 主循环（`GetKeyFromBuf`） | ISR（`isKeysBufFull` 读 R） | 无 |
| `g_IRReceiverIRQ_Cnt` | ISR | ISR | 不需要 |

三个变量都不是 `volatile`，也没有关中断。按 C 标准这属于无定义行为：编译器可以假定 `g_KeysBuf_W` 在 `IRReceiver_Test` 的 `while` 循环里不会被改动（它是 `static`、地址从未外泄，理论上可被提到寄存器）。

**本工程为什么侥幸能跑**：`IRReceiver_Test` 循环体里有 `LCD_PrintString` 等外部函数调用，且 `PutKeyToBuf` 只能经由导出的 `IRReceiver_IRQ_Callback` 到达，编译器在分 TU 编译时无法排除"外部函数会调用它"，于是每次调用后都会重新装载。这条"侥幸"在两种情况下一夜消失：

1. 打开 LTO —— 编译器能看到全部调用者，发现没有任何同步路径写它；
2. 把 `IRReceiver_Read` 内联进一个局部可见全部代码的循环。

正确写法是 `volatile`（或用临界区 / RTOS 队列）。这不是性能问题，是"能不能被优化掉"的问题。

### 11. 环形缓冲区存的是**字节流**，而读方假设它存的是**记录**

```c
int IRReceiver_Read(uint8_t *pDev, uint8_t *pData)    /* :308 */
{
    if (isKeysBufEmpty())
        return -1;                       /* 只判了一次空 */

    *pDev  = GetKeyFromBuf();            /* ← 这里可能被 ISR 插入新数据 */
    *pData = GetKeyFromBuf();
    return 0;
}
```

写方是两次独立的 `PutKeyToBuf()`：

```c
PutKeyToBuf(datas[0]);                   /* device */
PutKeyToBuf(datas[2]);                   /* key    */
```

于是存在三个问题：

1. **配对关系不原子**：两次 `GetKeyFromBuf` 之间可以夹进一个 ISR，把 `dev` 和 `data` 拼成"上一帧的 device + 下一帧的 key"。同一只遥控器 device 相同，察觉不到；换一只就错。
2. **单字节残留**：缓冲区里只剩 1 字节时，`isKeysBufEmpty()` 为假，函数照样读两个 —— 第二个返回哨兵值 `0xff`，且返回码仍报"成功"。此后所有配对整体错位半个字节。
3. **写方也不原子**：ISR 在两次 `PutKeyToBuf` 之间被打断（更高优先级中断），读者同样可能只看到半个记录。

这类"字节流当记录用"的错误在 Day06 的环形缓冲区里也讨论过：**必须让"一次入队 = 一条完整记录"**，或者给缓冲区加长度字段/分隔符。这里是同一个坑的第二个案例。

### 12. `IRReceiver_Init`：一个禁用的块 + 一句写错引脚的注释

```c
void IRReceiver_Init(void)                           /* :285 */
{
    /* PA10在MX_GPIO_Init()中已经被配置为双边沿触发, 并使能了中断 */
#if 0
    GPIO_InitStruct.Pin  = GPIO_PIN_10;
    GPIO_InitStruct.Mode = GPIO_MODE_EVT_RISING_FALLING;   /* ← EVT，不是 IT */
    GPIO_InitStruct.Pull = GPIO_PULLUP;
    HAL_GPIO_Init(GPIOB, &GPIO_InitStruct);                 /* ← 端口是 B */
#endif
}
```

这一段有三处值得记：

| 问题 | 说明 |
| --- | --- |
| 注释说 **PA10** | 实际引脚是 **PB10**（`driver_ir_receiver.c:44` 之外的 `lab_pins.c:114-117`）。写 PA10 会直接踩 Day14 记过的 EXTI 线陷阱 |
| 端口是 `GPIOB` | 说明作者知道是 B 口，注释与代码自相矛盾 |
| 模式是 `GPIO_MODE_EVT_*` | **EVT 只连事件线（SEV/WFE 用），不置 `EXTI_IMR`** ⇒ 即使把那行 `#if 0` 删掉，`EXTI15_10_IRQHandler` 依然不会被调用 |

第三点最值得记：`_IT_` 与 `_EVT_` 只差三个字母，效果是"中断"与"事件"两条完全不同的通路。想打开中断必须是 `GPIO_MODE_IT_RISING_FALLING`。

至于"谁配置了 PB10"——本工程是 `lab_pins.c:114-117`：

```c
GPIO_InitStruct.Pin  = GPIO_PIN_10;
GPIO_InitStruct.Mode = GPIO_MODE_IT_RISING_FALLING;
GPIO_InitStruct.Pull = GPIO_PULLUP;
HAL_GPIO_Init(GPIOB, &GPIO_InitStruct);
```

这与驱动注释说的"在 `MX_GPIO_Init()` 中已配置"不一致：本工程的 `MX_GPIO_Init` 只配 PC13（Day14 已核），红外接收的引脚是我补的 `lab_pins.c` 负责的。**驱动注释描述的是一份不存在的 CubeMX 工程。**

### 13. PB10 的 EXTI 线：为什么"配置了端口"这件事是必需的

EXTI 10 号线上只有**一个**选择开关 `AFIO->EXTICR[2]`，决定它盯哪个端口。若没人把 EXTI10 映射到 GPIOB，复位值指向 PA10 = `USART1_RX` —— 串口每收一个字节都会进一次"红外中断"。

这个坑在 P0.6 已记录过一次（当天配 PB10 时发现），本篇是它的**另一个受害面**：驱动自己的注释恰好停在"PA10"这个错误答案上，等于把正确答案写反了。

### 14. PA8 上三种驱动方式不能共存

| 使用者 | 如何驱动 PA8 | 关键代码 |
| --- | --- | --- |
| `IRSender` | TIM1_CH1 的 PWM（AF 复用） | `driver_ir_sender.c:39-46` |
| `PassiveBuzzer` | TIM1_CH1 的 PWM（AF 复用） | `driver_passive_buzzer.c:39-41,84,102` |
| `ActiveBuzzer` | 纯 GPIO 推挽 | `driver_active_buzzer.c:53,73-75` |

教材 §11.14.4 也点明了这个三方共用。从源码看，三者的互斥关系是**机械的**：

- `IRSender_Init` 与 `PassiveBuzzer_Init` 操作**同一个 `htim1`、同一个 `TIM_CHANNEL_1`**，谁后调用谁覆盖 `Prescaler/Period/Pulse`；
- `ActiveBuzzer_Init` 把 PA8 重新配成 `GPIO_MODE_OUTPUT_PP`，此时 TIM1 的 CH1 波形**再也出不到引脚上**（复用功能被关掉了）。

有一个常见误解值得澄清：**`IRSender_Init` 自己没有配 PA8，但它并不因此失效。** 因为 `main()` 里 `MX_TIM1_Init()`（`main.c:88`）已经调过 `HAL_TIM_PWM_Init(&htim1)` 和 `HAL_TIM_MspPostInit(&htim1)`，后者在 `tim.c:263-268` 把 PA8 配成了 `GPIO_MODE_AF_PP`。所以"IR 发送依赖无源蜂鸣器先跑"这个推断是**错的** —— 需要验证这个结论，只能回到 `tim.c` 看谁调了 `MspPostInit`，不能只看驱动文件。

| 调用的顺序 | 结果 |
| --- | --- |
| 只调 `IRSender_Init` | 正常（PA8 由 `MX_TIM1_Init` 配好） |
| `IRSender_Init` → `PassiveBuzzer_Init` | 蜂鸣器的 1 kHz 覆盖 38 kHz，IR 发出的是可听见的方波 |
| `PassiveBuzzer_Init` → `IRSender_Init` | 38 kHz 覆盖 1 kHz，蜂鸣器只剩轻微噪声 |
| 任何顺序 + `ActiveBuzzer_*` | GPIO 模式夺走引脚，PWM 全部不出脚 |

### 15. `Pulse = 473` 的"75%"其实是熄灭段

```c
g_HPWM_IRSender->Init.Period = 1894;     /* 38 kHz */       /* :67 */
sConfig.OCMode     = TIM_OCMODE_PWM1;
sConfig.OCPolarity = TIM_OCPOLARITY_LOW; /* 硬件上低电平亮灯 */
sConfig.Pulse      = 473;                /* 在 PWM1 模式下,75%占空比 */
```

算一遍就清楚了。ARR = 1894 ⇒ 周期 = 1895 tick；72 MHz/1895 = **37 995 Hz**（38 kHz 达标）。PWM1 模式下"有效电平"是 `CNT < CCR`，而 `OCPolarity = LOW` 把有效电平翻成低：

| 段 | CNT 范围 | tick 数 | 占比 | LED |
| --- | --- | --- | --- | --- |
| 低（有效） | 0..472 | 473 | **24.96%** | 亮（载波） |
| 高（无效） | 473..1894 | 1422 | **75.04%** | 灭 |

所以注释里的"75%占空比"是**熄灭段**的占比。真正驱动红外 LED 的载波占空比是 25%。

这个差别不是学术问题：占空比决定 LED 峰值电流。如果设计者以为自己在用 75%，就会按 75% 选限流电阻，实际只跑到 1/3 的驱动强度 —— 表现为"近距离能收到、偏一点就收不到"。至于 25% 本身是否合适，取决于板上的限流电阻与 LED 型号，本篇**没有实测发射距离**，不下结论。

> 教材内部对"占空比"有两个定义（§10.1.2 按高电平时间比、§10.3.3 按 `Pulse` = 有效电平宽度），`OCPolarity = LOW` 时两者互补。这条口径问题在 P0.7 记过，此处是它在红外发射上的具体实例。

### 16. W25Q64：教材只给引脚，协议得自己补

教材 §11.18 只有 50 行、没有代码：给了 SPI1 的 `PA7 MOSI / PA5 SCK / PA6 MISO` 与 `PB9 片选`，然后说"驱动见 `driver_spiflash_w25q64.c`"。所以本篇的协议部分**不是抄教材**，而是从 472 行驱动里反推出来的。

驱动实际用到的命令只有 5 条：

| 命令 | 名字 | 参数 | 驱动位置 |
| --- | --- | --- | --- |
| `0x03` | Read Data | 24 位地址 + N 字节 | `:237` |
| `0x02` | Page Program | 24 位地址 + ≤256 B | `:304` |
| `0x20` | Sector Erase | 24 位地址（A11–A0 忽略） | `:372` |
| `0x05` | Read Status Register 1 | — | `:159` |
| `0x06` | Write Enable | — | `:195` |

**没有 `0x9F`（JEDEC ID）。** 这是一个明确的缺口：驱动从头到尾**没有验证过对面是不是 W25Q64**。`W25Q64_Init()` 是个空函数（`:214-218`），注释只是说"片选与 SPI 在 CubeMX 里配好了"。

页/扇区算术部分，`W25Q64_Write` 是**正确的**，值得单独指出（因为它是整份驱动里少数没坑的地方）：

```c
cur_len = offset & (256-1);          /* 页内偏移 */
cur_len = 256 - cur_len;             /* 到本页末尾还能写多少 */
if (cur_len > len) cur_len = len;
for (; phy_pos < offset + len; ) { ... phy_pos += cur_len; cur_len = min(remain, 256); }
```

第一次写完必然落在 256 字节边界上，此后每次都是整页 —— 这正好满足了"Page Program 不得跨页，否则在页内回卷"的硬件约束。判据 D 的算术也能印证：`Erase(0, 100)` 走 `100/4096 == 0`，一次都不进循环。

边界没检查的是**上界**：`offset + len` 超过 8 MB 后，W25Q64 会忽略高位地址，回卷到 0 覆盖掉自己 —— 驱动没有拦。

### 17. `(off & 4095) && (len & 4095)`：`&&` 写成 `||`

```c
if ((offset & (4096-1)) && (len & (4096-1)))
    return -1;                                        /* :360 */
```

本意是"offset 或 len 任何一个不对齐就拒绝"，实际只拒绝了"两个都不对齐"。判据 D1 的真值表：

| offset | len | 情形 | `&&` 接受 | `\|\|` 接受 |
| --- | --- | --- | --- | --- |
| 0 | 4096 | 都对齐 | 是 ✅ | 是 ✅ |
| 4096 | 4096 | 都对齐 | 是 ✅ | 是 ✅ |
| 0 | **100** | 只 len 错 | **是** ❌ | 否 |
| **100** | 4096 | 只 off 错 | **是** ❌ | 否 |
| 100 | 100 | 都错 | 否 ✅ | 否 |

对角线上的两格被放过，而它们恰恰是最危险的 —— "两个都错"的调用一眼就能看出来，"只错一个"的调用看起来很正常。两个后果（判据 D2、D3 实测）：

| 调用 | 判据 | 循环次数 | 驱动返回 | 实际后果 |
| --- | --- | --- | --- | --- |
| `Erase(0, 100)` | 通过 | `100/4096 = 0` | **100** | 一个扇区都没擦，却报"擦了 100 字节" |
| `Erase(100, 4096)` | 通过 | 1 | 4096 | 命令原样发 `0x64`，芯片截断 A11–A0 后擦 **0x0000** ⇒ 越界擦掉 0x0 扇区 |

第二种更隐蔽：命令里发的地址是 `0x64`（驱动如实转发），**截断发生在芯片内部**。所以日志/示波器看到的地址是"对"的，被擦的是另一块地方。这类"错误发生在两层之间"的问题，只看驱动永远看不懂。

### 18. `W25Q64_WaitReady`：同一个后置自减，方向相反的第二个实例

```c
int timeout = W25Q64_TIMEOUT;                    /* 500 */
while (timeout--)
{
    ...
    if ((rx_buf[1] & 1) == 0) return 0;          /* BUSY 位清零 = 就绪 */
    mdelay(1);
}
if (!timeout) { return -1; }                     /* :173 —— 死代码 */
return 0;                                        /* :177 —— 超时也走这里 */
```

Day18 §3 的 SR04 是 `uint32_t` 版本：耗尽后 `0 → 0xFFFFFFFF`。这里是 `int` 版本：耗尽后 `0 → -1`。**两个值都不是 0**，所以 `!timeout` 恒假。

判据 E1–E3 的读数：

```
芯片永不就绪：循环退出时 timeout=-1，!timeout=0，函数返回 0
uint32_t 耗尽得 0xFFFFFFFF、int 耗尽得 -1，两者都不等于 0 => 两处都是死代码
```

但**危害方向相反**，这一点是本篇最值得记的对比：

| 驱动 | 类型 | 超时后 timeout | `if (!timeout)` | 函数返回 | 危害 |
| --- | --- | --- | --- | --- | --- |
| `SR04_Read` | `uint32_t` | `0xFFFFFFFF` | 假 | 继续算，返回 `0` | 把垃圾距离当有效值上报 |
| `W25Q64_WaitReady` | `int` | `-1` | 假 | `0` = **成功** | 把"没准备好"当"已就绪"上报 |

SR04 是"该报错没报"，`WaitReady` 是"该报错反而报成功"。**同一个写法，两种病症** —— 这正是它值得写两遍的原因：背下"后置自减有坑"是不够的，得能判断每种类型耗尽后到底是什么值。

### 19. 两个组合缺陷：`err` 检查链条断在两头

**组合一：`WaitReady` 永不失败 ⇒ `Write` 的 `if (err)` 永不触发。**

```c
err = W25Q64_WaitReady();
if (err) { return -1; }               /* :328-332 */
```

判据 E4 直接灌进"芯片永不就绪"这个输入，`err` 得 0，`if (err)` 判成功。于是 `W25Q64_Write` 在无芯片、CS 断线、MISO 悬空的情况下**依然返回 `len`**。

**组合二：`W25Q64_Erase` 漏写 `err =`。**

```c
W25Q64_Select();
W25Q64_Tx(tmpbuf, 4, W25Q64_TIMEOUT);   /* :378 —— 没有 err = */
if (err) {                              /* 用的是 WriteEnable 的残留值 */
    W25Q64_Deselect();
    return -1;
}
```

对照 `W25Q64_Read`（`:245`）与 `W25Q64_Write`（`:311`）都是 `err = W25Q64_Tx(...)`，只有 `Erase` 漏了赋值。这是典型的**复制粘贴漂移**：四处结构相同的代码，三处对、一处错。判据 E5 用"`err` 仍是 0 而 Tx 实际返回 -1"把这个洞显示出来。

**两个缺陷合起来的最终后果需要说清，不能夸大**：

| 场景 | 返回值路径 | 值比较路径 |
| --- | --- | --- |
| 芯片缺失 | 全部报成功（`Write` 返回 len、`Erase` 返回 len） | `W25Q64_Test` 的 `val1 == val2` 会失败，打印 `Test Failed` |
| 擦除命令没发出去 | 仍报成功 | 上一步的数据没被擦，写入变成 AND（1→0 只能单向），大概率不匹配 |

所以准确结论是：**没有一条错误返回码是可信的；唯一的检测手段是 `W25Q64_Test` 里那次值比较。** 任何不调用 `_Test` 的业务代码，都会在无芯片时"成功地"跑完。

### 20. `W25Q64_Read` 的 uint32 → uint16 静默截断

```c
static int W25Q64_Rx(uint8_t *pRxData, uint16_t Size, uint32_t Timeout);   /* :134 */

err = W25Q64_Rx(buf, len, W25Q64_TIMEOUT);    /* :253，len 是 uint32_t */
...
return len;                                    /* :261，仍报 32 位原值 */
```

判据 G1：`len = 70000` 传给 `uint16_t Size` 得 **4464**，函数末尾仍 `return len = 70000`。即搬了 4464 字节、报成功 70000 字节，调用方无从察觉。

`W25Q64_Write` 里传的是 `cur_len`（≤256），不受影响；只有 `Read` 这一处。这也是"参数类型不一致"这类问题的典型表现：编译器不会警告 `uint32_t → uint16_t`（不是 `-Wconversion` 默认范围），运行时不报错，返回值还掩盖了它。

### 21. `W25Q64_Test` 的 payload 只有 7 位会动

```c
val1 = system_get_ns();                         /* :445 —— 想造一个"随机"值 */
W25Q64_Write(sector * 4096, (uint8_t *)&val1, 4);
...
W25Q64_Read (sector * 4096, (uint8_t *)&val2, 4);
if (val1 == val2) "Test ok"; else "Test Failed";
```

用"当前时间"当测试数据是个合理的想法 —— 每次写的不一样，能顺带测出"写入没生效"。但 `system_get_ns()` 在本工程里上界是 **1 000 000 = `0x000F4240`**（判据 F1）。按小端写进 4 个字节：

| 字节 | 取值范围 | 说明 |
| --- | --- | --- |
| byte0 | 0x00–0xFF | 全变 |
| byte1 | 0x00–0xFF | 全变，但只到 0x42 的上界组合 |
| byte2 | 0x00–**0x0F** | 高 4 位恒定 |
| byte3 | **0x00** | 恒为 0 |

判据 F2 的读数是"32 个位里只有 **7** 个可能为 1"（`0x0F4240` 的 popcount）。所以：

- **byte3 永远是 0** ⇒ 任何"第 4 字节粘 0"的故障，跑完 8 MB 全盘自测也发现不了；
- byte2 高 4 位永远是 0 ⇒ 那 4 位的数据线故障同样检不出。

这是同一个坏时基的**第三个受害者**：第一个是 SR04（垃圾距离）、第二个是红外（完全不通）、第三个是 Flash 自测（覆盖面缩水到 5/8）。三次都是"看起来好好的"。

修法很简单 —— 用 `0x5A5A5A5A` 之类的固定花样加地址异或，或干脆在 payload 里混入地址：

```c
uint32_t pattern = 0xA5A50000u | (sector * 4096);
```

判据 A1 那个"发送端 34 段 = 接收端 68 边沿"的记账也是同一个道理：**测试数据的形状决定了测试能发现什么**。

## 系统调用/接口卡片

> 裸机环境没有"线程/进程安全"，对应位置改写为**可重入性与中断安全** —— 即"这个函数能不能被 ISR 打断/重入"。

### `int IRSender_Write(uint8_t device, uint8_t data)`

**作用**：按 NEC 协议发送一帧完整的红外遥控码（引导码 + 32 位数据 + 停止位）。

**原型或命令**：`void IRSender_Write(uint8_t device, uint8_t data);`（`driver_ir_sender.c:93`）

**参数**：
- `device`：设备 ID，发送时低字节原码、高字节按位取反
- `data`：按键码，同样发原码 + 取反（用于接收端校验）

**返回值和错误**：**无返回值**。所有 `HAL_TIM_PWM_Start/Stop` 的 `HAL_StatusTypeDef` 都被丢弃。

**资源所有权**：占用 `htim1` 的 `TIM_CHANNEL_1` 与 PA8 引脚；函数内每次 `Start` 后必定 `Stop`，不留下运行中的 PWM（但**不恢复** TIM1 的 `Prescaler/Period`，全局状态被改成 38 kHz）。

**可重入性与中断安全**：**不可重入**。`g_HPWM_IRSender` 是文件级静态指针，且函数会修改共享的 `htim1`；在 ISR 里调用会与主循环的发送交错、产生被截断的波形。

**最小示例**：
```c
IRSender_Init();                 /* 必需：设定 38 kHz 与 25% 载波 */
IRSender_Write(0x55, 0xa2);      /* 约 66.5 ms 阻塞 */
```

**常见误用**：
1. 以为 `IRSender_Init` 配了 PA8 —— 实际由 `MX_TIM1_Init` 的 `HAL_TIM_MspPostInit` 配（`tim.c:98,263`）；
2. 与 `PassiveBuzzer_*` 混用，后者覆盖 38 kHz；
3. 之后调用 `ActiveBuzzer_*`，PA8 被改成 GPIO，PWM 彻底不出脚；
4. 在 RTOS 任务里当"非阻塞"用 —— 它是 66 ms 的忙等。

### `int IRReceiver_Read(uint8_t *pDev, uint8_t *pData)`

**作用**：从环形缓冲区取出一条 `(device, key)` 记录。

**原型或命令**：`int IRReceiver_Read(uint8_t *pDev, uint8_t *pData);`（`driver_ir_receiver.c:308`）

**参数**：`pDev` / `pData` 为输出，**不检查是否为 NULL**。

**返回值和错误**：`0` = 成功，`-1` = 缓冲区空。**没有第三个返回值** —— 无法区分"没数据"与"解码失败"。

**资源所有权**：无；但会推进 `g_KeysBuf_R`（消费掉 1–2 字节）。

**可重入性与中断安全**：**不原子**。两次 `GetKeyFromBuf()` 之间可被 ISR 插入（见 §11）；与 `IRReceiver_IRQ_Callback` 共享 `g_KeysBuf[*]`/`_R`/`_W` 且均非 `volatile`。

**最小示例**：
```c
uint8_t dev, dat;
if (!IRReceiver_Read(&dev, &dat))
    LCD_PrintString(0, 4, IRReceiver_CodeToString(dat));
```

**常见误用**：
1. 只判一次空就读两个字节 ⇒ 可能拿到哨兵 `0xff`；
2. 假定缓冲区里"总是一对一对的" ⇒ 单字节残留会让后续全部错位；
3. 在本工程里期待它返回 0 —— 由于 §6 的时基缺陷，它**永远返回 -1**。

### `void udelay(int us)` / `void mdelay(int ms)`

**作用**：微秒/毫秒级忙等延时。

**原型或命令**：`void udelay(int us);`、`void mdelay(int ms);`（`driver_timer.c:53`、`:112`）

**参数**：`us` 为微秒（`int`）；`mdelay(ms)` 内部循环 `ms` 次 `udelay(1000)`。

**返回值和错误**：无。

**资源所有权**：只读 `TIM4->CNT` 与 `TIM4->ARR`，不改变任何硬件状态；不关中断。

**可重入性与中断安全**：**可重入、可重入中断**（纯读）。但中断里用它会让中断响应时间变长（`RoundEncoder` 的 `mdelay(2)` 就是这样，Day18 §13）。

**最小示例**：
```c
udelay(9000);      /* 实际 8991 us：ticks = 9000*999/1000 */
```

**常见误用**：
1. 以为 `udelay(1)` 真等 1 µs —— 实际 `ticks = 0`，只等计数器跳一次（0–1 µs，均值 0.5）；
2. 用它做"精确定时"—— 函数调用、循环开销都叠加在上面，误差在 0.1% 量级；
3. 在 ISR 里 `mdelay(2)`，把中断延迟拉长到毫秒级。

### `uint64_t system_get_ns(void)`

**作用**：取"系统时间（ns）"。

**原型或命令**：`uint64_t system_get_ns(void);`（`driver_timer.c:135`）

**参数**：无。

**返回值和错误**：返回值域**取决于 `HAL_GetTick()`**。正常工作时应单调递增；本工程里 $\in [0, 10^6)$ ns，**每 1 ms 回绕**。

**资源所有权**：无；纯读 `htim4` 与 `HAL_GetTick()`。

**可重入性与中断安全**：无共享写，可重入。

**最小示例**：
```c
uint64_t t0 = system_get_ns();
/* ... */
uint64_t dt = system_get_ns() - t0;   /* dt 可能因回绕而下溢 */
```

**常见误用**：
1. 用它做**跨毫秒**的差值 —— 必然下溢（本工程的 SR04、编码器、红外接收全是这个错）；
2. 把它当单调时钟做超时判断 —— `dt > 100ms` 在回绕下恒真；
3. 用它生成"随机"测试数据 —— 只有低 20 位会变（§21）。

### `static int W25Q64_TxRx(uint8_t *pTx, uint8_t *pRx, uint16_t Size, uint32_t Timeout)`

**作用**：全双工 SPI 传输（**不含片选**）。

**原型或命令**：见 `driver_spiflash_w25q64.c:95`；同族还有 `W25Q64_Tx`（`:115`）、`W25Q64_Rx`（`:134`）。

**参数**：
- `pTxData` / `pRxData`：发送/接收缓冲，长度均为 `Size`
- `Size`：**`uint16_t`** —— 超过 65535 会被静默截断
- `Timeout`：单位为 **ms**（传给 `HAL_SPI_Transmit*`）

**返回值和错误**：`0` 成功、`-1` 失败（只区分 `HAL_OK` 与否，丢弃 `HAL_TIMEOUT`/`HAL_BUSY`/`HAL_ERROR`）。

**资源所有权**：不操作 CS。调用者必须在前后 `W25Q64_Select()` / `W25Q64_Deselect()`。

**可重入性与中断安全**：**不可重入**。`g_HSPI_Flash` 指向共享的 `hspi1`，且 CS/polling 期间必须独占。在 ISR 里调用会与主循环竞争同一 SPI 外设。

**最小示例**：
```c
uint8_t tx[2] = {0x05, 0xff}, rx[2];      /* 读状态寄存器 1 */
W25Q64_Select();
W25Q64_TxRx(tx, rx, 2, 500);
W25Q64_Deselect();
if (rx[1] & 1) { /* BUSY */ }
```

**常见误用**：
1. 忘记加 CS，命令根本不生效（驱动内部三个函数都依赖调用者）；
2. 把 `Timeout` 当微秒传 500（意为 500 ms）；
3. 用 `W25Q64_Rx` 读大块数据，`uint16_t` 截断后返回值仍报原长度（§20）。

### `int W25Q64_WaitReady(void)`

**作用**：轮询状态寄存器 1 的 BUSY 位，直到芯片空闲。

**原型或命令**：`static int W25Q64_WaitReady(void);`（`driver_spiflash_w25q64.c:153`）

**参数**：无。

**返回值和错误**：文档承诺 `0` = 就绪、`-1` = 超时。**实测：永不返回 `-1`**（§18），超时也返回 `0`。

**资源所有权**：每次轮询自己做 `Select`/`Deselect`，不留下选中的状态。

**可重入性与中断安全**：不可重入（经 `W25Q64_TxRx` 使用共享 `hspi1`）。且 `mdelay(1)` × 500 ⇒ 最坏**阻塞约 500 ms**，绝不可在 ISR 调用。

**最小示例**：
```c
W25Q64_WriteEnable();
/* 发 page program ... */
if (W25Q64_WaitReady() != 0) { /* 这个分支永远进不去 */ }
```

**常见误用**：
1. 相信它的返回值 —— 无芯片时会立刻"就绪"；
2. 在擦除后立即读，以为返回值保证了完成 —— 超时情形下数据可能还没写进去；
3. 把它放在中断里，阻塞 500 ms。

## 最小可运行实验

**实验目标**：在不接板、不接遥控器的前提下，用主机端复算把下面的量算出来，全部可复核：

1. NEC 一帧为什么正好 68 个边沿，解析用到哪些下标；
2. 坏时基下一帧内 `cnt` 最大是多少（决定解码是否**可能**成功）；
3. 同一个解码逻辑在好时基下能否 100% 还原（排除"算法错了"这个假设）；
4. `udelay` 的 tick 算术为什么让发送正常、让 `udelay(1)` 折半；
5. `W25Q64_Erase` 的 `&&` 放过哪些调用、各自后果；
6. `W25Q64_WaitReady` 超时退出时 `timeout` 到底是什么值；
7. Flash 自测的 payload 有多少位会变。

**文件**：`notes/F103_HAL入门/lab_ir/lab_ir_w25q64.c`（619 行）+ `build.sh`

**七组判据**：

| 组 | 名字 | 判据数 | 断言的核心量 |
| --- | --- | --- | --- |
| A | NEC 边沿记账 | 6 | 68 / 下标 66 / 55 vs 5.5 / 门限容差 |
| B | 中断计数复位 | 6 | 坏时基 cnt ≤ 3、解析 0 次；好时基 68、12/12 还原 |
| C | 发送方向延时 | 6 | 8991 vs 0 tick；帧长 66.54 ms；34 段 = 68 边沿 |
| D | Erase 对齐判据 | 3 | 5 情形真值表；两种越界后果 |
| E | WaitReady 返回值 | 6 | 退出值 −1、返回 0；两个组合缺陷 |
| F | 自测 payload 熵 | 4 | 上界 0x000F4240、7/32 位、byte3 ≡ 0 |
| G | Read 长度截断 | 2 | 70000 → 4464 |

合计 **34 条判据**。

**为什么这些能在主机上算准**：它们全部只依赖
① 驱动的整数算术（`us*999/1000`、`offset & 4095`、`256 - (off & 255)`）；
② NEC 的公开时序常数；
③ 两个时间模型的返回值域。
没有一条依赖引脚电平、真实波形或芯片状态 —— 那些留在"未验证"里。

**做不到的**：本实验**不能**证明"装上真板后遥控器能用"。它证明的是"即使其余一切都对，这套代码在本工程的时基下也必然解不出码"。

## 常见错误和陷阱

| 陷阱 | 症状 | 根因 | 处理 |
| --- | --- | --- | --- |
| 用 `system_get_ns()` 做跨毫秒差值 | 计数/测距/解码全部异常，波形却正常 | `HAL_GetTick()` 恒 0，返回值每 1 ms 回绕 | 用 `udelay` 轮询硬件计数器，或先修 `HAL_IncTick` 的调用链（Day14 缺陷①） |
| `while (timeout--)` + `if (!timeout)` | 超时分支永不进入 | 后置自减：耗尽时 `0` 变成 `UINT_MAX` 或 `-1`，都不是 0 | 改成 `while (timeout > 0) { ...; timeout--; }` 或 `if (timeout <= 0)` |
| 判据用 `&&` 连接两个"应拒绝"条件 | 只错一个的输入全被接受 | `&&` 只覆盖"两个都错"的象限 | 应在**违规**上取 `\|\|`：`if ((off & 4095) \|\| (len & 4095)) return -1;` |
| `HAL_TIM_*_DeInit` 用在共享 `htim1` 上 | 另一个使用者的 PWM 频率被改掉 | `IRSender_Init` 与 `PassiveBuzzer_Init` 共用句柄与通道 | 一个定时器只归一个模块，或显式分通道 |
| 以为 `OCPolarity=LOW` 的 `Pulse` 就是占空比 | LED 驱动电流只有预期 1/3，通信距离短 | `Pulse` 是**有效电平**宽度，极性为低时它是"亮"的那段 | 按 `Pulse/(ARR+1)` 算有效占空比，再按熄灭段复核注释 |
| 环形缓冲区存字节、读方按记录读 | 偶发半个记录、device 与 key 张冠李戴 | 两次 `Put`/`Get` 之间可被 ISR 插入 | 一次入队一条完整记录，或用队列/加锁 |
| 共享变量缺 `volatile` | 优化等级或 LTO 一变就死循环 | 编译器可把 `static` 全局提到寄存器 | 加 `volatile`，或用临界区/RTOS 队列 |
| `GPIO_MODE_EVT_*` 当成 `_IT_*` | 事件能触发，中断不触发 | EVT 只置 `EXTI_EMR`，不置 `EXTI_IMR` | 要中断必须用 `GPIO_MODE_IT_*` |
| EXTI 线只配了引脚没配端口 | 别的外设一动作就进这个中断 | EXTI10 复位后指向 PA10（=USART1_RX） | 显式 `HAL_GPIO_Init(GPIOB, PIN_10)` 写 `AFIO->EXTICR` |
| `uint32_t` 实参传给 `uint16_t` 形参 | 大块读写只搬了一小部分还报成功 | 静默截断，默认无警告 | 形参用 `uint32_t`，或加范围检查 |
| 用"当前时间"当测试数据 | 自测通过但故障没被覆盖 | 时间值位宽有限，高位恒定 | 用固定花样 + 地址异或，保证每位都会变 |
| 复制粘贴后漏改一处 | 三处相同代码里只有一处不检查返回值 | 复制时忘写 `err =` | 四处结构相同的代码要一起读，用工具扫 `W25Q64_Tx(` 的行 |

## 故障排查方法

### 现象一：遥控器按键完全没反应

**第一步：先确认"是不是一个都不响应"。** 单击与长按同时失效 ⇒ 大概率是共因（时基），而不是"某一个按键的码不对"。

**第二步：在 `IRReceiver_IRQ_Callback` 里直接点灯。** 这是最快区分"中断没进"与"解码失败"的办法：

```c
void IRReceiver_IRQ_Callback(void)
{
    HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_9);   /* 每次边沿翻转，示波器/逻辑分析仪可看 */
    ...
}
```

- 灯不翻转 ⇒ 中断没进来，查 EXTI（§12、§13：`_IT_` 与端口映射）；
- 灯翻转但 `IRReceiver_Read` 恒 −1 ⇒ 解码层，查 §6。

**第三步：打印 `g_IRReceiverIRQ_Cnt` 的最大值。** 这是本篇最有效的单点观测：它是"解码是否可能成功"的**结构化**指标，不是"灵敏度"。

```c
static int g_max_cnt_debug = 0;
/* 在 cnt++ 之后 */
if (g_IRReceiverIRQ_Cnt > g_max_cnt_debug) g_max_cnt_debug = g_IRReceiverIRQ_Cnt;
```

- 最大值到 68 ⇒ 时基正常，问题在别处（校验、码表、缓冲区）；
- 最大值只有 2–3 ⇒ 就是 §6，与按键、遥控器、接收头都无关。

**第四步：验证时间源。** 一个 5 行的判据：

```c
uint64_t t0 = system_get_ns();
mdelay(100);
uint64_t dt = system_get_ns() - t0;
printf("%llu\n", dt);        /* 正常应 ≈ 1e8；回绕时应 < 1e6 */
```

`dt < 1e6` 就说明 `HAL_GetTick()` 没在动 —— 此时不必再看红外代码。

### 现象二：红外 LED 不亮（用手机摄像头看不到紫光）

**第一步：区分"定时器没跑"与"波形没出脚"。**

| 观测 | 结论 |
| --- | --- |
| `TIM1->CNT` 在变，脚上无波形 | GPIO 复用被夺走（`ActiveBuzzer_Init` 或 `HAL_GPIO_Init` 改回输入） |
| `TIM1->CNT` 不变 | `HAL_TIM_PWM_Start` 没成功（先看 MOE，高级定时器必须置 `BDTR.MOE`） |
| 脚上有波形但 LED 不亮 | 极性/限流/接插件 |

**第二步：确认 PA8 的模式寄存器。** `GPIOA->CRH` 的 `[11:8]` 应为 `0b1011`（`MODE=11` 输出 50 MHz，`CNF=10` 复用推挽）。若为 `0b0100`（浮空输入）说明没人配过。

**第三步：确认没有别的模块改过它。** 全仓只有三处写 PA8：`tim.c:263`（AF）、`driver_passive_buzzer.c:61`（AF）、`driver_active_buzzer.c:53`（GPIO 推挽）。哪个后执行哪个赢。

### 现象三：Flash 读写"成功"但数据不对

**第一步：先排掉"芯片根本不在"。** 因为返回值链条全断（§19），必须自己加一条 JEDEC ID 读：

```c
uint8_t tx[4] = {0x9F, 0, 0, 0}, rx[4];
W25Q64_Select();
W25Q64_TxRx(tx, rx, 4, 100);
W25Q64_Deselect();
/* 期望 rx[1..3] = 0xEF 0x40 0x17（Winbond / SPI / 64Mbit） */
```

`rx[1..3]` 全 `0x00` 或全 `0xFF` ⇒ 芯片没接上/CS 不对/MISO 断，**此时不需要再查擦写逻辑**。

**第二步：检查擦除是否真的发生。** 擦除后读应为全 `0xFF`。若仍是旧数据 ⇒ 擦除命令没发出去（§19 组合二）或地址被截断（§17）。

**第三步：检查写入是否跨页。** Page Program 跨页会在页内回卷，表现为"前 N 字节对、后面全错且重复"。用 `offset % 256` 与 `len` 判断是否跨界。

**第四步：检查 PB9 的共用。** PB9 同时是 W25Q64 CS 与 SR04 TRIG：

| 状态 | W25Q64 | SR04 |
| --- | --- | --- |
| PB9 = 低 | **选中**（危险：无时钟时不产生动作，但任何时钟都会被当命令） | TRIG 空闲 ✅ |
| PB9 = 高 | 未选中 | **触发一次测距**（脉宽 = 高电平持续时间） |

所以：**测距期间不要操作 Flash，操作 Flash 期间会误触发测距。** 两者本工程都是主循环同步调用，不会真交错，但任何一边改成中断/任务就会。

### 通用：判据先行

本篇的三类问题（时基、`&&`、后置自减）都是"代码看起来对、跑起来也'成功'"的形态。这类问题的排查顺序应该是**先找一个能证伪的量化指标**，而不是先读代码：

| 问题 | 量化指标 | 阈值 |
| --- | --- | --- |
| 红外不接受 | `cnt` 最大值 | 应到 68；只有 2–3 就是时基 |
| 时间源可用 | `mdelay(100)` 的 `dt` | 应 ≈ 1e8；< 1e6 就是回绕 |
| 擦除真发生 | 擦后读回 | 应全 0xFF |
| 芯片存在 | JEDEC ID | 应 0xEF4017 |
| 超时分支可达 | 故意让条件永不满足，看返回值 | 必须返回失败 |

最后一条是通例：**任何"超时/失败"分支，都要在开发期故意触发一次**，否则你不知道它是死代码还是活代码。本篇的 SR04、`WaitReady`、`Erase` 三处都是从未被触发过的失败分支。

1. **红外接收在真板上到底能不能用。** 本篇证明的是"在本工程的时基下，即使硬件全对也解不出码"。若真板上 `HAL_IncTick` 的调用链被别处补上（例如课程 `03_nwatch_dshanmcu-f103_all` 里有 `SysTick_Handler`），结论会变 —— **我没有在本工程之外核对其余工程**。

3. **`W25Q64_TIMEOUT = 500` 的余量没有核对。** 数据手册的 `tSE`（4 KB 扇区擦除）典型 45 ms、最大 400 ms 是按惯例给出的，**未查证原厂文档**；若最大值超过 500 ms，`WaitReady` 即使修对也会误报超时。
