## 核心概念

### 1. 四个模块的共同点：慢、有符号、待校验

先把四者放进一张表，后面的每一节都是表格某一格的展开。

| 模块 | 物理接口 | 一次采集耗时 | 数据宽度 | 自带校验 | 驱动是否校验 | 错误处理质量 |
| --- | --- | --- | --- | --- | --- | --- |
| DHT11 | 单总线（开漏 1-Wire 变种） | ≥ 20 ms 启动 + ~4 ms 传输，周期 ≥ 2 s | 40 bit | 校验和（低 8 位） | 校验了，但**没取模** | 中：`-1` 被截断 |
| DS18B20 | 单总线（标准 1-Wire） | 转换最长 750 ms | 9 字节 RAM | CRC8 | **完全没校验** | 差：`-1` 被截断 |
| 光敏 | 模拟（ADC1_IN3） | 单次转换 µs 级 | 12 bit | 无 | 不适用 | 中：失败返回 `-1` |
| MPU6050 | I2C（400 kHz 级） | 12 次事务 ≈ 4.7 ms | 6×16 bit | 无 | 不适用 | 差：`Init` 恒返回 0 |

三列决定本篇的组织方式：**接口**决定电气与时序（§2、§3、§9），**宽度与校验**决定解码算法（§7、§11、§12、§13），
**错误处理**决定"读到脏数据时你能不能发现"（§7、§12、§17）。

一个贯穿全篇的判断：**这四个驱动里没有一个能可靠地报告失败**。它们各自的失效方式不同，
但共同点是——**失败时的表现与"传感器正常但环境没变化"难以区分**。

### 2. 单总线为什么能双向：开漏 + 上拉 = 线与

DHT11 与 DS18B20 都只用一根数据线完成双向通信。一根线怎么可能既发又收？

关键在于**两端的输出级都是开漏（open-drain）**，配合一个上拉电阻：

```text
        VDD (3.3V)
          │
         ┌┴┐ 4.7k 上拉
         └┬┘
          │
    ┌─────┴─────┐
    │   DATA    │
    ├───────────┤
   MCU         DS18B20
 (开漏)        (开漏)
```

开漏输出的两个状态：

| MCU 输出寄存器 | 引脚状态 | 总线电平（有上拉） |
| --- | --- | --- |
| 写 0 | 下拉管导通，强拉低 | **低** |
| 写 1 | 上下管都关断，高阻 | **由上拉拉高 → 高** |

因为高阻态不驱动任何电平，两端可以同时"输出"，实际电平 = **线与**（wired-AND）：

```text
总线电平 = 任何一端拉低 ? 低 : 高
```

任意一端拉低，总线就是低；两端都释放，上拉把它带回高。这就实现了"谁都能拉低，谁都能读"。

**为什么不能推挽（push-pull）**：如果两端都是推挽，一端输出高（接 VDD）、另一端输出低（接 GND），
VDD 与 GND 之间通过两个导通的三极管直接短路，电流只受器件内阻限制 —— 烧管。教材 `:524` 明确写了这一点。

**驱动的实现方式：从不切换模式。**

`driver_dht11.c` 的两个"切换"函数，函数体加起来只有一句话：

```c
static void DHT11_PinCfgAsOutput(void)      /* :63 */
{
    /* 对于STM32F103, 已经把DHT11的引脚配置为"open drain, pull-up" */
}                                            /* ← 空函数体 */

static void DHT11_PinCfgAsInput(void)       /* :78 */
{
    /* ... 让它输出1就不会驱动这个引脚, 并且可以读入引脚状态 */
    HAL_GPIO_WritePin(GPIOA, GPIO_PIN_1, GPIO_PIN_SET);   /* 只写 ODR = 1 */
}
```

这不是偷懒，而是开漏模式下的正确做法：**引脚始终是 `GPIO_MODE_OUTPUT_OD`，不需要在"输出"和"输入"之间切换。**

- 要驱动总线 → 写 0（拉低）或写 1（释放，由上拉拉高）
- 要读总线 → 直接读 `IDR`。**开漏输出模式下 IDR 仍然反映引脚真实电平**，因为输入通路一直在工作

`DS18B20_PinRelease()`（`:153`）与 `DS18B20_PinCfgAsInput()`（`:80`）同样是"写 1"，同一手法。

**这个手法依赖两个前提，缺一不可：**

1. 引脚被配置成 `GPIO_MODE_OUTPUT_OD` 且带 `GPIO_PULLUP` —— 本仓库由 `lab_pins.c:56-67` 保证：

   ```c
   HAL_GPIO_WritePin(GPIOA, GPIO_PIN_1, GPIO_PIN_SET);   /* 初值 1：释放总线 */
   GPIO_InitStruct.Pin   = GPIO_PIN_1;
   GPIO_InitStruct.Mode  = GPIO_MODE_OUTPUT_OD;
   GPIO_InitStruct.Pull  = GPIO_PULLUP;                  /* 内部上拉，约 40 kΩ */
   HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);
   ```

2. 若把模式改成 `GPIO_MODE_OUTPUT_PP`，`PinCfgAsInput()` 写 1 会**强推高电平**。
   此时 DHT11 想拉低回应（80 µs 响应信号）就会与 MCU 硬顶 —— 轻则读不到响应，重则长期对顶损伤器件。
   **这是移植时最容易踩的坑**：驱动自己不配引脚，把前提交给了外部。

> 内部上拉约 40 kΩ，比模块上常见的 4.7 kΩ 弱得多，上升沿更慢。
> 短线、低速下够用；长线或需要 1-Wire 强上拉时**必须外加**。这一点在 §9 的 DS18B20 转换供电里再次出现。

### 3. DHT11 的三个时间段：启动、响应、位

DHT11 每次通信由主机发起，时序分三段（教材 `:373-382`，驱动 `driver_dht11.c:134-229`）：

**第一段：启动信号（主机）**

```c
static void DHT11_Start(void)                 /* :134 */
{
    DHT11_PinSet(0);          /* 拉低 */
    mdelay(20);               /* 保持 20 ms */
    DHT11_PinCfgAsInput();    /* 写 1 释放总线 */
}
```

协议要求低电平 **> 18 ms**。20 ms 留有 2 ms 裕量。
注意 `mdelay(20)` 是**忙等**，依赖 TIM4 时基（Day13 / 速查表 §3.1）——
若 TIM4 没跑起来，这里不是"延时不精确"，而是**卡死**。这是 DHT11 的一条隐式依赖。

**第二段：响应（DHT11）**

```text
主机释放总线
    │
    ├──────── DHT11 拉低 80 µs ────────┤
    │                                  ├──── DHT11 拉高 80 µs ────┤
    └──────── 80 µs ───────────────────┴──────────────────────────┴──→ 数据
```

- 总线被拉低 ⇒ 设备已响应
- 随后设备拉高 **80 µs**，紧接着开始发数据
- 若主机释放后总线仍为高 ⇒ **设备没有响应**（教材 `:381`：检查线路）

**第三段：40 bit 数据（DHT11）**

每一位的格式是固定的前缀 + 可变的高电平时长：

```text
bit0:  ├── 50 µs 低 ──┼─ 26~28 µs 高 ─┤
bit1:  ├── 50 µs 低 ──┼──────── 70 µs 高 ────────┤
```

**50 µs 低电平是每一位的"起始时隙"，高电平的时长编码数值。**
判位的任务因此变成：**在低电平结束后的某个时刻采样，看总线还是不是高。**

40 bit = 湿度整数 + 湿度小数 + 温度整数 + 温度小数 + 校验和。
DHT11 的小数部分**恒为 0**（不支持小数温度），所以实际有效信息只有两个字节。

### 4. 为什么是 `udelay(60)`：教材那句"20-40us"的歧义

教材 `:376` 写：

> 主机发送开始信号结束后，**延时等待 20-40us 后**，读取 DHT11 的响应信号

驱动写的是（`driver_dht11.c:152`）：

```c
static int DHT11_Wait_Ack(void)
{
    udelay(60);
    return DHT11_PinRead();
}
```

看起来矛盾：教材说 20-40 µs，驱动等 60 µs。谁对？

把响应时间轴画出来就清楚了：

```text
t=0            主机释放总线
t=0~40 µs      DHT11 开始拉低（数据手册：20~40 µs 后拉低）
t=20~40 µs     ← DHT11 最早在这里拉低
t=100~120 µs   ← 80 µs 低响应结束
```

- DHT11 **最早**在 20 µs 才拉低，**最晚** 40 µs 才拉低
- 拉低持续 80 µs，所以在 **100~120 µs** 才释放

教材说的"20-40 µs 后读取"：若在 20 µs 采样，**DHT11 可能还没开始拉低**，此时总线仍是上拉的高电平
⇒ 被误判为"没有响应"。**教材这句是踩在 DHT11 下沿上的，不稳。**

驱动的 60 µs 落在哪里？

```text
        20 µs            40 µs              100~120 µs
          │                │                     │
   ───────┼────────────────┼─────────────────────┼──────
   高      │← 可能拉低 →│←── 最晚拉低 ────────→│  高
          │                │                     │
                    ▲
                  60 µs ← 稳落在窗口内
```

60 µs 在 40 µs（最晚拉低）与 100 µs（最早释放）之间，两侧裕量分别为 **+20 µs / +40 µs**。
在 µs 级软件延时（`udelay` 靠循环计数，误差通常 5~10%）下，这是能接受的。

> **判据**：这里要判断的不是"教材和驱动谁错"，而是"采样点必须落在 DHT11 拉低窗口的内部"。
> 教材给的是 DHT11 **开始**拉低的时间，驱动给的是**采样**时间。把前者的区间当成后者的取值，
> 就会在 20 µs 采样并读到假的高电平。

### 5. `udelay(40)`：判位裕量的算术

`DHT11_ReadByte`（`:190`）的核心：

```c
for (i = 0; i < 8; i++)
{
    if (DHT11_WaitFor_Val(1, 1000)) return -1;   /* 等低电平结束，进入高电平 */
    udelay(40);                                   /* ← 40 µs 后采样 */
    data <<= 1;
    if (DHT11_PinRead() == 1) data |= 1;
    if (DHT11_WaitFor_Val(0, 1000)) return -1;   /* 等高电平结束 */
}
```

采样点距高电平起点的 40 µs，要区分的是：

| 数据位 | 高电平宽度 | 40 µs 处是否仍为高 | 裕量 |
| --- | --- | --- | --- |
| 0 | 26~28 µs | **否**（已回低） | 12~14 µs |
| 1 | 70 µs | **是** | 30 µs |

所以 40 µs 的判读是"读 0 时裕量 12 µs，读 1 时裕量 30 µs"，**偏向 0**。

若取中点 ~48 µs，两侧裕量约 20 µs / 22 µs，更均衡。驱动取 40 µs 的原因推测是：
`WaitFor_Val` 本身有检测延迟（循环粒度 1 µs + 函数调用开销），实际采样点晚于名义值，
取小一点留出手续费。**这是源码推论，不是注释里的说法**（驱动没有解释这个数）。

**这个参数是怎么标定的**：`WaitFor_Val` 用 `udelay(1)` 轮询，它的时间分辨率取决于 `udelay(1)` 的真实耗时。
若 `udelay(1)` 实际是 1.5 µs，则 `WaitFor_Val` 的检测延迟可达 1.5 µs，采样点后移。
在没有示波器的情况下，40 µs 这类参数只能靠**"改大改小看读数是否稳定"** 来二分，而不是靠算。

**判位的有效窗口**：把上面两个约束合起来，采样时刻 $t$ 满足

```text
28 µs  <  t  <  70 µs
└─ bit0 已结束 ─┘  └─ bit1 尚未结束 ─┘
```

窗口宽 **42 µs**，相对宽度很大 —— 这说明 DHT11 的位判读对延时误差不敏感，
40 µs 取的是窗口靠左的位置（靠近下界，偏向 0）。

**可证伪的预测**（需真板，一改一测即可验证窗口）：

| 把 `udelay(40)` 改成 | 预期现象 | 机制 |
| --- | --- | --- |
| **20 µs** | 0 被大量误判成 1 ⇒ 湿度/温度**系统性偏高** | 20 µs < 28 µs，bit0 的高电平还没结束 |
| **60 µs** | 仍然正确（在窗口内） | 28 < 60 < 70 |
| **75 µs** | 1 被大量误判成 0 ⇒ 读数**系统性偏低** | 75 µs > 70 µs，bit1 的高电平已结束 |

三条预测构成一次完整的上界/下界验证：**只有 60 µs 那条会通过**，另两条会把窗口边界暴露出来。
这是没有示波器时确定时序参数的通用方法——**把参数推到两侧，看哪一侧先坏**。

### 6. DHT11 的读周期：为什么是 2 秒，以及失败时的屏幕表现

`DHT11_Test`（`:306`）：

```c
while (1)
{
    if (DHT11_Read(&hum, &temp) != 0)
    {
        //printf("\ndht11 read err!\n\r");     ← 注释掉了
        DHT11_Init();                          /* 只重新释放总线 */
    }
    else
    {
        LCD_PrintString(0, 0, "DHT11:");
        ...
    }
    mdelay(2000);   /* 读取周期是2S, 不能读太频繁 */
}
```

两个观察：

**(a) 2 s 周期是器件约束，不是随便写的。** DHT11 数据手册要求采样间隔 ≥ 1 s，
驱动取 2 s 是留了余量。违反的表现不是"读不到"，而是**读到的值滞后于真实温湿度**
（器件内部采样率跟不上查询率，返回上一次的结果）。这类"陈旧但合法"的数据是最难发现的。

**(b) 失败路径没有任何外部可见信号。** `printf` 被注释掉，LCD 也不刷新。
失败时屏幕**保持上一帧**，与以下三种情况完全同形：

- 传感器坏了（一直是上一次的值）
- 程序卡在 `mdelay` 里（`TIM4` 挂了）
- 读数正常但环境没变（温湿度本来稳定）

**这是观测性缺陷，不是功能缺陷。** 判据应该能区分"没响应"与"做完了"——
和 `F103_17_ADC_Polling` 那个假阳性判据（未建模设备恒读 0 让"等清零"秒过）是同一类错误的镜像：
那边是"把没响应当成功"，这边是"把失败藏成不变"。

> 改进的最小代价：失败时在 LCD 固定位置打一个字符（如 `ERR`），不引入 printf。
> 三条 `printf` 都保留注释状态，说明作者当初调试完就关掉了——**调试输出被当成临时脚手架，而不是诊断能力**。

### 7. DHT11 的校验和与错误码：两处缺陷，一处被量程掩盖

**校验和（`:285`）**

```c
if (hum_m + hum_n + temp_m + temp_n == check)
```

协议规定：校验和 = 前四字节之和的**低 8 位**。驱动没有取模。

后果分两种：

| 前四字节之和 S | 驱动判断 | 正确判断 | 差异 |
| --- | --- | --- | --- |
| S ≤ 255（合法量程内，最大 140） | `S == check` ✓ | `S & 0xFF == check` ✓ | **无差异** |
| S > 255（数据异常） | `S == check`，**必然不等** ⇒ 判失败 | `S & 0xFF == check` 可能通过 | 驱动更严格 |

**所以这个缺陷在 DHT11 的合法量程内不会误判**（判据 D3）：湿度 20~90、温度 0~50、小数恒 0，
和最大 140，永远够不到 256。它只在数据本身已异常时才起作用，而那时判失败**恰好是正确的方向**
（宁可报错不给脏数据）。真正的代价是**诊断信息丢失**：把"数据异常"报成"校验失败"。

**错误码截断（`:252`、`:278`）**

```c
unsigned char hum_m, hum_n, temp_m, temp_n, check;   /* :252-254 */

hum_m = DHT11_ReadByte();      /* DHT11_ReadByte 失败返回 -1 */
```

`-1` 存进 `unsigned char` 变成 **`0xFF`（255）**。随后这个 255 直接参与校验和。

由于截断后的 0xFF 落在 8 位数据值域内，**没有任何取值层面的检测点**：
读取失败和"读到 255"完全无法区分。唯一的兜底是校验和，而它恰好成立的概率取决于数据。

> **本节的一条假设被自己的判据推翻了。**
> 我最初写下的判断是"错误检测降级为概率性，漏检率 1/256"。把它写成判据 D4 后运行，
> 得到 **`FAIL`**：前四字节和 S = 0xFF+0+25+0 = 280 > 255，而驱动判 `280 == check`，
> **256 种 check 值没有一个能通过** ⇒ 漏检率是 **0**，不是 1/256。
>
> 原因：驱动那句"没取模"的比较，在 S > 255 时**反而成了保护**（永远不等 ⇒ 永远判失败）。
> 所以要触发误判，必须让 S 恰好等于 255 且 check 被截断成 0xFF。
>
> 修正后的结论（判据 D4 的最终形态）：
>
> | 情形 | 是否误判 |
> | --- | --- |
> | check 字节失败（→0xFF），且 S = 255 | **误判成功**，返回超量程数据 |
> | check 字节失败，S ≠ 255 | 判失败（安全） |
> | 数据字节失败（→0xFF），其余非零 ⇒ S > 255 | 判失败（安全） |
> | 数据字节失败，其余全 0 ⇒ S = 255，check = 0xFF | 误判成功（概率 1/256 × 数据分布） |
>
> 而 S = 255 需要湿度 200 + 温度 55 这类**超出 DHT11 量程**的组合，
> 合法量程内凑不出来。**结论：缺陷真实存在，但被量程掩盖**——和 §11 的 DS18B20 精度判断同构。
>
> 这件事的方法论意义：**"1/256 漏检"是个听起来很专业的错误结论**。
> 它错在把"check 有 256 种取值"当成了"256 种里有 1 种通过"，而忘了比较的另一侧是一个可能 > 255 的 int。
> 判据程序当场推翻了它——这正是写判据而不是写注释的价值。

### 8. 小结：DHT11 的四条可检验结论

| 编号 | 结论 | 证据类型 | 可证伪方式 |

| A | `PinCfgAsOutput` 空函数成立的前提是 `GPIO_MODE_OUTPUT_OD` + `PULLUP` | 源码核对（`lab_pins.c:56-67`） | 改成 `_PP`，读响应信号应恒为高 |

### 9. DS18B20 与 DHT11：同一套思想，不同的常数

两者都是单总线、都靠"低电平启动 + 高电平时长编码"，但常数差一个数量级：

| 环节 | DHT11 | DS18B20 | 差异原因 |
| --- | --- | --- | --- |
| 复位/启动低电平 | 20 ms | **≥ 480 µs** | DHT11 用长启动区分，DS18B20 用标准 1-Wire 复位脉冲 |
| 设备响应低电平 | 80 µs | **60~240 µs** | 1-Wire 存在脉冲（presence pulse） |
| 位起始低电平 | 50 µs | **≥ 1 µs**（写）/ ≥1 µs（读） | DS18B20 靠采样点区分，不靠低电平宽度 |
| 写 0 | — | 低 ≥ 60 µs，周期 60~120 µs | 1-Wire 写时隙 |
| 写 1 | — | 低 ≥ 1 µs 后释放，周期 ≥ 60 µs | 同上 |
| 读时隙 | — | 拉低 ≥ 1 µs，**15 µs 内采完** | 主从都要在 15 µs 内完成 |
| 单次数据量 | 40 bit | 9 字节 RAM（72 bit） | |
| 转换时间 | — | 最长 **750 ms**（12 bit） | 内部 ADC |

**关键差异在"位如何编码"**：

- DHT11：低电平固定 50 µs，**高电平时长**编码（26 µs = 0，70 µs = 1）
- DS18B20：**低电平时长**编码（写 0 = 长低 60 µs，写 1 = 短低 1 µs 后释放）

DHT11 的"读"是主机被动测量；DS18B20 的读写时隙都由主机发起，设备只在时隙内响应。

### 10. DS18B20 的读时隙与"读 bit 探测忙闲"

```c
static int DS18B20_ReadBit(void)              /* :218 */
{
    int val;
    DS18B20_PinSetForTime(0, 2);   /* 拉低 2 µs（协议要求 ≥1 µs）*/
    DS18B20_PinRelease();          /* 释放，由上拉拉高 */
    udelay(10);                    /* 10 µs 后采样 */
    val = DS18B20_PinRead();
    udelay(50);                    /* 补足时隙到 ~62 µs */
    return val;
}
```

时间轴：

```text
        0    2 µs        12 µs                        62 µs
        ├─低─┤
             ├────────── 释放（上拉） ──────────────┤
                          ▲
                        采样点
```

- 拉低 **2 µs**：满足协议"≥ 1 µs"，同时给设备一个明确的时隙起点
- 采样在释放后 **10 µs**：设备会在拉低后 15 µs 内输出有效位（0 或 1），10 µs 采样留有 5 µs 余量
- 再等 **50 µs**：把整个时隙补到 ~62 µs，远大于协议的 60 µs 最小值，避免下一次操作过早

**这个函数被复用来做"忙闲探测"**（`driver_ds18b20.c:315`）：

```c
static int DS18B20_WaitReady(int timeout_us)
{
    while (timeout_us--)
    {
        if (DS18B20_ReadBit() == 1) return 0;   /* 读到 1 ⇒ 转换完成 */
        udelay(1);
    }
    return -1;
}
```

`DS18B20_StartConvert`（`:336`）发完 `0x44`（Convert T）后调用它，等待转换完成。
机制是：**转换期间设备读时隙返回 0，转换完成后返回 1**。

**为什么这样探测是安全的**：每次 `ReadBit` 只拉低 2 µs，而 1-Wire 复位的门槛是 **480 µs**。
2 µs ≪ 480 µs ⇒ 设备不会把这种短脉冲误认为复位命令。用"读"来探测，不需要额外的引脚。

> **跨到 FreeRTOS 的注意点**：`WaitReady` 是纯忙等。正常 12 bit 转换约 750 ms，
> 也就是 CPU 被 `DS18B20_Read_Temperature` 独占 750 ms。若移植到 RTOS 任务里，
> **必须**改成 `vTaskDelay` + 分次探测，否则会饿死所有同级及更低优先级任务。
> 这与 `aviation-node` 项目里"任务忙等导致监督任务看不见"是同一类问题的不同表现。

### 11. `-Wparentheses` 三连：编译器警告是真缺陷

`driver_ds18b20.c:463-467` 是构建日志里 3 条警告的来源：

```c
if (ram[4] & (3<<5) == 0)            /* 警告 1 */
    i = 3;
else if (ram[4] & (3<<5) == (1<<5))  /* 警告 2 */
    i = 2;
else if (ram[4] & (3<<5) == (2<<5))  /* 警告 3 */
    i = 1;
else
    i = 0;
```

C 的优先级：`==`（8 级）**高于** `&`（9 级）。所以第一行实际被解析成：

```c
ram[4] & ((3<<5) == 0)     /* (3<<5)=96，96==0 为假(0) */
= ram[4] & 0
= 0                        /* 恒假 */
```

三个条件逐一说一遍：

| 源码 | 实际语义 | 结果 |
| --- | --- | --- |
| `ram[4] & (3<<5) == 0` | `ram[4] & 0` | **恒 0（假）** |
| `ram[4] & (3<<5) == (1<<5)` | `ram[4] & 0` | **恒 0（假）** |
| `ram[4] & (3<<5) == (2<<5)` | `ram[4] & 0` | **恒 0（假）** |

**三个分支全部是死代码，永远落到 `else i = 0`（按 12 bit 解释）。**
判据 D1 对 `ram[4] ∈ {0x00, 0x20, 0x40, 0x60}` 逐一验证：正确写法分别得 3/2/1/0，
驱动写法**全部得 0**。

**为什么一直没暴露？**

`DS18B20_Init`（`:399`）的函数体只有一句：

```c
void DS18B20_Init(void) { DS18B20_PinRelease(); }   /* 只释放总线 */
```

它**从不写配置寄存器**。DS18B20 出厂默认配置寄存器 = `0x7F`，bit6:5 = `11` = **12 bit 分辨率**。
于是 `i = 0` 恰好是对的。

> **缺陷真实存在，但因默认配置恰好落在唯一正确的那一支而不表现。**
> 一旦有人用 `WRITE_SCRATCHPAD`（`0x4E`）改成 9/10/11 bit 省电或提速，
> 驱动仍按 12 bit 解释低位 ⇒ 低位置是无效噪声 ⇒ **温度末位随机跳动**。
> 这是"潜伏缺陷"（latent defect）的典型：不是"现在错的"，是"条件一变就错"。

**这条给写作与评审的两个结论**：

1. **构建日志里"13 条警告全部来自课程驱动"不是一个可以忽略的数字。**
   Day14 记这一条时把它当作"代码风格"；现在知道其中 3 条是**逻辑错误**。
   警告需要逐条看，不能按来源批量归类。
2. 开关型缺陷（只在某个配置下出现）**必须用"条件矩阵"测**，而不是"跑一遍通了就算"。
   判据 D1 的 4 行就是条件矩阵。

### 12. 负温解码：把补码当成了符号-数值

`DS18B20_Read_Temperature` 的换算部分（`:444-492`）：

```c
static const double val[] = {0.0625, 0.125, 0.25, 0.5, 1, 2, 4, 8, 16, 32, 64};

for (i = 0; i < 8; i++)                 /* ram[0] 的 8 位 */
    if (ram[0] & (1<<i)) sum += val[i];
for (i = 0; i < 3; i++)                 /* ram[1] 的低 3 位 */
    if (ram[1] & (1<<i)) sum += val[8+i];
if (ram[1] & (1<<3))                    /* bit3 当符号位 */
    sum = 0 - sum;                      /* ← 错在这里 */
```

**12 位温度寄存器是二进制补码**，不是"符号位 + 绝对值"。

以 **-0.5 °C** 为例：

```text
真值 -0.5 °C
原始值 = -0.5 / 0.0625 = -8
12 位补码 = 4096 - 8 = 4088 = 0xFF8
ram[0] = 0xF8 = 1111 1000
ram[1] = 0x0F = 0000 1111
```

驱动的算法：

| 步骤 | 计算 | 结果 |
| --- | --- | --- |
| ram[0] 各位置位求和 | bit3+bit4+bit5+bit6+bit7 = 0.5+1+2+4+8 | 15.5 |
| ram[1] 低 3 位求和 | bit0+1+2 = 16+32+64 | +112 ⇒ 127.5 |
| bit3 为 1 ⇒ 取负 | 0 - 127.5 | **-127.5** |
| 真值 | 4088 - 4096 = -8 ⇒ ×0.0625 | **-0.5** |

**输出 -127.5 °C，误差 -127 °C。**

正确写法：

```c
int raw = ((ram[1] & 0x0F) << 8) | ram[0];
if (raw & 0x800) raw -= 4096;        /* 12 位补码转有符号 */
double temp = raw * 0.0625;
```

判据 D2 的四组负温读数：

| 真值 | raw | 驱动输出 | 误差 |
| --- | --- | --- | --- |
| -0.5 °C | `0xFFF8` | -127.5000 | **-127.000** |
| -10.125 °C | `0xFF5E` | -117.8750 | **-107.750** |
| -25.0625 °C | `0xFE6F` | -102.9375 | **-77.875** |
| -23.0 °C | `0xFE90` | -105.0000 | **-82.000** |

**误差不是常数**，所以不能"减一个固定值"修正。原因：驱动算的是"低 11 位的原码值"，
而补码的真值是 `低11位 - 2048`。两者的差随数值变化：

```text
误差 = 128 - m/8      （m = raw & 0x7FF）
```

- m = 2040（-0.5 °C）⇒ 128 - 255 = -127 ✓
- m = 1647（-25.0625 °C）⇒ 128 - 205.875 = -77.875 ✓

**符号位判断本身是对的**（`ram[1] & 0x08` 确实能区分正负），错的是"取绝对值的方式"。

> **可证伪的板上预测**：把 DS18B20 放进冰箱或用手握住降到 0 °C 以下，
> `DS18B20_Test` 的显示会从 `+0.5` 直接跳到 **`-127.5`** 附近，而不是平滑降到 `0` 再继续下降。
> 这是本篇最容易在 5 分钟内验证的一条——不需要示波器，只需要一个能低于 0 °C 的东西。
>
> 注意 DHT11 **不支持负温**（量程 0~50 °C），所以同样的问题在 DHT11 上不可见。

### 13. CRC8 从不校验：9 字节里浪费了 1 字节

`DS18B20_Read_RAM`（`:367`）读 9 字节：

```c
for (i = 0; i < 9; i++)
    ram[i] = DS18B20_ReadByte();
return 0;                       /* 无条件成功 */
```

9 字节布局（教材 §11.9.2）：

| 字节 | 内容 |
| --- | --- |
| `ram[0]` | 温度 LSB |
| `ram[1]` | 温度 MSB（bit7~4 是符号扩展） |
| `ram[2]` | TH 报警上限 |
| `ram[3]` | TL 报警下限 |
| `ram[4]` | 配置寄存器（bit6:5 = 分辨率，bit4~0 恒 1） |
| `ram[5:7]` | 保留（0xFF） |
| `ram[8]` | **CRC8** |

`DS18B20_Read_Temperature` 用到了 `ram[0]`、`ram[1]`、`ram[4]`，**`ram[8]` 一次都没读**。

三个连带问题：

1. **CRC 白给了。** 1-Wire 长线、有电机等干扰源时，某个 bit 翻转不会被发现。
   温度读数会"看起来正常但错了 1~2 度"，比报错危险得多。
2. **`DS18B20_ReadByte` 的失败同样被截断**（与 §7 同构）：返回 `-1`，赋给 `unsigned char ram[i]` ⇒ `0xFF`。
3. **`Read_RAM` 无条件返回 0**，即使 9 个字节全是 0xFF 也报成功。

CRC8 算法是 Dallas 标准（多项式 `x^8 + x^5 + x^4 + 1`，即 `0x31` 反射为 `0x8C`），
一百多行代码就能补上，且可以完全在主机端验证（有标准测试向量）。

> **这一条和 §11 是同类问题**：驱动的注释说明了流程（"读 9 字节"），
> 但没有说明"9 字节里最后一个是干什么用的"。读驱动时如果只看到 `for (i=0;i<9;i++)`，
> 会以为 9 是"数据长度"；实际是"数据 + 校验"。

### 14. 光敏：`Init` 只校准，PA3 由别人配

`driver_light_sensor.c` 全文 119 行，核心两处：

```c
void LightSensor_Init(void)                    /* :56 */
{
    /* PA3用作ADC(ADC1_IN3) */                 /* ← 注释说 PA3，但函数体不配 PA3 */
    HAL_ADCEx_Calibration_Start(g_HADC_LightSensor);

int LightSensor_Read(uint32_t *pData)          /* :73 */
{
    HAL_ADC_Start(g_HADC_LightSensor);
    if (HAL_OK == HAL_ADC_PollForConversion(g_HADC_LightSensor, LIGHT_SENSOR_ADC_TIMEOUT))

        *pData = HAL_ADC_GetValue(g_HADC_LightSensor);

```

**PA3 到底由谁配成模拟输入？** 追两条链：

```text
LightSensor_Init()
  → HAL_ADCEx_Calibration_Start(&hadc1)        /* 只校准 */

MX_ADC1_Init()                                  /* main.c:87，工程启动时调 */
  → HAL_ADC_Init(&hadc1)
    → HAL_ADC_MspInit(&hadc1)                   /* adc.c:70 附近 */
      → __HAL_RCC_GPIOA_CLK_ENABLE()
```

**为什么"只 Start 不 Stop"在本工程里安全？**

`adc.c:46-51` 的四个配置决定了这件事：

| 配置项 | 值 | 作用 |
| --- | --- | --- |
| `ContinuousConvMode` | `DISABLE` | **单次转换**：`ADON` 在转换完成后自动清零 |
| `ScanConvMode` | `ADC_SCAN_DISABLE` | 不扫描多通道 |
| `ExternalTrigConv` | `ADC_SOFTWARE_START` | 软件触发，`HAL_ADC_Start` 即启动 |
| `NbrOfConversion` | 1 | 单通道一轮 |

因为是单次转换，`PollForConversion` 返回时转换已完成、`ADON` 已自动清零，
所以不调 `HAL_ADC_Stop` 不会留下运行中的转换。

> **这个安全是"配置恰好对"，不是"代码正确"。** 若把 `ContinuousConvMode` 改成 `ENABLE`，
> 转换会一直跑，每次 `LightSensor_Read` 都启动一轮新的却从不停止，
> ADC 时钟持续占用、DR 被反复覆盖。**这是一条依赖外部配置的隐含契约**，
> 与 §2 的"开漏依赖 `lab_pins.c`"是同一类脆弱性。

### 15. 光敏：教材没有给出"读数向哪边变"

教材 §11.16.2（`:1561` 起）对原理只写了一句：

> 光敏电阻会因为光照强度的变化而改变阻值，使用一个分压电路来测量电压后，就可以反应出光照的强度

**没有分压比，没有光敏电阻在分压电路的上臂还是下臂。**

这不是小事：

| 光敏电阻位置 | 光照增强 ⇒ 电阻 | ADC 读数 |
| --- | --- | --- |
| 上臂（接 VDD） | 减小 | **减小** |
| 下臂（接 GND） | 减小 | **增大** |

两种接法得到的曲线**方向相反**、都是单调的，都能"反应光照强度"。
所以只读教材，**无法知道读数变大意味着更亮还是更暗**。

教材 §11.16.4 的"配置"说明是**一张图片**，§11.16.3 的"核心代码"只有一行校准调用。
**信息缺口是结构性的**（与 Day16 的"§11.3–§11.19 的 CubeMX 小节在抽取文本中为空"同源）。

驱动的行为也帮不上忙：

```c
int LightSensor_Read(uint32_t *pData)   /* 只返回 0~4095 的原始值 */
```

没有任何标定、阈值或方向说明。`LightSensor_Test` 只是把原始值打到屏上。

> **判断方法**：这类"方向未知"的模拟量，唯一可靠的确定方式是**实验二分**——
> 遮住传感器读一次，用手电筒照读一次，比较两次读数。
> 在拿到这两读数之前，任何"亮度百分比"的换算都建立在猜测上。
> 这与 Day13 的 PWM 极性、Day16 的电机正反转是同一类问题：**文本只给机制，方向必须实测。**

### 16. MPU6050：与 OLED 共用 I2C1，以及逐字节读的代价

**共用总线的地址核查**

| 设备 | 驱动宏 | 8 位地址 | 7 位地址 |
| --- | --- | --- | --- |
| OLED | `driver_oled.c` | `0x78` | `0x3C` |
| MPU6050 | `MPU6050_I2C_ADDR` | `0xD0` | `0x68` |

`0x78` 与 `0xD0` 不冲突，可共用 I2C1（PB6/PB7）。
HAL 的 `HAL_I2C_Master_Transmit` 接受 **8 位地址**（含 R/W 位），内部右移一位后使用。
所以 `0xD0` = 7 位 `0x68` 左移一位，与 `WHO_AM_I` 寄存器默认返回的 `0x68` 一致（`:56` 注释已写明）。

**配置解读**（`MPU6050_Init`，`:116-124`）

```c
MPU6050_WriteRegister(MPU6050_PWR_MGMT_1,  0x00);  /* 解除休眠（bit6 = 0）*/
MPU6050_WriteRegister(MPU6050_PWR_MGMT_2,  0x00);  /* 全部轴使能 */
MPU6050_WriteRegister(MPU6050_SMPLRT_DIV,  0x09);  /* 采样率 = 1k/(1+9) = 100 Hz */
MPU6050_WriteRegister(MPU6050_CONFIG,      0x06);  /* DLPF_CFG = 6 ⇒ 5 Hz 带宽 */
MPU6050_WriteRegister(MPU6050_GYRO_CONFIG, 0x18);  /* FS_SEL = 3 ⇒ ±2000 °/s */
MPU6050_WriteRegister(MPU6050_ACCEL_CONFIG,0x18);  /* AFS_SEL = 3 ⇒ ±16 g */
```

两处值得注意：

1. **`PWR_MGMT_1 = 0x00` 没有选时钟源**（bit2:0 = 000 ⇒ 内部 8 MHz RC 振荡器）。
   做姿态积分时，RC 时钟的温漂会直接体现为陀螺零偏漂移。常规做法是选 PLL（bit2:0 = 001，用 X 轴陀螺作参考）。
2. **±16 g + 5 Hz 带宽的组合对"测倾角"不理想**：
   - ±16 g 的灵敏度是 2048 LSB/g，±2 g 是 16384 LSB/g —— **分辨率损失 8 倍**
   - 5 Hz 低通在 100 Hz 采样下引入约 **30 ms 群延迟**（相位滞后）
   注释里写的"典型值 0x01(2G)"与实际写的 `0x18(16G)` 相差 8 倍，**注释容易误导读者以为用的是 2 g**。

**逐字节读的代价（判据 D6）**

`MPU6050_ReadData`（`:159-201`）对 6 个 16 位量做了 **12 次单字节读**：

```c
err |= MPU6050_ReadRegister(MPU6050_ACCEL_XOUT_H, &datah);
err |= MPU6050_ReadRegister(MPU6050_ACCEL_XOUT_L, &datal);
*pAccX = (datah << 8) | datal;
...
```

一次 `HAL_I2C_Mem_Read(..., 1 字节)` 的总线帧：

```text
S(1) + 从地址(9) + 寄存器(9) + Sr(1) + 从地址(9) + 数据(9) + P(1) = 39 位
```

100 kHz 下 = **390 µs/次**，12 次 = **4680 µs**。

而 burst 读（从 `0x3B` 连续读 14 字节，含温度与陀螺）：

```text
S(1) + 从地址(9) + 寄存器(9) + Sr(1) + 从地址(9) + 14×9 + P(1) = 156 位 = 1560 µs
```

| 方式 | 耗时 | 占 100 Hz 周期（10 ms） |
| --- | --- | --- |
| 逐字节 ×12 | 4680 µs | **46.8%** |
| burst ×1 | 1560 µs | 15.6% |

两个后果：

1. **时间预算**：逐字节读吃掉近一半的采样周期，剩下的时间还要做显示和别的任务。
   这还没算 `HAL_I2C_Mem_Read` 的软件开销。
2. **数据一致性（撕裂）**：高字节和低字节来自**两次独立事务**。
   MPU6050 的寄存器对在两次读之间可能被新采样覆盖 ⇒ 拼出来的 16 位值是"半新半旧"。
   **高速旋转时会出现偶发尖峰**，而且只在特定转速/相位下出现，极难复现。

> 数据手册明确要求 burst 读：一次事务内读完整组，寄存器在事务期间被锁存。
> **这条是本篇最可能在真实项目里造成实际故障的问题**——不是"算错了"，是"偶发一个尖峰"，
> 而尖峰进了姿态积分就会被放大。

### 17. `Init` 恒返回 0 与返回值/输出参数语义冲突

**问题一：`MPU6050_Init` 的返回值是假的**

```c
int MPU6050_Init(void)                          /* :116 */
{
    MPU6050_WriteRegister(MPU6050_PWR_MGMT_1, 0x00);   /* 返回值全部丢弃 */
    ...
    MPU6050_WriteRegister(MPU6050_ACCEL_CONFIG, 0x18);
    return 0;                                          /* 无条件成功 */
}
```

`MPU6050_WriteRegister` 返回 `HAL_I2C_Master_Transmit` 的结果（`HAL_OK=0`、`HAL_ERROR=1`、
`HAL_BUSY=2`、`HAL_TIMEOUT=3`），但六次调用**一次都没检查**。

后果：**I2C 总线断线、MPU6050 没接、地址错、供电不足 —— `MPU6050_Init()` 全部返回 0。**

对比同文件的 `MPU6050_GetID`（`:142`）会检查返回值并返回 `-1`。
所以调用方若按常规"`if (MPU6050_Init() != 0)` 判断初始化失败"，**永远不会进入错误分支**。

**问题二：`MPU6050_ReadData` 返回值与输出参数不一致**

```c
uint8_t datal, datah;          /* ← 未初始化 */
int err = 0;

err |= MPU6050_ReadRegister(MPU6050_ACCEL_XOUT_H, &datah);
err |= MPU6050_ReadRegister(MPU6050_ACCEL_XOUT_L, &datal);
if (pAccX)
    *pAccX = (datah << 8) | datal;      /* 读失败时 datah/datal 是栈上垃圾，照样拼 */
...
return err;
```

两个问题叠在一起：

- `datal`/`datah` **没有初始化**，读失败时 HAL 不保证写入 `*pdata`
- 无论成败，`*pAccX` 都被赋值

于是**函数返回错误码的同时，已经把垃圾值写进了所有输出参数**。
调用方即使检查了 `err`，也不能信任已经拿到的数据；若只检查 `err` 却仍使用了输出，
就会拿到随机值。正确做法是失败时**不写输出参数**，或先把输出置为安全值。

另外 `err |= ...` 把 12 次调用的状态码**按位或**在一起：`HAL_ERROR(1) | HAL_TIMEOUT(3)` = 3，
最终错误码无法区分"哪个寄存器失败了"。

### 18. 四个驱动的错误处理横评

| 驱动 | 函数 | 失效表现 | 能否被发现 |
| --- | --- | --- | --- |
| DHT11 | `DHT11_Read` | `-1` 截断成 0xFF 进入数据 | 靠校验和偶然拦住；合法量程内不触发 |
| DHT11 | `DHT11_Test` | 失败时屏幕保持上一帧 | **不能**（printf 被注释） |
| DS18B20 | `DS18B20_Read_RAM` | 无条件返回 0 | **不能** |
| DS18B20 | `DS18B20_Read_Temperature` | 负温输出 -127 °C 量级 | 能（数值荒谬，但可能被当成"传感器坏了"） |
| DS18B20 | `DS18B20_WaitReady` | 传感器不在时忙等 63 s | 能（卡死），但无法区分"慢"与"坏" |
| 光敏 | `LightSensor_Read` | 返回 `-1` | **能**（唯一正确报告失败的） |
| MPU6050 | `MPU6050_Init` | 恒返回 0 | **不能** |
| MPU6050 | `MPU6050_ReadData` | 返回错误码但输出参数已被污染 | 半能（检查返回值就不用输出，但常规写法会用） |

**只有光敏的 `LightSensor_Read` 做了正确的错误传播。** 其余七个函数各有不同的失效方式。

这张表是本节最有价值的产出：**它不是"驱动写得差"，而是"教学代码的错误处理优先级低于功能演示"**。
真实项目里必须自己补错误路径，不能直接复用。

## 系统调用/接口卡片

> 裸机环境没有"线程/进程安全"，对应位置改为**可重入性与中断安全**——这在本章的四个模块里
> 全部是"不可重入"：它们都直接操作共享的引脚/外设，且内部有 µs 级忙等。

### `DHT11_Read`

**作用**：发起一次完整的 DHT11 采集，返回湿度与温度。

**原型**：

```c
int DHT11_Read(int *hum, int *temp);        /* driver_dht11.h */
```

**参数**：

- `hum`：输出，湿度百分数（只含整数部分）
- `temp`：输出，温度摄氏度（只含整数部分）

**返回值和错误**：`0` 成功，`-1` 失败（无响应 / 超时 / 校验和错）。

**资源所有权**：无动态资源。占用 PA1 约 **25 ms**（20 ms 启动 + 传输），期间独占总线。

**可重入性与中断安全**：**不可重入**。`DHT11_Start` 的 `mdelay(20)` 依赖 TIM4 时基，
若在中断里调用会与主循环争用同一引脚。**必须在同一个上下文里调用完毕。**

**最小示例**：

```c
int hum, temp;
if (0 == DHT11_Read(&hum, &temp)) {
    /* 只有到这一支才能信任 hum/temp */
} else {
    /* 注意：失败时 hum/temp 的内容是未定义的，调用方不要读 */
}
```

**常见误用**：

- 失败后仍使用 `hum`/`temp` —— 输出参数在失败路径上未被赋值
- 循环里高频调用 —— 器件要求间隔 ≥ 1 s，驱动测试用 2 s
- 期望小数值 —— 驱动丢弃了小数部分（`*hum = hum_m`）

---

### `DS18B20_Read_Temperature`

**作用**：启动一次温度转换，等待完成，读回 9 字节 RAM 并换算成摄氏度。

**原型**：

```c
int DS18B20_Read_Temperature(double *temp);
```

**参数**：`temp`：输出，摄氏度（**负温时错误**，见 §12）。

**返回值和错误**：`0` 成功，`-1` 失败（复位失败 / 转换超时 / 读 RAM 失败）。

**资源所有权**：无动态资源。占用 PA1 **最长 750 ms**（12 bit 转换）+ 9 字节传输时间。

**可重入性与中断安全**：**不可重入**，理由同上。且 `WaitReady` 是纯忙等，
在 RTOS 里会独占 CPU 达数百毫秒，**必须先改造再移植**。

**最小示例**：

```c
double t;
if (0 == DS18B20_Read_Temperature(&t)) {
    /* 正温可用；负温请自行按 12 位补码重算（§12）*/
}
```

**常见误用**：

- 拿来测 0 °C 以下 —— 驱动输出 -127 °C 量级
- 信 `ram[8]` 被校验过 —— 从未使用
- 在 RTOS 任务里直接调用 —— 750 ms 忙等饿死其他任务
- 以为它和 DHT11 能同时接 —— 都占 PA1

---

### `LightSensor_Read`

**作用**：触发一次 ADC1_IN3（PA3）单次转换，取回 12 位原始码。

**原型**：

```c
int LightSensor_Read(uint32_t *pData);
```

**参数**：`pData`：输出，0~4095 的原始 ADC 码（**不是亮度值**）。

**返回值和错误**：`0` 成功，`-1` 转换超时（`LIGHT_SENSOR_ADC_TIMEOUT = 500 ms`）。

**资源所有权**：无。ADC1 由 `MX_ADC1_Init` 全局初始化，本函数不申请也不释放。

**可重入性与中断安全**：**不可重入**（共享 `hadc1` 句柄与 DR 寄存器）。
转换期间不得有别的代码读写 ADC1。

**最小示例**：

```c
uint32_t code;
if (0 == LightSensor_Read(&code))
    printf("adc=%u\n", (unsigned)code);      /* 方向未知，见 §15 */
```

**常见误用**：

- 把 `code` 当"亮度百分比"直接显示 —— 未经标定
- 假定 `code` 大 = 亮 —— 取决于分压中光敏电阻的位置
- 在本函数外调用 `HAL_ADC_Start` —— 会与句柄状态机冲突

### `MPU6050_Init`

**作用**：写 6 个配置寄存器，解除休眠并设定量程/采样率/DLPF。

**原型**：

```c
int MPU6050_Init(void);
```

**参数**：无。

**返回值和错误**：**恒返回 0**。六次 I2C 写的结果全部丢弃（§17）。

**资源所有权**：无。使用全局 `hi2c1`。

**可重入性与中断安全**：**不可重入**（共享 I2C1）。

**最小示例**：

```c
MPU6050_Init();                                   /* 返回值没有意义 */
if (MPU6050_GetID() != 0x68) {                    /* ← 真正能判存在性的调用 */
    /* 设备不在或总线异常 */
}
```

**常见误用**：

- `if (MPU6050_Init() != 0) { 报错 }` —— 永不成立
- 不校验 `WHO_AM_I` 就信任后续读数

### `MPU6050_ReadData`

**作用**：读 6 个 16 位量（加速度 XYZ、角速度 XYZ）。

**原型**：

```c
int MPU6050_ReadData(int16_t *pAccX, int16_t *pAccY, int16_t *pAccZ,
                     int16_t *pGyroX, int16_t *pGyroY, int16_t *pGyroZ);
```

**参数**：六个输出指针，**可以为 `NULL`**（内部有 `if (ptr)` 保护）。

**返回值和错误**：`0` 全部成功，非 0 = 12 次调用的状态码按位或（无法定位是哪一个失败）。

**资源所有权**：无。总线占用约 **4.7 ms**（§16 判据 D6）。

**可重入性与中断安全**：**不可重入**（共享 I2C1；且与 OLED 抢总线）。

**最小示例**：

```c
int16_t ax, ay, az, gx, gy, gz;
if (0 == MPU6050_ReadData(&ax, &ay, &az, &gx, &gy, &gz)) {
    /* 注意：这里只保证"12 次调用都返回 HAL_OK"，
       不保证高低字节来自同一次采样（§16 撕裂） */
}
```

**常见误用**：

- 失败时仍使用输出参数 —— 它们已被垃圾值写入
- 用返回值做错误定位 —— 按位或后信息丢失
- 在高速运动场景下直接用 —— 逐字节读有撕裂风险，应改 burst

**一次真实的判据推翻过程（方法记录）**

D4 首个版本写的是：

```c
/* 错误版：以为"256 种 check 值里有 1 种通过"就是 1/256 漏检 */
for (k = 0; k < 256; k++)
    if (dht11_checksum_as_written(0xFF, 0, 25, 0, (unsigned char)k))
        pass_cnt++;
CHECK(pass_cnt == 1, "...1/256 概率...");
```

运行结果 `pass_cnt = 0` ⇒ `CHECK` 判 `FAIL` ⇒ 整程序 `rc=1`。

原因：S = 0xFF + 25 = 280 > 255，而 `dht11_checksum_as_written` 做的是 `int` 比较 `280 == check`，
`check` 最大 255 ⇒ **无解**。

这暴露了我的两个错误：

1. 把"check 有 256 种取值"当成"总有一种能匹配"，忽略了比较的另一侧可能超出 255
2. 把"缺陷"直接等同于"高频误判"，没有先问"触发条件在真实量程内可达吗"

修正后 D4 变成 4 条判据，结论从"1/256 漏检"改为"**缺陷真实存在，但被 DHT11 的量程掩盖**"。

**这次翻车的价值大于任何一个 PASS**：如果只写注释而不写判据，
"1/256 漏检"这个错误结论会原样进入讲义并被记住。

## 常见错误和陷阱

| 陷阱 | 症状 | 根因 | 处理 |
| --- | --- | --- | --- |
| 把单总线引脚配成 `OUTPUT_PP` | DHT11 恒"无响应"，或长期对顶发热 | 推挽强推高电平，与设备拉低冲突 | 必须 `OUTPUT_OD` + `PULLUP`（§2） |
| 照抄教材"延时 20-40 µs 后读响应" | 偶发"没有响应"，重试就好 | 20 µs 时 DHT11 可能还没拉低 | 采样点移到 60 µs（§4） |
| DHT11 高频轮询 | 读数滞后、变化迟缓 | 器件采样率跟不上，返回旧值 | 周期 ≥ 1 s，驱动取 2 s（§6） |
| DHT11 读失败后仍用 `hum`/`temp` | 显示随机温湿度 | 失败路径不写输出参数 | 只在返回 0 时使用输出（§7） |
| 用 DS18B20 测 0 °C 以下 | 显示 -127 °C 量级 | 把补码当符号-数值（§12） | 按 12 位补码重算 |
| 以为 DS18B20 校验过数据 | 干扰环境下温度偶发跳变 | `ram[8]` CRC 从未使用 | 自行补 Dallas CRC8（§13） |
| 传感器没接时跑 `DS18B20_Read_Temperature` | 程序卡住约 1 分钟 | `WaitReady(1000000)` 每次迭代 63 µs（§10） | 缩短迭代次数或改超时口径 |
| 在 RTOS 任务里直接调 DS18B20 | 其他任务全部停顿 | 750 ms 纯忙等 | 改分次探测 + `vTaskDelay` |
| 把光敏 ADC 码当亮度百分比 | 显示"亮度"但方向可能是反的 | 分压方向未标定（§15） | 遮光/照光两点标定 |
| 只调 `LightSensor_Init` 就以为配好了引脚 | 换工程后 ADC 读到 0 或浮动值 | PA3 由 `MX_ADC1_Init` 配，不在本驱动（§14） | 确认 `adc.c` 的 MspInit |
| 把 ADC 改成连续转换后仍只 Start 不 Stop | ADC 一直被占用、DR 覆盖 | 单次模式才允许不 Stop（§14） | 连续模式必须 Stop |
| 用 `MPU6050_Init()` 返回值判断设备存在 | 永远"初始化成功" | 恒返回 0（§17） | 改查 `WHO_AM_I` |
| MPU6050 高速旋转时偶发尖峰 | 姿态积分被放大 | 逐字节读导致高低字节跨采样（§16） | 改 burst 读 14 字节 |
| MPU6050 返回错误后仍用输出参数 | 随机加速度值 | 失败时输出已写入栈垃圾（§17） | 检查返回值则不使用输出 |
| DHT11 与 DS18B20 同时接 | 两者都读不到，或时好时坏 | 共用 PA1，两个开漏叠加（§2） | 一次只接一个 |

## 故障排查方法

按"先分接口层、再分数据层"的顺序，每步都有可执行的判据。

**第一步：确定是电气、时序、还是解码**

```text
能读到数据（哪怕数值荒谬）？
├── 否 → 电气 / 时序问题（第二节）
│     ├── 用万用表量 DQ/PA1 空闲电平：应为 3.3 V
│     │     └── 是 0 V → 引脚被配成推挽输出 0，或总线短路
│     ├── 量上拉电阻：模块应为 4.7 kΩ 左右
│     └── 有示波器 → 抓三段：启动低 20 ms / 响应低 80 µs / 位时隙 50 µs
└── 是 → 数据层问题（第三节）
      ├── 数值荒谬但稳定 → 解码算法（先查负温补码）
      ├── 数值偶发跳变 → 校验缺失 / 撕裂（DS18B20 CRC、MPU6050 burst）
      └── 数值滞后 → 采样周期过短
```

**第二步（DHT11/DS18B20）：用"人为制造已知错误"确认判据有效**

在 `DHT11_Read` 前把总线强制拉低 50 ms（模拟设备不响应）：

- 若返回 `-1` ⇒ 错误检测有效
- 若返回 0 并给出湿度 255 ⇒ 撞上 §7 的截断缺陷

**第三步（DS18B20）：用两点法验证温度解码**

| 测试 | 预期（修正后） | 预期（当前驱动） |
| --- | --- | --- |
| 室温 | +20~30 °C | 同左（正温正确） |
| 冰水混合物 | ≈ 0 °C | 接近 0（若为 -0.5 则已是负温 ⇒ 跳到 -127） |
| 加盐冰 | -5~-10 °C | **-100 °C 量级** |

**第三步是本节最省时间的验证**：一杯冰水加盐就能把 §12 的缺陷变成可见读数。

**第四步（光敏）：两点标定**

```text
遮住传感器 → 记录 code_dark
手电直照   → 记录 code_bright
若 code_bright > code_dark  ⇒ 光敏电阻在分压下臂，读数随亮度增大
若 code_bright < code_dark  ⇒ 光敏电阻在分压上臂，读数随亮度减小
```

**第五步（MPU6050）：区分"接线错"与"读法错"**

```text
MPU6050_GetID() == 0x68 ?
├── 否 → 接线 / 地址 / I2C 时钟（与 OLED 共用总线，先确认 OLED 能显示）
└── 是 → 设备在线。此时若数据有尖峰：
      ├── 静止时也有 → 逐字节读撕裂（D6），改 burst
      └── 只有运动时 → 量程 / DLPF 配置（±16 g + 5 Hz）
```

**第六步：与主机判据对账**

改动任何驱动后，先跑

```bash
cd notes/F103_HAL入门/lab_sensor && ./build.sh
```

若 30 条判据中有变化，说明改到了算术部分。**这一步不需要开发板，比烧写快两个数量级。**
