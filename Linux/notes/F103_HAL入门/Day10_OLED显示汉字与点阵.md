## 核心概念

### 1. 一个字节 = 一列 8 个像素，**bit0 在最上面**

教材 8.5.1：屏是 128×64，每个像素 1 bit；GDDRAM 分 64 行 × 128 列，这 64 行又分 8 页，
每页 8 行。**写在 GDDRAM 里的第 1 个字节对应左上角第 1 列的 8 个像素**。

```text
       列 0   列 1   列 2  ...  列 127
      ┌──────────────────────────────┐
page0 │ byte  byte  byte       byte  │  行 0..7     ┐
page1 │ byte  byte  byte       byte  │  行 8..15    │
page2 │ byte  byte  byte       byte  │  行 16..23   │ 8 页
  ⋮   │  ⋮     ⋮     ⋮          ⋮    │              │
page7 │ byte  byte  byte       byte  │  行 56..63   ┘
      └──────────────────────────────┘
              ↑ 每格 = 1 字节 = 一列 8 个像素的开关
```

字节内部的方向，教材写的是"bit7 对应第 7 行，bit0 对应第 0 行"。**第 0 行是页内最上面那一行**，
所以等价于一句话：**bit0 在上，bit7 在下**。

这一条是整篇的地基，也是最容易搞反的一条。用本工程的 `ascii_font` 里 `'A'` 的字模可以自己验：

```c
{0x00,0x00,0xC0,0x38,0xE0,0x00,0x00,0x00,   /* 上半页：列 0..7 */
 0x20,0x3C,0x23,0x02,0x02,0x27,0x38,0x20}   /* 下半页：列 0..7 */
```

按 **bit0 在上** 展开上半页：列 2 = `0xC0` = bit6/bit7 → 页内第 6、7 行；列 3 = `0x38` =
bit3/4/5 → 第 3、4、5 行；列 4 = `0xE0` = bit5/6/7 → 第 5、6、7 行。
三列合起来是"中间窄、两侧低"的 **A 的尖顶**，尖在列 3 的第 3 行。
按 **bit7 在上** 展开则变成"两侧在第 0 行、中间在第 2 行"的**倒 U**，不是 `'A'`。

光靠推理不够直观。本篇的最小实验把它变成可观测量：

```text
$ ./render_hanzi                 # bit0 在上（SSD1306 约定）
################
.......#........
......#.........
.....#..........
..###########...
..#.........#...
..#.........#...
..#.........#...   ← page y 结束
..#.........#...
..###########...
..#.........#...
..#.........#...
..#.........#...
..#.........#...
..###########...
..#.........#...

$ ./render_hanzi --msb           # bit7 在上（错的方向）
..#.........#...
..#.........#...
..###########...
.....#..........
......#.........
.......#.........
###############.
................   ← "百" 的顶横跑到了页底，整体上下颠倒
```

**同一份点阵，换个方向位就成了另一个东西。** 移植别的屏（有些屏 MSB 在上）时，这条差异必须先在
纸上算清，不能靠"试出来"。

### 2. 汉字为什么是 32 字节：16 列 × 2 页

一个字宽 16 像素 = 16 列 = 16 个字节；高 16 像素必须跨 **两页**（每页只有 8 行）。
所以：

```text
32 字节 = upper[0..15]（page y 的 16 列） + lower[0..15]（page y+1 的 16 列）
```

教材 8.5.4 那句"上半部的第 1 列对应点阵数据里第 1 个字节，下半部的第 1 列对应第 17 个字节"
说的就是这件事——**先按列把上半部分写满 16 个，再写下半部分**，而不是"一个字节的高 4 位 / 低 4 位"。

对照本工程的 ASCII 字模 `ascii_font[128][16]`：宽 8 像素 = 8 列 = 8 字节上半 + 8 字节下半。
`OLED_PutChar` 因此写 `[c][0..7]` 到 `page`、`[c][8..15]` 到 `page+1`（`driver_oled.c:542-545`）。
**两种字号用的是同一条布局规则，只是列数不同。** 记住这条，就不用为汉字另学一套。

### 3. 页地址模式：写完 128 列会绕回同页开头

教材 8.5.2 的三种模式，差别只在"地址怎么自增"：

| 模式 | 每写 1 字节 | 走到最右列后 |
| --- | --- | --- |
| 页地址（本工程用） | 列 + 1 | **回到第 0 列，页不变** |
| 行地址 | 列 + 1 | 列回 0，页 + 1 |
| 列地址 | 页 + 1 | 页回 0，列 + 1 |

页模式的"列回 0、页不变"这一点很关键：**它不会替你换页**。所以画完上半页必须显式重发
"设置页地址 + 设置列地址"两条命令，这正是 `OLED_PutChar` 里那两次 `OLED_SetPosition` 的理由，
也是我的 `OLED_PutHanzi16` 里两次 `OLED_SetPosition` 的理由。

命令本身的编码（`driver_oled.c:265-334`）：

```c
OLED_SetColAddr_PAGE(addr):
    0x00 | (addr & 0x0F)     /* 低 4 位 → 命令 0x0x */
    0x10 | (addr >> 4)       /* 高 4 位 → 命令 0x1x */
OLED_SetPageAddr_PAGE(addr):
    0xB0 | addr              /* 0xB0..0xB7 选页 0..7，addr > 7 静默返回 */
```

**一条 `OLED_SetPosition(page, col)` 实际是 3 次 I2C 传输**（低列、高列、页），
这一点在算耗时时必须计入。

### 4. Control byte：0x00 是命令，0x40 是数据

Day09 §7 已经给出位定义，这里只补一个字模相关的用法：一个汉字的两次写作是

```text
[0x78] [0x00] [0xB0|page]                 ← 命令：设页
[0x78] [0x00] [0x00|lo] [0x00] [0x10|hi]  ← 命令：设列（driver_oled.c 里是两次独立传输）
[0x78] [0x40] [upper 16 字节]             ← 数据：一整页的 16 列
[0x78] [0x00] [0xB0|page+1]               ← 命令：设下一页
[0x78] [0x00] [0x00|lo] [0x00] [0x10|hi]  ← 命令：同一列范围
[0x78] [0x40] [lower 16 字节]             ← 数据
```

注意数据那两次：**16 个字节一次传完**，而不是逐列传。页模式的地址自增会替我们把列号从 `col`
推到 `col+15`；一次传完还顺带消掉了一个隐患——逐列传时如果中途失败，屏幕上会出现"半个字"。

### 5. 两套坐标系：ASCII 用字符格，汉字用像素列

这是本工程里最容易错的地方，因为它**不会报错，只会画歪**：

| | 宽 | 参数语义 | 合法范围 |
| --- | --- | --- | --- |
| `OLED_PutChar(x, y, c)` | 8 px | `x` = **字符格**，内部 `col = x*8` | `x` 0..15，`y` 0..7 |
| `OLED_PrintHanzi(page, col, s)` | 16 px | `col` = **像素列** | `col` 0..112，步长 16 |

一行 128 像素：ASCII 放 **16 个**，汉字放 **8 个**。所以"第 3 个汉字"的 `col` 是 48 而不是 3。
混排时（本篇的 `OLED_Hanzi_Test` 就是这样）必须自己换算：

```c
OLED_PrintString(0, 0, "DShanMCU-103");   /* 12 个字符格 = 96 像素 */
OLED_PrintHanzi(2, 0, "百问网");          /* 48 像素，占满 page 2..3 */
OLED_PrintString(4, 0, "16x16 hanzi");    /* 换到 page 4..5 */
```

教材 8.5 的示例程序只显示汉字，没有混排，所以这一层换算它没讲。

### 6. 取字方式：教材按"字节"取，我们要按"码点"取

教材的 Keil 工程里，源码文件通常是 **GB2312** 编码：

```c
OLED_ShowCHinese(0, 0, 0);      /* "第 0 个字"——按数组下标取 */
```

**下标即编号**，因为 GB2312 里一个汉字正好 2 字节，`"百问网"` 的长度是 6，下标 0/1/2 各对一字。

本工程的源码文件是 **UTF-8**（Linux/GCC 默认），一个汉字是 **3 字节**：

```text
$ printf '百问网' | od -An -tx1
 e7 99 be e9 97 ae e7 bd 91
 └─"百"─┘ └─"问"─┘ └─"网"─┘
```

按字节切会把汉字切碎（`"百问网"[1]` 是 `0x99`，一个非法首字节）。所以正确做法是
**先解码出 Unicode 码点，再按码点查表**，这就是 `Hanzi16_Find(cp)` 的接口形状：

```text
e7 99 be  ──UTF-8 解码──▶  U+767E  ──查表──▶  upper/lower 共 32 字节
```

码点可以自己算（进阶练习）：
`0xE7 = 1110_0111` → 取低 4 位 `0111`；`0x99` → `011001`；`0xBE` → `111110`；
拼成 `0111 011001 111110` = `0x767E`。三个字分别是 `U+767E` / `U+95EE` / `U+7F51`，
已写入 `hanzi_font.c` 的 `code` 字段。

**换了编码，扫字符串的算法就得换。** 这一条也是"课程代码在 Keil 能跑、搬到 GCC 就错位"的常见原因之一。

### 7. 96 字节很便宜，3500 字就装不下了

三个字 = 3 × 32 = **96 字节**。看起来免费。但按同一单价推：

```text
3500 个常用汉字 × 32 B = 112 000 B ≈ 109 KB
GB2312 一级+二级 6763 字 × 32 B = 216 416 B ≈ 211 KB
本工程当前固件占用：.text 17 088 B + .rodata 2 284 B ≈ 18.9 KB（LAB_TEST=12）
STM32F103C8T6 的 Flash：64 KB
```

结论：**整本字库放不进片内 Flash**。三条出路（教材没讲，属于本工程的拓展）：

1. **子集字库**：只取界面用到的几十个汉字，像本篇这样按码点列表，几十到几百字节。
2. **外部 Flash**：本板有 W25Q64（8 MB，M12 模块），字库放那里，按需读 32 字节（Day12 的主题）。
3. **点阵压缩**：16×16 汉字常有大量空行，游程编码或取半宽字（16×8）能压到 1/2 以下，
   代价是解码时间。

本篇选第 1 条——因为它同时把"码点查表"这个接口立起来了，后面换任何字库来源，调用方都不用改。

### 8. 3 次传输还是 6 次：两条写法都合法，代价不同

`OLED_PutChar` 画一个 ASCII 字符是 6 次 I2C 传输（Day06 §3 数过）。
我的 `OLED_PutHanzi16` 是：

| 步骤 | 传输次数 | 每次字节数 |
| --- | --- | --- |
| `OLED_SetPosition(page, col)` | 3 | 各 2（控制字节 + 命令） |
| 写 `upper` 16 字节 | 1 | 17（控制字节 + 16 数据） |
| `OLED_SetPosition(page+1, col)` | 3 | 各 2 |
| 写 `lower` 16 字节 | 1 | 17 |
| **合计** | **8 次** | 42 字节 |

按 Day09 §9 的算法（每字节 9 个 SCL，100 kHz 下每 SCL 10 µs）：

```text
42 × 9 = 378 个 SCL ≈ 3.8 ms/汉字     （理论估算，未用逻辑分析仪测）
8 个汉字一行 ≈ 30 ms
```

对照 `OLED_PrintString` 一行 16 字符 ≈ 46 ms（Day06）。**同样一屏信息量，汉字的实际耗时更低**——
因为一个汉字顶两个字符格，而传输次数的增量（8 vs 3）远小于列数增量（16 vs 8）带来的收益。
这个结论只在"用页模式、两页各一次写完"的前提下成立；若按教材那样逐列写 32 字节，
传输次数会涨到 30 次以上，优势就没了。

## 系统调用/接口卡片

### `void OLED_SetPosition(uint8_t page, uint8_t col)`

作用：页地址模式下设置起始页与起始列。

参数：`page` 0..7（`> 7` 静默返回，但**列地址仍然会被写入**，这是 Day06 §2 那个 `y=7` 缺陷的成因）；
`col` 0..127（`> 0x7F` 静默返回）。

返回值和错误：`void`，越界不报错。

资源所有权：无。

常见误用：以为它一次设置好两页——它只设一页，页模式的地址自增**不会跨页**。

### `HAL_StatusTypeDef HAL_I2C_Mem_Write(..., uint16_t MemAddress, uint16_t MemAddSize, uint8_t *pData, uint16_t Size, uint32_t Timeout)`

作用：在设备地址后先发 `MemAddress`，再发 `Size` 字节数据。

参数：对 SSD1306，`MemAddress` 位置放的是 **Control byte**（`0x40` = 后续是显存数据），
不是寄存器地址——与 `driver_mpu6050.c` 里 `Mem_Read(..., reg, ...)` 的语义不同（Day09 §6）。

返回值和错误：`HAL_OK` / `HAL_ERROR`（含 `AF` 无应答）/ `HAL_BUSY` / `HAL_TIMEOUT`。

常见误用：`Size + 1` 超过 255（F1 的 I2C 单次传输受 `uint8_t` 计数限制）；忽略返回值。

### `int OLED_PrintHanzi(uint8_t page, uint8_t col, const char *utf8)`（本篇新增）

作用：按 UTF-8 解码后逐字绘制 16×16 汉字；`'\n'` 换到下一组页（`page += 2`），
列不够 16 时自动换行。

参数：`page` 0..6（要留 `page+1`）；`col` 0..112、须 8 对齐。

返回值和错误：返回画出的字形数；**不返回错误**——未收录的码点画空心方框，非法 UTF-8 序列停止扫描。
设计理由：显示函数不该因为一个字缺失就中断整行。

常见误用：把 `page` 当"行号"（一行 = 2 页）；传给它的字符串在中断里构造（`snprintf` 会阻塞）。

### `void OLED_PutHanzi16(uint8_t page, uint8_t col, const void *g)`（本篇新增）

作用：画单个字形，`g == NULL` 时画 16×16 空心方框。

参数：`g` 由 `Hanzi16_Find(cp)` 提供。用 `const void *` 是为了让头文件不依赖 `hanzi_font.h`，
代价是丢掉类型检查——这是本篇的一处取舍，不是最佳实践。

返回值和错误：`void`；`page + 1 > 7` 或 `col > 127` 时直接返回，不写半屏。

### `const hanzi16_t *Hanzi16_Find(uint16_t code)`

作用：按 Unicode 码点线性查表。

返回值和错误：命中返回指针，未命中返回 `NULL`。

性能：3 个字的表线性扫一遍是 3 次比较。若字库扩到几百字，应改成按码点排序 + 二分，
或建 256 项一级索引——**当前实现没有做，因为 3 个字不值得**（YAGNI）。

## 常见错误和陷阱

| 陷阱 | 症状 | 根因 | 处理 |
| --- | --- | --- | --- |
| 位序搞反（当作 bit7 在上） | 字形上下颠倒，像镜面 | 不同屏/取模软件的 MSB、LSB 约定不同 | 用 `--msb` 对照一次，或纸上按 bit0 展开 |
| `upper` / `lower` 写反 | 字被从中间横切成两半并对调 | 教材的"第 17 个字节"讲的就是下半从 16 开始 | 前 16 字节给 `page`，后 16 给 `page+1` |
| 汉字用 `x*8` 算列 | 每个字只占半宽、相邻字互相覆盖 | ASCII 是字符格，汉字是像素列 | 汉字 `col` 直接给像素，步长 16 |
| `page` 取 7 | 只显示上半截 | 页模式不跨页，`page+1=8` 被静默拒绝 | 允许范围 0..6 |
| 按字节切 UTF-8 字符串 | 方框 + 整行错位 | 汉字 3 字节，`"百问网"[1]` 是续字节 | 先解码码点再查表 |
| 把 `MemAddress` 写成寄存器号 | 屏不响应或花屏 | SSD1306 此处是 Control byte（0x40） | 命令 0x00、数据 0x40 |
| 逐列写 32 字节 | 偶发"半个字"、耗时长 4 倍 | 每次传输都要重新设列地址 | 一整页 16 字节一次写完 |
| 字库想放全量汉字 | 链接报 Flash 溢出 | 3500 字 ≈ 109 KB > 64 KB | 子集 / 外部 Flash / 压缩 |
| 在 ISR 里调 `OLED_PrintHanzi` | 系统卡顿、丢中断 | 一个字 ≈ 3.8 ms（估算） | ISR 只置标志 |

## 故障排查方法

"汉字显示不对"要分三层查，**每层只看一个证据**：

1. **有没有东西出来**。
   - 全黑 → 回到 Day09 §故障排查第 1、2 步（电平、`IsDeviceReady`），先确认屏在线；
   - 有方框 → 屏和总线都正常，**问题在字库查表**（码点没命中）。打一行
     `printf("cp=%04X\n", cp)` 看解出来的码点是否等于 `0x767E`。
2. **字的方向对不对**。
   - 上下颠倒 → 位序（本篇 §1）；
   - 上下半对调 → `upper`/`lower` 切分（§2）；
   - 左右镜像 → 取模软件设了"反向"，重新生成时改设置，别在代码里补。
3. **位置对不对**。
   - 每个字只画了一半、或相邻字重叠 → `col` 用了字符格（§5）；
   - 画到页外、只剩上半截 → `page` 取 7 或 `col` 越界，`SetPosition` 是静默失败，不会报错。

第 1 步的"方框"是设计出来的诊断信号：**没有方框说明根本没写进显存，有方框说明写进去了只是没查到字**。
把这两种失败分开，比只看"屏上是空的"快得多。

## 练习题

### 基础题

题目：从教材 8.5.4 的「问」字点阵出发，写出它 `upper[0..15]` 与 `lower[0..15]` 的分界在第几个字节，
并说明「问」的第 1 列在屏幕上会点亮哪几行（页内行号）。

```c
{0x00,0xF8,0x01,0x02,0x00,0xE2,0x22,0x22,0x22,0xE2,0x02,0x02,0x02,0xFE,0x00,0x00},
{0x00,0xFF,0x00,0x00,0x00,0x1F,0x08,0x08,0x08,0x1F,0x00,0x40,0x80,0x7F,0x00,0x00},
```

提示：分界在第 16/17 字节之间；`0x00` 表示该列 8 行全灭；用 `render_hanzi` 验证。

验收标准：能指出前 16 字节属于 `page`、后 16 属于 `page+1`；能说出第 1 列（`0x00`）
上下半页都不点亮，第 2 列 `0xF8`（bit3..7）点亮下半页的第 3..7 行。

### 改错题

题目：下面的函数"能把点阵写进去，但屏幕上的字是横切成两半并对调的"，指出问题并修正。

```c
static void put_glyph(uint8_t x, uint8_t y, const hanzi16_t *g)
{
    OLED_SetPosition(y, x * 8);
    HAL_I2C_Mem_Write(&hi2c1, 0x78, 0x40, I2C_MEMADD_SIZE_8BIT,
                      (uint8_t *)g->lower, 16, 500);
    OLED_SetPosition(y + 1, x * 8);
    HAL_I2C_Mem_Write(&hi2c1, 0x78, 0x40, I2C_MEMADD_SIZE_8BIT,
                      (uint8_t *)g->upper, 16, 500);
}
```

提示：① `upper` 与 `lower` 谁该在 `page`；② 调用方按"字符格"传 `x` 时，汉字实际只占了 8 列。

验收标准：能指出 `upper`/`lower` 对调，并且 `x * 8` 会让 16 列宽的字只画 8 列、右边 8 列不刷新
（与上一行残留混在一起，看起来像"字被挤扁"）；给出把 `col` 改成像素列、步长 16 的修正。

### 综合题

题目：设计一个"一行 4 个汉字 + 每字后面跟一个小 ASCII 数字"的混排布局，
要求：① 给出的坐标换算能同时支持 `OLED_PrintString` 与 `OLED_PrintHanzi`；
② 说明 4 组内容共需多少个像素列、是否放得下一行；
③ 若要把字库扩到 200 个汉字，给出 Flash 预算与"要不要改查表策略"的判断。

提示：汉字 16 px + ASCII 8 px = 24 px/组；128/24 = 5 组余 8 px。200 × 32 B = 6400 B。
查表 200 次线性比较在每次刷新时的成本要用"多少个 SCL 周期"来比。

验收标准：能写出 `col = i * 24` 的换算并说明第 5 组会溢出必须换行；
能算出 200 字占 6.25 KB、相对当前 64 KB Flash 的占比与余量；
能判断"200 次比较 ≈ 微秒级，远小于一个汉字 3.8 ms 的 I2C 时间"，因此**不必**改二分——
判据是"优化成本 vs 优化收益"，不是"有没有更快的算法"。
