## 核心概念

### 1. 教材写下的契约，只有两句

教材 §11.1 的原文是这两句，其余都是表格：

> "这些驱动程序依赖于 STM32CubeMX 提供的初始化代码。比如 `driver_oled.c` 里面要使用 I2C1 通道，
> I2C1 的初始化代码是 STM32CubeMX 生成的：`MX_I2C1_Init` 被用来初始化 I2C1 本身，
> `HAL_I2C_MspInit` 被用来初始化 I2C 引脚。`driver_oled.c` 只使用 I2C1 的函数收发数据，
> **它不涉及 I2C1 的初始化**。"
>
> "观看模块的头文件就可以知道接口函数的用法，每个驱动文件里都有一个测试函数，
> 参考测试函数也可以知道怎么使用这个驱动。"

把这两句拆成可验证的命题：

| 教材的命题 | 可验证形式 | 本篇结论 |
| --- | --- | --- |
| 驱动不做外设的初始化 | 驱动里有无 `__HAL_RCC_xxx_CLK_ENABLE`、`HAL_xxx_Init` | **对**，20 个驱动只有 1 处时钟使能 |
| 驱动不做引脚的初始化 | 驱动里有无 `HAL_GPIO_Init` | **不成立**，6 个驱动会自己配引脚 |
| 每个驱动都有测试函数 | 驱动里有无 `*_Test` | **基本对**，20 个里有 19 个 |

第二行是关键：教材那句话只举了 I2C 的例子，而 GPIO 类驱动会自己重配引脚。
所以"依赖 CubeMX"这件事**按外设类型分档**，不是一刀切——见 §2。

### 2. 三个层次的责任划分

接入一个模块要动三样东西：**外设本体**（时钟、控制寄存器）、**引脚**（模式、复用、上下拉）、
**数据**（协议收发）。这套库把三者的责任分得很清楚，而且可以用一行命令证明：

```text
$ grep -nE "__HAL_RCC_[A-Z0-9]+_CLK_ENABLE" Drivers/DshanMCU-F103/*.c
driver_led.c:55:    __HAL_RCC_GPIOC_CLK_ENABLE()
```

**20 个驱动、75 个公开函数，只有这一处时钟使能。** 没有任何驱动开过 TIM/I2C/SPI/USART 的时钟。

责任表（每行都有对应的 grep 判据）：

| 层次 | 谁负责 | 判据命令 | 结果 |
| --- | --- | --- | --- |
| 外设时钟 | CubeMX 的 `MspInit` | `grep -c "__HAL_RCC_TIM\\|__HAL_RCC_I2C\\|__HAL_RCC_SPI" Drivers/*/*.c` | 0 |
| 外设本体配置 | CubeMX 的 `MX_xxx_Init` | 驱动里有无 `HAL_xxx_Init`（非 GPIO） | 有 2 处（`HAL_TIM_Base_Init`） |
| 引脚模式 | **混合**：6 个驱动自己配，14 个全靠 CubeMX | `grep -l HAL_GPIO_Init driver_*.c` | 6 个 |
| GPIO 端口时钟 | 全部由 CubeMX 提供 | 见上面的唯一一处 | 只有 `driver_led.c` 例外 |
| 数据收发 | 驱动 | —— | —— |

**"配寄存器"和"开时钟"是两件事**——Day13 §8 已经用 `PassiveBuzzer_Init` 证明过一次
（它调 `TIM_Base_SetConfig` 却不触发 `HAL_TIM_Base_MspInit`，时钟不开）。这里把结论推广到整个库：

> 这套库的惯例是：**可以重配引脚，从不主动开时钟**。
> 所以"我把 driver_xxx.c 拷进我的工程"永远是半句话——还得把对应的
> `__HAL_RCC_xxx_CLK_ENABLE` 补上，而驱动不会提醒你，HAL 也不会报错。

`driver_led.c:41-42` 的注释正好说明了这个例外的原因：

```c
 * 功能描述： LED初始化函数, 在HAL的初始化代码里已经配置好了GPIO引脚,
 *            但是为了不依赖于stm32cubemx, 此函数也实现了GPIO的配置
```

**LED 是唯一一个"为了不依赖 CubeMX"而自开时钟的驱动**——它是开机第一个能跑的模块（`LAB_TEST=0`），
必须能独立工作。其余模块都假定"CubeMX 已经把地基铺好了"。

### 3. 「17 / 19 / 20 / 22」四个数字的对账

这套库的文件数经常被说错，四个数字都是对的，但指的是不同东西：

```text
22 个 .c 文件  = 20 个带同名 .h 的驱动 + driver_irq.c（中断分发）+ ascii_font.c（字模数据）
20 个 .h      = 19 个有 Test 的驱动 + driver_timer.c（udelay/mdelay/system_get_ns，基础设施）
19 个模块     = 20 个头文件 - driver_timer        ← "19 模块驱动表" 的口径
17 行         = 教材 §11.1 的表行数（LED … 直流电机）
```

差集是 `driver_lcd.c` 与 `driver_uart.c`：**有驱动、有 `Test()`、有版权头（百问科技 2023.08.04），
但教材第 11 章没有对应小节**（10.3 到 10.19 共 17 节，没有 LCD 和 UART）。
`driver_lcd.c` 的 `Test` 在 `main.c` 里被标注为"LCD 驱动是 OLED 的别名封装，与 12 同效"。

扫描器把这件事直接打了出来：

```text
== 与教材第 11 章表的对账 ==
  教材 §11.1 表            : 17 行（LED … 直流电机）
  本库带 Test 的驱动       : 19 个 = 20 个头文件 - driver_timer（基础设施，无 Init/Test）
  差集                     : driver_lcd、driver_uart —— 有驱动、有 Test，但教材第 11 章无对应小节
  => “19 模块”的口径 = 带 Test 函数的驱动数，不是教材表的行数；两个数都对，指的不是同一批文件。
```

**为什么要较这个真**：说"学了 19 个模块"而教材只讲 17 个，面试官翻书就会发现对不上；
说"17 个"又漏了两个能跑的驱动。正确的说法是"教材 17 节，库里 19 个带自测的驱动，
多出的 LCD 与 UART 没有教材小节，是我按头文件契约接入的"。

### 4. 三函数骨架与返回类型的两套约定

除 OLED/LCD（9 个和 8 个函数）与 W25Q64（5 个）外，**每个驱动都是同一个形状**：

```text
Xxx_Init(void)          —— 初始化：配引脚 / 记句柄
Xxx_<动作>(...)         —— 唯一一个业务函数：读值 或 设值
Xxx_Test(void)          —— 自测：一个可观察的现象
```

75 个公开函数的返回类型分布（扫描实测）：

| 返回类型 | 个数 | 占比 | 例子 |
| --- | --- | --- | --- |
| `void` | 52 | 69% | `DHT11_Init`、`IRSender_Write`、`Motor_SetSpeed` |
| `int` | 21 | 28% | `Led_Init`、`Key_Read`、`W25Q64_Write`、`MPU6050_Init` |
| 其它 | 2 | 3% | `const char *IRReceiver_CodeToString`、`uint64_t system_get_ns` |

**同一个语义动作，两种约定并存**：

```c
int  Led_Init(void);      /* 能报错 */
void DHT11_Init(void);    /* 不能报错 */
```

这不是笔误，而是"越靠近 GPIO 的驱动越可能返回 `int`"这个倾向的残留：
`Led_Init` 返回 `int`，`ActiveBuzzer_Init`/`ColorLED_Init`/`Motor_Init` 却返回 `void`。

代价很具体：`DHT11_Init` 里 `HAL_GPIO_Init` 不可能失败（HAL 对 GPIO 无条件返回成功），
所以返回 `void` 在这里**确实是合理的**；但 `MPU6050_Init` 返回 `int` 是因为 I2C 可能失败——
**判断标准应是"底层操作能否失败"，而不是统一改成某个类型**。这条判据 Day07（UART）、Day09（I2C）
已经分别用过一次。

### 5. `DeInit` 一个都没有：资源归谁

```text
$ grep -c "DeInit" Drivers/DshanMCU-F103/*.h | grep -v ":0"
（无输出 —— 20 个头文件里没有任何 DeInit 声明）

$ grep -l "DeInit" Drivers/DshanMCU-F103/*.c
driver_ir_sender.c
driver_passive_buzzer.c      ← 这两个是调用 HAL_TIM_Base_DeInit，不是自己的反初始化
```

所以 **0/20**。对比一下 `Core/Src/tim.c`：CubeMX 生成了 `HAL_TIM_Base_MspDeInit`（`tim.c:325`），
但它**只做了一件事**——`__HAL_RCC_TIM1/2_CLK_DISABLE()`，**没有复位引脚**（没有 `HAL_GPIO_DeInit`）：

```c
/* tim.c:325-350，TIM1 / TIM2 两个分支完全同构，各一行 */
void HAL_TIM_Base_MspDeInit(TIM_HandleTypeDef* tim_baseHandle)
{
  if (tim_baseHandle->Instance == TIM1) {
    __HAL_RCC_TIM1_CLK_DISABLE();
  } else if (...) { ... }
}
```

也就是说：**CubeMX 侧的 `DeInit` 本来就不归还引脚**，驱动侧连 `DeInit` 都没有。两头都不还。

三档状态在"资源归还"这件事上的分工：

| 场景 | 谁负责归还 | 后果 |
| --- | --- | --- |
| 上电跑一次就复位 | 没人，也不需要 | 无 |
| 一个模块用完切另一个 | 新模块的 `Init` 覆盖引脚 | 旧模块的时钟仍在跑，功耗不归零 |
| 出错后要恢复到安全状态 | **没人** | 引脚停在上次的状态 |

第 3 行是真正的风险。Day13 的 `ColorLED_Set` 每次先 `HAL_TIM_PWM_Stop` 三通道再重配，
说明作者知道"改配置前要先停"——但那是**同一个模块内**的自我保护，跨模块没有对称的机制。
`Motor_SetSpeed` 之后想"把电机停下来"只能靠 `SetSpeed(0)`，不能靠 `Motor_DeInit`。

**本篇不补 `DeInit`**，理由与 Day12 一致：没有真板，写完无法验证"关掉时钟后引脚是否真的回到
输入态"，按 §1.1 不能记为已完成。它作为改错题留在 §练习题。

### 6. 引脚冲突：五组已核实的争用

模块能否共存，最终由引脚决定。以下五组全部来自源码（去注释后 grep 宏定义或 `HAL_GPIO_Init`），
**不是上板现象**：

| 冲突对 | 引脚 | 证据 | 现象 |
| --- | --- | --- | --- |
| 有源蜂鸣器 / 无源蜂鸣器 / 红外发射 | PA8 | `driver_active_buzzer.c`（`GPIOA, GPIO_PIN_8`）、`driver_passive_buzzer.c`（TIM1_CH1）、`driver_ir_sender.c`（TIM1_CH1） | 三方争用，后初始化者覆盖 |
| DS18B20 / DHT11 | PA1 | 两个 `.c` 都是 `GPIOA, GPIO_PIN_1` | 单总线，两种时序无法并存 |
| W25Q64 / HC-SR04 | PB9 | `driver_spiflash_w25q64.c:50`（CS）、`driver_ultrasonic_sr04.c:41`（TRIG） | **反相位**：CS 低有效、TRIG 高有效 |
| 全彩 LED / JTAG | PA15、PB3 | 教材 §11.2 + `driver_color_led.c` 走 TIM2 重映射 | 没配 `SWJ_CFG` 时归调试口 |
| 直流电机 / JTAG | PB4 | 教材 §11.2 + `driver_motor.c` 走 TIM3 重映射 | 同上 |

第 3 行值得单独讲，因为它是**极性相反**的冲突，比同极性冲突更隐蔽：

```c
/* driver_spiflash_w25q64.c:65,80 */
HAL_GPIO_WritePin(W25Q64_CS_GPIO_GROUP, W25Q64_CS_GPIO_PIN, GPIO_PIN_RESET);  /* 选中：低 */
HAL_GPIO_WritePin(W25Q64_CS_GPIO_GROUP, W25Q64_CS_GPIO_PIN, GPIO_PIN_SET);    /* 释放：高 */

/* driver_ultrasonic_sr04.c:80,82 */
HAL_GPIO_WritePin(SR04_TRIG_GPIO_GROUP, SR04_TRIG_GPIO_PIN, GPIO_PIN_SET);    /* 触发：高 */
HAL_GPIO_WritePin(SR04_TRIG_GPIO_GROUP, SR04_TRIG_GPIO_PIN, GPIO_PIN_RESET);  /* 静默：低 */
```

空闲时两者都是高（CS 释放 / TRIG 静默），所以**同时接着不会立刻出错**——`main.c` 的注释
写的"可同时接、不能同时访问"就是这个意思。但一旦超声波发出 10 µs 的高脉冲，恰好在
W25Q64 一次事务中间，那一瞬间 CS 被拉低（**又一次片选**），SPI 从机就会把后续时钟
当成新命令的开头。这是**两个驱动各自都正确、合起来出错**的典型。

排查这类问题不能靠读单个驱动，只能靠一张全局引脚表——这正是本篇综合题的题目。

### 7. `Test()` 是耦合源，但链接器只留一个

教材说"参考测试函数就知道怎么用"——这是对的，代价是测试函数会把它的依赖全部拖进镜像。

`main.c:110-113` 的注释记录了一次实测：

```c
 * @note   必须用预处理而不是运行期 switch：实测运行期 switch 会把 19 个 Test
 *         全部当作可能调用点保留，镜像从 10.9 KB 涨到 33.9 KB。
 *         这里用 #if 之后，只有选中的那个 Test 会进镜像，其余由
 *         --gc-sections 回收（可用 arm-none-eabi-nm 核对符号表）。
```

本次用 `nm` 独立复核了这句注释的后半句：

```text
LAB_TEST=0   → 保留的 *_Test: Led_Test
LAB_TEST=5   → 保留的 *_Test: PassiveBuzzer_Test
LAB_TEST=10  → 保留的 *_Test: Motor_Test
```

**三个镜像各自只剩 1 个 `*_Test` 符号**，注释可信。但引用它的一方仍然留下来：
Day13 实测 `LAB_TEST=5` 比 `=0` 多 4 980 B，其中 2 048 B 是 `ascii_font`，
因为 `PassiveBuzzer_Test` 调了 `LCD_PrintString`。

完整的因果链是：

```text
Test() 里 printf 到 OLED/LCD
  → 依赖 LCD_PrintString
    → 依赖 ascii_font（2048 B 只读数据）
      → 选任何一个"带屏幕打印"的 Test，字库都会进镜像（不论实际用不用得上）
```

这也解释了为什么 `-ffunction-sections -fdata-sections` + `--gc-sections` 只能回收**没被引用**的部分：
字库**被引用了**，所以留着是正确行为，不是链接器的问题。

### 8. 静态扫描的两个陷阱（都是本篇自己踩的）

写 `scan_drivers.sh` 的过程中，两个陷阱各踩了一次，都值得记住。

**陷阱一：没去注释会统计出并不存在的依赖。** 第一版直接 grep `htim[0-9]`，结果报出
`driver_motor.c` 依赖 `htim1` 和 `htim3`。回看源码：

```c
/* driver_motor.c:55-59 */
extern TIM_HandleTypeDef htim3;
static TIM_HandleTypeDef *g_HPWM_BIN1 = &htim3;
//extern TIM_HandleTypeDef htim1;
//static TIM_HandleTypeDef *g_HPWM_BIN2 = &htim1;
```

`htim1` 那两行是**被注释掉的**。去掉注释后 `driver_motor.c` 只依赖 `htim3`。
21 个文件里错 1 个——如果这就是全部结论，误差率 4.8%，看起来不高，但错的那一个是"电机用了
定时器 1"，会直接把 §6 的冲突表写错（PA8 本来是 TIM1_CH1，电机根本不在那儿）。

**陷阱二：检查的粒度决定答案。** 文档块字段检查我按"整个头文件里有没有『返 回 值』"实现，
结果 20/20 全过。但实际是：

```text
『返 回 值』（有空格） 58 处
『返回值』   （无空格） 17 处，集中在 driver_lcd.h(7)、driver_motor.h(2)、driver_oled.h(8)
58 + 17 = 75 = 公开函数总数     ← 每个函数都有这个字段，只是两种拼法
```

按整文件粒度判，20/20 通过；按**每个函数**粒度判，17 个文档块会被漏掉。
扫描器的输出里必须写清粒度，否则"通过"是假通过——这与 Day03 的「构建绿 ≠ 配置对」、
Day11 的「CS 没配但 HAL 返回 `HAL_OK`」是同一类问题：**判据的自洽性不等于事实的完整性**。

所以一个可信的静态扫描器至少要写清三件事：**扫什么文件、按什么粒度、去没去注释**。

## 系统调用/接口卡片

驱动库没有统一接口，所以这里给的是"契约条款"——每一条都能用 grep 判据验证。

### `Xxx_Init(void)` 或 `Xxx_Init(参数)`

作用：记录句柄 + 配置引脚（**不**开外设时钟）。

参数：多数无参；`Motor_Init(int32_t channel)`、`ColorLED_Init(void)` 例外。

返回值和错误：`int`（`Led_Init`/`MPU6050_Init`）或 `void`（其余 18 个）。

资源所有权：不分配内存；持有的是 `static` 的文件级句柄指针（如 `g_HPWM_BIN1`）。

线程/进程安全：不可重入——重入会把引脚重配一遍，若此时正在收发会破坏时序。

最小示例：`Led_Init(); Led_Control(LED_GREEN, 1);`

常见误用：**不先开外设时钟就调它**。20 个驱动里 19 个假定时钟已开，
唯一开时钟的是 `driver_led.c:55`。

### 反初始化：**不存在**

作用：无。

返回值和错误：无。

资源所有权：**不归还**。引脚、外设时钟、定时器通道都留在 `Init` 之后的状态。

线程/进程安全：不适用。

最小示例：无（这正是缺口）。

常见误用：以为"`Init` 和 `DeInit` 应该成对"——这套库不成对。跨模块切换时只能靠
新模块的 `Init` 覆盖旧引脚，`main.c` 用**编译期互斥**（`#if LAB_TEST`）绕开了这个问题，
那是规避，不是修复。

### `Xxx_Test(void)`

作用：一个可观察的自测，兼作"怎么用这个驱动"的示例代码。教材 §11.1 明确推荐读它。

参数：无。

返回值和错误：`void`。测试失败**不返回错误**，只能靠人看现象。

资源所有权：会调用 `mdelay`/`HAL_Delay` 产生阻塞；有的会进死循环直到按键——
它写给"人在旁边看"的场景，不是自动化测试。

最小示例：`PassiveBuzzer_Test();`（`LAB_TEST=5`）

常见误用：把它当单元测试接进 CI。它没有断言、返回 `void`、依赖人眼，
**不是测试，是演示**。真要做测试得自己加断言（Day11–Day13 的 `lab_*` 主机程序就是这个思路）。

### `extern TIM_HandleTypeDef htimN;` / `extern I2C_HandleTypeDef hi2c1;`

作用：驱动通过 `extern` 直接引用 CubeMX 生成的全局句柄，而不是由调用方传入。

返回值和错误：不适用。

资源所有权：**句柄归 CubeMX 的 `main.c` 所有**，驱动只借用。生命周期问题因此变成
"先 `MX_xxx_Init` 再 `Xxx_Init`"的调用顺序问题。

线程/进程安全：句柄本身有 `__HAL_LOCK` 保护，但驱动不检查 `State`，所以并发调
`OLED_PrintString` 仍会破坏 I2C 事务。

最小示例：`driver_spiflash_w25q64.c` 用 `hspi1`，`driver_mpu6050.c`/`driver_oled.c` 用 `hi2c1`。

常见误用：在自己的工程里把 `MX_xxx_Init` 删了——编译照样过（`extern` 变成未定义引用，
链接阶段才报错），或者干脆按教材示例复制了 `main.c` 却没复制对应的 `MX_xxx_Init`。

| 驱动 | 借用的句柄 | 若缺失 |
| --- | --- | --- |
| `driver_oled.c`、`driver_mpu6050.c` | `hi2c1` | 链接失败或 I2C 无输出 |
| `driver_spiflash_w25q64.c` | `hspi1` | 同上（SPI） |
| `driver_color_led.c` | `htim2` | PWM 无输出 |
| `driver_passive_buzzer.c`、`driver_ir_sender.c` | `htim1` | 同上，且两者互斥 |
| `driver_motor.c` | `htim3` | 电机 B 无 PWM |
| `driver_uart.c` | `huart1` | 串口无收发 |
| `driver_timer.c` | `htim4` | `udelay`/`system_get_ns` 失效 |
| 其余 13 个 | 无（纯 GPIO） | —— |

## 常见错误和陷阱

| 陷阱 | 症状 | 根因 | 处理 |
| --- | --- | --- | --- |
| 只拷 `.c`/`.h` 不拷 `MX_xxx_Init` | 链接失败，或外设无输出 | 驱动靠 `extern` 借句柄 | 按 §卡片表补齐对应初始化 |
| 拷了 `MX_xxx_Init` 但删了 `MspInit` | 寄存器写了、外设不动 | 时钟在 `MspInit` 里开 | 两个文件都要拷 |
| 以为 `Xxx_Init` 会开时钟 | 单独用蜂鸣器不响 | 全库只有 `driver_led.c` 开时钟 | 自查 `__HAL_RCC_*_CLK_ENABLE` |
| 以为 `Init`/`DeInit` 成对 | 找不到 `DeInit` | 全库 0/20 提供 | 见 §5，跨模块靠新 `Init` 覆盖 |
| 把 `Xxx_Test` 当单元测试 | CI 里挂起或永远通过 | 无断言、返回 `void`、有阻塞 | 自己写带断言的主机程序 |
| 用运行期 `switch` 分发 Test | 镜像 10.9 KB → 33.9 KB | 所有 Test 都成为可能调用点 | 用预处理 `#if`（`main.c:110`） |
| 有源蜂鸣器和无源蜂鸣器同时接 | 声音怪或没声 | 都在 PA8 | 编译期互斥（`LAB_TEST=4/5/6`） |
| DS18B20 与 DHT11 同时接 | 两边读数都错 | 都是 PA1 单总线 | 二选一 |
| W25Q64 与 HC-SR04 同时访问 | Flash 偶发读错 | PB9 反相位（CS 低有效 / TRIG 高有效） | 分时访问，或换引脚 |
| 静态扫描报出不存在的依赖 | 冲突表写错 | 没去注释（`//extern htim1`） | 先 `sed` 去注释再 grep |
| 扫描器"全过"但其实漏判 | 17 个文档块没检查 | 检查粒度是整文件 | 按函数粒度，并写明粒度 |

## 故障排查方法

把一个新模块接进自己的工程，按这七步走，前四步不需要板：

1. **它借什么句柄**。`grep -n "extern.*HandleTypeDef" Drivers/xxx.c`。
   有 `hi2c1`/`hspi1`/`htim1` 就必须有对应的 `MX_xxx_Init`。13 个驱动不需要这步。
2. **它要哪些引脚**。`grep -nE "GPIO_PIN_[0-9]+|GPIO[A-C], GPIO_PIN" Drivers/xxx.c`。
   **先去注释**，否则会把 `//` 掉的旧接线算进来（§8 陷阱一）。
3. **引脚有没有被占**。对照 §6 的冲突表，尤其 PA8（三方）、PA1（两方）、PB9（反相位）、
   PA15/PB3/PB4（调试口）。这一步是纯文本比对，快且可靠。
4. **时钟谁开**。`grep -c "__HAL_RCC_.*_CLK_ENABLE" Drivers/xxx.c`。多数是 0，
   说明必须保证对应的 `MspInit` 被调用过。
5. **极性/电平**。GPIO 模块看 `GPIO_PIN_SET` 是高有效还是低有效；PWM 模块看 `OCPolarity`
   （Day13 §6 的两个口径）。这一步开始需要硬件手册或实测。
6. **单模块自测**。调 `Xxx_Test()`。它有可观察现象，但**没有判据**——现象对不对要靠人看。
7. **只在两个模块同时用时出错**。这时不要读驱动，直接回第 3 步做引脚交集，
   并检查**极性是否相反**（反相位冲突比同极性更难发现）。

⚠️ 注意：第 6 步之前的结论全部是**源码级**的。`HAL_GPIO_Init` 返回 `HAL_OK` 不代表引脚真的
`MX_GPIO_Init` 配对了（Day11 的 CS 问题），编译通过不代表 `MspInit` 被调了（Day13 的时钟问题）。

## 练习题

### 基础题

题目：把 §6 的冲突检查从"五组已知"扩展成"全部模块的两两交集"。要求：

① 用一条命令导出所有驱动的引脚集合（先去注释）；
② 列出所有在同一引脚上出现两次及以上的模块；
③ 判断每一组是"同极性"还是"反相位"，并说明反相位为什么更危险。

提示：`sed -E 's://.*::'` 去行注释；`grep -oE "GPIO[A-C], ?GPIO_PIN_[0-9]+"` 抓引脚；
用 `sort` + `uniq -c` 找重复。别忘了 `driver_motor.c` 里有 10 处 `HAL_GPIO_Init`
（同一个引脚在不同通道的配置里重复出现，按行数统计会重复计数）。

验收标准：至少找出 §6 之外的两组（提示方向：`driver_rotary_encoder.c` 的 PB0/PB1/PB12 与
其它模块是否有交集）；对每组给出 `文件:行号`；能说明"空载时不冲突、加载时冲突"与
"任何时刻都冲突"的区别。

### 改错题

题目：下面是为 `driver_dht11.c` 补的 `DeInit`，写在驱动文件末尾。它有三处问题。

```c
void DHT11_DeInit(void)
{
    GPIO_InitTypeDef GPIO_InitStruct = { 0 };          /* ① */

    HAL_GPIO_DeInit(GPIOA, GPIO_PIN_1);                /* ② */

    GPIO_InitStruct.Pin  = GPIO_PIN_1;
    GPIO_InitStruct.Mode = GPIO_MODE_ANALOG;           /* ③ */
    GPIO_InitStruct.Pull = GPIO_NOPULL;
    HAL_GPIO_Init(GPIOA, &GPIO_InitStruct);
}
```

提示：①`GPIOA` 的时钟在 `DeInit` 时还在吗？②`HAL_GPIO_DeInit` 把引脚复位成什么模式？
③F103 的引脚复位后是浮空**输入**，写 `GPIO_MODE_ANALOG` 会不会引入额外状态？
再看 `Core/Src/tim.c:325` 的 `HAL_TIM_Base_MspDeInit` 到底做了几件事。

验收标准：能指出 ① 如果 `DeInit` 之后还要再 `Init`，必须自己重新开时钟（因为 `driver_led.c`
是唯一开时钟的地方）；能说明 ② 与 ③ 重复（`HAL_GPIO_DeInit` 已复位，再 `HAL_GPIO_Init`
要么冗余要么覆盖成非默认态）；能指出 `tim.c:325` 的参照实现**只有"关时钟"一步、不含复位引脚**，
所以"与 CubeMX 对齐"并不能作为完整性的理由，必须自己定义清楚 `DeInit` 的语义；

### 综合题

题目：设计一个"模块注册表"，让引脚冲突在**编译期**暴露，而不是上板才发现。要求：

① 用一个头文件集中声明所有模块的引脚占用（`{模块, 端口, 引脚}` 表）；
② 给出一种编译期检测重复占用的手段（提示：C11 `_Static_assert`、枚举重定义、
   或生成期脚本三者选一）；
③ 说明它抓不住哪一类冲突。

提示：编译期方案只能在**常量**上工作；`#if LAB_TEST` 已经做了"单选"，所以注册表要解决的是
"选了 A 又手动加了 B"这种人类错误，不是宏分支。

验收标准：能写出至少能抓住 PA8 三方争用与 PA1 双方争用的断言（或脚本），并说明
"同一引脚但不同时刻使用"（W25Q64 + SR04 反相位）以及"引脚不冲突但外设冲突"
（两个驱动共用 `htim1` 的不同通道）这两类它抓不住；能给出每类的补充手段。
