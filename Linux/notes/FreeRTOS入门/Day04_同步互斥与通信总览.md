## 核心概念

### 1. 同步与互斥的分界只有一句："我等你" vs "你不能进"

教材用同一个厕所场景讲两件事（`rtos.txt:3175-3177`）：

| | 教材原话 | 在等什么 | 依赖方向 |
| --- | --- | --- | --- |
| **同步** | "我正在用厕所，你等会" | 等**另一个动作完成** | A 完成 → B 才能开始 |
| **互斥** | "我正在用厕所，你不能进来" | 等**资源被归还** | 谁先到谁用，无先后要求 |

教材紧接着说了关键的一句：**"互斥"操作可以使用"同步"来实现**——
"我'等'你用完厕所，我再用厕所"。这里的机制是**休眠-唤醒**，不是忙等：
B 不是站在门口不停张望，而是"眯一会"，由 A 用完后叫醒（`rtos.txt:3181-3188`）。

### 2. 两个生活例子，一个说依赖、一个说资源

教材给的两个团队例子恰好覆盖两个方向（`rtos.txt:3179`）：

- **报表**："同事 A 先写完报表，经理 B 才能拿去向领导汇报"——
  这是**同步**，本质是**数据依赖**：B 的输入是 A 的输出。B 早来没有意义，因为东西还没做出来。
- **会议室**："同事 A 已经使用会议室了，经理 B 也想使用，即使经理 B 是领导，他也得等着"——
  这是**互斥**，本质是**资源争用**：谁先用是无所谓的，只要求不同时。

第三句才是本章的枢纽：**"经理 B 跟同事 A 说：你用完会议室就提醒我。这就是使用'同步'来实现'互斥'。"**
也就是说，"互斥"是需求，"同步"是手段之一。这个视角在 Day06/Day07 会再次出现：
二值信号量既能当"事件通知"（同步），也能当"锁"（互斥）——**同一个对象，两种用法，
区别只在于"谁负责 give"**。

教材因此给了一句定义（`rtos.txt:3190-3192`）：

> 同一时间只能有一个人使用的资源，被称为**临界资源**。

串口是最典型的临界资源：两个任务同时打印，"打印出来的信息就是 A、B 混杂，无法分辨"。

### 3. 裸机里能用的写法，在 RTOS 里"大概率没问题"——错在概率

教材 10.2 的第一版就是上一篇 §5 的那个例子，这里补两个之前没展开的点：

```c
static int bCanUse = 1;
if (bCanUse) { bCanUse = 0; /* 使用 LCD */ bCanUse = 1; return 0; }
return -1;
```

教材的判词很讲究（`rtos.txt:3206`）：**"在 RTOS 里，使用上述代码实现互斥操作时，
大概率是没问题的，但是无法确保万无一失。"**

"大概率没问题"不是敷衍——它精确描述了失败条件：只有切换点正好落在
「读完 `bCanUse`」与「写回 `bCanUse`」之间才会失败，而这个窗口只有几条指令宽。
所以这类 bug 的实际表现是**跑一万次都对，演示时也对，出货后偶发一次**。

这也是为什么"没复现"不能作为"没有 bug"的证据。Day01 §7 的排查方法里已经写了这条。

### 4. `bCanUse--` 为什么仍错：一条 C 语句 = 三条机器指令

教材把 `bCanUse--` 编译后的样子直接写出来了（`rtos.txt:3226-3228`）：

```asm
04.1  LDR R0, [bCanUse]   ; 读
04.2  DEC R0, #1          ; 改
04.3  STR R0, [bCanUse]   ; 写
```

失败路径（`rtos.txt:3231-3234`）：A 执行完 04.1 拿到 R0 = 1 后被切出 →
B 完整跑完 04.1–04.3 把 `bCanUse` 减成 0、判 0 成立进入临界区、然后也被切出 →
A 从 04.2 继续，R0 减成 0、04.3 写回 → A 判 0 也成立 → **两个任务都在临界区里**。

教材的归纳只有一句（`rtos.txt:3236`）：**"不能保证万无一失的原因在于：在判断过程中，被打断了。"**

**注意这里的推进**：第一版错在"两条语句之间"，第二版错在"一条语句的三条指令之间"。
它把"原子性"这个词从"语句级"压到了"指令级"——
这正好对上了 Day01 §3 推出的第 3 条前提："切换可以发生在任意两条机器指令之间，
但不能发生在一条机器指令中间"。**教材 10.2 就是这句话的证明。**

### 5. 关中断能修，但教材自己把这版标成"有缺陷"

教材给了两版改进（`rtos.txt:3238-3280`），思路一致：把"判断 + 置位"这段压到关中断里。

```c
/* 示例 1 */
disable_irq();
if (bCanUse) { bCanUse = 0; enable_irq();
    /* 使用 LCD */
    bCanUse = 1; return 0; }
enable_irq();
return -1;
```

关键在于**临界区的边界画在哪**：`enable_irq()` 放在"使用 LCD"**之前**，
也就是关中断只包住"判断 + 置位"这几条指令，不包住真正的耗时工作。
这个边界是对的——否则中断延迟会等于 LCD 的打印时间。

但教材紧接着写了一句：**"这是一个有缺陷的互斥示例：12_task_sync_exclusion"**（`rtos.txt:3282`）。
教材没展开缺陷在哪，这里只列**能从代码本身证明**的三条：

| 缺陷 | 为什么 | 后果 |
| --- | --- | --- |
| **不区分资源** | `disable_irq()` 是全局的，锁 A 和锁 B 效果一样 | 两个无关资源也会互相阻塞；而且中断被一起关掉 |
| **无法跨任务等待** | 拿不到就 `return -1`，调用者只能自己重试 | 没有阻塞、没有唤醒、**没有超时**——正是 §6"三类操作"里缺的两类 |
| **状态机无法容错** | 第二版用"减一"表达占用，只容得下两个使用者；第三个并发调用者把它减到 -2，`else` 分支加回 -1 后**永久损坏** | 一次异常（如任务被删）就让这个"锁"再也不会恢复 |

第三条是"用计数当锁"的通用错误：**计数的语义是"还剩几个资源"，
不是"现在还欠几个"**，负数在这里没有意义。等到 Day06 学计数信号量时会看到，
FreeRTOS 的做法是**上限封顶**而不是让它变负——`F103_12` 实测的
`gives=2 coalesced=5` 就是"满了之后多余的 give 被合并掉，不会溢出"。

这也是"为什么要有内核对象"的答案：关中断只是**手段**，它缺的是
"阻塞 / 唤醒 / 超时"这套**语义**，而语义必须由内核维护的任务列表来实现。

### 6. 五类对象共享同一套操作动词，所以可以一张表记住

教材先给了共同点（`rtos.txt:3286-3291`）：它们都有**获取/释放、阻塞/唤醒、超时**，
并且行为都是这三句：

> 任务 A 获取资源，用完后释放；A 获取不到则阻塞，B 释放并唤醒 A；
> A 获取不到则阻塞**并定个闹钟**——要么超时返回，要么在这段时间内被唤醒。

**第三句里的"闹钟"就是 Day03 §2 那个"阻塞可以带超时"的实际用途。**
它的重要性在于让"等不到"变成**可返回的错误**而不是死等，
这也是所有实时系统里"降级路径"的接口形式。

### 7. 教材的"四问"：一张能现场用的选型表

教材承认这些对象"五花八门，记不住怎么办？我也记不住，通过对比的方法来区分它们"
（`rtos.txt:3293`），然后给了四问：

1. 能否传**信息**？还是只能传**状态**？
2. 为**众生**（所有任务都能用）？还是只**为你**（只能指定任务用）？
3. 我生产，**你们**消费？
4. 我上锁，**只能由我**开锁？

对应成表（教材 `rtos.txt:3297-3319` 的整理）：

| 内核对象 | 生产者 | 消费者 | 数据/状态 | 唤醒几个 | 一句话 |
| --- | --- | --- | --- | --- | --- |
| **队列** | ALL | ALL | **数据**：若干个数据 | **1 个** | 谁都能扔，谁都能取 |
| **事件组** | ALL | ALL | **状态**：多个位（与/或） | **多个（广播）** | 谁都能置位，可等单个或多个位 |
| **信号量** | ALL | ALL | **数量** 0~n | **1 个** | 维持资源个数 |
| **任务通知** | ALL | **只有我** | 数据、状态都可以 | 1 个（N 对 1） | 必须指定接收任务，只能它自己取 |
| **互斥量** | A 上锁 | A 开锁 | **位**：0/1 | 1 个 | **谁上锁谁开锁** |

四个判据各自的判别力：

- **第 1 问（信息 vs 状态）** 分掉队列：只有队列能传"若干个数据"，
  其余都只表达"发生了什么"或"还剩几个"。
- **第 2 问（众生 vs 只为你）** 分掉任务通知：它把数据直接写进**接收任务的 TCB**，
  所以必须点名收件人，且只有收件人能取。代价是**会被覆盖**——
  发得太快、收得太慢时，中间的通知丢了，**而没有任何计数告诉你丢了几条**。
- **第 3 问（唤醒几个）** 分掉事件组：它是唯一"像广播"的，因为多个任务可以同时等不同的位组合。
  队列与信号量都只唤醒**一个**等待者——这条差别在 Day08 的双任务等待对照里会被实测放大。
- **第 4 问（谁能开锁）** 分掉互斥量：只有它要求"A 上锁、A 开锁"。
  这一条不是礼节，它使能**优先级继承**（Day07 / `F103_16` 实测：`mutex` 轮持锁者 `prio 1→3`，
  `binary-sem` 轮恒为 1）。**如果允许别的任务替你开锁，继承就无从谈起。**

### 8. 对照本仓库已有的实测：三个对象各留了一个指针

本篇没有新实验，但 `F103_12` 已经给三个对象各留了一条读数，正好能把上表的抽象落到地上：

| 读数（`exp12_sync.log`） | 它证明了哪一格 |
| --- | --- |
| `bin waited=801/802` | 信号量的"阻塞 + 唤醒"（§6 前两句），等待时长可观测 |
| `take2(0ms)=pdFALSE` | **超时 = 0 是合法用法**：不阻塞地试一次（§6 第三句的边界情形） |
| `event wait_all got=0x03 waited=200` | 事件组**能一次等多个位且要求全中**（"与"语义），这是广播能力的另一半 |
| `event timeout waited=300` | 事件组也有"闹钟"，与信号量同一套超时机制 |
| `bytes=7 gives=2 coalesced=5` | **二值信号量有上限**，7 次 give 只有 2 次真的增加计数——对应 §5 第三条缺陷 |

最后一条值得单独说：`coalesced=5` 是"这 5 次 give 没有产生额外效果"。
它不是错误，正是**语义**——二值信号量表达的是"有没有事件待处理"，
而不是"发生了几个事件"。**要数清次数就必须换计数信号量或队列。**
教材表格里"信号量：数量 0~n"那个 `n` 就是这条分界线。

## 系统调用/接口卡片

> 本章仍然**没有新 API**——教材只讲概念与对比。五个对象的具体接口分别在
> Day05（队列）、Day06（信号量）、Day07（互斥量）、Day08（事件组/任务通知）给出。
> 本节只钉死三个"所有对象共用"的语义点，因为它们容易在细节章里被忽略。

### 超时参数（所有阻塞式获取接口共用）

作用：给"等待"加一个上界，让等不到也能返回。

原型：形如 `xQueueReceive( handle, &item, xTicksToWait )` / `xSemaphoreTake( h, xTicksToWait )`
/ `xEventGroupWaitBits( h, bits, clear, wait_all, xTicksToWait )`——**最后一个参数长得一样**。

参数：tick 数。三个特殊值：

| 取值 | 语义 | 实测/出处 |
| --- | --- | --- |
| `portMAX_DELAY` | **永不超时**（除非关了 `INCLUDE_vTaskSuspend`） | `F103_10` 的 `consume` 用它阻塞在队列上 |
| `0` | **立刻返回**，只试一次，不阻塞 | `F103_12` 的 `take2(0ms)=pdFALSE` |
| 其它 N | 最多等 N tick | `F103_12` 的 `waited=200` / `waited=300` |

返回值和错误：拿不到就返回 `pdFALSE`（或 `errQUEUE_EMPTY` 系列的封装值）。
**这是唯一的失败信号，必须检查**——用 `v` 开头的接口（如 `vTaskDelay`）没有失败路径，
用 `x` 开头的都有（Day02 §8 的命名索引表）。

资源所有权：无。

线程/进程安全：任务态可阻塞；**ISR 里不能阻塞**，必须用 `...FromISR` 变体且超时参数不存在。

最小示例：

```c
if (xSemaphoreTake( s_sem, pdMS_TO_TICKS(100) ) == pdTRUE) {
    /* 拿到了 */
} else {
    /* 超时：走降级路径，不要当成错误直接崩 */
}
```

常见误用：① 把 `0` 当成 `portMAX_DELAY`（语义正好相反）；
② 检查返回值但不处理超时分支（等于把阻塞又变回了死等）。

### "谁生产 / 谁消费"的所有权规则

作用：决定 `give` 该在哪一侧调用。

规则：

| 对象 | 谁可以 give / set / post | 谁可以 take / wait |
| --- | --- | --- |
| 队列 | 任何人（含 ISR） | 任何人（含 ISR） |
| 事件组 | 任何人 | 任何人 |
| 信号量（二值/计数） | 任何人 | 任何人 |
| 任务通知 | 任何人，但**必须点名接收任务** | **只有接收任务自己** |
| 互斥量 | **只有持有者** | 只有持有者（取锁者） |

常见误用：① 用信号量做互斥，然后由**非持有者** give（"解锁"变成广播，
锁的语义被破坏，优先级继承也失效）；② 用任务通知做"多个任务等同一个事件"——
它只能唤醒一个指定任务。

### 临界资源的边界怎么画（不是 API，是判据）

作用：决定关中断 / 取锁的范围。

判据（从 §5 的示例 1 推出来的）：

```text
临界区只包住"对共享状态的判断与修改"，
不包住"对临界资源的实际使用"。
```

教材示例 1 把 `enable_irq()` 放在"使用 LCD"**之前**，就是这条判据的正面例子。
反面例子是"整个函数关中断"——中断延迟会等于 LCD 打印时间，把实时性彻底毁掉。

常见误用：为了"保险"把整段包进锁里，结果锁的持有时间包含了耗时操作，
高优先级任务全部要等它（Day07 的优先级反转就是这么放大的）。

## 结果观察

### 三个对象各一条读数（实测）

```text
[bin]   waited=801/802               ← 阻塞被唤醒，时长可测
[take2] take2(0ms)=pdFALSE           ← 超时 0：试一次就走
[event] wait_all got=0x03 waited=200 ← 两个位全中，200 tick 内等到
[event] timeout waited=300           ← 闹钟响，超时返回
[isr]   bytes=7 gives=2 coalesced=5  ← 二值信号量封顶，多余的 give 被合并
```

## 常见错误和陷阱

| 陷阱 | 症状 | 根因 | 处理 |
| --- | --- | --- | --- |
| 关中断当锁用 | 中断延迟变大、实时性崩 | 关中断是全局的，不区分资源 | 用内核对象；临界区只包判断与修改 |
| 用计数表达"占用" | 出一次异常后锁永久坏掉 | 计数语义是"剩余资源"，负值无意义 | 用互斥量；计数值本身由内核封顶 |
| 把"大概率没问题"当"没问题" | 演示全对，出货偶发 | 失败窗口只有几条指令宽 | 判据是"有没有非原子的读-改-写"，不是"跑了几次没坏" |
| 用信号量做互斥却让非持有者 give | 锁失效、优先级继承不生效 | 互斥量的第 4 问："谁能开锁" | 只让持有者释放 |
| 用二值信号量数事件次数 | 计数总是偏小 | 二值信号量上限 1，多余 give 被合并（`coalesced=5`） | 换计数信号量或队列 |
| 用任务通知做"一对多" | 只有一个任务被唤醒 | 它必须点名接收者，N 对 1 | 换事件组（广播）或队列 |
| 超时传 `0` 以为是"永久等待" | 一次都拿不到就失败 | 语义正好相反：`0` = 不阻塞 | 永久等待用 `portMAX_DELAY` |
| 不检查带 `x` 前缀的返回值 | 拿不到也往下走 | 失败返回 `pdFALSE`，不检查就读未初始化数据 | 检查并把超时分支当降级路径 |

## 故障排查方法

1. **"两个任务偶尔同时进了临界区。"** 先看临界区里**有没有阻塞调用**
   （`vTaskDelay`、队列/信号量获取、`printf`）。取锁之后又阻塞，等于把锁交给别人；
   这属于设计错误，不是锁的 bug。
2. **"锁加了但中断里还是会乱。"** 中断里访问同一资源必须用 `...FromISR` 变体，
   或干脆不在中断里访问。关中断只能保护"不会被中断打断"，保护不了"另一个任务同时进来"。
3. **"用二值信号量，事件次数总是少。"** 打印 `coalesced` 之类计数确认。
   二值信号量表达"有没有"，计数信号量才表达"几个"。
4. **"高优先级任务被低优先级拖住。"** 看你用的是信号量还是互斥量。
   只有互斥量有优先级继承（`F103_16`：`binary-sem` 等锁 405 tick vs `mutex` 105 tick）。
5. **"选型拿不定。"** 按 §7 四问顺序问：
   要传数据吗 → 队列；要唤醒多个/等多条件 → 事件组；只是"有没有事件" → 信号量；
   只有一个收件人且想省 RAM → 任务通知；是一把锁 → 互斥量。
