## 核心概念

### 1. 四种裸机模式，缺陷收敛到同一句话

教材用同一个场景（妈妈喂饭 / 回信息）把四种模式串起来，并在开头就把结论讲了：

> 前面三种方法都无法解决一个问题：假设有 A、B 两个都很耗时的函数，
> 无法降低它们相互之间的影响。第 4 种方法可以解决这个问题，但是实践起来有难度。（`rtos.txt:37`）

逐条看"残余影响"落在哪里，这比记名字有用：

| 模式 | 写法 | 及时性 | 残余的相互影响 |
| --- | --- | --- | --- |
| **轮询** | `while(1){ 喂(); 回(); }` | 都不及时 | **双向**：谁慢拖累谁（`rtos.txt:72`） |
| **前后台** | 主循环做后台，中断做前台 | 中断及时 | **单向**：中断里的事慢了会拖累后台（`rtos.txt:131-135`） |
| **定时器驱动** | 定时器中断里求模调度 | 按周期 | 前提是"每件事 < 一个周期"，超了就退化成轮询（`rtos.txt:292-298`） |
| **状态机** | 每次只执行一个状态就返回 | 都不及时但**不阻塞** | 拆分不好仍退化（`rtos.txt:606`） |

两个值得停一下的细节：

- **前后台有一个隐藏前提**：教材说"如果电脑'滴'、小孩'啊'不会同时、相近发出，
  那么两者相互之间没有影响"，而"在不能满足这个前提的情况下……程序遭遇到了轮询模式的缺点"（`rtos.txt:193-199`）。
  也就是说**前后台模式的安全性依赖于"中断不会挤在一起"这个物理假设**，
  一旦外设并发性上来（多个传感器同时来数据），假设就破了。
- **定时器驱动本质是"分时复用的轮询"**：调度点从"主循环一轮"变成了"每 N 个 tick"，
  但每一格里的工作仍然是串行、不可打断的。

### 2. 状态机"能解决"，但代价是把函数拆碎

教材给的状态机写法是：主循环还是轮询，但**每个函数内部用 `switch(state)` 只执行一个状态就返回**
（`rtos.txt:338-340`）。所以"喂一口饭"被拆成"舀饭 / 喂饭 / 舀菜 / 喂菜"四个状态。

它解决的问题是**单次执行时间**：任何一次调用都很快，所以 A、B 能真正交替推进。
它没解决的是**可读性与可维护性**：

> 第 4 种方法可以解决这个问题，但是实践起来有难度。（`rtos.txt:37`）

"有难度"具体是：每个耗时函数都要被手工切成状态、状态变量要 `static`、
跨状态需要的中间数据只能塞进文件级变量、再加一个并发场景就要重切一遍。
一个 200 行的顺序逻辑切成 6 个状态之后，**再也看不出它原本是顺序的**。

### 3. 多任务不是"并行"，是"交叉执行"——而这个幻觉是竞态的来源

教材对这个问题的回答非常直接（`rtos.txt:609`）：

> 但是脑子只有一个啊，虽然说"一心多用"，但是谁能同时思考两件事？
> 只是她反应快……本质是：**交叉执行**

以及（`rtos.txt:706-708`）：

> 多任务系统会依次给这些任务分配时间：你执行一会，我执行一会，如此循环。
> 只要切换的间隔足够短，用户会"感觉这些任务在同时运行"。

**这两句话是后面九篇的全部前提。** 由它直接推出三条：

1. 任何时刻只有一个任务在跑 ⇒ 不存在"真的同时"，只存在"切换点在哪"。
2. 切换点由 tick 中断（或更高优先级就绪）决定 ⇒ **切换可以发生在任意两条机器指令之间**，
   但不能发生在一条机器指令中间。
3. 所以"一条 C 语句"是不是"原子的"，取决于编译器把它编成了几条指令——
   这正是 §4 那个 bug 的根。

### 4. 多任务让"每个任务的代码"更简单，让"共享状态"更危险

教材强调了收益（`rtos.txt:696-704`）：

> 编写它们时甚至都不需要考虑它和其他函数的相互影响。就好像有 2 个单板：
> 一个只运行"喂饭任务"这个函数、另一个只运行"回信息任务"这个函数。

这个收益是真的：**任务内部的顺序逻辑不用再被切成状态机**。
但代价被教材放在紧接着的 2.2.2 里——一旦两个任务碰同一份数据，
原本"我这段时间没人动它"的隐式假设就没了。

一句话总结这个交换：

| | 裸机（状态机） | 多任务 |
| --- | --- | --- |
| 单个任务的写法 | 必须切成状态 | 可以是顺序代码（`for(;;)` 里顺序写） |
| 单次执行时间 | 天然短（一个状态） | **可能很长**，靠优先级/阻塞点保证别人能跑 |
| 共享数据的风险 | 只在中断与主循环之间 | **任意两个任务之间**，且切换点不可预测 |

### 5. 教材 2.2.2 的两版错误写法，错在同一个层面

教材举的例子是"两个任务共用一个串口打印"，想用全局变量 `g_canuse` 做互斥。

**第一版**（`rtos.txt:848-876`）：

```c
if( g_canuse ) {        /* ① 判断 */
    g_canuse = 0;       /* ② 清零 */
    printf(str);        /* ③ 打印 */
    g_canuse = 1;       /* ④ 恢复 */
}
```

失败路径：A 执行完 ①、还没执行 ② 时被切换；此刻 `g_canuse` 仍是 1，
B 的 ① 也成立 → B 打印出 `abc` 后被切回 → A 从 ② 继续 → 串口上出现 `abc0123456789`（`rtos.txt:878-888`）。

**第二版**（`rtos.txt:892-944`）想把"判断"和"清零"压到一起：

```c
g_canuse--;             /* ① 减一 */
if( g_canuse == 0 ) {   /* ② 判断 */
    printf(str);        /* ③ 打印 */
}
g_canuse++;             /* ④ 加一 */
```

教材指出它**仍然错**，理由是本篇最该记住的一句：

> 因为"①减一"这个操作会分为 3 个步骤：a. 从内存读取变量的值放入寄存器里，
> b. 修改寄存器的值让它减一，c. 把寄存器的值写到内存上的变量上去。（`rtos.txt:930-932`）

A 做完 a、b、还没做 c 时被切换，`g_canuse` 内存里仍是 1，B 照样进得去。

**两版错在同一个层面：它们都假设"一条 C 语句是不可分割的"。**
第一版是"两条语句之间"被切，第二版是"一条语句的机器指令之间"被切。
教材的结论不是"再想个更聪明的变量写法"，而是直接关门：

> 访问公用的资源的时候要考虑"互斥操作"。任何一种多任务系统都会提供相应的函数。（`rtos.txt:946-948`）

**这条判据值得单独抄下来：用普通变量（含 `volatile`）做互斥，是设计错误，不是性能取舍。**
`volatile` 只保证"每次都从内存读"，不保证"读-改-写不可分割"——
它治不了 `g_canuse--` 的三步拆分。

同理，本仓库 `aviation-node` 踩过的另一个坑（跨任务 tick 差用无符号减法下溢，
`[stat] age=4294967292`）也是同一族问题：**对共享值的"读—算—用"不是原子的**。

### 6. 同步：轮询式等待在浪费 CPU

教材 2.2.3 的问题陈述很短（`rtos.txt:956-958`）：

> 如果任务之间有依赖关系，比如任务 A 执行了某个操作之后，需要任务 B 进行后续的处理。
> 如果代码如下编写的话，任务 B 大部分时间做的都是无用功。

这段话的分量在于它给了"为什么要事件驱动"的**量化依据**：轮询等待时，
B 明明没有工作可做，却占着 CPU 时间片。而多任务的收益恰恰来自"把 CPU 让给有活的任务"。
所以"阻塞"不是"偷懒"，它是**把 CPU 归还给系统的唯一手段**。

这也是 Day03 里"空闲任务必须存在"的另一面：良好设计的任务平时都在阻塞，
万一全都阻塞了，才需要空闲任务兜底。

### 7. 什么时候**不该**上 RTOS

教材没写这一节，但前六条的推理直接给出判据。本仓库的实际配置又给了一条硬约束
（堆只有 4 KB，空闲任务一项就吃掉 616 B，见 Day02 §6）：

| 场景 | 结论 | 依据 |
| --- | --- | --- |
| 只有"按固定周期做一件事"，每件都短 | **不需要** RTOS，定时器驱动就够 | `rtos.txt:292` 的前提成立 |
| 有多个**耗时不可控**且需并行推进的逻辑 | 需要 | 状态机可解但"实践有难度" |
| 中断里想做的事超过几十 µs | 需要（把活丢给任务） | 前后台的单向拖累（`rtos.txt:131-135`） |
| 多个任务间要传数据/事件 | 需要（队列/信号量/事件组） | 2.2.2 / 2.2.3 |
| RAM 只有 4 KB 且已用掉大半 | **慎用**；先用裸机 | 空闲任务 + TCB + 栈的固定开销 |
| 要求最坏执行时间可证明 | 慎用；裸机 + 状态机更容易论证 | 每次切换都可能引入不可预测的延迟 |

**"能不能上"和"该不该上"是两个问题。** 本仓库的 `F103_10` 用 4 KB 堆跑三个任务，
能跑，但已经要精算每个栈（Day03 §8 的水位表就是为此存在的）。

### 8. 第 2 章的伪码 → 真实 API 的映射

教材第 2 章故意用伪码（`create_task`、`start_scheduler`，`rtos.txt:677-691`），
因为那时还没讲 API。对照关系如下，写代码时以右列为准：

| 教材伪码 | 真实 API | 出处 |
| --- | --- | --- |
| `create_task(任务函数)` | `xTaskCreate( fn, name, stack_depth, param, prio, &handle )` | `tasks.c` |
| `start_scheduler()` | `vTaskStartScheduler()` | `tasks.c` |
| 无（教材 2.2.2 说"系统会提供函数"） | `xSemaphoreCreateMutex()` / `xSemaphoreTake()` / `xSemaphoreGive()` | `queue.c`（Day07） |
| 无（教材 2.2.3 提"依赖关系"） | `xQueueSend()` / `xQueueReceive()` / `xEventGroup*` / 任务通知 | `queue.c` / `event_groups.c`（Day05、Day08） |

## 系统调用/接口卡片

> **本章没有真实 API。** 教材第 2 章不涉及任何函数原型，这一节的目的是把"伪码 → 真实接口"
> 钉死，避免读到后面时把伪码当签名。

### `create_task(...)`（教材伪码）

作用：教材用来表示"创建一个任务"。

原型：**不存在**。教材写作 `create_task(喂饭任务);`（`rtos.txt:677`）。

参数：教材只传了任务函数。

返回值和错误：未提及。

资源所有权：未提及。

线程/进程安全：不适用。

最小示例：不适用。

常见误用：① 把这个名字当成真实 API 去查手册；
② 以为"创建任务"不需要给栈大小和优先级——真实 `xTaskCreate` 必填这两项，
而栈大小的单位是 **word**（Day03 §8）。

### `start_scheduler()`（教材伪码）

作用：教材用来表示"启动调度器"。

原型：**不存在**。真实是 `void vTaskStartScheduler( void );`

参数：无。

返回值和错误：真实 API 是 `void`——**"失败不返回"**。它只有在堆不足、无法创建空闲任务/定时器任务时
才会返回；正常情况下永不返回。所以"它返回了"本身就是失败信号
（本仓库 `F103_10/main.c:186` 就有一行兜底打印"调度器未能启动"）。

资源所有权：内部会创建**空闲任务**（`configMINIMAL_STACK_SIZE`）与
**软件定时器任务**（若 `configUSE_TIMERS == 1`，栈为 `configTIMER_TASK_STACK_DEPTH`）。

线程/进程安全：只能在 `main` 里调一次。

最小示例：

```c
xTaskCreate( ... );            /* 先建任务 */
vTaskStartScheduler();         /* 正常不返回 */
printf("调度器未能启动（堆不足？）\r\n");   /* 执行到这一行即失败 */
for (;;) { }
```

常见误用：① 在 `vTaskStartScheduler()` 之后继续写业务代码（不可达）；
② 不写"返回即失败"的兜底，导致堆不足时表现为"程序什么都没做"。

## 最小可运行实验

`experiments/F103_10_FreeRTOS_Tasks/`——它就是 2.2.1「多任务模式」的落地，
只是把"喂饭 / 回信息"换成了"生产 / 消费"：

```text
produce (prio 2, 160 字)  ──每 200 ms 投递──▶  queue(depth=8)
consume (prio 3, 256 字)  ◀──阻塞等待────────┘
monitor (prio 1, 192 字)  ──每 1000 ms 打印计数 + 栈水位
```

三件事恰好对应本章三个阶段：

| 实验构件 | 对应的教材内容 | 它替教材证明了什么 |
| --- | --- | --- |
| 三个任务各自 `for(;;)` 顺序写 | 2.2.1 多任务模式 | 任务内部不用切成状态机 |
| 队列传数据（而非共享变量） | 2.2.2 互斥操作 | 不靠全局变量也能安全交接 |
| `consume` 阻塞在 `xQueueReceive(..., portMAX_DELAY)` | 2.2.3 同步操作 | 阻塞等待不浪费 CPU |

## 结果观察

### 交叉执行确实发生了（实测）

```text
[consume] seq=1 tick=1
[consume] seq=2 tick=203      ← 间隔 202 tick
[monitor] tick=1003 produced=5 consumed=5 dropped=0 queued=0
```

**`consume` 和 `monitor` 的打印在日志里交错出现**，而两者都是无限循环。
这正是 §3 说的"交叉执行"：`consume` 阻塞在队列上、`monitor` 阻塞在 `vTaskDelay` 上，
两者都不会霸占 CPU。**如果其中任何一个不阻塞，另一个就永远不会打印**——
这就是教材 `rtos.txt:2675` 那个"被饿死"的反例。

### 交接完整性（实测）

```text
[monitor] tick=11062 produced=55 consumed=55 dropped=0 queued=0
```

`produced == consumed`、`dropped = 0`、`queued = 0`。这三个数同时成立说明
**队列作为"互斥 + 同步"的载体是有效的**：生产者从不因为消费者正在读而损坏数据
（互斥），消费者从不在没数据时占用 CPU（同步）。

### 本章**没有**验证的东西

- 教材 2.2.2 的字符串混杂竞态**没有复现**。复现它需要一个能被两个任务真并发写、
  且能观察到部分输出的通道；QEMU 的串口是单字符同步输出，构造不出"打印到一半被切走"的窗口。
  所以这一段是**教材推理 + 代码阅读**，不是本机实测。
- 四种裸机模式**没有在本仓库各写一版做对照**。本篇的四种模式表格是教材原文的归纳。

## 常见错误和陷阱

| 陷阱 | 症状 | 根因 | 处理 |
| --- | --- | --- | --- |
| 用全局变量做互斥 | 长时间运行后偶发数据混杂 | "判断"与"置位"是两条语句，或一条语句被拆成多条机器指令（`rtos.txt:930`） | 用 `xSemaphoreCreateMutex()`；不要自己发明 |
| 以为 `volatile` 能当锁 | 加了 `volatile` 仍然错 | `volatile` 只保证不缓存，不保证原子 | 同上；原子性靠临界区/互斥量 |
| 用轮询等待共享数据 | CPU 占用高、功耗高 | 不阻塞 = 不让出 CPU（`rtos.txt:958`） | 改成阻塞式 `xQueueReceive` / `xSemaphoreTake` |
| 前后台模式用于多路并发外设 | 偶发丢数据 | 该模式依赖"中断不会同时来"的假设（`rtos.txt:193-199`） | 中断里只做最少的搬运，其余交任务 |
| 状态机拆得太碎 | 逻辑不可读、改一处崩三处 | 顺序逻辑被切散，中间状态塞进静态变量 | 逻辑确实需要并行推进时，考虑 RTOS 而非继续切状态 |
| 在小 RAM 上盲目上 RTOS | 什么都还没做就 `heap` 不足 | 空闲任务 + TCB + 栈的固定开销（本仓库 616 B / 4096 B） | 先算固定开销；本仓库必须精算每个栈 |
| 把 `create_task` 当真实 API | 编译找不到符号 | 教材第 2 章用伪码 | 用 `xTaskCreate`，注意栈单位是 **word** |
| 在 `vTaskStartScheduler()` 后写业务 | 那些代码永远不执行 | 它正常不返回 | 业务全部放任务里；只留"返回即失败"的兜底 |

## 故障排查方法

1. **"多任务跑起来但只有一个任务在打印。"** 先查另外两个任务有没有**阻塞点**
   （`vTaskDelay` / `xQueueReceive` / `xSemaphoreTake`）。没有阻塞点的高优先级任务会饿死别人
   （`rtos.txt:2675`）。
2. **"加了互斥还是乱。"** 检查互斥是否包住了**全部**共享访问，而不只是写的那一半；
   再检查是否在中断里访问了同一个资源（需要用 `...FromISR` 变体或临界区）。
3. **"偶发一次，无法复现。"** 这是竞态的正常形态。做法是**缩小切换窗口**而不是等它复现：
   把相关任务的优先级调到相同（强制时间片轮转）、把 tick 频率调高，让切换点变密集。
   **注意：改这些参数只是提高命中率，不能证明修复。** 修复的证据只有"代码里不再存在
   非原子的读-改-写"，以及 TSan 类工具的干净报告（本仓库的 Linux 侧实验 `SYS_06` 用过 TSan）。
4. **"上 RTOS 后 RAM 不够。"** 先算三笔固定开销：空闲任务栈（`configMINIMAL_STACK_SIZE`）、
   每个任务的 TCB（约 92 B）、每个任务的栈（深度 × 4）。再看 §7 的判据，可能根本不该上。
5. **"调度器没启动。"** `vTaskStartScheduler()` 返回了就是失败——看 `heap_free`，
   通常是堆不足无法创建空闲任务。
