# 嵌入式内存预算：三种"余量"不能混着读

**建立日期**：2026-10-28
**来源审查**：[`projects/aviation-node/docs/resource-review.md`](../projects/aviation-node/docs/resource-review.md)
**记录性质**：§2–§3 是**实测**（`arm-none-eabi-size` / `nm -S` + 链接脚本）；§4–§5 是**地址算术推算**，
不是实测峰值；无真板读数。

---

## 1. 为什么单独立一份笔记

`aviation-node` 的文档里同时出现过两个数字：

- README §10.1：RAM 已占 8 KB 的 **79.98%**，"还能不能加功能"
- 同一份文档：链接器"**余 1640 B**"
- `[stat]` 日志：稳态 `xPortGetFreeHeapSize()` = **120 B**

三个数字都是对的，但指向三件不同的事。混着读会得到两个相反的结论：
"还剩 1.6 KB，可以加" 和 "只剩 120 B，什么都加不了"。

这类混淆不是笔误，是**没有区分内存的三个所有者**。这份笔记把三个口径拆开并给出核算方法。

---

## 2. 三个口径

| 口径 | 8 KB 目标下的数值 | 谁在用 | 能不能拿来加功能 |
| --- | --- | --- | --- |
| **A. 链接器尾部余量** | 1640 B | MSP 主栈（中断嵌套时向下生长） | **不能**。占它等于压缩中断栈，溢出不在链接期报错 |
| **B. FreeRTOS 动态余量** | 120 B（稳态） | 新建任务/队列/信号量 | **只有它能**。这是"加功能"的唯一真实额度 |
| **C. 链接脚本静态预留** | 1024 B（`_Min_Stack_Size`） | MSP 主栈的**声明部分** | 不能。它只是"链接器保证留了这么多"，不是可用额度 |

**关键认知**：A 和 C 是**同一块内存的两段**，不是两块。
`_estack` 向下到 `.bss` 末尾之间，先经过 C 声明的 1024 B，再经过 A 那 1640 B。
所以"MSP 实际能用多少"是两者之和，而不是取其中一个。

---

## 3. 实测推导（8 KB / STM32F100RB 布局）

构建：`build-qemu/aviation_node.elf`，Arm GNU Toolchain 14.2 rel1。

```text
   text    data     bss     dec     hex
  18156     100    6452   24708    6084
```

按地址逐段展开（`nm -S` 实测）：

```text
.data              100 B   0x20000000 .. 0x20000064
.bss 实体         4912 B   0x20000064 .. 0x20001394   （ucHeap 4096 + __sf 312 + 其余 504）
对齐                 4 B   0x20001394 .. 0x20001398
._user_heap_stack 1536 B   0x20001398 .. 0x20001998   （_Min_Heap_Size 512 + _Min_Stack_Size 1024）
尾部余量          1640 B   0x20001998 .. 0x20002000
------------------------------------------------------------
合计               8192 B
```

### 3.1 第一个坑：`size` 报的 `bss` 不是"静态变量"

`size` 报 `bss = 6452`，但 `.bss` 里的实际变量只有 **4912 B**。差额 1540 B
（`4912 + 1536 + 4 = 6452`）来自 `._user_heap_stack`——它是 `NOBITS`（不占文件空间），
所以被计入 `bss`。

于是有三个都在说"RAM 占用"的数：

| 说法 | 数值 | 含堆栈预留 | 用途 |
| --- | --- | --- | --- |
| `.bss` 实体 | 4912 B | 否 | 查"变量是不是太多了" |
| `size` 的 `bss` | 6452 B | 是 | 报表口径 |
| `data + bss` | 6552 B | 是 | **最接近"链接器已分配"的数** |

`8192 − 6552 = 1640` 就是 A 口径的尾部余量。三者对得上，只是问的问题不同。

### 3.2 MSP 主栈到底有多少

按地址算，MSP 从 `_estack = 0x20002000` 向下，安全的边界是**静态变量区末尾** `0x20001398`
之后的堆预留起点 `0x20001598`（`0x20001398 + 0x200`）：

```text
0x20002000 − 0x20001598 = 0x0A68 = 2664 B
```

也就是 **1024（声明）+ 1640（未声明）= 2664 B**。

但这 2664 B 里，中间的 512 B（`_Min_Heap_Size`）属于另一套堆机制。FreeRTOS 用的是 heap_4
在 `.bss` 里预置的 `ucHeap` 静态数组（4096 B），**并不走** `_Min_Heap_Size` 那 512 B。
如果项目里没有任何 `malloc`，这 512 B 就是纯预留；newlib 的 `printf` 可能间接触发
`malloc`，所以不能直接删——**这一点未验证**，见 §6。

## 4. FreeRTOS heap 是怎么被吃掉的

`configTOTAL_HEAP_SIZE = 4 * 1024`（实测配置项）。启动日志给出两个锚点：
三任务 + 队列 + 互斥量之后 **736 B** 剩余，idle 稳定后 **120 B**。

| 项 | 大小 | 占堆比例 | 依据 |
| --- | --- | --- | --- |
| `rx` 栈 224 字 | 896 B | 21.9% | `xTaskCreate(..., 224, ...)` |
| `ctrl` 栈 224 字 | 896 B | 21.9% | 同上 |
| `health` 栈 256 字 | 1024 B | 25.0% | 同上 |
| **三任务栈小计** | **2816 B** | **68.75%** | |
| idle 栈 128 字 | 512 B | 12.5% | `configMINIMAL_STACK_SIZE = 128` |
| 四个 TCB | ≈ 400 B | ≈10% | 由差额推算 |
| RX 队列（深度 64 × 1 B + 结构） | ≈ 184 B | ≈4.5% | `RX_QUEUE_DEPTH = 64` |
| 互斥量 | ≈ 80 B | ≈2% | `xSemaphoreCreateMutex()` |

**结论**：任务栈占掉近 69%，其余全是固定开销。稳态 120 B 意味着**连一个 128 字栈的新任务
（512 B 栈 + ≈100 B TCB）都建不起来**——必须先把 `configTOTAL_HEAP_SIZE` 提上去。

注意这里的关键关系：**多给任务栈只减少堆余量，不改变 `.bss` 总量**（`ucHeap` 是固定大小的静态数组）。
调 `configTOTAL_HEAP_SIZE` 才是改 `.bss`，而那是**全局共享**的配置，所有实验一起受影响。

## 5. 加功能前怎么核算（以"双通道冗余"为例）

核算顺序固定三步：**估新增字节 → 改哪个量 → 链接能不能过**。

### 方案 A：独立 `rx2` 任务 + 独立队列

| 项 | 估算 |
| --- | --- |
| 第二 rx 任务（栈 192 字 = 768 B + TCB ≈100 B） | 868 B |
| 第二 RX 队列（深度 64） | 184 B |
| 第二解析器 `av_parser_t` | ≈56 B |
| 通道状态 ×2 | ≈40 B |
| 表决与降级决策 | ≈16 B |
| **合计** | **≈1164 B** |

`configTOTAL_HEAP_SIZE` 4096 → 6144（+2048，留对齐余量）。
`.bss` 增加 2048 ⇒ RAM 总量 `6552 + 2048 = 8600 > 8192` ⇒ **链接失败**（`region RAM overflowed`）。

这不是调参问题，是硬约束：**8 KB 目标上不可能有第二个独立 rx 任务**。

### 方案 B：单 `rx` 任务轮询两路

| 项 | 估算 |
| --- | --- |
| 第二队列 + 解析器 + 通道状态 + 表决 | **≈296 B** |

`configTOTAL_HEAP_SIZE` → 4608（+512）。RAM 总量 `6552 + 512 = 7064`，尾部余量
`8192 − 7064 = 1128 B`，仍大于 `_Min_Stack_Size`（1024）⇒ **可链接**。

代价：MSP 缓冲从 1640 B 降到 1128 B（**压缩 31%**），而 MSP 峰值**从未实测**。
另外实时性退化——轮询时一路阻塞会影响另一路。

### 方案 C：换真板目标（20 KB）

`STM32F103C8Tx.ld` 的 RAM 是 20 KB，方案 A 在该目标下余量充足。
但项目**没有对真板目标的构建与运行验证**，只能写"待验证"，不能写成"真板上可行"。

| 方案 | 新增 RAM | 8 KB 可链接 | 实时性 | 结论 |
| --- | --- | --- | --- | --- |
| A 独立任务 | ≈1164 B | **否** | 最好 | 8 KB 下不可行 |
| B 共享任务 | ≈296 B | 是（余 1128 B） | 退化 | 勉强可行，代价是 MSP 裕度 |
| C 真板 20 KB | — | 未验证 | 同 A | 需真板构建与实测 |

### 核算方法本身（可复用）

1. **估字节**：栈 = 字数 × 4（Cortex-M 上 `StackType_t` 为 4 B）；TCB、队列、信号量按 heap_4 对齐估。
2. **定位到哪个量**：新增任务/队列 ⇒ 改 `configTOTAL_HEAP_SIZE`（改 `.bss`）；
   新增静态变量 ⇒ 直接进 `.bss`；两者都影响"链接能不能过"。
3. **先算链接**：`data + bss + 新增 ≤ RAM 总量`，再看尾部余量是否仍 ≥ `_Min_Stack_Size`。
   链接过了才算"物理上可能"，实时性和栈峰值是另一回事，不能混进来。
4. **别用尾部余量当额度**：它已经是 MSP 的缓冲，动它等于先借主栈的钱。

## 6. 常见误判（每条都有本项目的对应读数）

| 误判 | 为什么错 | 证据 |
| --- | --- | --- |
| "余 1640 B，可以加 1.6 KB 功能" | 1640 B 是 MSP 的缓冲，占它压缩中断栈，且溢出**不在链接期报错** | 地址算术见 §3.1 |
| "`size` 报 bss 6452，静态变量太多了" | 6452 含 1536 B 堆栈预留，实际变量只有 4912 B | `nm -S` 逐符号 |
| "稳态堆 120 B 说明内存还有 120 B 可用" | 120 B 连一个 TCB 都放不下；加任务要先改 `configTOTAL_HEAP_SIZE` | §4 明细 |
| "多给任务栈不影响总内存" | 影响的是**堆余量**不是 `.bss`；但堆不够时 `xTaskCreate` 会**返回失败**，必须检查返回值 | `F103_16` 的 4 KB 堆耗尽事故 |
| "FreeRTOS 用的是链接脚本的 `_Min_Heap_Size`" | heap_4 用 `.bss` 里的静态数组 `ucHeap`；`_Min_Heap_Size` 是给 newlib `malloc` 的 | `nm`：`ucHeap` 4096 B @ `0x20000248` |

最后一条的推论值得单独记：**`xTaskCreate` 的返回值必须检查**。`F103_16` 曾经因为
4 KB 堆被耗尽而静默失败，日志停在半截，排查方向完全跑偏（详见该实验 README 的失败复盘）。
