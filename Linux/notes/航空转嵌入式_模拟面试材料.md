## 1. 60 秒自我介绍（可直接背）

> 我做航空飞管 C 软件出身，现在系统补嵌入式和 Linux 底层。路径是三段：
> 第一段补 Linux 用户态与内核的机制，自己写了六组实验——文件与进程、IPC 与线程、Socket 与多路复用、
> Reactor、C++20 协程、调试与性能替代工具链，每组都有判定器和负向验证，总计 200 多条断言。
> 第二段把 FreeRTOS 的同步、定时器、栈溢出、优先级反转、看门狗逐项做成可仿真的实验，
> 每一项都留了 QEMU 原始日志。
> 第三段是一个航空主题的节点项目：PC 注入 → 帧解析 → 三层有效性判定 → 模式状态机 → 降级与恢复 →
> 停喂门控，全链路在 QEMU 上跑通，并写了 24 项不变量的机器判定和 16 组负向验证。
> 我的做法是**先把判据写对，再让代码通过**——一条"等硬件清零"的判据在仿真里假通过过，
> 那次教训我现在写进了每个外设实验的第一条检查。

## 2. 五分钟项目介绍（结构固定，按顺序讲）

1. **要解决什么**：传感器数据可能错帧、越界、突变、静默、丢帧；地面站可能掉线。
   节点要在数据不可信时**降级而不是瞎飞**，并且**故障时必须停止喂狗**。
2. **怎么分层**：L4 应用/控制 → L3 业务 → L2 数据判定 → L1 运行支撑 → L0 硬件。
   关键约束：`av_frame` 只依赖 `stdint`，`av_mode` 不认识 `AV_F_*` 位定义——
   **新增故障位不需要动状态机**。
3. **判定的四层顺序**：帧（长度 + CRC16-CCITT）→ 样本（越界 + 突变率）→ 时间（心跳超时 / 序号停滞）
   → 对端（地面站心跳 500 ms）。每层独立置位，互不掩盖。
4. **状态机**：INIT / NORMAL / DEGRADED / SAFE。降级与恢复**不对称**：
   `DEGRADED → SAFE` 需要故障持续 3000 ms（实测停留 3005/3004/3009 ms），
   恢复分两级 `SAFE → DEGRADED`（205–246 tick）→ `NORMAL`（161–185 tick）。
5. **监督**：rx / ctrl / health 三个任务；喂狗是"与"语义——数据通道健康**且**没有 STALE 才喂。
6. **可观测**：ASCII 日志（人看）+ USART2 二进制下行帧（机器看，25 B / 100 ms）。
7. **怎么验证**：`tests/qemu-stm32/aviation/` 下注入脚本 + 判定器；
   上行日志 24 项不变量（C1–C17）+ 下行 7 项（L1–L7），全部机器判定。
8. **边界**：CAN / ADC / 示波器 / `IWDG` 复位**没有真板证据**，一律标"待真板"。

## 3. 架构图（口头描述版）

```text
L4 应用/控制   ctrl 任务：按模式决定输出（限幅 / 保持 / 安全值）
L3 业务逻辑   av_mode：INIT→NORMAL→DEGRADED→SAFE，两级恢复，滞回门限
L2 数据判定   帧(CRC) → 样本(越界/突变) → 时间(心跳/序号) → 对端(地面站)
L1 运行支撑   rx / health 任务、队列、tick 差、喂狗"与"语义、下行帧
L0 硬件       USART1(注入) / USART2(下行) / SysTick / 待板：CAN、ADC、IWDG
```

图与模块依赖表在 `projects/aviation-node/docs/architecture.md`；
一句话取舍：**把"故障怎么判"和"判完之后怎么改模式"拆成两层**，
代价是多一层标志位传递，收益是新增判据不触碰状态机。

## 4. 关键时序（一次控制周期的实测证据）

- 控制周期：`[stat]` 每 5019–5048 ms 打一次汇总（**实测**，多次运行）。
- 上行帧间隔 ≈58 tick（50 Hz `SENSOR` + 10 Hz `STATUS`）。
- 下行帧：100 ms 周期，实测**帧间隔中位 100 ms、最大 117 ms**（544 帧 / 13600 B，CRC 全通过，`SEQ` 0→31 连续循环）。
- 六类延迟（**实测区间**，不是单点）：

| 延迟 | 实测 |
| --- | --- |
| 故障标志置位 → 模式改判 | 0 tick（**注意**：这只表示"标志→改模式"，不是"故障发生→检出"） |
| 故障清除 → 恢复 NORMAL | 82–163 tick |
| 故障清除 → `SAFE → DEGRADED` | 205–246 tick |
| `DEGRADED → SAFE` | 3003–3017 ms（门限 3000） |
| SAFE 停留 | 2508–6924 ms |
| 注入阻塞开始 → 心跳判超时 | 415–496 tick |

**"0 tick"必须主动解释**，否则会被当成"实时性极好"：跨端没有共同时基，
"故障真正发生 → 软件检出"只能上真板 + 逻辑分析仪测。

## 5. 一次真实故障定位（推荐讲这个）

**现象**：`[stat] age=4294967292`（约 2³²），一个"年龄"变成天文数字。

> **可追溯性说明**：这个读数出现在**修复前**的运行里，修复后的当前日志中 `age` 是
> `35 / 38 / 1800 / 1219 / 6239 / 11266` 这类正常量级，`grep 4294967292` 在当前日志里**为 0**。
> 面试时可以说"当时打出来的是……"，但**不要说**"现在复现给我看"——
> 现在能复现的是判定器 C15 这条回归判据，不是这个读数本身。

**定位**：跨任务的 tick 差用无符号减法 `now - last`，当 `last` 由别的任务在"未来"更新时下溢。
不是巧合：`health` 与 `rx` 不在同一任务，读到的 `last` 可能比自己的 `now` 新。

**修复**：抽出 `av_tick.h::av_tick_elapsed()` 统一处理；`hb` 走同一路径——
下溢会让"心跳超时"误判，直接导致误停喂。

**回归判据**：判定器 C15 专门检查 `age` 的量级，任何人重新引入下溢都会 FAIL。

**为什么值得讲**：这类 bug 在单任务代码里永远不出现，只有多任务共享时间戳才会暴露；
而且它的症状（一个计数异常）跟后果（误停喂狗）相隔很远。

### 备用故事 A：判据假阳性（F103_17）

ADC 未建模、寄存器恒读 0，而首版判据写的是"等 `RSTCAL`/`CAL` 被硬件清零"——
位从未被置起，等待**立刻成功**，日志打印"校准 ok"。
修法：判据拆两段，先看"写进去的位读不读得回"，再看"硬件有没有清掉"。
结论一句话：**先问"设备没响应时这条判据会打印什么"**。

### 备用故事 B：事件循环挂死（SYS_04）

服务端偶发不响应，8 个客户端全部超时。`/proc/<pid>/wchan` 显示卡在 `inet_csk_accept`——
监听 fd 没设非阻塞。同一组还发现把 `EPOLLONESHOT` 无差别套到监听 fd 上，
只 `accepted=4`：**监听 fd 没有人替它重挂**。

## 6. 一次性能优化（只讲有读数的）

**场景**：8 连接 × 20 帧 × 200 B，每帧业务耗时 2 ms。

| 方案 | 总耗时 | 说明 |
| --- | --- | --- |
| 单 Reactor 单线程 | 339 ms | 串行理论下限 320 ms |
| Reactor + 4 线程池 | **85 ms** | 约为串行的 25%，`q_drops=0` |
| 主从 Reactor（2 sub） | 169 ms | `handoff=8`，两个 sub 各 80 帧 |

**代价与边界**（必须一起说）：

- 线程池引入"每连接一个在飞 job"的所有权约束，回包必须回到所属连接；
- 采集规模只有 8 连接，**不是压测**，不能外推吞吐；
- ET 在同一规模下 338 ms，与 LT 无差异——**收益前提不成立就不外推**。

## 7. 一次设计取舍（讲这个，因为它有反例）

**问题**：监督任务 `health` 的优先级该多高？

**取舍**：保持它优先级最低，理由是"监控不能抢占被监控者"。

**代价（实测反例）**：注入 800 ms 忙等故障时，`health` 被饿死（`rx 3 > health 2`），
**看不见**这次卡死。承认这个盲区后，采取的是：
① 把阻塞写成编译期注入（仅 QEMU 构建，默认 0，不进真板）；
② 把"监督任务优先级最低 ⇒ 看不见忙等"写进 README 与架构文档；
③ 不在文档里声称"覆盖了所有阻塞故障"。

**面试表述**：这是一个**取舍而不是缺陷**，但前提是我明确说出了它的不覆盖范围。

### 备用取舍：地面站失联为什么不改飞行模式

`AV_F_GROUND` 只在 500 ms 门槛后置位，且**不在** `AV_F_MODE_MASK` 里——
地面站掉线可观测但不触发 SAFE。理由是"单通道下行，地面站掉线不等于数据不可信"；
代价写在 `s_ground_seen` 门控上：**从未连上过的场景看不见失联**（用"不误报"换"漏报一种情况"）。

## 8. 项目局限性（主动说，不等人问）

1. **无真板证据**：CAN/ADC/示波器/`IWDG` 复位与复位原因全部待板；CAN 在 QEMU 里
   `0x40006400` 未映射，第一次访问即 HardFault。
2. **单通道**：一路 USART 注入，没有冗余通道、没有投票。
3. **下行单向**：地面站不发控制指令，所以无法演示"上行指令 → 模式切换"。
4. **无持久化**：故障记录掉电即失。
5. **无时间基准**：跨端没有同步时钟，端到端延迟测不了。
6. **无 BSP 抽象**：寄存器直接访问，没有 HAL 层。
7. **无 WCET / 抖动数据**：只测了周期量级（5019–5048 ms），没有最坏执行时间与中断延迟。
8. **资源**：FLASH 18256 B（13.93%）、RAM 6552 B（79.98%，**偏高**）、稳态堆 120 B、栈 100/104/88 字。

## 9. 下一步改进（按顺序，且说清前置）

1. **真板闭环**（阻塞项，无替代方案）：`IWDG` 复位 + `RCC->CSR` 复位原因；
   然后按 `F103_18` CAN → `F103_17` ADC → `F103_19` DMA 补功能验证。
2. **R13–R16 追踪项**：只有拿到真板证据才能填进需求追踪矩阵，**不预填**。
3. **RAM 79.98% 的余量审查**：先量化每个缓冲区的实际峰值，再决定是否裁剪。
4. **故障记录持久化**：内部 Flash 或外部 EEPROM，需先解决"掉电中途写"的原子性问题。
5. **冗余通道**：第二路注入 + 双通道一致性判定（这是从"能观测"到"能容错"的一步）。

## 10. 不能说（口径纠正表）

| 不要说 | 因为 | 应该说 |
| --- | --- | --- |
| "完成了 CAN 通信" | 只有构建级 + 反汇编核对 | "CAN 回环驱动到构建级，QEMU 里该地址段未映射，功能待上板" |
| "做过性能优化，吞吐提升 4 倍" | 8 连接、单次业务并发对照 | "在同一 8 连接规模下，线程池把总耗时从 339 ms 降到 85 ms，不是吞吐基线" |
| "实时性满足要求" | 无 WCET、无抖动、无中断延迟 | "周期量级已实测，WCET 与抖动需上板测" |
| "看门狗已闭环" | 只有软件停喂门控，`IWDG` 未建模 | "停喂门控已实测，`IWDG` 计时与复位待板" |
| "覆盖了所有故障" | 八类异常有用例，复位原因/CAN/ADC 没有 | "八类异常已覆盖，硬件类故障待板" |
| "用了 epoll 所以性能高" | ET 在本规模无收益 | "选 epoll 是为了正确性与扩展性，本规模下与 LT 无差异" |

## 11. 一句话收尾（可背）

> 我做的不是"让演示跑起来"，而是**让每个结论都有读数和反例**：
> 判据先在小规模上被破坏版验证过，性能数字只在同一环境下比较，
> 没上板的部分一律写"待真板"。这套习惯来自一次假通过——
> 判据在设备没响应时也会打印成功。
