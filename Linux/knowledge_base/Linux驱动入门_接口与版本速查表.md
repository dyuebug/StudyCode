## 2. 先分清三种生命周期

| 层次 | 建立 | 释放 | 不应混淆 |
| --- | --- | --- | --- |
| 模块 | 模块初始化回调；模块可注册一个驱动 | 模块退出回调；注销驱动 | 加载成功不等于设备已经匹配 |
| 设备绑定 | 总线匹配后调用 `probe()`，成功后建立绑定 | `remove()` 等解绑路径 | 模块可以管理多个设备实例 |
| 打开实例 | 用户态 `open()` 对应文件对象和驱动回调 | 文件对象最终释放时触发 `.release` | 不是每一次 `close()` 都立刻调用 `.release` |

`dup()`、`fork()` 等可以共享同一个打开文件描述；最后一个相关引用释放时才进入最终释放路径。驱动还要考虑解绑时仍有打开实例的情况，不能假设删除节点就消除了已有引用。

## 3. 模块与日志接口卡片

### `module_init()` / `module_exit()`

- **作用与示例**：`module_init(hello_init)`、`module_exit(hello_exit)` 声明初始化和退出回调，不是当场调用函数。
- **参数/返回**：初始化函数通常为 `int callback(void)`，成功返回 `0`，失败返回负错误码；退出函数为 `void callback(void)`。
- **资源所有权**：初始化失败时必须自己回滚此前成功取得的资源，不能指望退出函数自动补救。
- **并发约束**：退出前必须停止设备事件源及异步回调，并处理对象引用；有退出函数不代表自动并发安全。
- **区别与误用**：模块入口不同于普通应用入口，也不同于每个设备的 `probe()`。

### `__init` / `__exit` / `MODULE_LICENSE()`

- **作用**：前两者标记初始化/退出代码段；许可证宏记录模块许可证信息。
- **约束**：模块初始化成功后，标为 `__init` 的代码可被释放，后续运行路径不能再调用它；内建驱动通常不能像模块一样卸载。
- **常见误用**：把回调函数误标成 `__init`；认为写了 `GPL` 就证明代码已经合规或达到工程质量。

### `printk()` / `pr_info()` / `pr_err()`

- **作用与示例**：内核日志接口，如 `pr_info("module initialized\n")`；用户态通常使用 `printf()`。
- **输出位置**：内核日志缓冲区；是否立即显示到控制台取决于日志级别和系统配置。
- **并发与成本**：可用于多种上下文，但高频打印影响时序和性能，不能代替同步；必要时使用限速或设备相关日志接口。
- **排查**：日志访问权限、级别、是否看到了当前模块的记录。不要用清空日志作为排查第一步。

## 4. 字符设备和节点接口卡片

### `register_chrdev()` / `unregister_chrdev()`

- **作用与示例**：`register_chrdev(0, "hello", &hello_operations)` 为一段字符设备号关联操作表。
- **参数**：主设备号为 `0` 时请求动态分配；名称用于注册信息；操作表由驱动提供。
- **返回值**：动态分配成功返回正的主设备号；指定主设备号成功通常返回 `0`；失败返回负错误码。
- **所有权**：成功注册后保存实际设备号，后续注销；注册失败不能按成功路径继续创建设备对象。
- **并发**：注册不会替驱动保护共享缓冲区或实例状态。
- **区别与误用**：注册字符设备不等于自动创建 `/dev` 节点；现代代码也常用 `alloc_chrdev_region()`、`cdev_init()`、`cdev_add()` 管理。

### `class_create()` / `device_create()`

- **作用**：前者创建设备类；后者注册该类中的设备对象并关联设备号、名称，配合 devtmpfs/udev 等机制形成用户态节点。
- **参数**：类名、父设备、`dev_t`、私有数据、节点名称等；具体签名查目标头文件。
- **返回与错误**：成功为对象指针；失败可能为 `ERR_PTR`，使用 `IS_ERR()` / `PTR_ERR()`，不能只与 `NULL` 比较。
- **所有权**：成功创建对象才执行对应 `device_destroy()` / `class_destroy()`；失败按已成功的步骤逆序清理。
- **并发与边界**：设备出现后可能立即被用户打开，内部状态要先准备好；注销节点不能撤回已打开的文件对象。
- **版本提醒**：上游 Linux 6.4 起，`class_create()` 去掉旧的 `THIS_MODULE` 参数；厂商回移可能不同，实际声明优先。

### `struct file_operations`

- **作用**：把 VFS 操作连接到驱动实现，例如 `.read`、`.write`、`.poll`、`.unlocked_ioctl`。
- **参数/返回**：不同成员有不同回调签名；读写通常返回 `ssize_t`，实际处理字节数或负错误码。
- **所有权**：操作表和它引用的对象必须在可能被调用期间有效；`.owner = THIS_MODULE` 有助于模块引用管理，但不替代设备对象生命周期设计。
- **并发**：多个进程或线程可同时进入回调，不能默认串行。
- **误用**：未实现某个成员却假设用户操作必定进入自己的函数；给回调套用不兼容的函数类型。

## 5. 用户态 I/O 与跨空间拷贝

### `open()` / `read()` / `write()` / `close()`

| 接口 | 常见参数与成功返回 | 失败表现与关注点 | 所有权 |
| --- | --- | --- | --- |
| `open(path, flags)` | 路径、访问标志；返回非负文件描述符 | 返回 `-1` 并设置 `errno`；`0` 也可能是合法描述符 | 成功后由调用方关闭 |
| `read(descriptor, buffer, count)` | 最多请求 `count` 字节；返回实际字节数；正长度请求返回 `0` 通常表示 EOF | `-1` / `errno`；关注短读、`EINTR`、非阻塞 `EAGAIN`；零长度请求通常直接返回 `0` | 缓冲区属于用户程序 |
| `write(descriptor, buffer, count)` | 返回实际写入字节数 | 短写、`EINTR`、`EAGAIN`；设备协议未必允许按字节盲目续写 | 同上 |
| `close(descriptor)` | 成功 `0` | 失败 `-1`；Linux 下不要盲目重试，描述符可能已被释放并复用 | 不再使用已关闭描述符 |

内核回调返回负错误码，用户态通常观察到 `-1` 和 `errno`，不是直接收到 `-EFAULT`。同一个打开文件描述可能共享偏移；字符串和二进制整数必须先约定协议。

### `copy_to_user()` / `copy_from_user()`

- **作用**：在内核与用户缓冲区之间复制数据，方向以用户空间为参照。
- **参数**：目标地址、源地址、字节数；地址类型标记常含 `__user`。
- **返回**：未复制的字节数，`0` 才表示全部复制完成；不是成功字节数，也不是普通负 `errno`。
- **资源**：不分配目标缓冲区；驱动必须保证内核缓冲区大小、初始化范围和寿命。
- **上下文**：可能因缺页而睡眠，不能放在硬中断上下文或持有自旋锁的临界区。
- **误用**：直接解引用用户指针；忽略请求长度；部分复制后无条件报告全部成功；复制未初始化数据给用户。

## 6. platform、设备树与 GPIO

### `platform_driver_register()` / `probe()` / `remove()`

- **作用**：注册平台驱动；总线根据设备及匹配表决定是否尝试 `probe()`。
- **返回**：注册函数和 `probe()` 以 `0` 表示成功，负数表示失败；`-EPROBE_DEFER` 表示依赖尚未就绪，不等于永久失败。
- **所有权**：每个设备单独保存资源，失败回滚与正常解绑路径都要完整；不能依赖单个全局指针支持任意多实例。
- **并发**：绑定、解绑、文件操作和异步回调的交叉要单独设计。
- **版本**：不同内核的 `remove` 回调可能为 `int` 或 `void`；I2C 的 `probe/remove` 也有变化。不要抄一份签名跨版本使用。

### 设备树的 `compatible`、`reg`、`status`

- **作用**：描述硬件身份、总线相关地址/资源以及启用状态；不是执行 C 驱动逻辑。
- **匹配链**：启用节点被相应总线枚举 → 匹配表 → `probe()`；不是每个 DTS 节点都直接变成 `platform_device`。
- **`reg` 区别**：MMIO 节点常描述地址/长度；I2C 子节点通常是总线地址；SPI 子节点通常是片选号，解释取决于父总线和 binding。
- **错误排查**：修改的 DTB 是否真被启动器加载、父控制器是否启用、设备是否实例化、依赖是否可用。
- **所有权与并发**：取得设备树节点引用后按所用 API 规则释放；设备树描述不自动解决驱动并发。

### pinctrl / GPIO descriptor API

- **职责**：pinctrl 管复用和电气配置；GPIO API 管输入输出/事件。设备树按 binding 提供资源描述。
- **示例接口**：`devm_gpiod_get()` 请求描述符，失败用 `IS_ERR()`；`gpiod_get_value()` / `gpiod_set_value()` 的逻辑值涉及有效电平。
- **所有权**：`devm_` 资源随设备解绑清理，但不是异步回调自动停止的保证。
- **上下文**：来自可睡眠控制器的 GPIO 需使用适合睡眠的访问接口；不能在硬中断中随意访问。
- **误用**：把逻辑有效值恒等于物理高电平；复制另一块板的引脚号、电压或寄存器地址。

## 7. 等待、poll、通知和 ioctl

| 机制 | 核心语义与返回 | 并发/所有权要求 | 常见陷阱 |
| --- | --- | --- | --- |
| 阻塞 `read` | 无数据时等待条件，满足后重新取数据 | 条件和数据访问要有同步；信号/设备退出要能打断 | 忽略等待返回值；唤醒后假设数据一定还在 |
| 非阻塞 `read` | 无数据时内核返回 `-EAGAIN` | `O_NONBLOCK` 由驱动实现语义 | 返回 `0` 冒充“暂时没数据” |
| `wait_event_interruptible()` | 条件为真返回 `0`；被信号打断可返回 `-ERESTARTSYS` | 不应在持有不可睡眠锁时等待 | 把等待当成锁；忽略错误继续读 |
| `wake_up_interruptible()` | 唤醒等待者重新检查条件 | 先按同步协议发布数据/状态，再唤醒 | 只唤醒却不更新条件 |
| 驱动 `.poll` / `poll_wait()` | 注册等待关系并返回当前就绪掩码 | 不消费数据；检查条件与注册需正确配合 | 认为 `poll_wait()` 自己阻塞等待数据 |
| 用户态 `poll()` / `select()` | 等待多个描述符就绪或超时/错误 | 就绪后仍应处理非阻塞读和竞争 | 把就绪当成已获得一条独占消息 |
| `fasync_helper()` / `kill_fasync()` | 管理异步通知并发送如 `SIGIO` | 需要注册/释放通知关系；应用遵守信号处理约束 | 把信号当作可靠、无丢失的数据队列 |
| `.unlocked_ioctl` | 控制命令成功常返回 `0`，失败负错误码 | 明确 UAPI、长度、权限和兼容性；数据同步由驱动负责 | 以为名称含 unlocked 就无需加锁；不检查用户拷贝 |

`ioctl` 的未知命令通常应返回 `-ENOTTY`，不是无条件成功。现代接口设计还要考虑 `_IO*` 编码、固定宽度字段和 32/64 位兼容；本轮只要求能识别这些风险。

## 8. I2C / SPI / input / framebuffer 的角色

- **I2C**：`i2c_client` 表示设备，`i2c_adapter` 表示控制器/总线访问能力；`i2c_transfer()` 成功返回完成的消息数，应与期望数量比较，非负数也可能不完整。
- **SPI**：`spi_device` 连接设备与控制器，驱动按设备协议组织传输；控制器或设备可能要求特定片选、模式、速率和 DMA 缓冲区条件。
- **input**：驱动报告事件，由输入子系统统一呈现给应用；与每个设备自定义私有字符协议不同。
- **framebuffer/fbdev**：课程中的传统显示抽象；缓冲区布局、像素格式、刷新与 SPI 传输需适配。不能把所有现代显示驱动都归为 fbdev，后续还需了解 DRM/KMS。
- **限制**：普通用户程序不能假设直接访问硬件；但“所有设备逻辑都必须在内核实现”也过于绝对。用户态可以在授权和内核框架支持下使用设备接口，本课程主线学习的是内核驱动。

按 [环境与验证指南](../experiments/驱动入门_环境与验证指南.md) 先完成只打印模块的构建/加载/卸载，再考虑字符设备。观察点包括返回值、内核日志、设备实例、节点和用户态实际字节数；每层分别记录。

## 10. 练习题与验收

- **基础题**：解释模块、绑定设备和打开实例的生命周期差异。
- **改错题**：为何 `copy_to_user()` 返回非零后仍返回请求长度不合理？
- **综合题**：设计注册成功、类创建失败、设备创建失败和正常退出四条资源路径。

验收：能解释所用接口的返回值；能标出所有权；能指出三个版本/并发陷阱；有实验则另附真实证据，无实验则维持“未验证”。完整题目见 [工作簿](../notes/驱动入门_Day2-Day14_练习与验收工作簿.md)。
