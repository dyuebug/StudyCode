## 学到的知识

1. **`chroot` 与 `pivot_root` 的差别在进程之外。** 两者换完之后，进程内的所有读数都一样：
   `/` 是 ext4、`/dev` 是 devtmpfs、旧 `/init` 看不到、挂载表也一样。真正的差别是作用域——
   `chroot` 只改本进程 `fs->root`，`pivot_root` 改整个命名空间。所以只能用"切换前 fork 的观察者"
   去证，本日两组读数：`chroot → watcher_root=tmpfs + watcher_init=visible`、
   `pivot → watcher_root=ext4 + watcher_init=gone`。
2. **`pivot_root` 的三条门槛**：`new_root` 必须是挂载点（否则 `EINVAL(22)`）、`put_old` 必须在
   `new_root` 之下（否则 22）、`put_old` 不能与当前根同一文件系统（否则 `EBUSY(16)`）。
   源码位置 `fs/namespace.c::path_pivot_root()`。
3. **`pivot_root` 不搬挂载点。** `pivot-nomove` 组根照样换成 ext4，但 `/dev` 退化成空目录、
   `dev_vda=absent`。`MS_MOVE` 不是"再挂一次"，搬运后旧位置立刻不可访问。
4. **`umount` 的 `EBUSY` 只有两个来源**（`do_umount()` 末尾的 `propagate_mount_busy()`）：
   有子挂载，或引用计数超出"树内一份 + 调用一份"。分开它们只需要两条读数：
   `mountinfo` 的 `parent` 列（数子挂载）、`readlink /proc/self/fd/N`（找持有者）。
5. **initramfs 里旧根卸不掉的直接原因是 stdio。** `init/noinitramfs.c:18` 的 `default_rootfs()`
   （`rootfs_initcall`，`obj-y` 恒编译）在 rootfs 里建 `/dev/console`（chr 5:1，0600），
   `init/main.c:1603` 的 `console_on_rootfs()` 把它 dup 到 0/1/2；`execve` 不动 fd 表，
   这三个 fd 就一直钉着旧 rootfs。
6. **挂载表不能用来判断 chroot 有没有释放旧根。** 从 chroot 内部读 `/proc/self/mounts` 时，
   旧根那一行被内核隐藏（`mounts_rootfs=0`）；而旧根可达时（挂在 `/oldroot`）它是可见的
   （`mounts|0|/oldroot|rootfs`、`mounts_rootfs=1`）。
7. **`MNT_DETACH` 的 `EINVAL(22)` 可能是好消息**：严格卸载已经成功时再 DETACH，目标已不是挂载，
   于是返回 22。这条读数反过来印证"旧根真的从挂载表里消失了"。

## 实验和验证结果

- **环境**：QEMU 10.2.1 `-M virt`（ARMv7，512 MB，单核，virtio-blk）；内核 `Linux 7.0.14`
  （`~/kbuild/linux-source-7.0.0` 构建）；`arm-linux-gnueabihf-gcc` 15.2.0，
  `-O2 -g -Wall -Wextra -Werror -static`，零警告。
- **产物（实测）**：`stage1` 511332 B、`stage2` 510080 B、`initramfs.cpio.gz` 252159 B、
  `root_ext4.img` 8388608 B。
- **命令**：`./run.sh`（五组全跑）、`./run.sh <case>`（单组）、
  `./run.sh --judge <case> [log]`（只判不跑，`rc` 0/1/2）。
- **结果（实测）**：

  | 组 | 关键读数 | 判定 |
  | --- | --- | --- |
  | `chroot` | 观察者 `tmpfs` + `/init visible`；`mounts_rootfs=0`；`dev_vda=present` | PASS |
  | `pivot` | 观察者 `ext4` + `gone`；`umount_oldroot\|busy\|errno=16` → `detach\|ok` | PASS |
  | `pivot-late` | 卸载前 `mounts_count=5`/`rootfs=1`；`busy(16)` → 重绑 stdio → `ok`；之后 `4`/`0` | PASS |
  | `pivot-nomove` | `move|/dev|skipped`；`dev_type=ext4`；`mounts_dev=absent`；`dev_vda=absent` | PASS |
  | `pivot-ondir` | `pivot_root\|fail\|...\|errno=22`；`stage2\|skipped`；观察者仍见 `tmpfs` | PASS |

  合计 5 组通过、0 组失败；两轮全量运行结论一致。
- **因果实验（本轮核心证据，同一次运行内）**：

  ```text
  PROOT|boot_console|present|mode=020600
  PROOT|fd|1|/oldroot/dev/console
  PROOT|late_umount_keep_stdio|busy|errno=16
  PROOT|ctrl|tmpfs|umount_ok
  PROOT|stdio_rebind|ok
  PROOT|fd|1|/dev/console
  PROOT|late_umount_after_rebind|ok
  PROOT|late_umount_detach|fail|errno=22
  ```

- **负向验证（实测 `rc`）**：首卸改 `ok` → 1；删 `stdio_rebind|ok` → 1；重绑后改 `busy` → 1；
  重绑后 fd 改回旧根 → 1；删 `ctrl|tmpfs|umount_ok` → 1；删卸载前 fd 证据 → 1；
  删 `mounts_rootfs|1` → 1；日志不存在 → 2；未知用例 → 1；原日志 → 0。
- **证据路径**：`experiments/BSP_04_PivotRoot/logs/{chroot,pivot,pivot-late,pivot-nomove,pivot-ondir}.log`
  与同目录 `README.md`。

## 遇到的问题

### 现象 1：`pivot-late` 组按设计失败，且失败的是我自己写的假设

**现象**：该组原设计为"stage1 不卸，交给 `exec` 之后的 stage2 卸"，判据断言
`late_umount|ok`。实测 `late_umount|busy|errno=16`，判定器报 `缺失：PROOT|late_umount|ok`。

**分析过程**：先按源码确认 `EBUSY` 只有两个来源（子挂载 / 引用计数），再加三条取证：
`mountinfo` 的父 id（有无子挂载）、`/proc/self/fd`（谁打开着旧根里的文件）、
现挂一个 tmpfs 做严格卸载（卸载本身可不可用）。读数给出：无子挂载、
`0/1/2 → /oldroot/dev/console`、tmpfs 可严格卸载。

**解决或暂时结论**：改成单变量因果实验——同一次运行内先带着继承的 stdio 卸一次（必失败），
只重绑 0/1/2 到新根的 `/dev/console`，再卸同一挂载（成功）。再用探针确认
`/dev/console` 是内核建的（`mode=020600`，与 `default_rootfs()` 的 `init_mknod` 参数一致）。

**还需验证**：`MS_SHARED` 传播与 `MNT_LOCKED` 分支未覆盖；真板未验证。

### 现象 2：`-Werror` 下 `-Wformat-truncation` 挡住编译

**现象**：`snprintf(path, sizeof path, "/proc/self/fd/%s", de->d_name)`，`path[64]`，
编译器认为 `d_name` 最长 255 字节。

**分析过程**：`d_name` 的定义就是 `char[256]`，上界 15 + 255 = 270。

**解决或暂时结论**：缓冲改为 320 字节并注明上界来源；不放宽 `-Werror`。

**还需验证**：无。

### 现象 3：严格卸载成功之后，兜底 `MNT_DETACH` 报 `EINVAL(22)`

**现象**：`late_umount_after_rebind|ok` 紧跟一行 `late_umount_detach|fail|errno=22`。

**分析过程**：`do_umount()` 里 `EINVAL` 的路径之一是"目标已经不是挂载"（`check_mnt` 失败）。

**解决或暂时结论**：这不是错误，而是"前面真的卸掉了"的自洽证据，已写进判据
（`mounts_rootfs|0` 与它互相印证）。

**还需验证**：无。

### 现象 4：`mount("rootfs", ...)` 做对照时返回 `ENODEV(19)`

**现象**：想再挂一个同类型文件系统做对照，得到 `ctrl|rootfs|mount_fail|errno=19`。

**分析过程**：`rootfs` 不是用户态可挂的文件系统类型（内核自用）。

**解决或暂时结论**：保留这行作为记录，改用 tmpfs 做"严格卸载本身可用"的对照；
"只有内核自建的实例被钉住"这一点改由 stdio 重绑实验间接证明。

**还需验证**：如果要用更强的方式证明"整类 vs 实例"，需要换一个用户态可挂的 ramfs 类型做对照。
