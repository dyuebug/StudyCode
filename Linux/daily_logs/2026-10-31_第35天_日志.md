## 学到的知识

1. **漏调 `input_sync()` 不是丢事件，是帧边界与语义脱钩。** 删掉 `input_sync` 后实测收到 `key_events=24 syn_events=3`——不是 0。机制在 `drivers/input/input.c:351-354`：当 `dev->num_vals >= dev->max_vals - 2`（`max_vals` 初始为 10，即累积到 8 个）时，内核**自动插入 `input_value_sync` 并提交**。于是 24 个按键事件被切成 3 批、每批 8 个，一批跨了 4 次物理按键，用户态无法判断哪几个属于同一次按下。**这比"收不到事件"更难现场定位**：`ev#1..ev#6` 照样一个个打印 OK，只有计数对不上。

2. **`store()` 返回短值不会报错，参数照样被改。** sysfs 的 `DEVICE_ATTR_RW` 展开的 `store()` 必须 `return count`。改成 `return 3`（写入 `"200\n"` 共 4 字节）后实测 `write "200\n" rc=3`，而 `param_demo: interval set to 200ms` 照常打出——**用户态只看到短写，没有任何错误**。`echo` 之类不检查返回值的工具完全察觉不到。

3. **拒绝写入必须返回负 errno；返回 0 与"写了 0 字节"无法区分。** 越界写改成 `return 0` 后实测 `rc=0 errno=0(Success)`。只有 `return -EINVAL` 才让用户态得到 `rc=-1 errno=22`。

4. **只读属性的拒绝发生在 kernfs 层，驱动的 `store()` 根本没被调用。** 写 `stats`（`DEVICE_ATTR_RO`）得 `errno=13(EACCES)`，且不计入驱动自己的 `rejects`（实测 `rejects=2`，只含越界与非数字两次）。**属性权限不生效时，先分清是 kernfs 拒绝还是 store 校验拒绝，两者位置不同。**

5. **`inputN` 与 `eventN` 是两套独立编号。** 实测 `input: qemu-key-sim as .../input/input3` 而事件节点是 `/dev/input/event1`；同一天另一次运行是 `event2`。所以用户态必须按 `EVIOCGNAME` 匹配名字，不能假设编号。

6. **判据没跑和判据跑过是两种状态，只看"全是 OK"分不出来。** `make` 的 `init:` 目标没有先决条件时，make 见 `init` 文件已存在即判定最新，改了 `init.c` 也静默沿用旧二进制。首轮 QEMU 里 Day15 新增判据**一条都没执行**，整体却打印 `result: PASSED (failures=0)`。是 `strings init | grep Day15` 返回 0 才暴露。**判据缺席必须是失败，不能是沉默。**

## 遇到的问题

**现象 1**：首轮 QEMU 里 Day15 的判据一条都没出现，整体却是 `result: PASSED (failures=0)`。

**分析过程**：`ls -l init init.c` 发现 `init` 是 10-25 的旧二进制、`init.c` 是当天的；
`strings init | grep -c Day15` 返回 0。根因是 `Makefile` 的 `init:` 目标**没有先决条件**——
没有先决条件的目标在文件已存在时永远被视为最新。

**解决**：改为 `init: init.c`，重编译后 `strings init | grep -c Day15` 返回 4。

**现象 2**：判据修复后 `key_events=6 syn_events=5 failures=1`，`EV_SYN` 判据失败。

**分析过程**：一帧是 `EV_KEY` + `EV_SYN`，循环在读到第 6 个 `EV_KEY` 时立即退出，
该帧的 `EV_SYN` 还在队列里没读。所以 `syn_events` 恒为 `key_events - 1`，
**唯一能证明 `input_sync()` 生效的判据永远假失败**。

**解决**：退出条件改为帧闭合 `got_key < NEED || got_syn < got_key`。
注意修正后的 `got_syn >= got_key` 在零事件时是 `0 >= 0` 恒真，必须与 `got_key == 6` 联合判读
（负向验证 C 正是这种情形：删 `EV_KEY` 位后 `failures=1` 只由 `got_key` 那条贡献）。

**现象 3**：Day16 首次运行 `[FAIL] Day16 writes 计数 = 3`，驱动实际报告 `writes=2`。

**分析过程**：数错的是我的预期——成功写入只有 `200` 和 `50` 两次；写只读属性 `stats`
的失败在 kernfs 层就被拒绝，驱动的 `store()` 没被调用，因此**不计入 `rejects`**。

**解决**：判据改为 `w == 2`，并把"两类失败位置不同"写进 README 与知识库。

**还需验证**：以上全部是 QEMU 内的软件行为。真实按键的消抖、真实 sysfs 在并发下的可见性、
板上输入延迟，一条都没有验证。
