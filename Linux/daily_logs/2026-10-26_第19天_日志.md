## 学到的知识

1. **三件套的分工是三条独立失败路径**：zImage 管"能不能跑到串口"，DTB 管"知不知道自己在哪块板子上"，
   initramfs 管"根从哪来"。三者失败的现象完全不同，只有先分清路径才谈得上排查。
2. **DTB 是必要输入，不是可选补充配置**：不传 `-dtb`，qemu-vexpress 25 秒零输出。
   ARM 内核在配置串口之前就要读 DT 找 UART——死在最早期，连 panic 都发不出来。
3. **QEMU 会改写你传的 DTB**：磁盘上是 14543 B，内核收到的 `/sys/firmware/fdt` 是 49086 B；
   DTS 里 memory 声明 1 GiB，运行期 DT 里是 512 MiB（被 `-m 512M` 改写）。
   所以"属性真值"只能从 `/sys/firmware/devicetree/base/` 读，不能从磁盘 `.dtb` 推。
4. **`rdinit` 写错不会报"执行失败"**：内核先 `init_eaccess()` 检查，不存在就打印
   `check access for rdinit=... failed: -2, ignoring` 并**丢弃参数**，然后转去挂真实根 → VFS panic。
   对照 7.0.14 的 `init/main.c:1658-1665`，源码与实测一致。
5. **两种缺失可以 panic 在同一行**：`bad-init` 与 `no-initrd` 的 panic 文案逐字相同，
   唯一区别是前面有没有 `Unpacking initramfs...`。判断依据要选在"因果链上游"，不能选在末端。
6. **`panic=1` + `-no-reboot` 是拿来当退出机制用的**：负向用例里内核 panic 后自动重启，
   QEMU 立即退出，日志完整且不用等满超时。

## 实验和验证结果

**环境**：QEMU 10.2.1 `vexpress-a9`，Linux 7.0.14 ARMv7（`arm-linux-gnueabihf-gcc 15.2.0`），
内核树 `~/kbuild/linux-source-7.0.0`，DTB 复用 `tests/qemu-vexpress/100ask-vexpress.dtb`。

**镜像组成（实测）**：

| 件 | 大小 |
| --- | --- |
| `zImage` | 6405304 B |
| `100ask-vexpress.dtb` | 14543 B |
| `initramfs.cpio.gz`（只含一个静态 init） | 267535 B |
| 静态 `init` 未压缩 | 504576 B |

**四组对照（`./run.sh all`）**：

| 用例 | 变量 | 实测现象 |
| --- | --- | --- |
| `normal` | 三件套齐全 | `BOOT\|init\|pid=1` … `BOOT\|root_fstype\|rootfs`，10 项取证齐全，断电退出 |
| `bad-init` | `rdinit=/nosuch/init` | `check access ... failed: -2, ignoring` → `VFS: Unable to mount root fs` panic，有 `Unpacking` 行 |
| `no-initrd` | 不给 `-initrd` | 同样 VFS panic，但**没有** `Unpacking` 行 |
| `qemu-dtb` | 不给 `-dtb` | 25 s 零输出，仅 QEMU 音频后端噪音 |

**关键取证（`normal`）**：`fdt_raw|size=49086`、`dt_custom_node|present`、
`dt_memory|base=0x60000000|size=0x20000000|mib=512`、`rootfs_files|1`。

**未验证**：u-boot 阶段的镜像加载与 `bootz` 参数、真机 DDR 与时钟初始化、块设备根文件系统
（`root=/dev/xxx`、`rootwait`）、systemd/busybox init 的启动流程。

写完后才发现 `tests/qemu-vexpress/` 早已存在且已提交，覆盖范围完整得多。

本次会话前面几轮都在 F103 分支，脑子里沿用了"驱动侧没有运行期证据"的旧结论。

**解决**：删除自建装置（未提交），改为亲手重跑既有装置核实证据，再决定下一步。
**教训**：动手前先枚举已有资产；"我记得没有"不等于"确实没有"。

**现象 2**：预期 `rdinit` 写错会出现 `Failed to execute /nosuch/init`，实测却是 VFS panic。

**分析**：内核在 `kernel_init()` 里先做可达性检查，失败就丢弃参数并转去挂真实根，
根本走不到"执行 init"那一步。

**解决**：读 7.0.14 的 `init/main.c:1658-1665` 确认，并把源码行号写进 README。
**教训**：对内核行为的"预期"必须落到源码或实测，二者缺一就不要写进文档。

**现象 3**：本想断言"`/sys/firmware/fdt` 大小 == 磁盘 `.dtb` 大小"，实测是 49086 vs 14543。

**分析**：QEMU vexpress 在把 DT 交给内核前会按 `-m` 补齐/改写节点，内存节点从 1 GiB 变 512 MiB。

**解决**：把这条"不成立的等价关系"反过来做成知识点，并用 memory 节点数值自证。
**教训**：差一点就把一个错误的断言写进验收标准；能被实测推翻的断言，先实测。
