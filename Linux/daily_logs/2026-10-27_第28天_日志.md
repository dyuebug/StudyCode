## 学到的知识

1. **`ptrace` 的一次系统调用产生两个停点**（entry/exit），统计只能数 entry。
   `PTRACE_O_TRACESYSGOOD` 让停点信号变成 `SIGTRAP|0x80`，否则无法与断点区分。
2. **vDSO 是这类工具的固有盲区**：`clock_gettime(CLOCK_MONOTONIC)` 在 glibc 里不进内核，
   1000 次调用一个停点都没有；只有 `syscall(SYS_clock_gettime,…)` 才现形（`clock_gettime=1000`，
   总 `syscalls=1034`，差值 34 = 加载器与写日志）。
3. **回溯地址有两条相反的规则**：故障 PC 是"正在执行的指令"，原样查；返回地址指向 `call` 的下一条
   指令，必须减 1。首版对 PC 也减 1，`f3` 被解成 `frame_dummy|crtstuff.c:?`。
4. **PIE 下绝对地址查不到符号**：同一帧、同一二进制，`off=0x1309` 得到 `f3|crash.c:80`，
   绝对地址 `0x5d4b4e396309` 得到 `??`。这不是偶发，是方法错了就必定失败。
5. **三组 sanitizer 的失败形态不同**：ASan/UBSan 退出码 1，TSan 66；ASan 的泄漏由 LSan 报，
   类别是 `LeakSanitizer: detected memory leaks` 而非 `AddressSanitizer: ...`。
6. **编译器会消掉缺陷**（本单元最有价值的两条实测）：`-O1` 把 `p[8]=42` 当死存储删掉；
   把"分配后既不读也不 free"整对消掉（`objdump` 里 `leak_alloc` 只剩一条 `ret`）。
   `-fno-builtin-malloc` 不够，必须用 `volatile` 函数指针让编译器失去内建知识。
7. **"没有 perf"是两层问题**：`perf_event_open` 自身用户态 `fd=3` 可用（真读到
   `cycles=80018326`、`IPC=1.25`），systemwide 与他人进程才 `EACCES(13)`。
   缺的是权限和二进制，不是能力。
8. **判定器必须能被证伪**：23 条负向验证里有 2 条第一次就抓出了判定器自身的缺陷
   （见「遇到的问题」），如果只跑一次全绿就收工，这两处会一直藏着。

## 遇到的问题

### 问题一：ASan 首版看不见越界（`rc=0`）

**现象**：`char *p = malloc(8); p[8] = 42;` 跑完 ASan 报 `rc=0`，什么都没打印。

**分析过程**：读反汇编发现该语句整条不见了——`p[8]=42` 之后再没读过那块内存，`-O1` 判定为死存储。

**解决或暂时结论**：改 `volatile char *vp = p; vp[8] = 42;`，`heap-buffer-overflow ... WRITE of size 1`
如约出现。教训写入 README §3.6 与 §8 第 1 条：**工具没报 ≠ 缺陷不存在**。

**还需验证**：`-O2`/`-O3` 下的同类消除行为未系统扫描。

### 问题二：ASan 泄漏用例连试两版都不报

**现象**：`void *p = malloc(64); (void)p;` 无报告；改成"存全局后逃逸"仍无报告。

**分析过程**：`objdump` 显示 `leak_alloc` 只剩一条 `ret`——`-O1` 把"分配 + 不使用"整对消掉了。
加 `-fno-builtin-malloc -fno-builtin-free` 仍无效。

**解决或暂时结论**：用 `static void *(*volatile g_alloc)(size_t) = malloc;` 让编译器失去 malloc 的
内建知识，再短暂存进全局后清空（残留指针留在栈上会让 LSan 认为"还活着"），两步缺一不可。
最终 `ERROR: LeakSanitizer: detected memory leaks` + `64 byte(s) leaked in 1 allocation(s)`，`rc=1`。

**还需验证**：其他编译器（clang）下是否同样需要这两步，未测。

### 问题三：判定器自身三处缺陷（靠负向验证抓出来）

**现象与修正**：

1. `case.rc` 全部取不到（19 条断言 FAIL）——`load()` 把 `S06|case|name=…|begin/rc` 两行 `continue`
   掉了，没进段。修正为"这两行也入段"。
2. 第一次负向验证有 2 条没被抓：
   - 缺日志返回 `1` 而非 `2`——`load(LOG)` 在**模块导入时**执行，跳过了 `main()` 里的
     `except FileNotFoundError`。改为在 `main()` 内加载。
   - `tsan.race_rc_zeroed` 变异没生效——判定器读 `S06|case|name=…|rc=`，我变异的是
     `S06|sani|case=…|rc=`，**同值双写**而判据只校验了一处。改为两边都写变异，
     并新增 13 条 `sani.rc_matches_case` 一致性判据。
3. `sym.has_*` 的函数名列表里混进了 `abs` 反例行的 `??`——`SYMS` 同时存了 `sym` 与 `abs` 两类行，
   取函数名时未按 `|sym|` 过滤。修正后调用链为 `on_sig,f3,f2,f1,main,_start`。

**解决或暂时结论**：每次修正后都回归 `--judge`（101/101）与 `--negtest`（23/23）。

**还需验证**：变异数量仍小于判据数量（21 vs 101），未覆盖的判据是下一轮要补的。

### 问题四：`check_repo.sh` 两处误报

**现象**：`links` 报了 C++ lambda `= [](int fd, …)` 为断链；`tempfiles` 报了
`tests/qemu-stm32/aviation/__pycache__`。

**分析过程**：`git check-ignore` 证实 `__pycache__/` 已被根 `.gitignore:80` 覆盖，
不会入库，不该算残留；lambda 被链接正则误匹配。

**解决或暂时结论**：链接检查跳过含空格或 `<>{},` 的目标；残留检查先过一遍 `git check-ignore`。
两条都写进 `scripts/README.md`，避免下一个人重踩。断链检查做过一次注入验证（注入 `../no_such_dir/x.md`
后 `links` 立刻 FAIL）。

**还需验证**：`check_repo.sh` 只保证结构，不保证"文档结论真的实测过"——后者仍是人工判断。

### 问题五：负向验证的锚点写成了字面量，重跑一次就失效

**现象**：写完文档后从零全量 `make clean && ./run.sh` 重跑，判定器仍 101/101，但
`./run.sh --negtest` 变成 **20/23**，3 条报 `mutated=0`。

**分析过程**：这 3 条（`syscalls=1034`、`median_ns=41.64`、`ns_per_rt=42354.8`）把上一轮的
**实测读数**当成字面锚点，而读数本来就每次不同。规则"锚点找不到计 FAIL"正确地报了错——
如果当初把这种情况当"跳过"，负向验证会在无人察觉的情况下变成空跑。

**解决或暂时结论**：`negtest.py` 重写为"按用例块作用域 + 正则锚点"：变异只能落在目标块内，
数值锚点用 `[\d.]+`。过程中又发现符号行由 `symbolize.py` 统一追加在日志末尾，
**物理上全在最后一个用例块（`crash-ok`）里**，而 `judge.py` 按行内 `case=` 归档，
所以"改哪一块"与"该哪条判据红"不是同一个名字（已在变异表里注释标注）。
改完后在一次全新运行的日志上 23/23 通过——这本身就是跨运行漂移的验证。

**还需验证**：仍有一只"哑"判据漏网的风险——变异数量（21）少于判据数量（101），
未被覆盖的 80 条判据本轮没有独立变异证据。
