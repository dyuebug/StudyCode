## 学到的知识

1. **u-boot 的四件事可以逐条用日志点出来**：装镜像（`bytes read in`）、准备 DT（`Booting using the fdt blob at 0x...`）、
   传命令行（`Kernel command line:`）、跳转（`Starting kernel ...`）。四条缺任何一条，后面的内核日志就没有。
2. **`bootz` 的三参数形式是硬要求**：只给内核地址时 u-boot 打印 `Working FDT set to 0` +
   `FDT and ATAGS support not compiled in` 然后复位。默认环境里的 `fdt_addr=0x40000000` 存在，但**不会被自动采用**。
3. **DT 的字节数取决于谁交给内核**：u-boot 显式 fdt 8192 B，QEMU `-kernel`(virt) 1048576 B，
   BSP_01 的 vexpress 49086 B。同一个内核三份不同大小的 DT——"内核里的 DT 等于我手上的文件"从来不是恒等式。
4. **块设备根是只读挂载**：`VFS: Mounted root (ext4 filesystem) readonly on device 254:0`。
   init 不 remount 就直接 `mkdir /proc` 失败，后面三处 mount 全部 `errno=2`（ENOENT）——
   这是真实 init 系统第一步 remount 的原因，不是约定俗成。
5. **panic 括号里的 `major:minor` 会说话**：`unknown-block(254,1)` 说明 virtio-blk 已被认识（主设备号 254）、
   缺的只是第 1 号分区；`unknown-block(0,0)` 才是连块设备都没有。两种故障、两种修法。
6. **`rdinit` 与 `init` 的适用对象不能混**：块设备根写 `rdinit=/init` 无效，内核按默认序列找
   `/sbin/init`、`/etc/init`、`/bin/init`、`/bin/sh`，全都不在，最后 `No working init found`。
7. **`bootz` 的 initrd 参数只认 uImage/FIT**：裸 `initramfs.cpio.gz` 报 `Wrong Ramdisk Image Format`，
   `mkimage -T ramdisk` 只加 64 B 头（269941 B → 270005 B）就被接受。`CONFIG_GZIP=y` 说明的是
   "能解压"，不是"这条命令会认这个格式"。
8. **有 initramfs 时 `root=` 被跳过，而不是被覆盖**：`rdinit=`（默认 `/init`）指向的文件存在，
   内核就直接跑它，压根不去挂 `root=`。实测命令行明写 `root=/dev/vda rootfstype=ext4`，
   日志里 `virtio_blk ... [vda]` 有、`EXT4-fs (vda)` 一行都没有。判据是 `EXT4-fs (xxx): mounted filesystem`，
   不是 `bootargs` 的内容。

## 实验和验证结果

**环境**：QEMU 10.2.1 `-M virt`（`-m 512M -smp 1`），Linux 7.0.14 ARMv7（`arm-linux-gnueabihf-gcc 15.2.0`），
u-boot 2025.10-0ubuntu2.2 `qemu_arm`（1294880 B），工具链 `mke2fs` / `sfdisk` / `dd` 全部免 root。

**镜像（`mke2fs -d` 生成，未挂载）**：

| 文件 | 大小 | 内容 |
| --- | --- | --- |
| `disk_uboot.ext4` | 25165824 B | `/init` + `/boot/zimage` + `/boot/initrd.uimg` |
| `initramfs.cpio.gz` | 269941 B | newc cpio + gzip，仅含 `/init` |
| `initrd.uimg` | 270005 B | 上一行 + 64 B uImage 头（`mkimage -T ramdisk -C gzip`） |
| `disk_whole.ext4` | 16777216 B | 整盘 ext4，无分区表 |
| `disk_part.img` | 33554432 B | MBR + 20 MiB 分区，ext4 在分区里 |
| 静态 `init` | 507832 B | 加 remount / partitions / dev 取证 |

**八组对照（`bash run.sh`）**：

| 用例 | 变量 | 实测现象 |
| --- | --- | --- |
| `uboot-boot` | 装载 + 显式 fdt + bootargs | `6405304 bytes read in 25 ms`；`Kernel command line:` 与 `BOOT\|cmdline` 逐字一致；根 ext4 on vda |
| `uboot-nofdt` | `bootz` 只给内核地址 | `Working FDT set to 0` → `FDT and ATAGS support not compiled in` → `resetting`，无 `Starting kernel` |
| `uboot-badmagic` | `bootz` 指向未装载内存 | `zimage: Bad magic!` |
| `uboot-initrd` | 同上再装 uImage ramdisk，`rdinit=/init` | `## Loading init Ramdisk from Legacy Image at 48000000 ...`；`Unpacking initramfs...`；`Freeing initrd memory: 264K`；`root_mount dev=rootfs` |
| `uboot-initrd-vs-root` | 同上，命令行再加 `root=/dev/vda rootfstype=ext4 init=/init` | 根仍是 `rootfs`；`partitions` 有 `vda`，但全日志 **0 行** `EXT4-fs` |
| `kernel-whole` | `root=/dev/vda`，无分区表 | `virtio_blk : [vda] 32768 512-byte logical blocks`；`partitions=254:0:16384:vda` |
| `kernel-part` | `root=/dev/vda1`，有分区表 | `vda: vda1`；`partitions=254:0:32768:vda,254:1:20480:vda1` |
| `kernel-nopart` | `root=/dev/vda1`，无分区表 | `VFS: Cannot open root device "/dev/vda1" or unknown-block(254,1): error -6` + panic |

**关键取证**：`BOOT|root_mount|dev=/dev/root|fstype=ext4`（三个块设备用例一致）、
`BOOT|remount_root|ok`（补 remount 后才成立）、`BOOT|fdt_raw|size=8192`（u-boot 路径）、
`BOOT|root_mount|dev=rootfs|fstype=rootfs` + `BOOT|rootfs_files|1`（两个 initrd 用例）。

**未验证**：真实 vexpress 上的 u-boot（需自编源码）、BootROM/SPL 二级引导、SD/eMMC 异步探测与 `rootwait`、
initramfs 内含 busybox 并二次挂真实根的两阶段流程、FIT 形式的 ramdisk、真机 DDR 与时钟初始化。

## 遇到的问题

**现象 1**：所有 `wsl.exe` 调用报 `/bin/bash: not found` 或把命令里的 `$VAR` 展开成空。

**分析**：默认 WSL 发行版是 `docker-desktop`（Running），不是 `Ubuntu`（Stopped）；
那个发行版里没有 bash。另外 Git Bash 会把形如 `/bin/bash` 的参数改写成 Windows 路径。

**解决**：统一用 `MSYS_NO_PATHCONV=1` + `wsl.exe -d Ubuntu -e /bin/bash <脚本路径>`，逻辑一律写到磁盘脚本里。
**教训**：环境不确定时先 `wsl -l -v`，不要假设默认发行版就是工作环境。

**现象 2**：`init` 编译出来是 x86-64，内核报 `Failed to execute /init (error -8)`。

**分析**：Makefile 写的 `CC ?= arm-linux-gnueabihf-gcc`。GNU make 有内建默认值 `CC=cc`，内建默认算"已定义"，
`?=` 根本不生效。BSP_01 之所以没暴露，是因为它的 `run.sh` 在命令行上传了 `CC=...`，把这个洞盖住了。

**解决**：两个 Makefile 都改成 `ifeq ($(origin CC),default)`，并把 `Makefile` 加进目标依赖，
避免改编译器参数后不重编。同时在 `run.sh` 里加 `file init | grep ARM` 断言，让这类错误立刻停在构建阶段。
**教训**：能被"命令行覆盖"掩盖的默认值缺陷，会在别人直接 `make` 时爆发。

**现象 3**：apt 包的 u-boot 在 `vexpress-a9` 上 `-bios`、`-kernel` 两种装载都零输出。

**分析**：包里的 `qemu_arm` 构建是 `CONFIG_TARGET_QEMU_ARM_32BIT=y`、`# CONFIG_TARGET_VEXPRESS_CA9X4 is not set`、
`DEFAULT_DEVICE_TREE="qemu-arm"`——目标是 QEMU `virt`。零输出是因为它跑在不属于自己的机器上，
连串口都没初始化，所以没有任何可诊断信息。

**解决**：改用 `-M virt`，实测一次成功；把机器差异与代价写进 README 的「已知限制」。
**教训**：拿第三方二进制前先读它的构建配置（`TARGET_*`、`DEFAULT_DEVICE_TREE`），比反复试参数快。

**现象 4**：`-drive ...,if=virtio` 加 `root=/dev/vda`，内核报 `Cannot open root device "/dev/vda" ... error -6`。

**分析**：内核配置里 `# CONFIG_PCI is not set`，而 `if=virtio` 在 `-M virt` 上建的是 **virtio-blk-pci**。
设备在 PCI 总线上，内核既没有 PCI 子系统也没有对应驱动，等于不存在。

**解决**：改 `-device virtio-blk-device`（MMIO，`CONFIG_VIRTIO_MMIO=y` 已就绪），立刻出现 `virtio_blk virtio0: [vda]`。
**教训**：半虚拟化设备的"总线"决定了内核能不能看见它；同一句 `if=virtio` 在不同机器上落到不同总线。

**现象 5**：块设备根起来了，但 init 里三处 mount 全部 `errno=2`。

**分析**：`errno=2` 是 ENOENT，看起来像"proc 没编进内核"，真实原因是根以只读挂载，
`mkdir("/proc")` 返回 EROFS 被忽略，mount 时找不到挂载点。

**解决**：init 第一步 `mount(NULL, "/", NULL, MS_REMOUNT, NULL)`，日志里随即出现 `EXT4-fs (vda): re-mounted ... r/w.`。
**教训**：`mount` 报 ENOENT 时要先怀疑挂载点不存在，而不是先怀疑文件系统类型；同时不要忽略 `mkdir` 的返回值。

**现象 6**：u-boot 从 FAT 盘 `fatload` 内核与 gzip initramfs 后，`bootz` 报 `Wrong Ramdisk Image Format`。

**分析**：这份 u-boot 有 `CONFIG_GZIP=y`、`CONFIG_FIT=y`，但 `bootz` 的 ramdisk 校验只接受 uImage/FIT，
裸 gzip 文件不认——"能解压"和"认这个镜像格式"是两件事。

**解决**：先用块设备根绕开并把现象记进 `probes/logs/probe_uboot_load.log`；随后用 `mkimage -T ramdisk`
补包一层（`initramfs.cpio.gz` 269941 B → `initrd.uimg` 270005 B），同一条 `bootz` 立刻通过，
新增 `uboot-initrd` / `uboot-initrd-vs-root` 两组（`logs/uboot-initrd.log`）。
**教训**：`CONFIG_xxx=y` 只说明能力编进来了，不说明某条命令路径会自动使用它；
判据要用命令自己的输出去验，而不是读配置文件。
