## 学到的知识

1. **bootargs 是分层生效的，不是"一串参数"**。无 initramfs 时的顺序是
   `console=`（串口注册）→ `root=`（找设备）→ `rootfstype=`（挂文件系统）→ `init=`（exec 用户态）。
   每一层过了，日志里就多一条唯一的成功行；排查时问"**最后出现的成功行是哪条**"，而不是猜哪一步错。
2. **两个 `VFS: Unable to mount root fs` 不是一回事**。`root=` 错的 panic 里设备字段是
   `unknown-block(0,0)`（没找到设备）；`rootfstype=` 错是 `"/dev/vda" or unknown-block(254,0)`
   （找到了、挂在文件系统层）。设备字段是主次设备号还是 `(0,0)`，这条算术比文字描述可靠。
3. **`init=` 错反而是内核最健康的一组失败**。日志里 `EXT4-fs (vda): mounted filesystem` 与
   `VFS: Mounted root` 都在，只差用户态——看到 `Requested init /nope failed (error -2)`，
   `-2` 是 `ENOENT`，要查根文件系统里那个路径，不要重编内核。
4. **`console=` 没有失败模式**。它是**候选**控制台列表，名字对不上就跳过。所以串口完全没输出时，
   问题在 ① 之前（DTB、内存、时钟），不在 bootargs。
5. **panic 后 QEMU 不会返回非零码**。`-no-reboot` 只阻止重启、不阻止挂住，`timeout` 到点返回 **124**。
   124 是预期的失败形态，不是 harness 缺陷。
6. **三种"余量"不能混读**：链接器尾部（MSP 缓冲）、FreeRTOS 动态余量（唯一能加功能的额度）、
   链接脚本静态预留（`_Min_Stack_Size` 的声明部分）。前两者与第三者合起来才是"MSP 实际能用多少"。
7. **`size` 报的 `bss` 含堆栈预留**。本项目 `bss=6452`，实际静态变量只有 4912，
   差额 1540 来自 `._user_heap_stack`（`NOBITS`）。所以"变量太多"要看 `nm`，不要看 `size`。
8. **FreeRTOS heap 用的是 `.bss` 里的静态数组**，不是链接脚本的 `_Min_Heap_Size`。
   两者并存意味着 RAM 里有**两套堆机制**；`_Min_Heap_Size` 那 512 B 是否真的被 newlib 用到，未验证。

## 遇到的问题

### 1. BSP_05 首轮 3/6 失败：判据字符串是凭印象写的（已修）

**现象**：首轮 `bad-root` / `bad-type` / `bad-init` 三组判为失败，而实验本身的行为完全正确。
**分析过程**：逐份读实际日志，发现三处期望文案都不是内核真实输出：

| 我原本期望 | 内核实际输出 |
| --- | --- |
| `"vdz"` | `"/dev/vdz"`（带路径前缀） |
| `VFS: Cannot open root device`（`bad-type`） | **没有这一行**；实际是 `VFS: Unable to mount root fs on "/dev/vda"` |
| `Failed to execute /nope`（`bad-init`） | `Run /nope as init process` + `Requested init /nope failed (error -2)` |

**教训**：判据文案必须**从实测日志抄**，不能凭印象写。这三条如果我只看"测试失败"就下结论，
会得出"实验做错了"的错误方向——实际是**测试期望错了**。

### 2. `BADARGS|cmdline|absent`：没有 initramfs 时内核不挂 `/proc`（已修）

**现象**：`init` 里读 `/proc/cmdline` 得 `absent`。
**根因**：挂 `/proc` 是 init 的职责，没有 initramfs 时内核不会代劳。
**修复**：`init.c` 里 `mkdir("/proc", 0755)` + `mount("proc", "/proc", "proc", 0, NULL)`，
并在注释里写明这个前提，避免下次再踩。

### 3. `bad-console` 判据用了整行前缀匹配（已修）

**现象**：`bad-console` 判失败，但系统确实完整启动了。
**根因**：`judge_ok` 按 `BADARGS|cmdline|console=ttyAMA0` 这一整串做前缀匹配，
而该组实际行是 `BADARGS|cmdline|console=ttyS9 console=ttyAMA0 ...`（两个 console 参数）。
**修复**：改成两段子串匹配（`BADARGS|cmdline|` + `console=ttyAMA0`）。

### 4. 提交 message 描述失准（已用 amend 修正，非 force push 内容）

**现象**：`7a3834e` 的 message 写"run.sh 也带上了阶段 README 记录的负向验证改进"。
**实际**：`SYS_01/02/03` 的 `run.sh` 改动是新增**裸 `--judge`** 分支（无组名时判定 `logs/` 下全部日志），
用于对齐 `scripts/run_stage.sh` 的接口，与负向验证无关。
**处理**：软回退三个提交、修正该句后重放，`git diff backup-pre-reword HEAD` 为空（文件逐字节一致），
`--force-with-lease` 推送。本地保留 `backup-pre-reword` 分支指向旧历史。
**教训**：写提交 message 时，凡是"为什么改"的因果陈述，先 `git show` 看一眼 diff 再说。
