## 学到的知识

1. **"驱动只做业务、初始化全在 CubeMX"这条约定，责任边界必须看驱动注释才清楚。**
   课程驱动不是"能自己跑"的库：`driver_ultrasonic_sr04.c` 里写着
   `Trig PB9, Echo PB8 在MX_GPIO_Init里被初始化为输出/输入引脚了`，
   这句话就是"我需要你先把引脚配好"的契约。读库先读这段话，比看 `Test()` 更省时间。

2. **同一根线不能有两种空闲电平——这才是"能插、不能同时访问"的机制。**
   M6 超声波与 M12 Flash 共用 PB9：W25Q64 的 CS 低有效（空闲应为高），
   HC-SR04 的 TRIG 靠高脉冲触发（空闲应为低）。课程只给了结论"可以同时接，但不能同时访问"，
   结论背后的物理约束要自己从引脚对照表推出来。选低（让 SR04 可用）时，
   flash 只是被选中而收不到时钟，不会误执行命令——这条是源码推论，未用逻辑分析仪确认。

3. **EXTI 线号是"一个号、十多个端口选一个"，选错端口等于接到别的外设上。**
   EXTI10 默认映射端口 A，而 PA10 正是 USART1_RX。若不显式 `HAL_GPIO_Init(GPIOB, PIN_10)`，
   串口每收一个字节都会触发一次"红外接收中断"。这类错误在代码上完全看不出来，
   只会在真板上表现成"红外莫名其妙收到数据"。

4. **`--gc-sections` 裁不掉"向量表可达"的东西。**
   19 个 `Test` 里只留 1 个是可行的（`nm` 验证），但 `EXTI15_10_IRQHandler → HAL_GPIO_EXTI_IRQHandler
   → HAL_GPIO_EXTI_Callback → IRReceiver_IRQ_Callback/RotaryEncoder_IRQ_Callback` 这条链
   只要中断入口在向量表里就必须在镜像里。这是使用中断驱动型库的固定成本。

5. **`size` 的总 bss 会骗人，`size -A` 才分得清"变量"与"预留"。**
   默认输出 `bss 3176`，`-A` 里是 `.bss 1636` + `._user_heap_stack 1540`。
   1540 B 是链接脚本为堆(512)+栈(1024) 做的溢出检查预留，不是运行期消耗。
   把预留算成消耗会低估余量，反过来会高估。

6. **Keil 的 `fputc` 重定向在 newlib 下是死代码。**
   `driver_uart.c` 定义了 `fputc`/`fgetc`（MicroLIB 的传统做法），但 newlib 的 `printf` 走 `_write`。
   `nm` 里 `_write` 在、`fputc` 不在（被 GC 回收）——这是"符号表能证明的事"，不用猜。

7. **`ARR` 与 `ARR+1` 是同一个边界问题的两种写法。**
   `driver_timer.c:83` 用 `ticks = us * reload / 1000` 换算 1 ms，其中 `reload = ARR = 999`，
   但 CNT 从 0 数到 ARR 共 1000 个值。于是 `mdelay(1000)` 只有 999 ms，每秒少 0.1%，一小时少 3.6 s。
   单看毫秒级看不出来；累积到"用 `mdelay` 当软件时钟"或"500 次轮询超时窗口"就有意义了。

8. **F1 上定时器时钟不等于 APB 时钟。**
   APB1 分频为 2 时，`TIMxCLK = 2 × PCLK1`（36 → 72 MHz）。这行规则写在
   `stm32f1xx_hal_timebase_tim.c:60-67`。而且 `HAL_InitTick` 会被调用**两次**
   （`hal.c:160` 复位时 HSI 8 MHz → PSC=7；`hal_rcc.c:945` 切到 72 MHz 后 → PSC=71）。
   跳过第二次重算，时基会快 9 倍（名义 1 ms 实际 111 µs）。

9. **"占空比"在同一份教材里有两个定义，`OCPolarity=LOW` 时两者互补。**
   教材 §10.1.2 定义占空比为"高电平时间/周期"，§10.3.3 又把 `Pulse` 定义为"有效电平的宽度"。
   红外那组 `473/1895` 按前者是 24.96%、按后者是 75.04%，驱动的注释写的是 75%。
   要回答"LED 实际导通多久"，还缺原理图——这一点教材没讲，是它自身的口径缺口。

10. **换 HAL 时基有两条责任，只做第一条会静默失败。**
    ① 让定时器按 1 ms 产生更新中断（本工程 TIM4 已做）；
    ② 在更新中断里让 `uwTick` 递增（本工程**缺失**：全仓 `HAL_IncTick` 只有声明和弱定义，
    没有调用点，`stm32f1xx_it.c` 也没有 `SysTick_Handler`）。
    后果不是"慢一点"，而是 `HAL_GetTick()` 恒 0 ⇒ `HAL_Delay` 循环条件恒真 ⇒
    所有依赖 `HAL_GetTick()` 的超时判据永不超时。**这是今天最有行动价值的一条。**

11. **"配寄存器"和"开时钟"是两件事，极限情况下驱动只做前者。**
    20 个驱动、75 个公开函数里只有**一处**时钟使能（`driver_led.c:55`，因为它要能独立开机自检）。
    `PassiveBuzzer_Init` 只调 `TIM_Base_SetConfig` 不调 `HAL_TIM_Base_Init`，所以它自己不开 TIM1 时钟，
    能响完全依赖 `main.c` 先调过 `MX_TIM1_Init()`——而 HAL 不会返回任何错误。

12. **静态扫描器的"通过"可能是假通过，要看粒度和去没去注释。**
    我自己写的 `scan_drivers.sh` 踩了两次：先是没有去注释，把 `//extern TIM_HandleTypeDef htim1`
    当成了真依赖（会直接写错引脚冲突表）；再是文档字段检查按"整文件"粒度做，得到 20/20 全过，
    而实际上有 17 个文档块用另一种拼法（`返回值` vs `返 回 值`），按函数粒度会漏判。
    可信的扫描器必须写清：扫什么、什么粒度、去没去注释。

## 遇到的问题

**现象**：把课程 `01_freertos_template` 的 `Core/` 与 20 个驱动放到一起后，构建是绿的，
但读驱动源码时发现多处注释写着"XX 在 `MX_GPIO_Init` 里已经被配置好了"，而这个 `gpio.c`
**全文只有一处 `HAL_GPIO_Init`，配的是 PC13**。

**分析过程**：

1. 先怀疑自己拷贝不全 → 但 `usart.c`/`i2c.c`/`spi.c`/`tim.c`/`adc.c` 的 `HAL_xxx_MspInit`
   都在，AF 引脚（PA9/PA10、PB6/PB7、PA5/6/7、PA8、PA2/PA15/PB3、PB4、PA3）确实齐。
   缺的只是**纯 GPIO**。
2. 再比对课程里所有 `gpio.c`：`01_单片机程序/01_文档配套的源码/01_template` 也只有 PC13；
   只有 `03_参考的源码/.../03_nwatch_dshanmcu-f103_all` 有完整配置（PB0/PB1/PB8/PB9/PB10/PB12/PB14/PB15、
   PA0/PA1/PA4、PC13 + EXTI 段 + NVIC）。但 NWatch 是手表产品，它**没有 PB13**（红外避障）。
3. 结论：**课程里不存在一份"20 个模块全配齐"的 CubeMX 工程**。模板给的是最小骨架，
   学员按需自己加。所以"模板 + 全部驱动"这个组合本身就有缺口，不是拷贝出错。

**解决**：不改 CubeMX 生成物（改了下次重新生成就丢），新增 `Core/Src/lab_pins.c` 只补
"驱动要求、模板没给"的 8 个纯 GPIO + `EXTI15_10_IRQn` 使能，文件头写清每一条的来源与理由。
并在 README §6.1 记账：代价 +288 B text。

**顺带查出一个更隐蔽的**：`driver_ir_receiver.c` 的注释写 "PA10 在 MX_GPIO_Init 中已被配置为双边沿"，
但它自己 `#if 0` 掉的自配置代码是 `GPIO_PIN_10` + `GPIOB`，`driver_irq.c` 也按 `GPIO_PIN_10` 分发，
而 USART1_RX 已占 PA10 → **注释是笔误，实际是 PB10**。更关键的是：
EXTI 线号 10 只有一个，端口由 `AFIO->EXTICR` 决定，不配就默认落端口 A。
已核对 `stm32f1xx_hal_gpio.c:292-295`：`HAL_GPIO_Init` 的 IT/EVT 分支确实写 `AFIO->EXTICR`。

**还需验证**：PB12/PB13 的上下拉选择（课程 `03_nwatch` 对 PB12 用 `NOPULL`，
本工程改用 `PULLUP`；PB13 课程未提，本工程按 LM393 开集输出给 `PULLUP`）。
这两处是工程推断，真板上要实测按键/避障是否稳定，才算闭环。

## 今日复盘

- **已经掌握**：Keil→GCC 迁移要动哪四处（启动文件、链接脚本、`-nostartfiles` 后的 syscall 桩、
  `printf` 重定向），以及每处怎么用符号表验证而不是"看起来对"。
- **只能照着做**：Cursor + clangd 的 `--query-driver` / 8.3 短路径这两条，是踩出来的，
  不是从原理推出来的；换个工具链版本还得再验一次。
- **最值得记录的错**：把"构建绿"当成"配置对"。构建对引脚配置完全不敏感——
  少配 8 个 GPIO 也能 0 error，因为驱动只是在运行时读写寄存器。
  这一次是靠读驱动注释发现的，如果没读，问题要到真板上才以"读数恒 0"的形式出现。
- **如何迁移**：下次接任何第三方驱动库，先 grep 一遍 `MX_GPIO_Init` / `MX_xxx_Init`
  这类"我依赖你配好"的注释，把依赖清单先列出来，再开始编译。

- **晚段已掌握**：定时器从 `CK_PSC` 到引脚电平的整条换算链（`PSC → ARR → CCR → OCPolarity`），
  以及"换时基要两条责任"这件事。这两条都能用算术自证，不需要板。
- **晚段只能照着做**：五个 PWM 驱动的实际极性、红外模块是高电平点亮还是低电平点亮——
  没有原理图，只能给出两种口径并存，不能下结论。
- **晚段最值得记录的错**：把教材"驱动不涉及外设初始化"当成全称命题。
  实测 6 个驱动会自己配引脚、1 个还会自己开 GPIO 时钟，只有外设时钟是真正的边界。
  读文档要把它拆成**可 grep 的命题**再验证，否则会把一句举例当成定律。
  同一类错误在扫描器上又犯了一次：整文件粒度的"20/20 全过"是假通过。
