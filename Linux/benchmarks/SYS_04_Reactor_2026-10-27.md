# SYS_04_Reactor_2026-10-27

实验：`Linux/experiments/SYS_04_Reactor/`（阶段 4，Reactor 三种形态的时延对比）

> **性质说明**：这是"同一把尺子下的形态对比"，不是吞吐压测。
> 8 连接、160 帧、回环网络，**不产生 QPS 结论，不得外推**到真实负载。

## 测试方法

服务端与客户端各一次运行，`run.sh` 逐用例起停：

- 服务端：`./reactor_srv --mode <single|pool|master> [--et|--oneshot|--oneshot-broken|--et-broken] --delay-us N`，
  业务耗时用 `nanosleep(delay_us)` 模拟。
- 客户端：`./loadgen <port> 8 20 200 2000 <gap_ms>`，8 条连接、每连接 20 帧、
  payload 200 字节（帧长 204 字节 = 4 字节大端长度 + payload），
  每连接 payload 用不同字节填充（`'a' + idx % 26`）以捕获串包。
- `TCP_NODELAY` 打开；`SO_RCVTIMEO = SO_SNDTIMEO = 2000 ms`。
- 时间基准：`clock_gettime(CLOCK_MONOTONIC)`，客户端统计 `total_ms`（建连到收尾），
  服务端统计 `serve_ms`（进入主循环到退出）。
- 每个用例的服务端 `--idle-exit` 默认 400 ms；两个破坏版用 `--max-run 6000` 强制退出。

复现命令：

```bash
cd Linux/experiments/SYS_04_Reactor
make && ./run.sh                      # 产出 logs/reactor.log 并自动判定
python3 -I judge.py logs/reactor.log  # 26/26
python3 -I negtest.py                 # 判定器负向验证 14 次
```

## 结论（仅限本环境）

1. **线程池把业务耗时挪走后接近线性**：`pool4 = 85 ms`，为 `single = 339 ms` 的 25%，
   与 4 个 worker 一致量级。
2. **主从双 sub 约 2 倍**：`master2 = 169 ms`，为 `single` 的 50%。低于 4 worker 是因为
   sub 数只有 2，且 accept 与转交仍在主线程单点。
3. **ET 在此规模无收益**：`et = 338 ms` vs `single = 339 ms`。ET 被证明的只有正确性。
4. **`single` 的串行下限成立**：339 ms ≥ 160 帧 × 2 ms = 320 ms 的理论串行耗时。
5. **破坏版必然失效**：`et-broken` 服务端只处理 8 帧、客户端 0 帧；`oneshot-broken`
   服务端 8 帧（每连接恰好第一帧）、客户端 8 帧。两者都因"连接静止收不到 FIN"撞上
   `--max-run`，说明"只靠连接空闲判定退出"的服务器退不出去。

## 限制

- 8 连接 / 160 帧 / 回环，未做连接数与吞吐扫描；无 QPS、无 p99 延迟分布。
- `--delay-us` 是人为 `nanosleep`，不代表任何真实业务的计算分布。
- 主循环 `epoll_wait` 超时 50 ms 为轮询退出条件而设，不是延迟指标。
- 未测真实网络（RTT/丢包/重传）、`SO_REUSEPORT`/`EPOLLEXCLUSIVE` 惊群、
  `accept4`、写缓冲背压（`buf_drops` 从未触发）。
- 未做竞争检测（环境无 `gdb`/`valgrind`/`perf`，且不允许 `sudo` 安装）。
- 时间读数跨运行漂移几十毫秒，判定器一律用倍数关系与下限，不写死常量（见实验 README
  「跨运行漂移」）。
