# Day10 学习讲解：APP 与驱动更多交互方式

> 本日主线：数据不是随时都有时，应用怎么等待、驱动怎么发布、信号和退出怎么处理。
> 建议拆两次完成 120～150 分钟内容：先阻塞/非阻塞与 poll，再预览异步通知和 ioctl。

## 1. 先分清数据、等待、通知和控制

这些机制不是一条必须依次替换的升级路线，而是解决不同问题，可以同时存在。

| 机制 | 主要回答什么 | 不代表什么 |
| --- | --- | --- |
| `read/write` | 数据如何交换 | 不保证数据随时可用 |
| 阻塞 read | 没数据时能否等待 | 不是 CPU 不停循环查询 |
| 非阻塞 read | 暂时不能完成时尽快返回 | 不等于自动异步执行 |
| `poll/select` | 多个描述符中哪些当前可操作 | 不预留或消费那条数据 |
| `SIGIO` 异步通知 | 有事件时提醒应用 | 不是无丢失消息队列 |
| `ioctl` | 传递配置/控制命令 | 不天然免锁或自动安全 |

## 3. 用三个状态定义读的语义

建议实验协议先定义“运行但无数据 / 有数据 / 已停止”，而不只是空或非空。

| 状态 | 阻塞 read | 非阻塞 read | poll |
| --- | --- | --- | --- |
| 运行、队列空 | 等待事件或停止/信号 | `-EAGAIN` | 当前无可读数据 |
| 运行、队列有记录 | 按同步协议取记录 | 同样可以立即取记录 | 返回可读掩码 |
| 已停止且队列空 | 按约定返回错误或 EOF，不永久等待 | 同样遵守停止语义 | 按约定返回 HUP/ERR 等 |

停止时是否允许读完残留记录、之后返回 `ENODEV` 还是 EOF，应由接口明确规定。零长度请求通常立即返回 0，不能把它与正长度读到 EOF 混为一谈。

用户态无数据通常观察到 `read` 返回 `-1` 且 `errno = EAGAIN`，不是返回 `0`；`0` 不应冒充“请稍后重试”。

## 4. 驱动等待时，到底是谁睡眠

应用线程进入驱动的进程上下文后，可以在条件不满足时被加入等待关系并让出 CPU。不是整个驱动或中断系统都睡着，也不是锁着共享队列不停忙转。

`wait_event_interruptible()` 会检查条件并参与等待/唤醒协议。正常满足条件时返回 0，被信号打断时可能返回 `-ERESTARTSYS`；系统调用层依据重启规则，让用户看到 `EINTR` 或重新执行。

合理的读取框架应表达下面这些步骤，具体加锁方式依生产者上下文设计：

```text
检查请求长度
循环：
  按同步协议检查队列与停止状态
  有记录 -> 原子地取得一条，释放相应锁后离开循环
  已停止 -> 释放相应锁，按约定结束
  非阻塞 -> 释放相应锁，返回 -EAGAIN
  解开不能跨等待持有的锁
  等待“有记录或已停止”
  若被信号打断 -> 处理/返回错误，不继续假装有记录
按交付协议拷贝给用户，处理拷贝失败
```

等待条件的读取也必须符合锁/内存可见性协议，不能只给入队加锁而让所有条件读取随意竞争。唤醒不是锁，不会替消费者独占记录。

## 5. 生产者必须先发布状态，再唤醒

本例由定时器回调采样 GPIO，编码按键信息，调用 `put_key()` 入队，然后 `wake_up_interruptible()` 和 `kill_fasync()`。

```text
事件到来 -> 采样/编码
  -> 按同步协议发布记录及队列状态
  -> 唤醒等待者 / 通知应用
  -> 消费者重新检查并竞争取得记录
```

如果只唤醒而不改变等待条件，线程醒后仍应继续等待。若先唤醒、后更新又没有正确同步，就可能出现错过状态变化的问题。

本例环形数组长度 128，使用一个空槽区分满/空，可用容量是 127；满时 `put_key()` 直接不存，没有报告溢出。事件密集时，“收到几次通知”不等于保存了几条记录。

## 6. `poll_wait()` 不会在回调里等到事件

驱动 `.poll` 一般做两件事：

1. 通过 `poll_wait(file, &wait_queue, wait)` 注册等待关系。
2. 检查当前状态并返回就绪掩码，如 `POLLIN | POLLRDNORM`。

它不是在 `.poll` 内调用阻塞 read。先注册等待关系再按同步协议检查状态，有助于覆盖注册/检查之间的状态变化；实际检查、唤醒与锁需要一起设计。

用户 `poll()` 返回值大于 0 时还要检查各项 `revents`；等于 0 表示超时；小于 0 要检查 `errno`。`select` 同样属于就绪等待，不能把就绪当作已经取到数据。

假设两个读者都收到可读，其中一个先拿走最后一条：另一个随后 read 仍可能无数据。常用策略是以非阻塞方式打开并在 read 时处理 `EAGAIN`，继续等待，而不是认定驱动一定出错。

## 7. 原始 read 路径哪里不完整

现有 `gpio_key_drv_read()` 检查了 `O_NONBLOCK`，但随后忽略等待返回值，直接取队列并固定拷出 4 字节。还存在：

- 请求长度、零长度和短缓冲区未完整处理。
- 信号打断后可能继续取空队列，将默认值当事件返回。
- 队列读写下标及数据缺少完整并发保护。
- 唤醒后被其他读者抢先消费，没有可靠的重新检查/取出协议。
- 用户拷贝失败仍报告成功；事件是否丢失没有约定。
- 没有完整停止状态与解绑时等待者的唤醒/引用管理。

因此本日先源码分析，不将原文件视为可安全压力测试的驱动。

## 8. 异步通知：提醒不是交付

典型应用先设通知接收者，再用 `fcntl` 启用 `O_ASYNC`；驱动 `.fasync` 通过 `fasync_helper()` 管理通知关系，事件发生时 `kill_fasync()` 发送如 SIGIO。

信号可能合并、延迟到达，应用仍要通过非阻塞 read 等接口取得真实数据。普通信号处理函数不能随意调用 `printf()`、内存分配等非异步信号安全操作；更完整的程序可采用安全的信号处理/转交方式。

要核对目标 VFS 和驱动在关闭文件、取消通知以及设备解绑时的清理路径，不能仅因代码没有 `.release` 就断言 VFS 不会调用 fasync 关闭清理，也不能认为内核机制替你解决了所有设备寿命问题。

本轮只需画出注册、通知、读取、关闭四步，不要求实现另一套完整应用。

## 9. ioctl 预览：控制协议要单独设计

控制命令适合表达配置、模式或查询等不自然属于字节流的操作。现代字符驱动常通过 `.unlocked_ioctl` 接入；`unlocked` 表示不再由旧的大内核锁包办，不表示无需同步。

一个可维护的接口需要约定：命令编号、方向与大小、固定宽度字段、允许范围、权限、用户拷贝错误、未知命令的 `-ENOTTY`，以及 32/64 位兼容。`_IO/_IOR/_IOW/_IOWR` 等编码有助于描述协议，但不会自动校验一切。

先辨别命令再读取相应参数；控制成功通常返回 0，错误返回负错误码。不能复制 Day3 的读写长度返回规则到所有 ioctl。

## 10. 五条必做测试设计

以下预期针对已经明确语义并修正的实验副本，不是原代码的保证。

| 输入/场景 | 预期与观察 | 结束/清理条件 |
| --- | --- | --- |
| 运行但无数据 | 非阻塞 EAGAIN；poll 到期返回 0；阻塞读等待 | 测试有期限，可取消 |
| 等待中发布一条记录 | 唤醒、可读、返回完整记录 | 读完关闭文件 |
| 阻塞期间收到信号 | 按重启规则处理 EINTR/重启，不伪造事件 | 应用按约定退出或继续 |
| 两个读者竞争一条记录 | 不重复消费；另一方 EAGAIN 或重新等待 | 两者都能正常结束 |
| 等待中停止设备 | 发布停止状态并唤醒，不永久睡眠/访问已释放对象 | 引用和回调均退出 |

无硬件时完成时序图和测试表；有匹配 BSP/事件源时，先修正错误与退出路径，再做有限次数实验。软件注入只能算软件接口证据，不算真实按键电气验证。
