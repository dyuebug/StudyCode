## 3. 匹配不是所有规则同时生效

常见上游 platform 匹配过程会先处理 `driver_override`，再尝试 OF（设备树）、ACPI、ID 表，最后才在适用条件下做名称比较；具体以目标内核 `platform_match()` 为准。

要避免一个常见误解：**驱动存在 ID 表但表内找不到时，不能一概说“还会兜底比名称”**。常见实现会直接返回 ID 表查找结果。Day6 无 ID 表的简单名称匹配，与本日有 ID 表的行为不同。

`driver_override` 也不是强行跳过所有初始化：它影响候选驱动选择，资源仍需申请，`probe` 仍可能失败。旧示例直接给该字段赋字符串；新内核有专门的设置与内存管理规则，不应把旧结构体初始化方式跨版本照搬。

本日的 `led_id_table` 第二维数据 `1/2/3` 可作为型号区分信息，但当前 `probe` 没有实际使用它。不要凭表存在就声称实现了不同硬件策略。

## 4. 匹配、探测、绑定是三件事

```text
设备进入总线，驱动也已注册
  -> 总线判断匹配
  -> 调用 probe 尝试初始化
       -> 成功：建立绑定
       -> 失败：回滚本次资源，不产生正常绑定
       -> -EPROBE_DEFER：依赖未就绪，等待后续重试机会
```

`probe` 可以被多次尝试，一个驱动也可能对多个设备各调用一次。它不能被误标为仅初始化阶段可用的 `__init` 回调。

`remove` 用于已经绑定设备的解绑清理，常见原因包括驱动注销、设备注销或明确解绑。失败的 `probe` 需要自己回滚，不能等待 `remove` 来收拾未完成的初始化。

## 5. 沿 `led_probe()` 追实例数据

源码先用 `platform_get_resource(pdev, IORESOURCE_IRQ, 0)` 取资源，再用全局计数作为次设备号，写入 `leds_desc`，创建设备对象，并把对应记录保存为 drvdata。

其中资源 `.start = (3 << 8) | n` 是课程的引脚编码演示，虽然标记为 `IORESOURCE_IRQ`，**不能直接把这个整数当作 Linux IRQ 号使用**。真实驱动应按资源类型/binding 取得正确的 GPIO 或 IRQ。

`platform_set_drvdata()` 不会复制结构体，也不会自动申请或保护它。这里保存的是全局数组某一项的地址；`remove` 再通过 `platform_get_drvdata()` 找到它，按次设备号删除设备对象。

阅读时逐项问：分配是否越界？失败是否消耗了编号？解绑后编号是否回收？旧打开文件会不会仍指向这项？

## 6. 三种生命周期并排看

| 层次 | 建立/开始 | 结束 | 关键边界 |
| --- | --- | --- | --- |
| 模块 | 初始化函数注册驱动 | 退出函数注销驱动 | 模块存在不等于有设备绑定 |
| 设备绑定 | 匹配后 `probe` 成功 | `remove`/解绑 | 每个设备一份状态 |
| 打开实例 | 应用 `open` 创建/关联文件状态 | 最后一个打开文件引用释放 | 节点删除不撤销已有文件引用 |

例如设备解绑后，驱动模块仍可能留在系统；节点已删除，但已有文件描述符仍可能调用操作表。`.owner` 管模块引用的一部分，不等于保住了被 `remove` 释放的设备私有数据。

这就是为什么“先删 `/dev` 节点，再释放一切”不是充分的退出协议。

## 7. 给 `probe` 写资源回滚表

下面是设计方法，不宣称原始源码已经实现：

| 成功取得的资源 | 下一步失败时 | 正常解绑时 |
| --- | --- | --- |
| 私有对象 | 释放对象 | 所有访问者退出后释放 |
| GPIO/MMIO/IRQ 等 | 只回收已成功取得的部分 | 先停止事件来源，再回收 |
| 用户可见设备对象 | 撤销发布并收回编号 | 阻止新访问，处理已有引用 |
| 等待者与异步任务 | 唤醒/取消并等待结束 | 同样需要停止协议 |

任何时候只能释放成功取得且属于本实例的资源。顺序不仅是机械逆序，还必须满足依赖：不能在回调可能运行时释放它访问的对象，不能持有回调需要的锁再同步等待回调结束。

`devm_` 能减少部分回滚代码，但不自动解决打开文件、停止标志、work 重排队与用户协议。

## 8. 现有 LED 详细示例的限制

至少找出以下问题中的三项并标注函数位置：

1. `g_ledcnt` 没有完整上限检查，反复探测可能越过 `LED_MAX_CNT`。
2. `remove` 删除节点，却没有回收/重新管理计数和编号。
3. `device_create()` 的失败没有完整处理。
4. 驱动注册失败时，模块初始化已经创建的类与字符设备号没有完整回滚。
5. 写回调忽略用户拷贝结果，缺少长度、次设备号范围与并发校验。
6. 用户打开与设备解绑交叉的对象寿命未处理。

这些缺陷使它更适合作为源码分析材料。不要在原实现上反复 bind/unbind 做压力测试来“试试看”。

## 9. 四种情况怎样推演和验证

| 场景 | 合理预期 | 应收集证据 |
| --- | --- | --- |
| 设备先、驱动后 | 驱动注册时尝试探测匹配设备 | 两次注册日志、probe 结果、绑定关系 |
| 驱动先、设备后 | 设备注册时找到候选驱动 | 设备出现时的 probe 日志 |
| 身份不匹配 | 两端可存在，但不会由此驱动接管 | sysfs 设备存在而无该绑定 |
| 依赖未就绪 | `probe` 可能返回延后错误 | 具体返回码、缺失依赖与后续重试 |

无板时画出四条调用图。有可恢复 Linux 时优先用 Day6 的纯日志示例验证前两项；本日详细 LED 副本必须先完成 API、范围、回滚与生命周期审查再加载。延后探测不一定能由纯日志示例直接产生，不要编造该现象。

## 10. 第一次复盘：理解与证据分开

在工作簿阶段验收表逐项填两栏：

- 理解：0 不会说明；1 有提示能解释；2 能独立解释并给出源码依据。
- 实验：未执行、构建失败、构建通过、接口验证、仿真或真实板卡；附真实证据。

重点回看：构建产物、设备号/协议、用户拷贝、主机/目标、设备/驱动/总线、三种生命周期。列出最弱的两个前置项，并各写一个可以观察到结果的补课动作。

能解释不等于能独立修改，能修改不等于已构建，构建通过也不等于安全退出。阶段复盘不要合成一个虚假的完成率。
