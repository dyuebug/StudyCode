# Day9 学习讲解：Pinctrl 和 GPIO

> 本日主线：把引脚复用、电气状态、GPIO 逻辑值和 IRQ 映射分开，再串回设备树与 probe。
> 缺原理图、板卡型号或电平信息时，只做分析，不靠猜引脚开展实验。

## 1. 同一个引脚为什么要分几层看

一个 SoC pad 可以复用为 GPIO、UART、SPI 等功能，还可能有上拉、下拉、驱动强度等电气配置。外设数据路径是否工作，既取决于复用，也取决于方向、电平和接线。

因此“知道 GPIO 编号”远远不够。今天用 75～100 分钟完成职责表、按键 IRQ 源码追踪与一张资源卡；真实接线和调试另计。

## 2. 四个角色各做什么

| 角色 | 主要职责 | 不是它单独负责的事 |
| --- | --- | --- |
| 设备树/binding | 描述连接、控制器引用、有效电平和状态 | 不执行实际读写算法 |
| pinctrl | 引脚复用及相关电气配置/状态 | 不等于应用事件队列 |
| GPIO controller | 提供方向、电平等 GPIO 能力 | 不自动理解设备业务含义 |
| GPIO consumer 驱动 | 申请线、按协议使用逻辑值/事件 | 不应绕过所有者随意抢占引脚 |

有些系统会由驱动核心或子系统选择 pinctrl 的 `default` 状态，有些需要驱动显式选择其他状态；不能一律要求每个驱动手动写相同的 pinctrl 初始化。`sleep` 等状态还能配合电源管理。

GPIO 与 pinctrl 有关联，但不是所有引脚功能都先“作为 GPIO 用”。例如配置成 SPI 功能后，主要由 SPI 控制器驱动传输，而不是应用用 GPIO API 模拟每个时钟。

## 3. 三种编号不要混用

- 原理图/封装上的 pad 名称：表示具体物理引脚及连接。
- 某 GPIO controller 内的 line offset：表示该控制器中的第几条线。
- 旧式 Linux 全局 GPIO 整数：依平台和注册关系映射，不能跨板照抄。

Linux IRQ 号又是独立命名空间。GPIO line 需要通过对应映射接口获得 IRQ，不能拿原理图脚号、旧全局 GPIO 号或 Day7 的教学位编码直接调用 `request_irq()`。

## 4. 设备树中的引脚描述怎样到达 consumer

典型 consumer 节点通过 `<名称>-gpios` 引用 GPIO 控制器、线偏移及控制器定义的标志；通过 `pinctrl-names` 与 `pinctrl-0` 等引用引脚状态。实际 cell 数和配置格式由控制器 binding 决定。

例如驱动按连接名 `led` 调用 `devm_gpiod_get(..., "led", ...)`，通常对应 `led-gpios`；不是去读 Day8 的私有字符串 `pin = "gpio5_3"`。

获取流程需要检查：

1. 属性是否按 binding 命名和编码。
2. 控制器驱动是否已经就绪；未就绪可能得到 `-EPROBE_DEFER`。
3. 引脚是否被其他 consumer 占用。
4. 获取函数是否返回 `ERR_PTR`；用 `IS_ERR/PTR_ERR`，不能只判空。
5. 初始化方向和逻辑电平是否符合设备安全状态。

`gpiod_get()` 成功后要对应 `gpiod_put()`；`devm_gpiod_get()` 由设备资源管理机制回收。两者都不意味着异步回调可以在解绑后继续访问。

## 5. 逻辑有效值不等于物理高电平

descriptor API 通常按有效极性转换逻辑值。以低有效 LED 为例：

| consumer 逻辑值 | 意义 | 典型物理电平 |
| --- | --- | --- |
| 1 | 断言/有效，LED 应点亮 | 低 |
| 0 | 撤销/无效，LED 应熄灭 | 高 |

高有效接线则相反。还要确认电路、电源与输出方式，不能只靠这张表推断某块未知板的实际电压。raw 访问与逻辑访问不同，本轮不以 raw API 绕过描述中的极性。

按键也一样：`gpiod_get_value()` 得到的逻辑值、原始电平以及物理按下状态之间，需要按 binding 与接线解释。给 API 读到的 `1` 直接起名“高电平”很容易误导后续事件编码。

## 6. 哪些 GPIO 访问可能睡眠

SoC 内部 GPIO 与经 I2C/SPI 扩展的 GPIO，访问代价和上下文限制可能不同。对于可能睡眠的控制器，应在允许睡眠的上下文使用相应 `_cansleep` 访问接口。

硬中断、tasklet、普通定时器回调不能随意调用可能睡眠的 GPIO 访问。不能为了消除告警把函数名字简单换掉：应把采样安排到线程化 IRQ 或 work 等允许睡眠的路径，并明确同步/停止协议。

`gpiod_cansleep()` 可辅助判断，但它不替代对整个调用路径的设计。Day11 会比较硬中断、定时器、work 和线程化中断。

## 7. 本日实际源码：只追 IRQ 获取

课程 [第8章资料](../../08_设备树示例_Pinctrl和GPIO/doc_pic/08_设备树示例_Pinctrl和GPIO.md) 和 [第9章资料](../../09_Pinctrl和GPIO/doc_pic/09_Pinctrl和GPIO.md) 主要给视频入口。本日可追踪的本地代码是 [01_irq_for_test/gpio_key_drv.c](../../10_应用程序和驱动程序的更多交互方式/source/01_irq_for_test/gpio_key_drv.c)。

逐步读 `gpio_key_probe()`：

1. 没有 OF 节点时，从 `platform_get_resource(..., IORESOURCE_IRQ, 0)` 取得 IRQ 资源。
2. 有 OF 节点时，用 `of_irq_get(node, 0)` 取得第一个中断映射。
3. 用上升沿和下降沿请求 IRQ，ISR 中打印计数。
4. `remove` 通过同一 IRQ 与 `dev_id` 配对释放。

这里 **OF 分支直接读取 interrupts 描述，不是先调用 GPIO 获取 API 再转 IRQ**。函数前的教学注释不能代替实际调用证据。它也没有提供完整字符设备读写或引脚 consumer 申请示例。

若采用另一种描述方案，可以先取得 GPIO descriptor，再通过 `gpiod_to_irq()` 转换。两条路线都要遵守对应 binding，不能从这份 ISR-only 示例推断已经配置了所有 GPIO/pinctrl。

## 8. 必须补看的错误路径

现有例子应至少审查：

- `of_irq_get()` 的负返回值是否被完整处理，尤其是延后探测。
- 取得 IRQ 失败时是否还错误地进入 `request_irq()`。
- 触发沿由何处定义，是否与设备、电路和 IRQ controller 能力一致。
- `request_irq()` 成功后中断可能立刻发生，ISR 依赖的状态是否先准备好。
- 全局 IRQ 变量是否只适合单实例，能否正确应对第二个设备。
- 请求和释放时的 `dev_id` 是否配对；共享 IRQ 更需要区分实例并判断来源。

中断 handler 返回 `IRQ_HANDLED` 表示该中断被处理，不是向用户程序返回一条数据。应用交互要在 Day10 通过队列、等待与回调连接起来。

## 9. 今天的资源卡和分步实验

### 无板必做

| 资源卡字段 | 要填写的内容 |
| --- | --- |
| 板卡/器件 | 型号、修订、手册来源；未知就写待确认 |
| 物理连接 | pad、连接器管脚、供电和输出允许电压 |
| 复用/电气 | pinctrl 状态、上下拉、驱动设置 |
| GPIO 语义 | controller、line offset、方向、有效极性 |
| IRQ 语义 | 映射方式、边沿/电平、共享与去抖需求 |
| 所有者 | 当前是否由其他驱动或系统功能占用 |
| 驱动获取 | 属性名、使用 API、失败返回与清理 |
| 证据 | 源码推断、软件观测、真实电平分别填写 |

### 有板条件实验

1. 确认供电、输入耐压、共地与安全接线，不在不支持热插拔的情况下带电改线。
2. 核对正在使用的 DTB、节点状态、父控制器和实际绑定。
3. 在副本补齐错误处理/退出后加载，只产生有限次数事件。
4. 对照真实信号、IRQ 计数和日志，区分抖动与独立按键操作。
5. 停止事件和消费者，正常卸载，确认 IRQ/设备资源已回收。

不要对工作系统关键引脚试验；没有实测就不填电压、响应时间或中断次数。
