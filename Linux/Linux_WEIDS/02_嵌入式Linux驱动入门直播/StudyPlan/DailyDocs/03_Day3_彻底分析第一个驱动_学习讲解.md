## 3. `Makefile` 到底告诉了我们什么

本目录 `obj-m += hello_drv.o` 告诉 Kbuild 将其构建为外部模块，最终预期产物为 `hello_drv.ko`。这不等同于执行普通的 `gcc hello_drv.c`。

- `make -C $(KERN_DIR)`：让目标内核构建系统工作。
- `M=...`：指明外部模块源码所在目录。
- `modules`：请求构建模块。
- `KVERSION = $(shell uname -r)`：取执行构建命令所在系统的内核版本；只适合已确认的本机模块场景。

**本目录 `all` 没有编译 `hello_drv_test.c` 的命令。** 因而不能因为目录中有测试源码，就认为 `make` 已生成测试程序。

如果只练习用户态构建，可在 Linux 实验副本中单独运行：

```bash
gcc -Wall -Wextra -O0 -g -o hello_drv_test hello_drv_test.c
file ./hello_drv_test
```

这只证明应用能编译，不证明驱动已加载或协议正确。跨板时还要改用目标工具链，并核对根文件系统 ABI。

## 4. `/dev/xyz` 如何连接操作表

应用的路径名首先经过文件系统解析。对于字符设备节点，VFS 根据设备号进入字符设备层，再找到驱动注册的操作表。

```text
用户态：write(descriptor, user_buffer, requested_count)
  -> 系统调用 / VFS
  -> 字符设备号与对应操作表
  -> hello_fops.write = hello_write
  -> 从用户缓冲区复制数据到 ker_val
  -> 回调返回实际处理长度或负错误码
  -> 用户态得到字节数，或 -1 并设置 errno
```

主设备号用于组织字符设备的操作映射，次设备号常用于区分驱动管理的实例。现代驱动也常用 `cdev` 系列接口显式管理范围；今天先理解课程 `register_chrdev()` 路线。

此驱动只有字符设备注册，没有类和设备对象创建。因此 `/dev/xyz` 不会凭空出现。若要手工建节点，必须在隔离目标上使用**本次实际分配**的主设备号和确认的次设备号；不能照抄课程截图，更不能覆盖系统已有节点。

## 5. 逐步追一次写入和读取

源码中的状态是 `ker_val`，初始为整数 `123`。

### 写入路径

1. 应用传入缓冲区地址与请求长度。
2. 驱动 `hello_write()` 无条件从该地址复制 4 字节到 `ker_val`。
3. 没有检查 `size`，也没有检查用户拷贝是否完整。
4. 不论实际是否成功，都返回 `4`。

### 读取路径

1. 应用提供目标缓冲区及容量。
2. 驱动无条件复制 `ker_val` 的 4 字节表示。
3. 没有处理小缓冲区、零长度请求、拷贝失败和文件偏移。
4. 每次都返回 `4`，没有 EOF 行为。

所以原实现不是“写一段任意字符串，再完整读回”。`cat` 通常会持续读到 EOF，而这里没有 EOF，可能形成无界重复读取与日志输出。先用有限次数、明确长度的专用测试程序。

## 6. 测试程序暴露出的协议错位

测试程序写入 `strlen(text) + 1` 个字节，读取后又按 `%s` 打印；驱动却把内容当作 4 字节整数。

| 不一致 | 可能后果 |
| --- | --- |
| 应用发送字符串，驱动取固定 4 字节 | 长文本被截断；短文本请求之外的数据可能被读取 |
| 应用读取整数表示却用 `%s` | 输出乱码或读到未初始化的缓冲区内容 |
| 仅在 `buf[1023]` 放终止符 | 不等于有效读取区间之后立即终止，也不能弥补协议错误 |
| 路径写死为 `/dev/xyz` | 与其他 hello 示例的 `/dev/hello` 不是同一约定 |
| 驱动总报告成功 | 应用日志看似正常，无法证明数据实际完整复制 |

“输出了几个字符”不是二进制协议正确的证据。

## 7. 在实验副本中先写协议卡

今天不要求直接重写驱动。先任选一种协议，讲清楚再修改，不能同时混用字符串和本机整数。

以下为**建议的新实验约定**，不是现有实现：

| 字段 | 固定宽度状态值方案 |
| --- | --- |
| 数据格式 | 无符号 32 位，约定字节序，不依赖 C `int` 的隐含布局 |
| 请求长度 | 零长度返回 0；非零但不足 4 返回 `EINVAL`；足够时处理 4 字节 |
| 写入 | 先拷入临时值，完整验证后再提交；成功返回 4 |
| 读取 | 读取一次当前值快照；成功返回 4 |
| 重复读取 | 每次返回当前快照，不提供普通文件 EOF；必须用有限次数测试 |
| 拷贝失败 | 内核返回 `-EFAULT`，写入不提交新状态 |
| 并发 | 用适合上下文的锁保护共享状态，用户拷贝不放在自旋锁内 |
| 定位 | 明确不支持 seek，不能指望偏移替你保存消息边界 |

若选字节串方案，则要另外定义最大长度、有效长度、是否包含 `\0`、短读/短写和偏移。不能只把 `4` 换成 `size`，就认为问题都解决了。

## 8. 分层实验步骤

### 无板必做

1. 在 `Makefile` 标注实际产物，确认测试程序不会自动生成。
2. 画一次 read 和一次 write 的地址方向图。
3. 填协议卡，写出正常、异常、重复调用语义。
4. 给原始实现与实验副本分别记录路径，不能把方案当成已修改。

### 有 Linux 条件时

1. 先通过 Day2 只打印模块的构建/加载/卸载闭环。
2. 在副本修正长度检查、拷贝错误、注册错误和协议，审查后构建。
3. 核对真实设备号与节点来源，观察内核日志。
4. 用按同一协议实现的有限次数测试程序运行下表，不直接用原字符串程序验收整数接口。
5. 关闭所有消费者，正常卸载；记录是否仍有节点或资源残留。

本文不宣称已经提供修正后的可执行实现，或已通过这些实验。

## 9. 测试表与观察点

| 输入/场景 | 建议协议的预期 | 必须记录 |
| --- | --- | --- |
| 零长度 read/write | 返回 0，不改变状态 | 实际返回与状态 |
| 1～3 字节缓冲区 | `-1` / `EINVAL` | `errno`，无越界访问 |
| 正常 4 字节写入再读取 | 返回 4，值一致 | 实际字节序与数值 |
| 大于 4 字节请求 | 本次仅处理 4 字节 | 应用不误认全部处理 |
| 连续读取两次 | 两次快照，非 EOF | 测试有次数上限 |
| 两个写者 | 符合所定义同步和覆盖语义 | 不出现混合值 |

失败定位顺序：构建产物 → 模块加载 → 设备号/节点 → 回调是否进入 → 用户协议 → 拷贝与同步。打开失败时保留具体 `errno`，不要先全局放开权限。
