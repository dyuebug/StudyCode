## 3. 先画真实分支，而不是理想化流程

```text
设备树 -> platform 匹配 -> probe
  -> 分配按键数组、取得 GPIO/IRQ
  -> 初始化 timer/tasklet/work
  -> request_threaded_irq

GPIO 中断 -> primary ISR
  +-> tasklet_schedule -> tasklet：采样、打印
  +-> mod_timer -> timer：采样、入队、唤醒、SIGIO 通知
  +-> schedule_work -> work：采样、打印进程信息
  +-> 返回 IRQ_WAKE_THREAD -> IRQ 线程：采样、打印

应用 read -> 等待队列 -> 从环形缓冲区取记录 -> 用户拷贝
应用 poll -> 注册等待关系 + 查询可读状态
```

这里不是“硬中断 → tasklet → work → 线程”的串行链。它们由同一 ISR 安排，是教学对比；真正把记录交给应用的是定时器分支。

生产代码应按设备时序和上下文需求选必要机制，避免重复采样、重复处理和难以收敛的退出依赖。

## 4. 每段代码处在哪种上下文

| 路径 | 典型上下文 | 可否睡眠 | 重点约束 |
| --- | --- | --- | --- |
| 模块初始化、probe/remove | 通常为可睡眠进程上下文 | 通常可以，仍看持锁情况 | 资源发布/回滚与并发入口 |
| read/ioctl | 发起系统调用的线程 | 通常可以 | 用户拷贝、信号、等待和寿命 |
| primary ISR | 硬中断 | 不可以 | 快速处理，不做可睡眠访问 |
| 普通 timer 回调 | 通常软中断路径 | 不可以 | 不用户拷贝、不随意睡眠 |
| tasklet | 软中断机制 | 不可以 | 同一 tasklet 串行不等于所有数据都免锁 |
| 普通 workqueue work | 工作线程 | 通常可以 | 共享状态与取消/重排队 |
| threaded IRQ 的 thread_fn | IRQ 线程 | 通常可以 | 需要正确返回值和停止配合 |

不要因为打印出 `current->comm` 就认定当前是普通用户线程；中断上下文的 `current` 也可能只是被中断任务。GPIO 能否睡眠仍取决于控制器和所用 API。

## 5. 定时器为什么能用来去抖

ISR 的 `mod_timer(..., jiffies + HZ/50)` 把采样推迟到一段时间以后；新的抖动可再次推后采样时机。目的通常是等待电平趋稳，而不是让 IRQ handler 忙等。

`HZ/50` 表达约 20ms 的目标延迟，但存在 tick 粒度、调度和执行延迟，不能把它当成测量出的精确响应时间。更清晰的新代码可用时间转换辅助函数，同时仍要按设备实际特性选值。

新旧内核的 timer 回调签名与初始化方式不同。本目录使用 `timer_setup()` 与 `from_timer()`，不能同旧 `setup_timer()` 回调参数混用。tasklet 也属于旧机制，现代化选择应结合目标内核与设备需求，不是今天必须继续扩展的方向。

## 6. 资源表比“有 exit”更重要

| 资源/状态 | 取得或初始化位置 | 访问者 | 退出时必须保证 |
| --- | --- | --- | --- |
| 按键数组 | `probe` 中 `kzalloc` | IRQ、timer、tasklet、work | 所有访问者结束后才 `kfree` |
| GPIO/IRQ 映射 | probe 获取、申请 IRQ | 采样分支与 ISR | 获取成功，所有权明确，申请/释放配对 |
| timer | `timer_setup`、ISR 重设 | 定时器回调 | 不再重设且同步等待回调结束 |
| tasklet | `tasklet_init`、ISR 调度 | tasklet 回调 | 停止调度并等待完成 |
| work | `INIT_WORK`、ISR 调度 | 工作线程 | 停止排队并同步取消/等待 |
| 字符接口/类/节点 | probe 注册与创建 | 用户线程 | 阻止新访问并处理旧引用 |
| 队列/等待条件 | 静态初始化和事件更新 | 生产者、读者、poll | 同步与停止唤醒完整 |

`gpio_to_desc()` 只是把旧编号转换成 descriptor，不等于通过 consumer 申请并取得了该线的所有权。不能因为拿到非空描述符就认定冲突管理和方向初始化都完成。

## 7. 原始实现中可定位的风险

至少选三项，在笔记里标出对应函数、触发条件、后果和修正方向：

1. **资源数量/分配检查**：`of_gpio_count()` 可能为负，单纯 `if (!count)` 不能覆盖；分配结果未完整检查。
2. **部分申请失败**：多个 IRQ 逐次申请却未完整处理每次返回值，也缺少只回收成功前缀的回滚。
3. **共享队列竞争**：读写下标、入队/取出与多读者缺少同步；等待返回值被忽略。
4. **定时器退出竞争**：`remove` 只用 `del_timer()`，不能据此保证已经运行的回调结束。
5. **work 未收敛**：`remove` 没有对应的同步 work 取消，随后释放数组，work 仍可能引用它。
6. **打开文件与解绑**：删除节点不能撤销旧文件引用，也没有完整停止/唤醒协议。
7. **旧接口与类型**：class/remove/tasklet 的签名和指针参数传递需按目标版本检查，不能压制警告来过编译。

这些不是声称每次都必然崩溃，而是指出存在可触发的不安全执行顺序。没有复现也不能认为风险不存在。

## 8. 为什么仅逆序调用几个 free 不够

设想如下执行：work 已排队但还没运行；`remove` 释放数组；工作线程稍后才运行并取得原数组指针。最后一步就是 use-after-free，即使用已释放对象。

完整退出设计应满足这些依赖，具体顺序要根据真实生产者关系确认：

```text
发布停止状态，阻止新用户操作和重新排队
  -> 停止硬件/IRQ 等生产者，并等待在途处理结束
  -> 同步停止 timer、tasklet、work、IRQ 线程等回调
  -> 唤醒等待者，使其按停止协议退出
  -> 撤销接口，处理已有文件/对象引用
  -> 释放不再被访问的资源与私有对象
```

`free_irq()`、适用版本的 `del_timer_sync()`/定时器关闭接口、`tasklet_kill()`、`cancel_work_sync()` 等可参与实现，但每个都只解决相应机制的一部分。必须先阻止新的排队/重设，并且不能持有回调自己需要的锁再同步等待它结束。

新内核的 timer shutdown 类接口与旧 BSP 不一定同时存在，按目标 API 设计，不复制一个“万能退出函数”跨版本使用。

## 9. 最小实践：先减法，后验证

### 无板必做

画真实分支图、上下文表和资源表。为“第二个 IRQ 申请失败”“阻塞 read 中解绑”“work 已排队时退出”各写一条执行时间线。

### 有匹配板卡的条件实验

先保留一个必要采样路径，在副本补齐申请失败、共享队列、用户协议和退出，再做有限次数事件测试。不要首先把所有机制一起运行来调试。

观察点至少包括：probe 返回、IRQ 数、真正入队数、用户成功读取数、丢弃/溢出计数、停止后回调是否仍能运行。没有计数和时间测量时，不能凭打印顺序宣称性能或无丢失。

原示例未审查前不做强制卸载、并发解绑或高频压力测试。修改前后必须保留差异和构建诊断，结果分源码推断、软件接口与硬件证据记录。
