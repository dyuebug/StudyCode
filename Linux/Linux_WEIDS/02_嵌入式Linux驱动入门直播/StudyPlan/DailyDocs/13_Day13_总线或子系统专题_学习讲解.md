## 3. 五个对象的关系

| 对象 | 含义 | 本例中的作用 |
| --- | --- | --- |
| I2C controller 驱动 | 控制 SoC 总线硬件 | 向 I2C 核心提供传输能力 |
| `i2c_adapter` | 某条 I2C 总线的访问对象 | `client->adapter` 是事务提交目标 |
| `i2c_client` | 总线上某个地址的设备实例 | 保存地址、设备对象等 |
| `i2c_driver` | 支持某类器件的驱动实现 | 匹配后进入 probe |
| 字符设备接口 | 面向应用的访问层 | `/dev/myat24c02` 与私有 ioctl |

```text
DTS 的 I2C 子节点 -> client（位于某 adapter 上）
                              |
i2c_driver 匹配 -> probe ------+-> 字符接口
                                      |
应用 ioctl -> 参数检查 -> i2c_msg 数组 -> i2c_transfer(adapter)
                                      -> controller -> EEPROM
```

I2C client 通常由总线与固件描述实例化，并不是每个 I2C 子节点先成为 platform_device。控制器本身则可能通过 platform 模型接入。

## 4. 两种地址必须分清

DTS 的 `reg = <0x50>` 是本例器件的 **7 位从设备地址**。线上传输的地址字节还包含读写位，不能把手册中的某个 8 位地址字节原样填进 `client->addr`。

EEPROM 内部还需要字节偏移地址。AT24C02 通常为 2Kbit，即 256 字节，随机读中发送的那个内部地址字节，与总线地址 `0x50` 不是同一回事。具体地址脚配置和器件变体仍按手册确认。

源码把用户提供的 `unsigned int` 截成 `unsigned char addr`，若不先验证范围，非法大地址会静默回绕；数据值也可能截断。应拒绝越界，而不是把截断当成正确寻址。

## 5. 一次随机读为什么是两条消息

本例 ioctl 读操作构造两个 `i2c_msg`：

- 消息 0：从设备地址相同，写 1 字节内部偏移。
- 消息 1：设置 `I2C_M_RD`，读 1 字节数据。

```text
START -> 从地址+写 -> 内部字节偏移
  -> repeated START -> 从地址+读 -> 数据字节 -> NACK -> STOP
```

消息应在同一次 `i2c_transfer(..., 2)` 中组织，并确认 adapter 支持该器件所需的传输能力/组合方式。拆成独立写和独立读，不应未经核对就声称有完全相同的总线语义。

成功返回的是**完成的消息数**：

| 返回 | 对请求 2 条消息的含义 | 修正副本的处理方向 |
| --- | --- | --- |
| 2 | 两条完成 | 才能交付该次读取结果 |
| 0 或 1 | 请求未完整完成 | 视为不完整传输，如映射为 `-EIO` |
| 负错误码 | 总线/控制器报告失败 | 保留适当错误，不能返回成功 |

不是返回字节数，也不是“非负就全部成功”。原实现完全忽略该返回值，读失败后可能把未初始化的 `data` 拷给用户。

## 6. 写事务与内部写周期

单字节写的消息内容是“内部地址 + 数据”，本例发送一条消息，所以应检查返回值是否为 `1`。

总线完成不代表 EEPROM 内部非易失写入已经完成。源码用 `mdelay(20)` 忙等固定时间，没有查询完成状态，也没处理发送失败。

更完整的方案需根据器件手册定义有界的写周期等待/ACK 检测、超时及错误传播；允许睡眠的进程上下文通常不应为这种长等待一直忙转。扩展到多字节写还要按真实页边界切分，不能假设跨页自动连续写。

写失败后也不能盲目无限重试：事务可能已经部分产生副作用，应结合协议和状态决定恢复方式。

## 7. 私有 ioctl 为什么还不是稳定 UAPI

原驱动用命令 `100/101`，把用户参数按两个整数、固定 8 字节拷入。应用也传两个 `int`。这是课程局部约定，不应推广成可跨 ABI 的通用 EEPROM 接口。

需要审查：

1. 命令是否有效，再决定读取何种参数；未知命令应返回 `-ENOTTY`，而非无条件 0。
2. `copy_from_user/copy_to_user` 是否完整，失败不能继续操作硬件或交付伪数据。
3. 地址与数值是否在范围内，命令行解析是否检查错误/尾字符。
4. UAPI 使用固定宽度字段、明确大小/对齐和兼容规则，避免隐含依赖本机整数布局。
5. 同一文件/器件的并发配置与事务是否需要设备级串行化。

I2C 核心的总线传输锁不等于保护了私有设备指针、用户参数和完整“传输后等待”的业务序列。

## 8. 实例与应用端同样需要审查

`probe` 把 client 保存到全局指针，注册字符设备、类和节点，但没有完整检查失败。第二个实例可能覆盖第一个；解绑后已有文件也不能再盲目使用已失效的设备关系。

改进方向是每实例保存状态，将打开文件关联到相应实例，失败回滚，并在解绑时阻止新传输、处理在途请求和引用寿命。I2C `probe/remove` 签名与 `class_create` 在不同内核有变化，按目标头文件适配。

应用也忽略 ioctl 返回值：读失败仍打印数据，错误参数数量/命令分支还可能导致访问不存在的参数。不能仅看屏幕上“Read addr ...”就判 EEPROM 读取成功。

## 9. 分步实验：先只读，再考虑受控写入

### 无板必做

画对象关系、两消息读事务、单消息写事务，标注每次 API 的期望返回数量；为传输失败设计用户可见错误。完成工作簿 Day13，不需要先在聊天中提交答案才能继续。

### 有板条件实验

1. 确认目标芯片/地址、电压、总线、上拉、写保护和当前绑定者；不盲扫工作总线。
2. 优先了解目标内核已有的 `at24` 与 nvmem 支持，生产场景通常优先复用；不为学习强行抢占正在使用的器件。
3. 在副本补齐用户协议、传输返回、实例与退出后构建，记录实际设备实例/绑定和节点。
4. 从已授权、已知用途的测试器件只读一小段，保留返回值和实际数据。
5. 只有明确允许覆盖的独立测试地址才可写；先保存原值、制定恢复/断电失败处理，再做有限写入与读回。
6. 关闭应用、等待在途操作结束，正常解绑/卸载，验证资源清理。

不要向未知 EEPROM 写入；它可能保存板卡身份、校准、启动或配置数据。没有波形证据就不声称验证了电气时序。

## 10. 最小测试与故障定位

| 场景 | 预期/证据 |
| --- | --- |
| 正常随机读 | 完成两条消息，再交付有效数据 |
| NACK/总线错误 | 具体错误传给应用，不打印未初始化值 |
| 返回 1 条消息 | 识别短传输，不能当成功 |
| 地址/参数非法 | 事务发出前拒绝，设备内容不变 |
| 写周期未结束 | 按有界等待/超时协议处理 |
| 在途请求遇到停止 | 不继续使用失效 client，不永久等待 |

NACK/短传输等故障优先用审查过的模拟或受控测试设计，不通过带电拔线制造。排查按“控制器/地址/绑定 → 事务内容 → API 返回 → 用户协议”进行。
