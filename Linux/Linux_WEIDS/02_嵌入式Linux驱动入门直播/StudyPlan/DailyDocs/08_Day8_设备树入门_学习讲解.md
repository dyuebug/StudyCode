# Day8 学习讲解：设备树入门

> 本日主线：从 DTS 中的节点走到内核设备对象、匹配表与 probe，区分描述存在、设备实例化和绑定成功。
> DTS 编译成功不代表启动时使用了该 DTB，更不代表硬件已经工作。

## 1. 设备树具体解决什么问题

Day6 已把硬件事实与驱动逻辑分开。设备树让许多无法自动发现的板级信息不再散落在板级 C 注册代码中，而由结构化的硬件描述提供。

它描述设备身份、连接、地址、引脚、电源、时钟等关系，不负责实现寄存器操作算法。驱动读取描述，仍要申请资源、处理失败、组织并发与管理退出。

本日目标不是背语法，而是能沿一个实际节点回答：它在谁下面？由谁枚举？怎样匹配？属性由谁读取？失败该查哪里？建议 90～120 分钟。

## 2. `.dts / .dtsi / .dtb` 各处在哪一步

| 名称 | 含义 | 需要核对 |
| --- | --- | --- |
| `.dts` | 设备树源文件，常用于具体板卡 | 是否为当前板型号/修订 |
| `.dtsi` | 被包含的共享片段，常描述 SoC 或公共硬件 | 覆盖关系和引用来源 |
| `dtc` | 设备树编译器 | 单独编译与内核预处理流程的区别 |
| `.dtb` | 供启动流程传给内核的二进制描述 | 实际加载的文件、启动项和地址 |
| 运行中的设备树 | 内核接收并解析后的描述 | 可能受启动器、overlay 等影响 |

含 `#include`、宏和内核绑定头文件的源文件通常需要内核构建流程的预处理，不能保证直接对任意 `.dts` 调 `dtc` 就成功。`.dtb` 不是可加载的 `.ko`，也不是应用程序。

## 3. 先认节点、属性、标签与引用

本日实际入口是 [07_platform_driver_for_dts](../../07_设备树入门/source/07_platform_driver_for_dts/)，先看 [1.dts](../../07_设备树入门/source/07_platform_driver_for_dts/1.dts) 的开头，再看 [led_drv.c](../../07_设备树入门/source/07_platform_driver_for_dts/led_drv.c)。

在 `1.dts` 中：

- `/` 是根节点。
- `myled_ok:` 是源代码标签，便于其他位置引用，不是 `/dev` 名称。
- `myled_for_test_ok` 是节点名。
- `compatible = "100ask,led"` 表示可用于 OF 匹配的身份。
- `pin = "gpio5_3"` 是这份教学驱动自定义读取的属性。

`&label` 通常表示对已定义标签的引用；设备树中的 phandle 用于表达节点关系。它不是 C 指针，也不能靠手写一个看似相同的数字跨树复用。

节点名里的 `@地址` 依其总线约定表示 unit address，不等于内核驱动名字。属性是否有效、类型和含义如何，受 binding 约束，不是随意命名后所有驱动都会理解。

## 4. `compatible` 怎样连接驱动

源码 `dts_device_ids` 有 `100ask,led`，并通过 `.driver.of_match_table` 交给驱动核心。这个字符串与节点相匹配，提供候选驱动关系。

```text
板级 DTS/DTSI
  -> 编译并部署 DTB
  -> 启动器实际传入内核
  -> 内核解析设备树
  -> 相应总线/控制器枚举可用设备节点
  -> 设备对象关联 of_node
  -> 总线用 OF 匹配表选驱动
  -> probe 读取资源并初始化
```

`compatible` 可以按从具体到更通用的兼容性列多个字符串，不能理解为任意“名称别名列表”。自动加载模块还涉及模块别名、安装和依赖索引；仅有 C 匹配表不保证任意 `.ko` 文件会自动加载。本例也不能因存在 `of_match_table` 就假定完整模块自动加载信息已经齐全。

## 5. 不是每个节点都变成 `platform_device`

根下或特定总线下的可用节点可能由 platform 枚举；I2C 控制器下的外设通常成为 `i2c_client`，SPI 控制器下通常成为 `spi_device`。CPU、内存、pinctrl 配置子节点等也不应全画成独立 platform 外设。

实例化取决于父总线、可用状态、内核配置及控制器驱动等条件。`status = "disabled"` 通常表示不启用；省略 `status` 往往表示可用，具体仍需对应 binding 和枚举路径。

`myled_for_test` 缺少本例驱动所需的 `compatible`，不能仅因为有 `pin` 就期待走相同的 OF 匹配路径。观察时要分别确认节点存在、实例是否创建以及有没有绑定，而不是只数 DTS 里写了几对花括号。

## 6. `reg` 必须由父总线解释

| 所在位置 | 常见含义 | 不能直接套用的解释 |
| --- | --- | --- |
| SoC MMIO 设备 | 地址范围，依地址/长度 cell 数和地址转换 | 不一定就是单个 32 位 CPU 地址 |
| I2C 子设备 | 常为 7 位总线地址 | 不是寄存器物理基址，也不是含 R/W 位的地址字节 |
| SPI 子设备 | 常为片选编号 | 不是 I2C 地址 |

`#address-cells` 与 `#size-cells` 描述子节点 `reg` 的编码方式；`ranges` 等还能参与总线地址转换。今天先会判断父节点，不能看到 `reg = <...>` 就一律叫“内存地址”。

## 7. 逐步读本例 `led_probe()`

本例通过 `pdev->dev.of_node` 区分设备来源：

1. 没有关联 OF 节点时，从旧式 platform resource 取教学引脚信息。
2. 有 OF 节点时，用 `of_property_read_string()` 读取私有 `pin` 字符串。
3. 从固定字符位置提取数字，存进全局描述数组。
4. 创建用户设备对象并保存 drvdata。

它有助于理解“同一驱动从不同描述来源获取信息”，但不是规范 GPIO 实现：

- 读取属性的返回值未检查，失败时字符串指针不能使用。
- `tmp_str[6] - '0'` 只解析某个固定位置，无法正确表达通用端口/多位引脚编号。
- 字符串 `pin` 不是通用 GPIO binding，不能换个驱动就自动识别。
- 仍有 Day7 的全局计数、范围、设备创建失败与解绑寿命问题。
- 写回调只打印引脚，不代表真实 GPIO 已配置或输出。

下一天将改用 GPIO 控制器引用与 consumer API 的思路，不继续把字符串解析当作正式引脚接口。

## 8. 不部署的离线小实验

无板可先填写节点对应表，列节点路径、父节点、`compatible`、读取属性的函数与预期实例类型。

若有 Linux 与 `dtc`，可在 `1.dts` 实验副本目录尝试离线编译/反编译，输出仅留在实验目录，**不替换启动文件**：

```bash
dtc -I dts -O dtb -o lecture-test.dtb ./1.dts
dtc -I dtb -O dts -o lecture-test-decoded.dts ./lecture-test.dtb
```

第一步成功后才做第二步；记录工具版本、完整诊断与两节点属性。警告不能一概忽略，反编译结果也不会还原原来的标签、宏和包含结构。

这项实验只验证描述的部分语法/编码，不验证 binding、启动生效或硬件。完整 BSP 设备树应优先通过对应内核构建流程和可用的 schema 检查。

## 9. 有板时怎样分层定位

先确认恢复入口、实际启动项与 DTB 来源，再按 BSP 支持的流程部署经过审查的副本。不要把用于学习的完整 `1.dts` 覆盖到未知板卡的启动分区。

| 观察结果 | 重点排查 |
| --- | --- |
| 运行树中没有修改节点 | 编译的文件、传输位置、启动器选项、overlay |
| 节点存在但没有设备实例 | 父控制器、状态、枚举路径、内核配置 |
| 实例存在却没绑定 | 驱动是否注册、总线、匹配表、模块别名 |
| 已尝试 probe 但失败/延后 | 属性读取、资源申请、依赖返回码 |
| probe 成功但无用户节点 | 是否实现该接口、创建返回值、devtmpfs/udev |

`/sys/firmware/devicetree/base`、`/sys/bus/platform/devices` 和相应驱动目录是常见只读观察入口；实际存在情况依内核配置。属性可能含 NUL 分隔的二进制数据，不能把它们当普通一行文本误读。

## 10. 练习与验收

完成工作簿 Day8，交付“节点 → 枚举对象 → 匹配表 → probe → 属性消费”的对应图，再设计两个反例：修改了未加载的 DTB；把 I2C `reg` 当成 MMIO 地址。
