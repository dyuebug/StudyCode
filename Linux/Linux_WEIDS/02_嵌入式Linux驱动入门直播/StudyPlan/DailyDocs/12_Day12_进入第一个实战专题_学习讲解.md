# Day12 学习讲解：进入第一个实战专题

> 本轮默认主线：SR501。DHT11 留作后续时序专题，不在同一天并行展开。
> 本日重点是数据/事件流和版本差异；框架版与“完善版”都不能仅凭名称当成可直接运行的完整驱动。

## 1. 从设备行为出发，而不是从 API 清单出发

SR501 类人体红外模块通常把检测电路的结果转换为数字输出。它的行为还受模块型号、保持时间、触发模式、预热与环境影响，不能直接等同于经过认证的“有人/无人真值”。

驱动首先必须决定对外表达什么：当前电平？电平变化？检测开始/结束？还是“自上次读以后发生过事件”？这些语义不同，存储与等待实现也不同。

建议 90～120 分钟完成事件流、版本表和一条方案的测试设计，真实硬件调试另计。不连接真实安防、航空或工业控制链路进行学习实验。

## 3. 把真实数据路径画出来

```text
设备端数字输出变化
  -> 已正确复用的 GPIO 输入
  -> GPIO 映射出的 IRQ
  -> ISR 设置 sr501_data = 1
  -> 唤醒 sr501_wq 上的等待者
  -> read 看到状态非零
  -> copy_to_user 将状态复制到用户缓冲区
  -> 清除 sr501_data
  -> 应用取得一次通知
```

这是完善版尝试表达的路径，不是已经验证的运行事实。原 ISR 不采样并编码当前 GPIO 电平，而是无论上升/下降沿都设置同一个 `1`。

因此应用读到 `1` 最多表示该实现试图报告“发生过边沿”，不能直接解释为此刻物理输出高，也不能推出每次读取都对应一次独立人体检测。

## 4. 两版本差异与仍然空缺的部分

| 机制 | 框架版 | 完善版源码可见内容 | 尚不能保证 |
| --- | --- | --- | --- |
| 字符接口 | 仅操作表骨架 | 注册设备号、创建类/设备对象 | 返回值和回滚完整 |
| GPIO | 未获取 | `gpiod_get` 后配置输入 | 失败、所有权与退出正确 |
| IRQ | ISR 占位 | GPIO 转 IRQ、请求双边沿 | 错误和回调语义正确 |
| 事件保存 | 无 | 一个全局 `sr501_data` 标志 | 保存每个边沿/多实例 |
| 阻塞 read | 返回 0 | 等待标志再拷贝并清零 | 信号、竞争、拷贝失败正确 |
| 非阻塞 | 未实现 | 没有检查 `O_NONBLOCK` | 无数据返回 EAGAIN |
| poll | 返回 0 | 仍返回 0，等待注册被注释 | 就绪和超时测试可用 |
| 退出 | 空函数 | `remove` 仍为空 | IRQ、GPIO、节点及等待者清理 |

“比前一版增加了代码”和“已经完整实现”必须分栏记录。

## 5. 在编译前就能发现的问题

这一组特别适合训练审查，而不是原样加载：

1. **构建对象不一致**：完善版 Makefile 仍写 `obj-m += gpio_key_drv.o`，不能据此构建本日目标 `sr501_drv.ko`。实验副本需先核对/修正 Kbuild 目标。
2. **唤醒参数不对**：`wake_up` 需要等待队列头指针，源码传入的是 `sr501_wq` 对象而非其地址。
3. **IRQ 返回不匹配**：通过 `request_irq()` 注册的 ISR 返回 `IRQ_WAKE_THREAD`，但没有配套线程处理函数；通常的普通处理完成应返回 `IRQ_HANDLED`，应按实际方案修正。
4. **设备名写成路径**：`device_create()` 的名称参数写了 `/dev/sr501`，应提供设备名而不是绝对路径；不能假定该调用已成功创建正确节点。
5. **错误检查缺失**：GPIO、方向、IRQ 映射、IRQ 申请和设备创建结果没有完整处理。
6. **退出未完成**：空 `remove` 不能释放 IRQ/GPIO/节点，模块退出也未完整销毁类和字符设备注册。

这里只指出源码事实与修正方向，原始课程文件没有因此被改动。

## 6. 一个状态位能保存多少信息

假设读者尚未运行时，连续发生三次边沿，ISR 每次都把标志设为 1。最终只能知道“至少发生过一次”，无法还原三次及其先后。

另外，在读者拷贝并清零的间隙又来一次 ISR，新的 `1` 可能被读者随后清零。没有同步，多读者也可能重复消费或相互覆盖。

按需求选择模型：

| 对外需求 | 适合的状态模型 | 仍需明确 |
| --- | --- | --- |
| 随时查询当前输出 | 当前电平快照 | 有效极性与采样时间 |
| 只关心自上次读后是否变化 | 合并 pending 标志/序列号 | 清除与更新的同步 |
| 保存每次边沿及顺序 | 事件队列，可含序号/时间戳 | 容量、溢出和多读者语义 |

队列也不能凭空保证无丢失，采样、IRQ 和缓冲区都有限制。业务若只需状态变化，就不必为了“更高级”强行保存所有抖动边沿。

## 7. 测试程序为什么可能一开始就卡住

`button_test` 以 `O_NONBLOCK` 打开后先读十次，原意是演示非阻塞读取；但完善版 `read` 没有检查该标志，所以第一个 read 就可能睡眠。

此外它没有调用 poll，后半段是无限阻塞读。若直接用它验收，会把驱动没实现的机制当成已实现，还可能没有有限退出条件。

修正后的实验应用应记录实际返回长度和 `errno`，设置次数/期限，明确终止时如何关闭文件。测试用例要基于同一版驱动的真实接口，而不是沿用“button”文件名带来的假设。

## 8. 中断、轮询、线程方案怎么比较

| 方案 | 主要取舍 | 退出要求 |
| --- | --- | --- |
| 中断驱动 | 事件到来触发处理；依赖 IRQ 映射与触发配置 | 停止事件源并等待在途回调结束 |
| 周期轮询 | 实现直观；短脉冲可能被漏采，周期影响延迟与开销 | 停止定时/循环并等待任务结束 |
| 内核线程采样 | 可在进程上下文等待和访问可睡眠资源 | 循环与等待条件都识别停止请求，等待线程退出 |

`kthread_stop()` 不是对任意循环的强制杀死：线程必须检查停止条件，阻塞等待也必须能在停止时结束。不要只在函数末尾加一次检查。

本轮只为一条方案设计最小实验。可通过 [推荐源码索引](../16_推荐先动手的源码目录.md) 阅读后续 SR501 调试/线程章节，DHT11 留待第二阶段。没有测量时不填写 CPU 占用或响应时间数字。

## 9. 有硬件前先过两道门

### 软件门禁

实验副本必须修正构建对象、回调返回、唤醒参数和设备名称，再补齐长度、用户拷贝、等待返回值、同步、非阻塞/停止语义及清理；按目标内核适配 API。

不要因为编译过了，就直接做卸载压力测试。若只完成部分修正，记录剩余风险并暂停加载。

### 硬件门禁

核对模块手册、供电、输出电平和 SoC 输入耐压、共地、引脚复用、DTS、IRQ 触发与现有占用者。预热和保持时间等参数按实际型号确认，不照抄另一个模块的数值。

有软件事件模拟时，可以先验证队列与等待；模拟结果不能写成真实 SR501 检测通过。

## 10. 四条最小验收用例

| 场景 | 要观察什么 | 不能推出什么 |
| --- | --- | --- |
| 无事件 | 非阻塞返回、poll 超时或阻塞等待符合约定 | 不代表传感器未接错 |
| 一次输出变化 | 物理信号、IRQ、记录、应用返回逐层对应 | 不代表整套检测可靠性达标 |
| 多次连续变化 | 合并/队列行为符合所选协议，溢出有定义 | 不默认每次边沿都保存 |
| 等待中停止 | 无永久等待、回调/引用收敛、资源回收 | 不因节点消失就断言无在途访问 |

原代码没有完整 poll/停止协议，上表是修正副本的目标，不是已经发生的结果。
