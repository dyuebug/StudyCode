## 3. 四层职责是什么

| 层次 | 负责什么 | 排查问题举例 |
| --- | --- | --- |
| 应用/显示接口 | 私有 ioctl 或 fbdev 操作 | 参数、像素格式、设备编号是否正确 |
| 缓冲与刷新策略 | 保存图像，决定何时/哪些区域发送 | 内存变化后是否真的安排刷新 |
| OLED 协议 | 初始化、寻址、命令/数据、像素布局 | 页/列、方向、位序是否匹配器件 |
| SPI core/controller | 按模式、速率和片选执行传输 | CPOL/CPHA、CS、总线错误、DMA 条件 |

SPI 是传输组织，framebuffer 是显示抽象，二者可以同时使用。SPI 核心不会自动理解 OLED 命令，更不会自动把任意像素数组变成器件显存布局。

## 4. 先理解 SPI 的几个设备参数

- SCLK、MOSI、MISO、CS 是常见信号；具体 OLED 可能只用发送方向，仍要按器件接线确认。
- CPOL/CPHA、位宽、位序和最高速率必须匹配设备要求，不能靠随机试模式代替手册。
- DTS 的 `reg` 通常是片选编号，不是 Day13 的 I2C 从地址。
- DC 等额外 GPIO 表示命令/数据选择，不等于片选。
- 复位、供电、pinctrl、有效极性与其他引脚占用也要核对。

`spi_message` 可包含多个 `spi_transfer`，但“把 transfer 加进 message”只是组织请求。同步提交如 `spi_sync()`、`spi_write()` 成功通常返回 0，失败为负错误码；这与 `i2c_transfer()` 返回完成消息数不同。

发送缓冲区还要满足目标控制器/API 的有效期和 DMA 可用性约束，不能看到一个指针就假设任意栈内存、映射内存都能直接传输。

## 5. 第28章提供的具体协议线索

`oled_write_cmd_data()` 先设置 DC，再调用 `spi_write()`；`OLED_DIsp_Set_Pos()` 发送页/列位置命令，`oled_write_datas()` 发送数据。结合应补齐的参数校验，一次完整显示操作的目标路径是：

```text
应用私有命令
  -> 校验并接收位置/长度/数据
  -> 设置 OLED 写入位置
  -> DC 选择命令或数据
  -> SPI 传输
  -> OLED 内部显存变化
  -> 实际显示受初始化与映射配置影响
```

原代码未完整检查用户拷贝、参数范围与 SPI 返回值，全局 `data_buf[1024]` 的长度还需验证，不能直接当安全 UAPI。DC 与 SPI 序列也应避免并发交错；先发布节点再初始化硬件会暴露半就绪状态。

它帮助理解数据路径，不代表今天需要修好并加载这份驱动。

## 6. framebuffer 改造改变了什么

第30章使用传统 fbdev：分配 `fb_info`，填写分辨率、像素格式、固定信息和操作表，申请显示缓冲区，调用 `register_framebuffer()`，再启动内核线程周期发送缓冲内容。

| 对比项 | 私有 SPI OLED 接口 | fbdev 改造 |
| --- | --- | --- |
| 应用认知 | 需要知道私有命令、页/列等 | 通过统一显示信息/缓冲区接口工作 |
| 用户节点 | 例子使用 `/dev/myoled` | 常见 `/dev/fbN`，实际编号不是固定 0 |
| 图像保存 | 命令参数或私有数据缓冲 | `fb_info` 关联的显示缓冲区 |
| 硬件更新 | 调用路径中直接发送 | 本例线程从缓冲区取数据发送 |
| 协议适配 | 应用/驱动协商私有布局 | 驱动需要把框架布局适配器件 |
| 资源管理 | 字符号、类、节点、GPIO、SPI 状态 | 还增加 fb_info、显存与刷新任务 |

支持哪些 `read/write/mmap` 行为依实际 `fb_ops`、框架与内核版本而定，不能仅因注册了 fbdev 就承诺所有应用访问方式都可用。fbdev 是课程使用的传统框架，现代 Linux 显示还需了解 DRM/KMS，不是所有显示都走 fbdev。

## 7. 都是 1024 字节，为何图案仍可能错

源码设置 128×64、1 bit/pixel，缓冲容量为 `128 * 64 / 8 = 1024` 字节，每行 `128 / 8 = 16` 字节。源码旁“rgb565”的注释与实际 1bpp 配置不符，应以字段和目标格式解释。

容量相同不等于布局相同：

- 框架的 packed-pixel 行布局常按 `pixel_y * line_length + pixel_x / 8` 找到字节，具体位序还要核对。
- 许多单色 OLED 采用 page 布局，一个字节表示同一列上连续 8 个垂直像素，字节位置与 `page * width + pixel_x` 有关。

因此可能需要位重排、页/列定位和地址模式设置。线程直接把整块缓冲区发出，不足以证明转换正确；即使屏幕有亮点，也要用单点、横线、竖线等图案辨认转置、镜像、位序和偏移。

## 8. 内存变化不等于屏幕刷新

第30章 `oled_thread()` 发送缓冲区后等待约 HZ 个 tick，再判断停止条件。它是周期刷新示意，不是应用每改一个像素都会立即发送。

需要分开取得证据：

1. 应用操作成功，改动的是当前设备正确的缓冲区。
2. 刷新路径确实执行，快照/并发更新策略明确。
3. SPI 提交实际完成且返回值正确。
4. DC、地址模式和像素数据符合器件协议。
5. 物理屏幕显示期望图案。

仅第1项成功不证明第5项。一次全屏发送完成也不保证没有撕裂、布局错误或地址回绕问题。

## 9. 文件名有 `ok` 也必须看退出

第30章仍有需要审查的边界：

- 多个资源分配、GPIO 获取、framebuffer 注册和线程创建未完整检查失败。
- framebuffer 在硬件/GPIO 初始化完成前就注册发布，存在半就绪访问窗口。
- 使用硬编码 `gpio_set_value(122, 0)`，带板级耦合，不能跨板照跑。
- 刷新中没有完整 SPI 错误传播和布局适配证据。
- `remove` 没有先停止刷新线程，随后释放 GPIO，线程仍可能使用它。
- 没有完整释放显示缓冲区与 `fb_info`，分配/释放需要与所用 API 和设备参数配对。

合理退出需先阻止新更新，停止并等待线程/异步任务结束，处理应用打开/映射引用，再撤销框架和回收资源。具体顺序按依赖设计，不能只多加一个 `kfree()`。

## 11. 总复盘必须有三条主线

```text
访问线：应用 -> 系统调用/子系统接口 -> 驱动 -> 控制器 -> 硬件

组织线：DTS/固件描述 -> 相应总线设备实例 -> 匹配 -> probe -> 资源

事件与寿命线：硬件事件 -> 合适上下文 -> 状态/队列 -> 唤醒/就绪
              -> 应用消费；停止时阻止新工作、等待旧访问、最后释放
```

模块构建/加载支撑驱动代码进入内核；它不是所有设备都必须采用的唯一交付方式。字符设备、总线和子系统分别解决不同层次的问题，不要画成一条强制升级阶梯。

写 400～800 字自己的驱动地图，附三个清楚点、三个薄弱点、真实产物路径和全部未验证项。完成工作簿总验收时，理解与实验分别记录，不预填学习成绩或成功日志。
