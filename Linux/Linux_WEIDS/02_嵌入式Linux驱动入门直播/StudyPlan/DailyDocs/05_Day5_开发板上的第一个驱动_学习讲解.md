# Day5 学习讲解：开发板上的第一个驱动

> 本日主线：区分构建主机与目标板，追踪多文件模块，再建立可恢复的部署流程。
> “模块能加载”“测试程序有返回”“LED 真实变化”是三层证据，不能互相替代。

## 1. 为什么今天不能只记几条命令

在 x86 主机上运行编译器，生成 ARM 板上的程序，是交叉编译。它不是只把 `gcc` 换一个名字：内核构建树、目标架构、配置、符号版本和用户态 ABI 都要分别匹配。

建议用 90～120 分钟完成环境卡、源码追踪与部署清单；工具安装、BSP 编译和板级调试另计。没有明确板卡时，今天仍可以完成方案，但不能填“亮灯成功”。

## 2. 先填写一张双机器环境卡

| 项目 | 要确认的事实 | 为什么不能省略 |
| --- | --- | --- |
| 构建主机 | 系统、架构、实验副本路径 | 它的 `uname -r` 不是板卡内核版本 |
| 目标板 | 型号、修订、SoC、启动介质 | 同一系列板也可能接线和 BSP 不同 |
| 目标内核 | `uname -r`、架构、配置与源码来源 | 版本字符串相同不保证模块 ABI 相同 |
| 工具链 | 前缀、编译器版本、目标 ABI | ARM32、ARM64 不能混用 |
| 内核构建树 | 已准备的目标输出、符号文件 | 任意下载的同版本源码不一定可用 |
| 根文件系统 | 位宽、libc、动态加载器 | 模块兼容与应用可执行是两件事 |
| 恢复方式 | 串口、快照/备份、备用启动项 | 失败时不能依赖已挂住的 SSH |

`modules_prepare` 可准备部分外部模块构建条件，但启用符号版本等配置时不能代替对应完整构建，尤其不能随意拿别处的 `Module.symvers` 拼接。

## 4. 多个 `.c` 如何形成一个 `.ko`

Makefile 用 `100ask_led-y := leddrv.o board_demo.o` 组织复合模块，再用 `obj-m += 100ask_led.o` 生成 `100ask_led.ko`。

```text
leddrv.c -----> leddrv.o -------+
                                +--> 100ask_led.ko
board_demo.c -> board_demo.o ---+

ledtest.c ----> 目标用户态可执行文件 ledtest
```

因此 `board_demo.o` 在这里不是单独加载的模块，`ledtest` 也不会被链接进内核模块。课程 Makefile 的 `all` 还单独调用交叉 `gcc` 构建应用；这与 Day3 只构建模块的 Makefile 不同。

固定路径 `/home/book/100ask_roc-rk3399-pc/linux-4.4` 是课程环境，不是你的环境。不要在未审查时直接 `make`，也不要在 PC 上使用该路径假装正在为本机内核构建。

## 5. 一次用户操作如何到达板级模板

```text
ledtest /dev/100ask_led0 on
  -> open：次设备号 0 -> p_led_opr->init(0)
  -> write：二进制字节 1 -> p_led_opr->ctl(0, 1)
  -> board_demo 中打印操作日志
  -> 用户关闭文件
```

这里 `on` 是应用解析的参数，驱动实际收到一个数值字节 `1`。不能直接把 `echo on` 或 ASCII 字符 `'0'` 当成同一协议：ASCII `'0'` 的数值并不是二进制 `0`。

模块初始化通过 `get_board_led_opr()` 得到板级操作表，通用字符设备层不直接写具体 GPIO 寄存器。这是 Day6 分离思想的前奏。

## 6. 构建前还要发现哪些风险

本模板不是生产级可加载参考：

- `register_chrdev()` 和各次 `device_create()` 的失败没有完整处理。
- 用户拷贝没有按返回值决定是否执行控制动作，请求长度也未完整验证。
- 设备节点先发布，板级操作表指针后设置；用户可能在状态就绪前打开节点。
- 次设备号缺少完整范围校验。
- 退出循环已经销毁每个节点，循环后又重复销毁次设备号 0。
- `ledtest` 没有检查 `write()` 的实际返回值，参数非 `on` 时一律按关闭处理。

首次板级实验前，在副本中先明确修正范围与退出方案，不能把“模板不访问真实硬件”理解为“任何错误都安全”。

## 7. 在构建主机执行什么

先在 Linux 构建主机把下列变量设置成已确认的实际值。命令中的校验会在变量未设置时停止，不替你猜板卡参数。当前目录必须是已审查的模块副本。

```bash
make -C "${KERNEL_BUILD_DIRECTORY:?请设置目标内核构建目录}" M="$PWD" ARCH="${TARGET_ARCHITECTURE:?请设置目标架构}" CROSS_COMPILE="${TARGET_COMPILER_PREFIX:?请设置目标工具链前缀}" modules
"${TARGET_COMPILER_PREFIX:?请设置目标工具链前缀}gcc" -Wall -Wextra -o ledtest ledtest.c
file ./100ask_led.ko ./ledtest
modinfo ./100ask_led.ko
```

- `ARCH` 用内核名称，如 `arm` 或 `arm64`，不是照抄主机架构输出。
- `CROSS_COMPILE` 是可执行文件前缀，通常含末尾连字符，不是单个编译器文件名。
- 直接调用 Kbuild 的 `modules` 不执行课程外层 `all` 中的用户程序构建，所以应用单独编译。
- `file` 检查架构，`modinfo` 检查元数据；都不是加载或硬件证据。

保存构建命令、完整诊断、源码版本和产物来源，再按板厂支持的传输方式放到板上。传输成功后核对实际文件，不覆盖启动内核/DTB 来试一个尚未审查的模块。

## 8. 在目标板执行什么

只有完成硬件/版本/副本审查并具备恢复入口后才继续。以下模板模块的预期仅是日志链路，不是亮灯。

1. 采集目标板 `uname -a`，核对产物对应的内核和架构。
2. 开启内核日志观察，确认没有其他同名模块、节点冲突或占用者。
3. 正常加载模块，检查退出状态、模块列表和真实节点设备号。
4. 有限次数测试一次开、一次关，观察两个回调是否按次设备号进入。
5. 停止测试程序、关闭文件，再正常卸载。
6. 核对节点、类和模块状态是否清理；保存所有异常。

只有在副本修正并确认模块/节点命名仍一致后，才可在目标板使用以下测试形式：

```bash
./ledtest /dev/100ask_led0 on
./ledtest /dev/100ask_led0 off
```

真实 LED 版本还必须核对原理图、复用、电压、有效电平与引脚所有者，增加电平/灯光证据；禁止把硬编码板级 MMIO 驱动加载到普通 PC 上。

## 9. 失败分层，不要靠反复加载碰运气

| 现象 | 先查哪层 |
| --- | --- |
| 板上 `Exec format error` | 用户程序目标架构/ABI，不是 `.ko` 本身 |
| 程序存在却报找不到文件 | 动态加载器/依赖库是否存在，也检查路径 |
| 模块格式或符号错误 | 目标构建树、配置、符号版本、依赖、签名 |
| `/dev` 没节点 | 注册返回值、类/设备对象、devtmpfs/udev |
| 日志显示 ctl 但灯不变 | 是否还是只打印的 `board_demo`，再查硬件链路 |
| 卸载卡住或报正在使用 | 打开引用、异步资源和消费者，不强制卸载 |
