# Day6 学习讲解：分离思想与驱动模型入门

> 本日主线：把板级事实、设备实例与通用算法分开，用最小 platform 示例看清设备和驱动如何相遇。
> 分离不是机械地拆成几个文件，也不会自动解决多实例、并发或退出问题。

## 1. 从一个具体变化理解“为什么分离”

假设两块板使用同类 LED，但板 A 接 GPIO X，板 B 接 GPIO Y，并且有效电平不同。如果字符驱动的每次 `open/write` 都写死 X、寄存器地址和电平，换板就得改通用逻辑。

合理的划分是：

- 板级描述提供“接到哪里、有哪些资源”。
- 驱动实现“如何申请资源、解释用户命令并控制这类设备”。
- 每个设备实例保存自己的资源句柄、状态和同步对象。

这样变更接线时，通用驱动可以不改；变更算法时，也不必复制每块板的描述。是否可复用，取决于接口是否表达清楚，而不是文件数量。

## 2. 四类信息分别放在哪里

| 类别 | 例子 | 不应混为一谈的内容 |
| --- | --- | --- |
| 硬件事实 | GPIO 连接、总线地址、时钟、中断、电源 | 不等于已经申请到资源 |
| 匹配身份 | 设备名称、设备 ID、`compatible` | 不等于某个 `/dev` 文件名 |
| 通用驱动逻辑 | 初始化、读写协议、事件处理、错误处理 | 不应为每块板复制一份 |
| 每实例状态 | GPIO 描述符、队列、锁、停止标志 | 不应简单放进全局唯一指针 |

Day5 的 `leddrv.c + board_demo.c` 已用操作表隔离通用层与板级层，但通用层仍通过指定函数拿到固定实现。设备模型进一步解决运行期有哪些设备、谁来匹配、绑定与解绑如何组织的问题。

## 3. `device / driver / bus` 的准确角色

- **device**：系统对某个设备实例的表示，包含身份、父子关系、资源和生命周期；不是硬件本体，也不是设备节点文件。
- **driver**：支持某类设备的实现，提供匹配信息和 `probe/remove` 等回调；同一驱动可能管理多个实例。
- **bus**：组织设备与驱动并提供匹配等规则的一层模型。I2C/SPI 对应真实总线；platform 则是管理许多不可自枚举设备的逻辑总线，不要求板上存在一根叫 platform 的导线。

```text
板级事实 -> 设备对象 ----+
                        +-> 总线匹配 -> probe 尝试初始化 -> 绑定
驱动实现 -> 驱动对象 ----+
```

匹配成功只是“可以尝试接管”；只有 `probe` 成功后才建立正常绑定。依赖未就绪、资源冲突等仍可能令探测失败或延后。

## 4. 本日先读真正最小的 platform 示例

从 [01_platform_bus_dev_drv](../../05_分离的设计思想与总线设备驱动模型/source/01_platform_bus_dev_drv/) 开始，依次读：

1. [Makefile](../../05_分离的设计思想与总线设备驱动模型/source/01_platform_bus_dev_drv/Makefile)：生成独立的 `hello_dev.ko` 与 `hello_drv.ko`。
2. [hello_dev.c](../../05_分离的设计思想与总线设备驱动模型/source/01_platform_bus_dev_drv/hello_dev.c)：注册设备对象。
3. [hello_drv.c](../../05_分离的设计思想与总线设备驱动模型/source/01_platform_bus_dev_drv/hello_drv.c)：注册驱动对象。

设备端的 `.name` 与驱动端 `.driver.name` 都为 `100ask_hello`，这个最小例子走名称匹配。设备与驱动分别编译、分别注册，不是因为 C 文件互相 `#include` 才发生绑定。

设备侧 `.dev.release` 表示设备对象引用最终释放时的回调；它不同于文件操作的 `.release`，也不同于驱动 `.remove`。本例静态对象只打印，不应照搬成动态分配对象的完整释放方案。

## 5. 逐条追生命周期

| 时机 | 设备模块 | 驱动模块 | 需要观察 |
| --- | --- | --- | --- |
| 加载设备端 | `platform_device_register()` | 尚可不存在 | 设备实例进入总线 |
| 加载驱动端 | 已有匹配设备 | `platform_driver_register()` | 注册期间就可能调用 `hello_probe()` |
| 正常解绑 | 实例可仍存在 | `hello_remove()` | 释放本次绑定资源 |
| 卸载设备端 | `platform_device_unregister()` | 若已绑定会走解绑 | 设备不再可用，引用按规则释放 |
| 卸载驱动端 | 设备不必消失 | 注销驱动、解绑它管理的实例 | 后续不能再调用已卸载代码 |

设备先出现或驱动先出现，都能在另一方注册时触发匹配；不是“必须先加载设备模块”的固定顺序。注册驱动可能立即触发 `probe()`，因此注册前就必须准备好回调依赖的全局基础设施。

## 6. platform 与字符设备不是替代关系

```text
向下：板级描述 -> platform_device -> 匹配 -> platform_driver/probe
                                                     |
                                              每实例硬件状态
                                                     |
向上：应用 -> /dev 节点 -> file_operations ------------+
```

platform 模型回答“这个设备如何进入内核并找到驱动”；字符设备接口回答“应用如何访问驱动提供的服务”。同一个驱动可以同时使用两者，也可以接入 input、LED 等子系统而不自定义字符协议。

最小 `hello_probe()` 只打印，所以它成功不代表已经提供 `/dev/hello`。今天观察的是绑定关系，不是 LED 或数据通路。

## 7. 资源获取示例要带着问题读

进一步看 [02_get_hardware_info/hello_drv.c](../../05_分离的设计思想与总线设备驱动模型/source/02_get_hardware_info/hello_drv.c)。它在 `probe` 中从 `pdev->resource[0].start` 取出教学引脚值，在 `write` 中调用 GPIO 占位操作。

这份文件用于讲设计，并非现成可执行版本：

- `gpio_xxx()` 是占位调用，不是可用内核 API。
- 退出函数定义为 `hello_drv_exit`，注册处却写成 `lhello_drv_exit`，名称不一致。
- 直接取资源下标前没有完整验证数量与类型。
- 全局 `pin/major/ker_val` 无法自然表达多个设备实例。
- `remove` 没有回收在 `probe` 中注册的字符设备资源。

正确学习方法是从这些问题写出“应获取什么、何时验证、由谁保存、何时释放”，而不是为了让编译器通过随意伪造一个 GPIO 函数。

## 8. 每实例状态应该怎样思考

为每个 `pdev` 建一个独立状态对象，包含资源、用户接口关联、锁和停止标志。`platform_set_drvdata()` 将状态挂到设备，`platform_get_drvdata()` 在相应回调取回。

这只解决“找回哪个实例”的问题，不会自动分配、加锁或延长对象寿命。仍需处理：

1. `probe` 部分失败时，哪些资源已经成功申请。
2. 用户接口发布后，其他线程可能马上访问。
3. `remove` 时若仍有打开文件，谁持有状态引用。
4. 事件源和异步任务何时停止，何时才允许释放内存。

## 9. 无板练习与条件实验

### 无板必做

把最小示例中的名称、设备对象、驱动对象、模块入口和 `probe/remove` 分别圈出；再用两块板的 LED 例子填写第 2 节归类表，画分离前后的依赖图。

### 可恢复 Linux 环境中的可选实验

只选择已审查的 `01_platform_bus_dev_drv` 纯日志副本，不选含 GPIO 占位符的版本。按目标 API 适配后构建；新旧内核 `platform_driver.remove` 的函数类型可能不同，以目标头文件为准。

分别执行“设备先、驱动后”与“驱动先、设备后”两轮。每轮记录：模块是否加载、sysfs 设备是否存在、`probe` 是否发生、正常卸载时 `remove` 是否发生。两轮之间完成正常清理，不留下同名设备。

若把设备名字改成不匹配的独立实验值，预期是两端可能注册成功但不调用该驱动的 `probe`。这只是测试设计，实际行为须由日志和绑定关系验证。

## 10. 排查与验收

“`insmod` 成功但没 `probe`”时按顺序查：设备是否存在 → 是否属于该总线 → 身份和匹配表是否正确 → 探测是否报错/延后。不要先怀疑用户态节点权限。
