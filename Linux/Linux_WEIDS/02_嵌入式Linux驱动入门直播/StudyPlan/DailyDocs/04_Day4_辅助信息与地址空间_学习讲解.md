# Day4 学习讲解：辅助信息与地址空间

> 本日主线：用 Day3 的读写解释用户地址、内核地址、硬件地址与访问权限，再理解用户拷贝的失败语义。
> 不通过故意制造内核崩溃来验证概念；涉及修改只使用可恢复环境中的实验副本。

## 1. 今天要把“环境不同”讲具体

“应用在用户态，驱动在内核态”不是终点。真正需要回答的是：这个地址属于谁？当前能否访问？访问是否可能睡眠？失败后是否已经改变设备状态？

本课程主线是内核驱动，但不能推导成“所有设备逻辑只能写在内核里”。Linux 也有受权限控制的用户态设备接口和用户态驱动方案。它们仍依赖内核提供的访问机制，不等于普通程序可以任意解引用物理地址。

## 2. 三种程序环境的对比

| 维度 | 典型裸机/RTOS 程序 | Linux 应用 | 本课程内核驱动 |
| --- | --- | --- | --- |
| 执行入口 | 启动代码、`main` 或任务入口 | 装载器/运行时到 `main` | 模块初始化及内核回调 |
| 地址视角 | 依芯片和 MPU/MMU 配置，不能一概而论 | 进程虚拟地址空间 | 内核虚拟地址与受控映射 |
| 权限 | 常直接控制外设，依系统配置 | 用户权限，通过系统接口申请服务 | 内核权限，也必须遵守资源与上下文规则 |
| 库与输出 | 芯片库、RTOS API、串口等 | libc、`printf`、系统调用 | 内核 API、`printk`/`pr_*` |
| 错误影响 | 可能影响整个固件系统 | 通常由进程隔离限制影响 | 可能破坏整个内核与系统 |
| 并发来源 | 中断、任务、DMA 等 | 线程、进程、信号等 | 用户调用、中断、定时器、work 等 |

单片机也可能使用保护机制，Linux 驱动也不是“有权限就能随便访问”。不要把表当成所有平台的绝对定律。

## 3. 先区分四种“地址”

1. **用户虚拟地址**：例如应用传给 `read()` 的缓冲区地址。它与某个进程的映射、权限及生命周期有关。
2. **内核虚拟地址**：例如内核分配的缓冲区、静态变量地址，也要保证对象仍存在且访问范围合法。
3. **物理/MMIO 地址**：硬件手册中的寄存器地址不能直接强转成普通 C 指针就访问，通常需资源申请、映射和专用 I/O 访问接口。
4. **设备/DMA 地址**：设备用于 DMA 的地址还可能经过 IOMMU 等转换，不应假设等于 CPU 虚拟或物理地址。

两个进程打印出相同地址数值，不代表引用同一物理内存。用户态切入内核后，也不是原来的用户指针自动变成可信内核缓冲区。

今天不展开页表和 DMA 编程，但必须知道“数值相等”和“访问语义相同”是两回事。

## 4. 逐个标出用户拷贝的方向

阅读 [05_transfer_data/hello_drv.c](../../02_彻底分析第1个驱动程序/source/05_transfer_data/hello_drv.c)，只追 `hello_read()` 和 `hello_write()`。

| 调用位置 | 源地址 | 目标地址 | 意义 |
| --- | --- | --- | --- |
| `.write` 的 `copy_from_user()` | 应用传入的 `buf` | 内核中的 `ker_val` | 从用户空间接收数据 |
| `.read` 的 `copy_to_user()` | 内核中的 `ker_val` | 应用提供的 `buf` | 把结果返回用户空间 |

名字里的 `to/from` 以用户空间为参照。`__user` 是用于检查的地址空间标记，不是运行期“自动校验全部参数”的魔法。

为何不能直接使用 `*buf` 或普通 `memcpy()`？用户范围可能无效、没有所需读写权限、跨页、缺页，或在调用期间被改变。内核提供的用户访问接口用于处理这类边界；驱动仍须验证协议长度和内部缓冲区范围。

## 5. 最容易记反的返回值

`copy_to_user()`、`copy_from_user()` 返回的是**未复制的字节数**：

- 请求 4，返回 0：全部复制完成。
- 请求 4，返回 1：只复制了其中一部分，仍有 1 字节未复制。
- 返回值不是“成功字节数”，通常也不是直接返回负 `errno`。

而驱动 `.read/.write` 的返回值是另一层协议：成功处理的字节数，或者负错误码。内核回调返回 `-EFAULT` 后，用户程序通常得到 `-1` 并从 `errno` 看到 `EFAULT`，不是直接得到负的错误常量。

不能把用户拷贝返回值原样当作读写成功长度，也不能忽略它并声称处理了全部请求。

## 6. 写入失败时，状态是否已经被污染

直接把用户数据拷进全局状态，遇到部分失败时，全局状态可能已经部分改变；仅仅随后返回错误，不会自动撤销修改。

对于“固定 4 字节配置值、要求整条提交”的新实验协议，合理的处理顺序是：

```text
检查请求长度
  -> 拷入独立临时值
  -> 若拷贝不完整：返回错误，不修改已发布状态
  -> 验证取值范围
  -> 按同步协议一次性提交新状态
  -> 返回实际处理长度
```

对于字节流，接口也可能允许部分传输，此时需返回真实成功量并维护相应状态。究竟采用哪种语义，取决于协议，不存在对所有设备通用的“一律返回 0”方案。

读取也要明确：拷出失败是否消费事件？如果事件已从队列取走再失败，是否允许丢失或需要保存待交付状态？用户内存可能部分被写入，不能承诺像数据库一样回滚用户缓冲区。

## 7. 用户拷贝为什么关系到休眠和锁

用户拷贝可能触发缺页处理并睡眠。硬中断、某些软中断路径，以及持有自旋锁的临界区不能随意睡眠。

因此常见的设计分两步：

- 写：在允许睡眠的进程上下文拷入临时缓冲区，再短暂加锁提交共享状态。
- 读：在锁内取得一致的快照或按协议取出记录，解锁后拷给用户。

但“拷贝移到锁外”不等于并发设计已经完成。还要回答快照是否过期、多个消费者是否会重复或丢失事件、拷贝失败是否需要恢复记录、设备解绑后对象是否仍有效。

互斥锁与自旋锁不是随意互换的优化选项。选锁必须从所有访问者的上下文出发，Day10/Day11 会继续补上等待与异步退出。

## 8. “辅助信息”与地址访问有何关系

对照 [完整 hello 驱动](../../01_单片机程序和Linux程序从上层到底层的完整比较/source/01_hello_drv/hello_drv.c)：

- 模块元数据帮助内核了解模块。
- 字符设备注册把设备号关联到操作表。
- 类和设备对象提供系统组织与用户接口呈现。
- 用户拷贝负责访问应用缓冲区。

这些解决不同层次的问题。`device_create()` 不会申请任意硬件寄存器，`/dev` 节点也不会让用户缓冲区变成内核地址。不要把“驱动能在系统中显示出来”和“数据访问已正确实现”混为一谈。

## 9. 今天怎么做实验

### 无板分析

给读写回调中的每个地址标注“来源、容量、生命周期、访问上下文”；对原实现固定复制 4 字节的行为，推演零长度、短缓冲区、完整缓冲区、拷贝部分失败四条路径。

### 可选 Linux 验证

先通过环境门禁，并在副本中实现约定的长度、临时缓冲区和错误路径。使用有限次数测试验证：正常值、非法长度、合法边界和错误返回。

若要测试不可访问的用户缓冲区，应在可恢复的隔离环境中，用经过审查的用户态测试程序构造受控映射/权限场景，并确认预期是驱动返回错误而不是系统崩溃；本日不要求执行这类故障注入。不要用任意地址强转、内核直接解引用或破坏性模块来试探。

## 10. 常见误判与验收

| 误判 | 应改成怎样的解释 |
| --- | --- |
| root 应用就能像裸机一样访问任意地址 | 权限提升不取消虚拟地址映射和内核接口约束 |
| `copy_from_user` 非零就是成功 | 非零代表未完整复制 |
| 返回 `-EFAULT` 就自动恢复内部状态 | 状态提交与回滚由驱动设计 |
| 有锁就能在任何上下文用户拷贝 | 自旋锁内或硬中断不能进行可睡眠访问 |
| 物理地址直接转指针即可 | 要使用对应资源、映射与访问 API |
