## 1. 学完今天，要能解释哪些问题

Day1 的应用程序由用户态运行环境启动。今天的代码则由内核装载和调用：它不只是换了几个函数名，而是换了运行权限、依赖环境和资源管理方式。

学完后应能独立完成三件事：

1. 指出模块初始化、模块退出和用户读写回调的不同触发时机。
2. 用构建产物、模块列表和内核日志说明一次加载/卸载发生了什么。
3. 解释字符设备注册与 `/dev` 节点创建不是同一件事。

建议分配：概念 15 分钟、源码 25 分钟、练习 20 分钟；具备环境时再做最小模块实验。没有 Linux 目标环境也可以完成源码分析，加载验证仍记“未执行”。

## 3. 为什么模块没有普通应用的 `main()`

普通 C 应用通常经过装载器、C 运行时等步骤后进入 `main()`；进程结束后，操作系统回收其进程资源。内核模块不是一个独立的用户进程，不能用 `./hello_drv.ko` 执行，也不链接用户态的 libc 来调用 `printf()`。

`module_init(hello_init)` 声明由内核在模块初始化时调用的函数，**不是执行到这一行就调用它**。初始化函数返回 `0` 表示成功，返回负错误码表示失败。`module_exit(hello_exit)` 声明正常卸载时的清理函数。

课程的 `01_simple` 直接写 `init_module()` 和 `cleanup_module()`，用于展示传统入口名称。但其 `int init_module()` 函数体为空，没有明确返回值，不应作为首次加载对象。第一次实验选择明确返回 `0`、只打印日志的 `02_printk`。

还要保留一个边界：驱动既可以编译为模块，也可以内建进内核。内建驱动不是通过每次 `insmod` 启动，也不具有普通模块的运行期卸载过程。

## 4. 逐项读懂 `02_printk`

不要先展开所有宏定义，先说明每个标记的职责。

| 源码中的标记 | 含义 | 不能据此推出什么 |
| --- | --- | --- |
| `hello_init()` | 初始化函数，打印后返回 `0` | 不能推出已经注册字符设备 |
| `hello_exit()` | 正常卸载时打印退出信息 | 不能推出任意资源都会自动释放 |
| `__init` | 初始化代码段标记，初始化成功后相关代码可被回收 | 不能把运行期回调也标成它 |
| `__exit` | 退出代码段标记，与模块/内建构建方式相关 | 不是负责释放内存的函数 |
| `MODULE_LICENSE("GPL")` | 向内核提供许可证元数据 | 不证明实现正确或已经完成合规审查 |
| `printk()` | 写入内核日志 | 不保证一定显示在当前终端 |

初始化失败尤其重要：如果初始化已申请资源 A，申请资源 B 时失败，应在返回错误前释放 A。内核不会把一次失败的初始化当作成功加载，再替你调用退出函数收尾。

## 5. 日志为什么不是 `printf()`

`printf()` 通常经用户态库向标准输出写数据；`printk()` 写入内核日志缓冲区。控制台是否显示内核日志，还受日志级别、控制台配置等影响。

因此需要分开观察：

- 加载命令是否成功退出。
- 模块是否在 `lsmod` 中出现。
- 内核日志是否出现本次初始化信息。
- 正常卸载后模块是否消失、退出日志是否出现。

`dmesg` 可能因权限不可读；“当前终端没显示”也不等于代码没有执行。新代码通常可用 `pr_info()`、`pr_err()` 或设备相关日志接口；今天先理解日志去向，不要求改造课程日志风格。

## 6. 从模块走到字符设备

`03_test` 在模块初始化中调用 `register_chrdev(0, "hello_drv", &hello_fops)`。首参数 `0` 请求动态主设备号；成功返回实际主设备号，失败返回负错误码，不能不检查就继续。

这里的 `hello_fops` 只有 `.owner`，没有 `.read`、`.write` 等函数。因此：

- 模块可以加载并注册字符设备。
- 不代表已经有可用的数据交换功能。
- 也没有 `class_create()` / `device_create()`，不能假定 `/dev/hello_drv` 自动出现。

完整 hello 示例才补上更多部分：

| 动作 | 解决的问题 | 对应清理 |
| --- | --- | --- |
| `register_chrdev()` | 把字符设备号范围关联到操作表 | `unregister_chrdev()` |
| `class_create()` | 建立设备类，组织用户可见设备对象 | `class_destroy()` |
| `device_create()` | 注册带设备号和名称的设备对象 | `device_destroy()` |
| devtmpfs/udev 等机制 | 根据系统配置呈现 `/dev` 节点及权限 | 依系统机制处理 |

设备节点是带设备号的特殊文件，不是把驱动源码放进 `/dev`。`/dev/hello` 的名字与注册名不必相同，访问最终依靠设备类型和设备号找到对应操作表。

## 7. 三种时机不要混在一起

```text
构建 hello_drv.c -> hello_drv.ko
                         |
insmod ----------------> 模块初始化
                         |
应用 open/read/write --> VFS / 字符设备层 -> file_operations 回调
                         |
最后一个打开文件引用释放 -> .release（若实现）
                         |
rmmod -----------------> 模块退出
```

`.release` 不是模块退出。`dup()`、`fork()` 等可能让多个文件描述符共享一个打开文件对象，不是每次 `close()` 都立即调用 `.release`。

`.owner = THIS_MODULE` 有助于文件操作期间的模块引用管理，但不会替你处理设备解绑、共享缓冲区并发、定时器或 work 的寿命。

## 8. 最小实验：只打印，不接硬件

### 8.1 加载前的门禁

只在可恢复的 Linux 虚拟机或明确允许模块实验的目标系统执行。先填写环境指南的环境卡，确认匹配构建树、模块加载权限、恢复方式和不存在其他同名模块。

Windows PowerShell 不能直接加载 Linux 模块。WSL 能执行 Linux 应用，不等于具备匹配模块构建树和加载能力。容器共享宿主内核，不是安全试载未知模块的隔离边界。

### 8.2 在 Linux 实验副本中构建

当前目录应为只包含已审查 `02_printk` 内容的实验副本；先核对 Kbuild 规则。

```bash
uname -a
ls -ld "/lib/modules/$(uname -r)/build"
make -C "/lib/modules/$(uname -r)/build" M="$PWD" modules
file ./hello_drv.ko
modinfo ./hello_drv.ko
```

`make -C` 进入内核构建目录，`M` 指向外部模块目录。`.ko` 的架构、`vermagic` 等信息应与目标匹配，但元数据匹配不保证所有符号、配置和签名条件都满足。

### 8.3 分两个终端观察

终端 A 观察日志，结束时 `Ctrl+C` 退出跟随：

```bash
sudo dmesg --follow
```

终端 B 每一步确认成功后再执行下一步：

```bash
sudo insmod ./hello_drv.ko
lsmod
sudo rmmod hello_drv
lsmod
```

预期是出现初始化日志、模块进入列表、出现退出日志、模块从列表消失。以上是**预期**，实际命令、退出状态和输出须由学习者记录。

出现 Oops、卡死或新的严重告警就停止实验并恢复环境，不使用强制加载/卸载选项。

## 9. 教学代码还缺哪些工程条件

从完整 hello 示例至少找三处，并说明影响，而不是只写“错误处理不足”：

1. 动态字符设备注册的负返回值没有完整检查，后续设备号可能无效。
2. `device_create()` 的错误没有完整处理，初始化可能假成功。
3. 用户拷贝返回值没有用来决定读写结果。
4. 全局缓冲区没有同步，多线程读写可能相互覆盖。
5. 未定义有效数据长度和偏移/EOF 语义，普通文件工具可能持续读取。
6. `class_create(THIS_MODULE, ...)` 属于旧签名，上游 Linux 6.4 起去掉首参数；应以目标头文件为准。

这些是审查结论，不表示本讲义已经修复课程代码。

## 10. 常见现象怎样定位

| 现象 | 优先检查 |
| --- | --- |
| `Invalid module format` | 模块架构、目标内核版本、符号版本和日志 |
| `Unknown symbol` | 具体符号、内核配置、依赖及构建来源 |
| 签名/密钥失败 | 目标安全策略与合规签名条件，不绕过策略 |
| 没有 `/dev/hello` | 选的是否为只打印版本，是否真的注册设备对象 |
| `rmmod` 提示模块正在使用 | 是否仍有进程打开设备或存在其他模块引用 |
