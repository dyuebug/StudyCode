 # 驱动学习方法说明：怎么读代码

 这份文档专门回答一个很实际的问题：

 **驱动代码到底该怎么读，才不容易一上来就读崩？**

 很多初学者不是不努力，而是顺序错了。

 ---

 ## 1. 不要一上来逐行读

 初学驱动时，最常见的低效方式就是：

 - 打开一个 `.c` 文件
 - 从第一行开始逐行看
 - 每遇到一个不会的函数就查
 - 最后看了很久，却不知道这个文件整体在干什么

 正确思路应该是：

 **先看结构，再看角色，最后才看细节。**

 ---

 ## 2. 正确的读代码顺序

 建议按下面顺序来。

 ### 第一步：先看这一章讲什么

 优先看：

 - `doc_pic/*.md`
 - `doc_pic/*.pdf`

 先回答：

 - 这章是解决什么问题的？
 - 它比上一章多了什么？
 - 它属于入门、过渡，还是专题实战？

 如果这一步没做，后面看代码容易像在黑暗里摸索。

 ### 第二步：看目录结构

 进入 `source/` 后，先不要急着读主代码。

 先看：

 - 有哪些子目录
 - 哪些目录像最小示例
 - 哪些目录像逐步完善版

 你先要知道：

 - 这个章节是不是按“从简单到复杂”组织的
 - 你现在应该先读哪个版本

 ### 第三步：先看 `Makefile`

 这是非常关键的一步。

 先看 `Makefile`，你能更快知道：

 - 这个目录编译出什么
 - 哪些是内核模块
 - 哪些是用户态测试程序
 - 文件之间的关系是什么

 很多初学者忽略 `Makefile`，结果连“谁跑在内核里、谁跑在用户态”都没分清。

 ### 第四步：先看驱动的骨架

 打开驱动源码后，不要先管所有细节，优先找：

 - 初始化函数
 - 清理函数
 - 是否注册字符设备
 - 是否有 file_operations
 - 是否有 probe / remove
 - 是否有设备树匹配表

 也就是说，先找“骨架”，再找“肉”。

 ### 第五步：再看应用或测试程序

 很多驱动例子都会配一个测试程序。

 这个程序非常重要，因为它能告诉你：

 - 这个驱动打算怎么被使用
 - 应用是通过什么接口访问驱动的
 - 驱动对外暴露的接口长什么样

 学驱动如果不看测试程序，经常只能看到“驱动内部做了什么”，却不知道“它对外如何工作”。

 ### 第六步：最后才补 API 细节

 当前面这些都大致明确后，再去补：

 - 某个 API 的参数
 - 某个结构体字段的用途
 - 某个回调到底何时触发

 这样你查资料时，目标会更明确，不容易陷进去。

 ---

 ## 3. 看驱动时最该先问的 6 个问题

 每打开一个新例子，都先问自己：

 1. 这个例子属于哪一章、解决什么问题？
 2. 这是驱动程序、测试程序，还是别的辅助文件？
 3. 它跑在用户态还是内核态？
 4. 这个目录最终编译出什么？
 5. 这个驱动对外提供什么接口？
 6. 这个例子比前一个例子多了什么机制？

 如果这 6 个问题能回答出来，你的阅读效率会明显提升。

 ---

 ## 4. 不同类型代码，关注点不一样

 ### 看应用程序时

 重点关注：

 - `main()`
 - `open/read/write/ioctl/poll` 等调用
 - 它如何访问设备文件

 ### 看最小驱动时

 重点关注：

 - `module_init`
 - `module_exit`
 - `printk`
 - 模块加载/卸载流程

 ### 看字符驱动时

 重点关注：

 - 设备号
 - 字符设备注册
 - `file_operations`
 - 应用和驱动的接口对应关系

 ### 看平台驱动/总线驱动时

 重点关注：

 - device / driver / bus
 - match
 - `probe` / `remove`
 - 设备树或平台数据

 ### 看设备树时

 重点关注：

 - 节点
 - `compatible`
 - `reg`
 - GPIO / pinctrl 属性

 ### 看 I2C / SPI / framebuffer 专题时

 重点关注：

 - 它属于哪类总线或子系统
 - 它相比普通字符驱动多了哪一层框架
 - 应用最终是怎么访问它的

 ---

 ## 5. 怎么判断自己“读懂了”

 不是你能跟着看完代码，就叫读懂。

 真正读懂，至少能说出：

 - 这段代码在整章里的角色
 - 它最终要完成什么功能
 - 它和应用程序或硬件怎么连接
 - 它新增了什么机制

 如果你只能说“这行好像是在注册设备”，那还只是局部理解。

 ---

 ## 6. 遇到读不下去时怎么办

 如果你读着读着开始烦躁，通常不是你能力不够，而是阅读粒度错了。

 这时建议立刻停下来，改成下面顺序：

 1. 回去看讲义标题和本章目标
 2. 看 `Makefile`
 3. 只抓主干函数
 4. 暂时跳过不懂的细节 API
 5. 看测试程序怎么调用它

 先把骨架抓住，再回来填细节。

 ---

 ## 7. 最后给你的原则

 学 Linux 驱动，读代码最重要的原则不是“读得细”，而是：

 **先读出结构，再读出关系，最后才读出实现细节。**

 这样你才不会在大量 `.c`、`.h`、`Makefile`、`.dts` 里迷路。
