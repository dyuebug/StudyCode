## 2. Cursor 使用总规则

### 2.1 默认沟通规则

- 始终使用中文简体回答。
- 技术名词可以保留英文，例如 `FreeRTOS`、`device tree`、`Makefile`、`driver`。
- 解释时优先采用“先讲方法，再给结论”的方式。
- 面向初学到进阶过渡阶段，讲解要清楚，但不要过度简化底层原理。
- 用户如果问“为什么”，必须解释推理过程和判断依据。
- 用户如果问“怎么学”，必须结合当前资料目录给出可执行步骤。

### 2.2 文件与工具规则

在 Cursor 中处理本工作区资料时：

1. 修改文件前必须先读取相关文件。
2. 不要凭空猜测目录结构，必须通过工具查看实际文件。
3. 优先使用现有资料，不重复造轮子。
4. 创建新学习文件、任务文件、日志文件时，必须使用 UTF-8 无 BOM。
5. 除非用户明确要求，不要执行 `git commit`、`git push`、删除文件、批量移动文件等高风险操作。
6. 如果需要运行命令，先说明目的，再执行；涉及破坏性操作必须先获得确认。

## 4. 总体学习路线

当前阶段建议采用以下路线：

```text
阶段 A：资料地图与环境确认
阶段 B：Linux 应用与驱动整体认知
阶段 C：第一个 Linux 驱动最小闭环
阶段 D：字符设备驱动与 APP 交互
阶段 E：总线 / 设备 / 驱动模型
阶段 F：设备树 / pinctrl / GPIO
阶段 G：中断 / poll / ioctl / 异步通知
阶段 H：SR501 / DHT11 / DS18B20 等传感器实战
阶段 I：I2C / SPI / Input / Framebuffer 专题
阶段 J：BSP / 驱动项目化整理与作品集
```

优先级原则：

```text
先主线，后专题；
先跑通，后深入；
先能讲清楚，再追求复杂；
先最小闭环，再扩展项目。
```

虚拟化学习原则：

```text
后续 Linux 驱动学习优先结合虚拟机和 QEMU 进行。
主机侧优先使用 Ubuntu 虚拟机作为开发环境；
目标侧优先使用资料中已有的 100ask_imx6ull-qemu 相关代码和环境作为模拟开发板；
在真实开发板不可用时，优先用 QEMU 完成编译、加载、日志观察和最小驱动验证闭环。
```

QEMU 学习目标不是替代真实硬件，而是先建立：

- 主机开发环境和目标运行环境的区别
- 交叉编译的基本流程
- `.ko` 模块如何进入目标系统
- `insmod` / `rmmod` / `dmesg` 的验证闭环
- 板级文件如 `board_100ask_imx6ull-qemu.c` 和具体模拟平台的关系

## 11. 能力分层标准

后续规划必须根据用户当前能力分层来安排。

### 第 0 层：刚接触

目标：建立地图。

表现：

- 不清楚应用、驱动、内核关系
- `.c`、`.ko`、`.dts`、`Makefile` 混在一起看

### 第 1 层：能区分角色

目标：分清文件身份。

表现：

- 知道 `printf` 和 `printk` 不一样
- 知道 `main()` 和 `module_init()` 不一样
- 知道 `.ko` 是内核模块产物

### 第 2 层：能看懂简单例子结构

目标：看懂一个完整小例子。

表现：

- 会先看 `Makefile`
- 能区分驱动文件和测试程序
- 能找出初始化、清理、接口函数

### 第 3 层：能串起多个概念

目标：形成 Linux 驱动主线。

表现：

- 知道 `device / driver / bus` 的关系
- 知道设备树用于描述硬件
- 知道应用和驱动之间有 `read/write/ioctl/poll` 等方式

### 第 4 层：能跟着改代码

目标：从阅读者变成初级实践者。

表现：

- 敢改 `printf` / `printk`
- 敢改测试程序
- 敢对比两个版本驱动差异
- 知道自己改的是应用层、驱动层还是设备树层

### 第 5 层：能带着问题读专题驱动

目标：进入 I2C、SPI、Input、Framebuffer 等专题。

表现：

- 能判断一个专题比前一个例子新增了什么机制
- 能沿着设备树、驱动、测试程序三条线读代码
- 能做小范围修改并验证结果
