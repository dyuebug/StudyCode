**日期**：2026-07-09

**目标环境**：Ubuntu 虚拟机 + 100ask_imx6ull-qemu 模拟开发板

## 1. 为什么要结合 QEMU 学

Linux 驱动学习不能只停留在“看懂代码”。真正的驱动学习至少要形成一个闭环：

```text
写代码 / 改代码
-> 编译生成模块
-> 放入目标系统
-> 加载模块
-> 查看内核日志
-> 运行测试程序
-> 卸载模块
-> 记录问题和结果
```

如果暂时没有真实开发板，就用 QEMU 作为模拟开发板。QEMU 的价值不是完全模拟所有真实硬件，而是让你先把“驱动工程流程”跑起来。

## 3. 虚拟机和 QEMU 分工

建议先建立两个角色：

| 角色 | 作用 | 类比 |
|---|---|---|
| Ubuntu 虚拟机 | 开发主机，负责编辑、编译、交叉编译 | 工程师电脑 |
| QEMU 模拟板 | 目标板，负责运行内核和驱动 | 开发板 |

学习时不要把它们混在一起。

你在 Ubuntu 虚拟机里做的是：

- 看源码
- 改源码
- 执行 `make`
- 得到 `.ko` 模块或测试程序
- 把产物放进 QEMU 目标系统可访问的位置

你在 QEMU 目标系统里做的是：

- `insmod xxx.ko`
- `dmesg`
- 运行测试程序
- `rmmod xxx`
- 观察驱动是否真的工作

## 4. 后续 14 天主线如何结合 QEMU

### Day1~Day3：先分层，不急着跑 QEMU

重点还是：

```text
应用程序 vs 驱动程序 vs 内核
```

这几天可以先在 Ubuntu 虚拟机里编译普通应用，例如：

```bash
gcc hello.c -o hello
./hello
```

目标是知道：这是用户态程序，不是驱动。

### Day4：理解用户空间和内核空间

开始把 QEMU 加入理解：

```text
Ubuntu 虚拟机里的 shell 是主机环境；
QEMU 里的 shell 是目标板环境；
驱动模块必须和目标内核匹配。
```

这一天重点理解：为什么用户程序不能随便访问内核地址和硬件寄存器。

### Day5：用 QEMU 跑第一个板级驱动闭环

这是 QEMU 最重要的切入点。

目标流程：

```text
Ubuntu 虚拟机中编译驱动
-> 得到 .ko
-> 放到 QEMU 文件系统
-> 在 QEMU 中 insmod
-> 用 dmesg 看 printk
-> 运行测试程序
-> rmmod 卸载
```

这一天先不追求理解全部寄存器，只要求跑通流程。

### Day6~Day7：理解 board 文件和驱动分离

重点观察：

```text
board_100ask_imx6ull-qemu.c
```

它代表的是特定板子的硬件差异。你要理解：为什么不同板子会有不同的 board 文件，而上层 LED 操作接口可以尽量统一。

### Day8~Day9：设备树和 QEMU

如果课程提供 QEMU 对应设备树，就重点看：

```text
compatible
reg
gpio
pinctrl
```

目标不是背语法，而是理解：QEMU 模拟板也需要一种方式告诉内核“硬件长什么样”。

### Day10~Day14：用 QEMU 验证交互方式

后续 `read/write/ioctl/poll` 等机制，如果不依赖真实传感器，也可以优先在 QEMU 或虚拟环境里验证调用路径。

## 5. 读 QEMU 板级源码时先看什么

以 `board_100ask_imx6ull-qemu.c` 为例，阅读顺序是：

1. 看文件名：确认它对应 `100ask_imx6ull-qemu` 模拟板。
2. 看包含的头文件：确认它是内核驱动相关代码。
3. 找核心结构体：例如 `iomux`、`imx6ull_gpio`。
4. 找初始化函数：例如 `board_demo_led_init()`。
5. 找控制函数：例如 `board_demo_led_ctl()`。
6. 找注册结构：例如 `struct led_operations board_demo_led_opr`。
7. 最后再看寄存器地址和位操作。

初学阶段不要一上来死磕寄存器地址。先看清楚：

```text
这个文件在描述 QEMU 模拟板上的 LED 硬件操作方式。
```

## 6. QEMU 学习中的常见错误

### 错误 1：把 Ubuntu 虚拟机当成目标开发板

错误现象：
在 Ubuntu 虚拟机里直接 `insmod` 给 ARM 板编译的 `.ko`。

错误原因：
没有区分主机架构和目标架构。

正确做法：
Ubuntu 虚拟机是开发主机；QEMU 里的系统才是目标板环境。

### 错误 2：模块和目标内核版本不匹配

错误现象：
`insmod` 失败，提示 invalid module format。

错误原因：
`.ko` 不是用目标内核对应的源码或头文件编译出来的。

正确做法：
驱动模块必须匹配 QEMU 目标系统运行的内核版本和配置。

### 错误 3：只看 QEMU 能不能启动，不看驱动日志

错误现象：
QEMU 启动了，但不知道驱动有没有加载成功。

错误原因：
没有使用 `dmesg` 检查内核日志。

正确做法：
每次 `insmod` 后立刻执行：

```bash
dmesg | tail
```

### 错误 4：一开始就纠结 LED 是否真的闪烁

错误现象：
在 QEMU 里看不到真实 LED，于是觉得实验没意义。

错误原因：
没有理解 QEMU 初期重点是验证驱动流程和调用路径。

正确做法：
先通过 `printk`、测试程序返回值、设备节点行为确认驱动路径是否走通。

### 错误 5：跳过 Makefile

错误现象：
不知道 `.ko` 是怎么生成的，也不知道用了哪个内核目录。

错误原因：
直接看 `.c`，没有先看构建规则。

正确做法：
读驱动目录时必须先看 `Makefile`。

## 7. 后续执行规则

从现在开始，后续学习规划按以下方式执行：

```text
能在 Ubuntu 虚拟机验证的，先在 Ubuntu 验证；
涉及开发板运行的，优先找 100ask_imx6ull-qemu；
没有真实硬件时，先用 QEMU 跑通模块加载、日志和测试程序；
涉及真实传感器的章节，先学习驱动结构和调用路径，再补真实硬件现象。
```

每次生成学习任务时，额外增加一个栏目：

```text
QEMU / 虚拟机验证任务
```

其中至少回答：

1. 今天内容是否能在 Ubuntu 虚拟机上验证？
2. 是否需要 QEMU 目标系统？
3. 需要生成什么产物？普通可执行文件还是 `.ko`？
4. 验证结果从哪里看？终端输出还是 `dmesg`？
