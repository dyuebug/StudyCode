## FreeRTOS-LTS 的正确打开方式

`rtos_doc_source/RTOSCode/FreeRTOS-LTS/` 包含多个独立上游组件，例如网络、MQTT、HTTP、JSON、PKCS11、SNTP、回退算法和 AWS IoT SDK。其目录中也包含各组件自己的许可证、变更记录、测试与依赖。

推荐顺序：

```text
先完成 STM32F103 + FreeRTOS 的任务、队列、同步实验
-> 遇到某个内核机制或配置项需要解释时，定位对应 FreeRTOS 内核/端口源码
-> 需要网络协议时，再选择单一组件，例如 coreMQTT 或 coreHTTP
-> 需要工程化测试时，再学习 Unity / CMock
-> 有安全与验证目标时，再了解 CBMC、MISRA、Coverity 材料
```

不要做的事：

- 不从 `FreeRTOS-LTS` 顶层开始逐文件阅读。
- 不把 AWS IoT SDK 当作 STM32 裸机或 Linux 驱动入门前置。
- 不修改上游或第三方代码后误以为是自己的项目成果。
- 不忽略各目录自带的 `LICENSE`、`SECURITY.md`、`MISRA.md` 和 `README.md`。

## 测试资料的进阶价值

当已完成 [[14_航空背景项目映射|航空背景项目]] 的第一版后，可以将测试材料转化为工程能力：

| 目标 | 可阅读材料 | 可落地到个人项目的成果 |
| --- | --- | --- |
| 单元测试 | Unity / CMock 示例 | 帧解析、CRC、状态机和边界保护的主机端单元测试 |
| Mock 外设 | CMock 示例 | 模拟 UART、I2C/SPI 错误和超时，不依赖真实板卡复现 |
| 静态检查 | MISRA / Coverity 相关材料 | 明确的编码规则、警告分级和整改记录 |
| 形式化思维 | CBMC 证明目录 | 为关键边界检查、长度校验和状态转换定义可验证性质 |

> [!tip] 航空软件背景的使用方式
> 你的优势不是宣称已经掌握所有第三方框架，而是把“需求—设计—测试—问题闭环”的习惯应用到独立项目：为通信帧解析、超时和故障降级写明确的测试用例和证据。

## 建立个人索引的规则

当遇到新目录时，先在 [[04_问题清单|问题清单]] 记录其归类，然后只回答五个问题：

1. 它是教学例程、自有模板、上游组件、测试依赖还是构建工具？
2. 当前学习阶段是否真的需要它？
3. 可以构建的最小目标是什么？
4. 入口 README、Makefile、工程文件或核心源码在哪里？
5. 使用或改动时需要遵守什么许可证、硬件和保密边界？
