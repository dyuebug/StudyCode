## 2. 三个"余量"不是同一个东西

这是本次审查最重要的一条。README 写的"余 1640 B"与"稳态堆 120 B"分别指两件不同的事，
混着读会得出错误结论。

| 口径 | 数值 | 来源 | 能被谁用 |
| --- | --- | --- | --- |
| **A. 链接器尾部余量** | 1640 B | `0x20002000 − 0x20001998` | MSP 主栈（中断嵌套）向下生长的缓冲；**不能**拿来建任务 |
| **B. FreeRTOS 动态余量** | 120 B（稳态） | `[stat]` 日志 `xPortGetFreeHeapSize()` | 唯一能用来"加功能"的内存 |
| **C. 静态主栈预留** | 1024 B | 链接脚本 `_Min_Stack_Size` | 链接器只保证这么多，峰值未测 |

推导（实测地址逐项相减）：

```text
.data              100 B   0x20000000 .. 0x20000064
.bss 实体         4912 B   0x20000064 .. 0x20001394   （含 ucHeap 4096 + __sf 312 + 其余 504）
对齐填充             4 B   0x20001394 .. 0x20001398
._user_heap_stack 1536 B   0x20001398 .. 0x20001998   （_Min_Heap_Size 512 + _Min_Stack_Size 1024）
尾部余量          1640 B   0x20001998 .. 0x20002000
------------------------------------------------------------
合计               8192 B
```

`.bss` 里 504 B 的"其余"由 FreeRTOS 内核对象构成（`pxReadyTasksLists` 256 B、
`xDelayedTaskList1/2` 各 32 B、`s_sensor` 54 B、`s_stats` 64 B 等），逐项可由
`nm -S --size-sort` 复现。

**结论**：1640 B 是"SRAM 顶部没被链接器占用的空间"，它在运行期供 MSP 使用。
把它当成"还能放 1.6 KB 代码/数据"会直接压缩中断栈，而中断栈溢出**不会**在链接期报错。

## 3. FreeRTOS heap 4096 B 的分配

实测锚点（启动日志 `xPortGetFreeHeapSize()`）：三任务 + 队列 + 互斥量之后 **736 B**，
idle 创建并稳定后 **120 B**。

| 项 | 大小 | 依据 |
| --- | --- | --- |
| `rx` 栈 224 字 | 896 B | 源码 `xTaskCreate(..., 224, ...)` |
| `ctrl` 栈 224 字 | 896 B | 同上 |
| `health` 栈 256 字 | 1024 B | 同上 |
| 三任务栈小计 | **2816 B** | 68.75% 的堆 |
| idle 栈 128 字 | 512 B | `configMINIMAL_STACK_SIZE = 128` |
| 四个 TCB（含 idle） | ≈ 400 B | 推算：`4096 − 736 − 2816 = 544` 是三 TCB + 队列 + 互斥量；idle 另占 ≈100 |
| RX 队列（深度 64 × 1 B）+ 结构 | ≈ 184 B | `RX_QUEUE_DEPTH = 64`；结构体按 heap_4 对齐推算 |
| 互斥量 | ≈ 80 B | `xSemaphoreCreateMutex()` |

稳态 120 B 与"736 − 512 − ≈100"吻合（124 B），误差来自对齐。

**js：任务栈是最大项，且它与"RAM 够不够"是互相挤压的关系**——多给栈只减少堆余量，
不改变 `.bss` 总量。这一点 README §10.1 已记录，本次实测确认。

## 4. 冗余通道成本（推算，未编译验证）

现状（`protocol.md` §6）：单数据源、单下行 TX、无表决。
"双通道"在 RAM 上的真实成本取决于**是否新增任务**：

### 方案 A：独立 `rx2` 任务 + 独立队列

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 第二 rx 任务 | 868 B | 栈 192 字（768 B）+ TCB ≈100 B |
| 第二 RX 队列 | 184 B | 深度 64 × 1 B + 队列结构 |
| 第二解析器 | ≈ 56 B | `av_parser_t`（32 B 载荷 + 状态） |
| 通道状态（×2） | ≈ 40 B | 每通道 `last_good`/`frames`/`crc_err`/`gap` |
| 表决与降级决策 | ≈ 16 B | 当前模式、分歧计数 |
| **合计** | **≈ 1164 B** | |

`configTOTAL_HEAP_SIZE` 需从 4096 提到至少 5260，实际取 6144（+2048）。

**链接可行性**：RAM 总量 `6552 + 2048 = 8600 > 8192` → **QEMU 8 KB 布局直接链接失败**
（`region RAM overflowed`）。方案 A 在 `stm32vldiscovery` 机型上不可行。

### 方案 B：单 `rx` 任务轮询两路（不加任务）

| 项 | 估算 |
| --- | --- |
| 第二 RX 队列 | 184 B |
| 第二解析器 | 56 B |
| 通道状态（×2） | 40 B |
| 表决 | 16 B |
| **合计** | **≈ 296 B** |

`configTOTAL_HEAP_SIZE` 提到 4608（+512）留出对齐余量。

**链接可行性**：RAM 总量 `6552 + 512 = 7064`，尾部余量 `8192 − 7064 = 1128 B`，
仍大于 `_Min_Stack_Size`（1024 B）→ 可链接，但 MSP 缓冲从 1640 B 降到 1128 B
（**压缩了 31% 的中断栈裕度，且没有实测 MSP 峰值**）。

### 方案 C：换真板目标（STM32F103C8T6，20 KB）

链接脚本 `STM32F103C8Tx.ld` 的 RAM 是 20 KB。方案 A 在此目标下余量充足。
但**项目当前没有对真板目标的构建验证**（`F103_QEMU` 之外的布局只做过 CMake 配置，
没有运行记录），不能写成"真板上可行"。

### 对比

| 方案 | 新增 RAM | 8 KB 可链接 | 实时性 | 结论 |
| --- | --- | --- | --- | --- |
| A 独立任务 | ≈1164 B | **否** | 最好（两路独立调度） | 8 KB 下不可行 |
| B 共享任务 | ≈296 B | 是（余 1128 B） | 退化（轮询，单路阻塞影响另一路） | 勉强可行，代价是 MSP 裕度 |
| C 真板 20 KB | — | 未验证 | 同 A | 需真板构建与实测 |

## 5. 审查结论

1. **"余 1640 B"不能当可用内存**。它是 MSP 的缓冲，不是应用可分配空间。
   项目文档此前没有区分这两个口径，本次已在 README §10.1 与 `architecture.md` §5 补上说明。
2. **稳态 120 B 是当前第一约束**：连一个 128 字栈的新任务（512 B + TCB）都建不起来。
   任何"再加一个任务"的需求都必须先提高 `configTOTAL_HEAP_SIZE`，而那是共享配置。
3. **双通道不应在 8 KB 目标上做完整版**。方案 A 链接失败是硬约束，不是调参问题。
   可行路径只有：方案 B（牺牲实时性与 MSP 裕度）或换真板目标（未验证）。
4. **更合理的下一步是"单通道健康度"而不是"双通道冗余"**：给现有通道补独立的
   帧计数/错误计数/超时统计（约 40 B），先把"通道坏了能不能看出来"做对，
   再谈"两路怎么表决"。后者需要真板证据支撑。
5. **FLASH 不是瓶颈**（18256 / 131072 = 13.93%），双通道逻辑代码约 2–3 KB 可以接受；
   瓶颈只在 RAM。

- 方案 C 的真板构建：未跑。
