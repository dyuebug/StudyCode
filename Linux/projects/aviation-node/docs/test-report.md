# 故障注入测试报告（`projects/aviation-node`）

> 记录性质：本报告中**所有数字都来自 `tests/qemu-stm32/logs/aviation_node.log` 的实测输出**，
> 测量环境为 QEMU 仿真（2026-10-27 一次运行）。标「推算」的是由实测值算出的差值，
> 标「未验证」的是本环境没有证据的部分（真板项）。没有这些标注的结论不得引用。

- 被测对象：`projects/aviation-node/`（教学级地面仿真节点，**不是**飞控）
- 证据日志：`tests/qemu-stm32/logs/aviation_node.log` 与 `logs/aviation_downlink.bin`
  （每次 `bash run.sh aviation-link` 会同时覆盖两者，且来自同一次运行）
- 机器判定：`tests/qemu-stm32/aviation/expect.py`（21 项不变量，退出码 0/1/2）与
  `aviation/link.py`（下行通道 L1–L7，退出码 0/1/2）
- 协议与状态规范：[`protocol.md`](protocol.md)；构建与运行：[`../README.md`](../README.md) §8

## 1. 环境与判定口径

| 项 | 值 |
| --- | --- |
| 目标 / 仿真器 | STM32F103（Cortex-M3）/ QEMU 10.2.1 `-M stm32vldiscovery` |
| 内核 | FreeRTOS-Kernel V11.3.0（裁剪子集），SysTick 1000 Hz |
| 编译器 | `arm-none-eabi-gcc` 14.2 rel1，`-mcpu=cortex-m3 -mthumb -mfloat-abi=soft`，零警告 |
| 构建 | `-DF103_QEMU=ON`（8 KB 链接脚本），`AV_DEBUG_BLOCK_RX_MS=800` |
| 固件体积 | FLASH 18028 B（含下行；调试注入段占 288 B）、RAM 6536 B、稳态空闲堆 432 B |
| 注入器 | `tests/qemu-stm32/aviation/inject.py`，50 Hz、11 段剧本，8.2 s 墙钟 |

**时间口径**：所有 `t=` 与 `ms` 都是**固件毫秒**。QEMU 以 24 MHz 驱动 SYSCLK 而固件按 8 MHz 计算，
实测时基偏差 2.90 倍；且跨运行漂移随时长累积（`t≈1100` 差 41、`t≈27000` 差 154）。
因此本报告只引用**同一份日志内的差值**或**跨运行的区间**，不引用单次绝对时刻作为判据。

**判定分三档**（与 `CLAUDE.md` §1.1 一致）：实测 / 构建级 / 未验证。本报告的用例全部是实测，
但只覆盖软件数据链；硬件外设见 §7。

## 2. 用例与结果总览

剧本每段只改一个变量，故障类别与 `av_health.h` 的标志位一一对应：

| # | 故障类别 | 注入手段（时段） | 预期 | 实测结论 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | 错帧 | `badcrc` 2.00–2.60 s，30 帧 CRC 取反 | 连续 3 帧才置 `CRC`；`crc` 计数 +30 | 降级 1 次，`crc=30` | C4 / C7 / C13 |
| 2 | 数据越界 | `range` 3.20–3.60 s，pitch 90.00° | 单帧即拒，`RNG` 置位，同拍降级 | 置位与降级同 tick | C4 / C12 |
| 3 | 数据突变 | `rate` 4.30–4.55 s，pitch 1.00°→45.00° | 拒收且不刷新 `last_good`，300 ms 后 `STALE` | `RATE` 后 246 tick `STALE` | C4 / C11 |
| 4 | 通信静默 | `silent` 5.00–7.00 s，无字节 | `T` + `STALE` → DEGRADED → 3000 ms → SAFE | 停留 3005 ms | C4 / C6a / C6c / C10 |
| 5 | 丢帧 | `drop` 7.60–7.66 s，连丢 3 帧（`SEQ` 仍递增） | 只增 `gap` 3，不降级 | `gap=133`，降级仍 5 次 | C7 / C13 |
| 6 | 任务阻塞 | 固件编译期注入，`t=16571` 起 800 ms | 心跳年龄 > 400 ms → 停喂，原因含 `HB` | `hb=441`，`reason=HB+FLAGS` | C14 |
| 7 | 时间戳年龄下溢 | 无需注入（rx 抢占 health 后的时间戳先后） | `age`/`hb` 恒 < 2³¹ | 修复前抓到 `age=4294967292`，修复后 0 例 | C15 |

第 7 项不是剧本里的故障段，而是实测中抓到的固件缺陷：`age` 曾是 `now - 时间戳` 的无符号减法，
当 rx（优先级 3）在 health（优先级 2）取 `now` 之后才写入时间戳时下溢。**`hb` 走同一条路径**，
下溢会让门控误读成"心跳早断了"并停一次喂狗——所以它不只是日志难看。修法见
`../README.md` §6.2，回归判据是 C15。

判定结果：**上行 21/21 通过（退出码 0）、下行 7/7 通过（退出码 0）**。

## 3. 逐项记录

### 3.1 错帧（`badcrc`）

- 预期：单帧 CRC 错不降级（避免偶发误码误触发），连续 3 帧置 `CRC` 并降级。
- 实测：`[mode] t=5667 NORMAL -> DEGRADED flags=0x04`；`[fault] t=5793 set=0x03`（`T`、`STALE`
  随后置位，因为链路对应用层已无可用帧）；`[fault] t=7197 clear=0x07` 后 `t=7300 -> NORMAL`。
- 交叉核对：`crc=30` 与 600 ms × 50 Hz 一致；`gap` 中计入这 30 帧；降级只发生 1 次
  （`NORMAL→DEGRADED` 总数恰为剧本预期的 5 次），说明 30 帧错帧没有反复触发。
- 检测与恢复：置位 → 降级 0 tick（同拍）；故障清除 → NORMAL **103 tick**。

### 3.2 数据越界（`range`）

- 预期：CRC 正确的帧仍需范围判据；单帧越界即拒收并降级。
- 实测：`[mode] t=8863 NORMAL -> DEGRADED flags=0x08` 与 `[fault] t=8863 set=0x08` 同一 tick；
  `[stat] t=10063 cmd=-50` 保持前一模式的值（未跟随越界值）。
- 检测与恢复：置位 → 降级 **0 tick**；清除 → NORMAL **163 tick**。

### 3.3 数据突变（`rate`）

- 预期：变化率判据以"上一次**收到**的样本"为参考；被拒样本不刷新 `last_good`，
  于是持续拒收会推进到 `STALE`（这是设计意图，也是首轮实测发现的耦合，见 `../README.md` §6.2）。
- 实测：`[mode] t=11905 ... flags=0x10` 与 `[fault] t=11905 set=0x10`；`[fault] t=12151 set=0x02`
  （`STALE`）。
- 读数解释（推算，可由日志核对）：`STALE` 从**最后一个有效样本**起算 300 ms，而 `RATE` 边沿本身
  已经晚于该样本约 54 tick——50 Hz 的注入帧在 2.90 倍时基下相当于每 **58 固件 tick** 一帧。
  所以 12151 − 11905 = 246 tick 是"300 ms 门限 − 一个帧间隔"，不是门限提前生效。
  佐证：`STALE` 一直持续到 `t=12616` 才清除（465 tick ≈ 8 个被拒帧）。
- 检测与恢复：置位 → 降级 0 tick；最后一类标志清除（`t=13580`）→ NORMAL **143 tick**。

### 3.4 通信静默（`silent`）

- 预期：300 ms 判 `T`（无 CRC 正确帧）与 `STALE`（无有效样本）——两条独立计时；
  停喂；DEGRADED 停留满 3000 ms 进 SAFE。
- 实测：`[fault] t=14084 set=0x03`、`[gate] t=14090 feed=OFF reason=FLAGS hb=119`、
  `[mode] t=17089 DEGRADED -> SAFE`（停留 **3005 ms**，门限 3000）。
- 恢复（两级）：`t=19370 clear=0x03` → `t=19594 SAFE -> DEGRADED`（**224 tick**）→
  `t=19755 -> NORMAL`（**161 tick**）。
- 剧本结束时再次进入 DEGRADED→SAFE，停留 **3007 ms**：同一门限的第二次独立观测。
- 注意 `DEGRADED → SAFE`（17089）落在阻塞注入窗口 [16571, 17371] **之内**，但两者无因果：
  停留计时由 ctrl 从 14084 起推进，与 rx 是否卡住无关。见 `../README.md` §10.2。

### 3.5 丢帧（`drop`）

- 预期：连丢 3 帧的时长约 174 固件 ms（3 × 20 ms 周期，含文本间隙），短于 300 ms 超时门限，
  因此**只**应体现在序号缺口上。
- 实测：`gap=133 = 30（错帧）+ 100（静默期时隙）+ 3（丢帧）`，`dup=0`；
  `NORMAL→DEGRADED` 仍为 5 次，没有多降一次。
- 局限（重要）：这两条**不能**证明"丢帧没有推迟任何一次恢复"。注入按墙钟排期、固件按虚拟时钟走，
  落点无法对准固定固件时刻；若丢帧正好压在某次恢复窗口上，那次 `-> NORMAL` 会晚 3 帧，
  日志里与"完全没影响"分不出来。

### 3.6 任务阻塞（固件侧注入）

- 为什么只能在固件侧注入：PC 侧无法让 rx 任务停止推进；停发字节只会产生 `T`/`STALE`（3.4 已覆盖）。
  因此用编译期开关 `AV_DEBUG_BLOCK_RX_MS`，QEMU 构建 800 ms、真板默认 0（不编译该段）。
- 落点：`AV_DEBUG_BLOCK_AT_MS = 16500`，位于静默段内（队列为空），所以不丢字节、
  不扰动解析器状态，`crc`/`gap` 算术不受影响。
- 实测：`[debug] t=16571 rx 阻塞开始 plant=800 ms` → `[gate] t=17012 feed=OFF reason=HB+FLAGS hb=441`
  → `[debug] t=17371 结束 dur=800` → `[gate] t=17617 reason=FLAGS hb=43`（`HB` 位撤销）。
- 检测延迟 **441 tick**：其中 400 是门限本身，其余是 health 的 100 ms 检查颗粒。
- 阻塞结束（17371）到标志全清（19370）之间隔着 1999 tick，**不是**阻塞的恢复代价：
  注入落在剧本 `silent` 段（5.00–7.00 s 真实时间）内，清零点由剧本恢复段决定。
- 已知设计约束（首版实测暴露）：若注入写成 `taskYIELD()` 忙等，rx（优先级 3）会饿死
  health（优先级 2），监督链在 800 ms 内一次都跑不到，只能事后读到 `hb=804` 的陈旧证据。
  这条反例见 `../README.md` §6.6——**监督任务的优先级决定它能否"看见"忙等**。

### 3.7 下行二进制通道（`aviation-link`）

- 预期：USART2 上的 `STATUS` 帧可被独立解析，且与同一次运行的 ASCII 日志交叉一致。
- 实测：`9625` 字节解出 `385` 帧，CRC/长度/类型错误各 0、跳过字节 0；`SEQ` 0→128 逐帧 +1；
  `uptime` 102→38748 ms 严格递增；帧间隔中位 100 ms、最大 114 ms。
- 交叉核对：7 组同一 `t` 的记录，mode/flags/frames/crc/gap 全部一致（L7）。
- 判定：`link.py` 7/7 通过。判据是**不变量**，不比对绝对时刻，理由同 §1 的时间口径。

## 4. 自动判定与负向验证

`expect.py` 从日志抽 21 项不变量（C1–C15，其中 C4 按五个故障位计 5 项），不比对硬编码时刻。
`link.py` 另判下行通道的 7 项（L1–L7）。判据清单见 `tests/qemu-stm32/README.md`「机器判定」一节。

负向验证（2026-10-27 实测，均在不重跑 QEMU 的前提下对日志/二进制副本执行）：

| 篡改 | 期望 | 实测 |
| --- | --- | --- |
| `gap=133` 改为 `134` | 只 FAIL C7，退出码 1 | `FAIL C7 … gap=134，期望 30 + 100 + 3 = 133`，`20/21`，exit=1 |
| 删除窗口内的 `reason=HB+FLAGS` 行 | 只 FAIL C14，退出码 1 | `FAIL C14 … 窗口内无 HB 门控行（窗口内 0 条）`，`20/21`，exit=1 |
| 删除全部 `[debug]` 行（模拟 `AV_DEBUG_BLOCK_RX_MS=0`） | 21/21，C14 标注"不适用" | `PASS C14 … 未启用调试注入（本条不适用）`，exit=0 |
| 把某条 `[stat]` 的 `age` 改成 `4294967292` | 只 FAIL C15，退出码 1 | `FAIL C15 … t=… age=4294967292`，exit=1 |
| 把 `feed=OFF` 改成 `ON`（该行有 T/STALE） | 只 FAIL C10，退出码 1 | `FAIL C10 … 1 条 stat 的 feed 与 flags/hb 矛盾`，exit=1 |
| 把 `feed=ON` 改成 `OFF`（该行无阻塞原因） | 只 FAIL C10，退出码 1 | 同上，走"两条原因都不成立却停喂"分支 |
| 日志路径不存在 | 退出码 2 | exit=2 |
| 下行 bin 里改一个载荷字节 | FAIL L2 与 L3（CRC 错 + 该帧被丢导致跳号） | 两项同时 FAIL，exit=1 |
| 下行 bin 里改一个 SOF 字节 | 只 FAIL L3（CRC 不覆盖 SOF，重同步会吞掉一帧） | 只 L3 FAIL，exit=1 |
| 截断下行 bin 尾部 | FAIL L6 或 L7（末尾状态缺失），不产生假 CRC 错 | 如预期，退出码 1 |
| 下行 bin 路径不存在 | 退出码 2 | exit=2 |

第三条保证"注入关掉"与"判定失效"在输出里可区分：总数仍是 21，但覆盖状态写在 C14 的说明里。
C15 与 C10 的两条反向篡改证明这两个判据不是恒真：它们各自只在对应缺陷出现时失败。

## 5. 延迟统计

`expect.py` 的 `[timing]` 段（纯统计，不参与判定）本轮输出：

| 延迟 | 实测 | 起点 | 性质 |
| --- | --- | --- | --- |
| 故障置位 → 降级 | 0 tick × 5 | 标志位被置上 | 不是"检测延迟"，两者常落在同一 tick |
| 故障清除 → NORMAL | 103 / 163 / 143 tick | 最后一类标志清除 | 3 个连续有效帧的代价 |
| 故障清除 → `SAFE→DEGRADED` | 224 tick | 同上（SAFE 之后） | 5 个连续有效帧 |
| DEGRADED → SAFE | 3005 / 3007 ms | 进入 DEGRADED | 3000 ms 门限 + 20 ms 网格 |
| 进入 SAFE → 退出 SAFE | 2505 ms | 进入 SAFE | **不是固件判据**，由剧本恢复时刻决定 |
| 阻塞开始 → 心跳判超时 | 441 tick | `[debug]` 行 | 400 门限 + 采样颗粒 |

跨运行区间（引用区间、不比对单次 `t=`）：清除→NORMAL 103–163 tick；清除→`SAFE→DEGRADED`
222–246 tick；`SAFE→DEGRADED`→NORMAL 161–185 tick；DEGRADED→SAFE 3003–3017 ms；
SAFE 停留 2505–2967 ms；阻塞→心跳 435–452 tick。

**"故障发生 → 被检出"这一段测不了**：故障发生在 PC 侧（墙钟），固件按虚拟时钟走，
两端没有共同时基，跨端对齐只能上真板 + 逻辑分析仪。本报告的所有延迟都是**固件侧**
（标志置位 / 状态迁移 / 阻塞开始）到固件侧的量。

## 6. 未覆盖与风险

| 项 | 状态 | 说明 |
| --- | --- | --- |
| CAN、ADC | **未验证** | QEMU 无模型，代码未实现；见 `../README.md` §9 |
| 示波器 / 逻辑分析仪时序 | **未验证** | 无仪器、无真板 |
| `IWDG` 计时与复位 | **构建级** | 寄存器写入路径已编入镜像（`nm`/`objdump` 可查），QEMU 中 `PR`/`RLR`/`SR` 读回 0，不计时 |
| `RCC->CSR` 复位原因 | **未验证** | 各 `*RSTF` 读回 0，复位原因不可读 |
| 故障记录掉电保持 | **未做** | 需 Flash/备份域，仿真不建模 |
| 硬件 ORE 溢出、RTOS 队列满丢弃 | **不可触发** | QEMU 用背压替代溢出，`qdrop`/`ore` 恒 0 |
| 长稳、抖动、最坏执行时间 | **未测量** | 剧本仅 8.2 s 墙钟；WCET 需真板 + 仪器 |
| 门限的精确边界（如"单帧/双帧 CRC 错不降级"） | **未单独立例** | 日志分辨率是 ctrl 的 20 ms 网格；"连续 3 帧"只有间接证据：600 ms 错帧期只产生 1 次降级、`crc=30` 全部计入 `gap` |
| 栈水位判据 | 实测（软件侧） | 52/176、106/224、64/224 字；`rx` 的最坏值取决于最长一次 `printf`，非注入构建为 116 |
| 下行帧周期稳定性 / 抖动 | **未测量** | 只有固件时间的中位 100 ms、最大 114；QEMU 串口无比特级时序，抖动与 WCET 需真板 + 逻辑分析仪 |
| 下行流控 / 重传 / 命令通道 | **未做** | USART2 只有 TX（`CR1 = UE\|TE`），丢帧由宿主 CRC 丢弃，见 `protocol.md` §6 |

**QEMU 特有的失真**（引用本报告数字时的前提）：时基 2.90 倍；串口无比特级时序；
GPIO/EXTI/TIM/RCC/IWDG 未建模。所有与**绝对时间**有关的结论只能在真板上复核。

## 7. 复现

```bash
cd Linux/tests/qemu-stm32
bash run.sh aviation                       # 只跑上行通道 + expect.py（覆盖 logs/aviation_node.log）
bash run.sh aviation-link                  # 额外抓 USART2 下行 + link.py，两条通道一起判定
python3 aviation/expect.py logs/aviation_node.log   # 只复跑上行判定，退出码 0/1/2
python3 aviation/link.py logs/aviation_downlink.bin --ascii logs/aviation_node.log

# 关掉固件侧注入重建镜像（C14 转为"不适用"）：
cd ../../projects/aviation-node
cmake -S . -B build-qemu -DF103_QEMU=ON -DAV_DEBUG_BLOCK_RX_MS=0 && cmake --build build-qemu
```

复跑会改变所有 `t=` 读数；判定器只判不变量，因此仍应稳定通过 21/21（上行）与 7/7（下行）。
`aviation` 与 `aviation-link` 都会覆盖 `logs/aviation_node.log`，两者的差别只在于后者多了
第二个串口后端——它会让时序轻微偏移，这正是 §2 第 3 项时段从 4.00–4.25 s 放宽到 4.30–4.55 s 的原因。
若某次运行在 C6c / C13 / C14 上失败，先看当时的主机负载（漂移会放大门限附近的读数），再看日志本身。
