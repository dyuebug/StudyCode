# 任务时序与实时性边界

> 本文回答三个问题：任务之间**按什么顺序**被唤醒、优先级为什么这样定、哪些时序结论
> 有实测证据、哪些必须回到真板。任务参数与数据链路见 [`../README.md`](../README.md) §3，
> 判据门限见 [`protocol.md`](protocol.md)，故障用例见 [`test-report.md`](test-report.md)。

## 1. 任务与同步资源

| 任务 | 优先级 | 栈（字） | 唤醒方式 | 周期 | 时限来源 |
| --- | --- | --- | --- | --- | --- |
| `ctrl` | 4（最高） | 224 | `vTaskDelay(20)` | 20 ms（50 Hz） | 被控对象时间常数 |
| `rx` | 3 | 176 | 队列接收（200 ms 超时） | 事件驱动 | 字节到达速率 |
| `health` | 2（最低） | 224 | `vTaskDelay(100)` | 100 ms | 故障需要多快被报出来 |
| `USART1_IRQ` | 硬件 5 | — | RXNE | 每字节 | UART 115200，约 87 µs/字节 |

`health` 还在同一轮里驱动 **USART2 下行**（25 B `STATUS` 帧 / 100 ms，轮询 `TXE`、无中断、
无 DMA）。它不产生新的任务，但把 health 的每轮工作量增加了约 25 字节 × 87 µs ≈ 2.2 ms
（115200、8N1，**推算**；QEMU 串口无比特级时序，实测不到），且这个等待是**阻塞式**的——
这是"超时即弃帧、不重试"这条设计的直接代价，见 `../README.md` §5 的 `av_downlink_status`
接口卡片。

同步资源：`s_rx_queue`（深度 64，元素 1 B，ISR → rx）、`s_log_mutex`（`printf` 串行化）、
两处临界区（`s_mode.good_streak` 自增、`av_mode_step` 调用）。没有任务间信号量之外的阻塞点。

## 2. 一个控制周期内的时序

```text
t(ms)   0        20        40        60        80       100
        |         |         |         |         |         |
ctrl    ●────────●─────────●─────────●─────────●─────────●        每 20 ms：读标志 → 状态机 → 限幅 → 输出
        │
rx      ●●●  ●●● ●●●  ●●●  ●●●  ●●●  ●●●  ●●●  ●●●  ●●●        每帧到达即解析；每 50 ms 打一次心跳
        │
health                        ●                                  每 100 ms：读心跳/标志 → 喂狗门控 → 下行
        │
USART1  ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑ ↑↑↑        每字节一次 RXNE（↑ 为一次中断）
USART2                          ▬▬▬                              每 100 ms 一帧 25 B，轮询 TXE（无中断）
```

要点：

- **`[fault]`/`[mode]` 由 ctrl 打印**（20 ms 分辨率），**`[gate]`/`[stat]` 由 health 打印**（100 ms）。
  所以故障置位的时间分辨率是 20 ms，而不是 100 ms——检测延迟的证据粒度不能比判定周期还粗。
- **`rx` 的心跳按"每轮循环"打点**，不是按字节：卡在队列接收上正是要被发现的故障，
  按字节打点会让"任务卡住但链路有数据"这种情况永远看起来健康。
- **喂狗只有一个调用点**（health）。任一通道不健康就整体停喂；各任务各喂各的会让
  看门狗对"部分任务卡死"完全失效（理由见 `experiments/F103_14_FreeRTOS_Watchdog/`）。
- **下行在 health 里同步发出**，排在喂狗门控之后：这样即使串口等待被截断，喂狗决策也已生效；
  反过来（先发帧再判门控）会让一次串口阻塞直接推迟喂狗判断。
- 下行帧与 `[stat]` 同轮但**不原子**：`av_downlink_status()` 的 `TXE` 轮询期间 rx（3）会抢占，
  所以同一 `now` 的两个视角里 `frames` 可能差 1–2。`link.py` 的交叉核对按此设计，见
  `../README.md` §3。

## 3. 优先级顺序的取舍

`ctrl > rx > health`：控制律的周期性是硬约束，解析（可积压到队列）和上报（100 ms 级）
都不能挤掉它。

代价写在 `health` 的优先级上：**它是三任务里最低的，因此它"看不见"比自己优先级更高的
任务在忙等。** 首版任务阻塞注入用 `taskYIELD()` 空转时，rx（3）反复把自己放回就绪态，
health（2）即使延时到期也抢不到 CPU，800 ms 内一次都没运行——事后只能读到 `hb=804`
的陈旧证据（详见 `../README.md` §6.6）。工程含义：

- 软件侧的"心跳超时 → 停喂"只在**被监督任务主动让出 CPU** 时有效；
- 真正的 CPU 饥饿要靠硬件看门狗兜底（复位），代价是失去故障归因。

这条不是 QEMU 特有的：任何 Cortex-M + FreeRTOS 配置都成立，只是真板上还要再测一次
（`IWDG` 与复位原因在仿真里未建模）。

## 4. 有实测证据的时序

全部来自 `tests/qemu-stm32/logs/aviation_node.log`（2026-10-27 一次运行）：

| 观测量 | 设计值 | 实测 | 说明 |
| --- | --- | --- | --- |
| `[stat]` 上报间隔 | 5000 ms（100 ms 网格上判 `≥5000`） | 5039 / 5047 / 5048 / 5035 / 5027 / 5019 / 5041 / 5031 / 5020 / 5027 ms（首条从上电算） | 落在 [5000, 5100] 内，符合"检查颗粒"预期 |
| DEGRADED 停留 | ≥3000 ms | 3005 / 3004 / 3009 ms | 门限 + 20 ms 状态机网格 |
| 注入帧间隔 | 20 ms（墙钟 50 Hz） | ≈58 固件 tick（推算） | 20 ms × 2.90 时基；用 `STALE` 244 tick（比 300 ms 少一个帧间隔）交叉核对 |
| 心跳超时检出 | 400 ms + 检查颗粒 | 415 tick | 其中 400 是门限本身，余量是 health 的 100 ms 采样颗粒 |
| 故障清除 → NORMAL | 3 个有效帧 | 82 / 123 / 101 tick | 82 短于 3 个帧间隔（174）不是异常：`good_streak` 由 rx 在清除前已累积 1–2 |
| `SAFE→DEGRADED` | 5 个有效帧 | 224 / 222 tick | 量级为 4 个帧间隔（232）− 网格 |
| `SAFE→DEGRADED`→NORMAL | 3 个有效帧 | 161 tick | 量级为 3 个帧间隔（174）− 网格 |
| 下行帧间隔 | 100 ms | 中位 100 / 最大 117 ms（固件时间） | 最大值的来源是 ctrl/rx 抢占 + health 自身 `printf`；只报告不判定 |

读法：**帧间隔 ≈58 tick 是这几行数字的量级单位**——恢复类延迟都在"N 个帧间隔 + 一个
20 ms 网格"附近。唯一例外是"故障清除 → NORMAL"的 82 tick：`good_streak` 在清除那一拍
可能已累积 1–2，剩余缺口只有 1–2 个帧间隔（`test-report.md` §3.1）。把这一点对上，表里的
数字就不必逐项记忆；但"帧数 − 1 × 间隔"不是精确公式，起点落在帧间隔的哪个相位上会差出
半分到一个间隔。

## 5. 没有证据的时序（不得外推）

| 项 | 为什么测不了 | 真板上怎么测 |
| --- | --- | --- |
| 周期抖动（jitter） | QEMU 时基 2.90 倍且随主机负载漂移 | GPIO 打点 + 逻辑分析仪，统计 N 个周期的峰峰值 |
| 最坏执行时间（WCET） | 无周期计数、无 DWT（仿真中 `CYCCNT` 恒 0） | DWT `CYCCNT` 或 GPIO 脉宽，按任务分段测 |
| 中断响应延迟 | QEMU 不模拟总线/Flash 等待周期 | 逻辑分析仪触发 GPIO，量 ISR 入口到出口 |
| 优先级反转/临界区时长 | 当前临界区都是常数级，但未测量 | 在临界区前后打点，取最大值 |
| `IWDG` 超时与复位点 | 未建模（`PR`/`RLR`/`SR` 读回 0） | 故意停喂，看复位时间与 `RCC->CSR` 的 `IWDGRSTF` |
| USART2 下行帧的发送时刻抖动 | QEMU 串口只搬字节，无比特级时序 | 逻辑分析仪抓 TX 引脚，量相邻帧 SOF 到 SOF 的间隔 |

**绝对时间只在真板有意义**：本表上面的所有 `t=` 都是固件毫秒，跨运行、跨机器不可比。

## 6. 变更时必须复查的时序约束

1. 把 `ctrl` 周期改小 → `CMD_STEP_CDEG` 的"每 20 ms 最多 1.00°"要同步改，否则限幅斜率变了。
2. 加任务或改优先级 → 重新核对 `health` 是否仍是最低的；若把监督任务提到被监督任务之上，
   §3 的可见性问题会换一种形式出现（监督者永远可运行，可能反过来饿死业务任务）。
3. 改 `AV_DEGRADED_TIMEOUT_MS` → 必须仍然明显大于 `AV_FAULT_HOLD_MS`（1000 ms），
   否则单次越界事件就能占满停留计时（首轮实测缺陷，见 `../README.md` §6.2）。
4. 往 `[stat]` 加字段 → 它跑在 health 的栈上，当前余量 64/224 字，先加栈再补字段。
5. 改 `health` 周期或往它身上加阻塞动作 → 下行帧周期、`[stat]` 间隔、超时检出颗粒会一起变；
   并重新确认"喂狗门控在阻塞动作之前"，否则一次串口等待会推迟喂狗判断。
6. 改下行帧布局 → `docs/protocol.md` §2.2、`av_downlink.h`、`link.py` 的 `PAYLOAD_FMT`
   三处必须同步；只改固件不改判定器，CRC 仍会通过（CRC 覆盖的是实际发出的字节），
   但字段会被按旧布局解读——这是本仓库里最容易"静默错"的一类改动。
