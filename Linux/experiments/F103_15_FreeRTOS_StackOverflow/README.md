# F103_15：FreeRTOS 栈溢出检出（让 `vApplicationStackOverflowHook` 真的触发一次）

> 结论先行：本实验在 QEMU 里**实测**触发了 `vApplicationStackOverflowHook`，钩子报出的是
> 被破坏任务的正确名字 `probe`。触发路径是 `configCHECK_FOR_STACK_OVERFLOW == 2` 的
> **paint 那一半**（栈底 4 个 `0xA5A5A5A5` 被写掉）；SP 越过栈块的那一半本实验**不触发**，
> 因为它会先撞坏相邻堆块，属于"溢出未被及时检出"的另一类故障。
>
> 这个结论不涉及任何绝对时间，因此不受 QEMU 2.90 倍时基影响。

## 学习目标

1. 把"栈溢出能被发现"从"配置里写了 `configCHECK_FOR_STACK_OVERFLOW = 2`"变成可观测事实：
   钩子被调用、拿到正确任务名、系统停机。
2. 说清检出的**时机**：检查发生在任务切换时，且检查的是**被换出去的那个任务**；因此
   "返回后栈指针合法"不等于"没溢出"，必须真的阻塞一次才能观察到。
3. 用 `uxTaskGetStackHighWaterMark` 作判据，而不是用地址算术（首轮实测在这个坑里漏检，
   见 §关键实现点 1）。
4. 给出三组可分别判定的证据：安全深度不误报、每帧字节数可标定、注入后确实归零并触发钩子。
5. 明确区分"paint 被写穿"与"SP 越过栈块"两种失效，不把前者说成"栈溢出全部场景已验证"。

## 核心概念

### 1. `configCHECK_FOR_STACK_OVERFLOW = 2` 是两半，不是一半

`stack_macros.h` 里对 `= 2` 的判据是**或**关系：

| 判据 | 内容 | 能发现什么 |
| --- | --- | --- |
| 前半（`= 1` 就有） | `pxTopOfStack <= pxStack + portSTACK_LIMIT_PADDING`（padding 默认 0） | 任务**保存的栈指针**已经越过栈块底 |
| 后半（`= 2` 新增） | 栈底 4 个字（16 B）不再全为 `0xA5A5A5A5` | 曾经写过、后来又弹回来的**越界写入** |

后半是必要的：越界写一笔再返回，SP 是合法的，只查 SP 会漏。本实验打的就是后半——
它不需要真的把栈指针留在栈块外，因此不会破坏相邻内存。

### 2. 检查时机：切换时，检查"被换出去的任务"

`taskCHECK_FOR_STACK_OVERFLOW()` 在 `tasks.c` 里被调用于
"选出下一个任务"之前，作用对象是**即将换出**的任务。推论有三条：

- 溢出后立刻停机是**不可能**的，最快也是下一次切换；
- 任务自己什么都观察不到——它返回时 SP 合法；
- 必须制造一次切换（本实验用 `vTaskDelay(1)`）。忙等不会切换，钩子也就不会运行；
  这与 [`F103_14`](../F103_14_FreeRTOS_Watchdog/README.md) 首版"忙等饿死监督任务"是同一类错误。

### 3. `uxTaskGetStackHighWaterMark` 读的不是"历史最低"，而是"当前扫描结果"

实现是 `prvTaskCheckFreeStackSpace`：从 `pxStack`（最低地址）**逐字节**向高地址扫
`tskSTACK_FILL_BYTE`（`0xA5`），扫到第一个非 `0xA5` 就停，字节数 ÷ 4 得到字数。
所以：

- 返回 0 ⇔ `pxStack` 处第一个字节已经不是 `0xA5` ⇔ paint 一定被写过；
- 它是**当前内存内容**的快照，不是计数器。栈上内容被后续调用覆盖时，读数会变；
- 这也解释了它为什么可以直接当注入判据：它和检出宏看的是**同一批字节**。

### 4. 为什么不用"最低局部地址 − 余量×4"反推栈底

帧里除了局部数组还有保存的寄存器与对齐填充，**最低被写字节 ≠ 最低局部变量地址**。
按这个公式估算，误差是几个字节量级——而 paint 只有 16 B，落在边界外一个字就整轮无效。
首轮实测就是这样漏检的（估算栈底 `0x20000240`，注入最低地址 `0x20000248`，差 +8 B，
恰好在 16 B paint 之外，钩子不响）。这不是"差一点"，而是判据本身选错了。

## 接口卡片

### `void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName)`

作用：检出宏发现异常后调用的用户钩子；由 `FreeRTOSConfig.h` 的 `configCHECK_FOR_STACK_OVERFLOW`
启用。

返回值/错误：无返回；**不会自动复位**、也不会自动删除任务。

资源所有权：内核不释放任何东西；钩子返回后调度继续（如果它返回），所以现场可继续被破坏。

最小示例：

```c
void vApplicationStackOverflowHook( TaskHandle_t xTask, char *pcTaskName )
{
    ( void ) xTask;
    taskDISABLE_INTERRUPTS();          /* 先停调度，再打印：打印本身要用栈 */
    printf( "\r\n[STACK OVERFLOW] 任务 %s\r\n", pcTaskName );
    for( ;; ) { }                      /* 停在现场，等看门狗复位或人工介入 */
}
```

常见误用：钩子里继续用大量栈或调用可能阻塞的 API（例如 `vTaskDelay`）——此时栈已经不安全，
被破坏的可能是别的任务；打印也会压栈，所以先 `taskDISABLE_INTERRUPTS()`。

### `UBaseType_t uxTaskGetStackHighWaterMark(TaskHandle_t xTask)`

作用：返回从 `pxStack` 起仍为填充值的字数（见核心概念 3）。

参数：`NULL` 表示当前任务。

返回值和错误：0 表示已无空闲字（可能是刚溢出，也可能是历史最低触底）；需
`INCLUDE_uxTaskGetStackHighWaterMark = 1`。

资源所有权：只读扫描，无分配。

常见误用：把 0 当成"刚好够用"；或者在另一任务里读，把"当前扫描结果"当成"峰值历史"——
在任务仍在跑时它是会被覆盖的。

### `__attribute__((noinline))` + `volatile` 数组（保帧手段）

作用：阻止编译器把递归折叠成循环/尾调用，保证每层真的有栈帧。

判据：标定出的"每帧字节数"若为 0，说明优化生效，整轮结论无效（代码里直接判 FAIL）。

## 最小可运行实验

三段，全部在同一个任务 `probe` 内顺序执行：

1. **对照**：`depth = 12`，读余量；要求远大于 32 字判据，且钩子不响。
2. **标定**：`depth = 16`，用两次探测的最低地址差 ÷ 帧数差，得到每帧字节数（实测 16 B）。
3. **注入**：从 `depth = 16` 起逐级加深（余量 > 8 字时每步 +4 帧，之后每步 +1 帧），
   每步 `probe()` 后读余量；**余量为 0 即判为 paint 已写穿**，立即停止加深，`vTaskDelay(1)`
   等切换，然后等钩子。若切换后仍打印出 `FAIL` 行，说明检出没生效。

越界量上界：步长 ≤ 1 帧 ⇒ 越过 `pxStack` 不超过 16 B。按 `heap_4` 的布局
（`BlockLink_t` 为 2 个 32 位字段，即 8 B 块头），这 16 B 会覆盖栈块下方的堆控制区。
**本实验的安全性依赖钩子立即停机**（之后不再 `malloc`/`free`），生产中不能依赖这种注入。

`run_exp15` 的判定与其它用例不同：本实验的**正常终点**是钩子里的死循环，QEMU 一定会被
`timeout` 杀掉，日志末尾的 `terminating on signal 15` 是预期。因此成败只看两条：

- 必须出现 `[STACK OVERFLOW] 任务 probe 的栈被写穿`；
- 不得出现 `[so] FAIL`。

## 预期现象

```text
[F103_15] configCHECK_FOR_STACK_OVERFLOW=2（2 = paint + SP 双重检查），任务栈 256 字

[so] 任务栈 256 字（1024 B）
[so] 对照 depth=12 → 最低地址 0x200004A0，余量 160 字（判据 ≥32）
[so] 标定 depth=16 → 最低地址 0x20000460，每帧 16 B
[so] depth=16 余量 160 字
...
[so] depth=60 余量 0 字
[so] 逐级加深：首次余量 <32 字在 depth=56，余量归零在 depth=60（按余量预测 52）
[so] 注入完成：depth=60 时 hwm=0，即栈底 16 B 的 0xA5 已被写穿；越界量不超过一帧（16 B）
[so] 返回后栈指针合法；vTaskDelay(1) 等待切换时的 paint 检查

[STACK OVERFLOW] 任务 probe 的栈被写穿，钩子已触发
qemu-system-arm: terminating on signal 15 from pid ... (timeout)     ← 预期
```

### 余量随深度的实测衰减

| depth | 余量（字） | 相邻差 |
| --- | --- | --- |
| 12 | 160 | — |
| 16 | 160 | 0 |
| 20 | 160 | 0 |
| 24 | 144 | −16 |
| 28 | 128 | −16 |
| 32 | 112 | −16 |
| 36 | 96 | −16 |
| 40 | 80 | −16 |
| 44 | 64 | −16 |
| 48 | 48 | −16 |
| 52 | 32 | −16 |
| 56 | 16 | −16 |
| 60 | **0** | −16 |

稳态段（24 帧以后）每 4 帧减 16 字，即 16 B/帧，与标定一致。前 8 帧（12 → 20）的写入
落在已被上层调用写过的区域里，**不消耗余量**——这正是"按余量粗估深度"必然偏小的来源
（预测 52，实测 60，偏 8 帧 ≈ 15%）。

两次运行（同一 ELF）读数逐字一致：无时间依赖，本实验的结论可稳定复现。

### 三组判据

| 判据 | 预期 | 实测 |
| --- | --- | --- |
| 安全深度不误报 | 钩子不响，余量 ≫32 字 | `depth=12` → 160 字，无钩子输出 |
| 每帧字节数可标定 | 非 0，且与衰减斜率一致 | 16 B/帧；稳态段 4 帧减 16 字 |
| 注入后余量归零 | `hwm == 0` | `depth=60` → 0 字 |
| 检出发动 | 钩子报出任务名并停机 | `[STACK OVERFLOW] 任务 probe`，之后无任何输出 |

判定逻辑不能只被"通过"验证。把判定表达式对四份日志各跑一次：

| 输入 | 结果 |
| --- | --- |
| 真实日志 | 判定通过 |
| 删掉 `[STACK OVERFLOW]` 行 | 判定失败：无钩子报告 |
| 注入一条 `[so] FAIL` | 判定失败：出现 FAIL 行 |
| 空日志 | 判定失败：无钩子报告 |

## 关键实现点

### 1. 首轮失败保留为证据：判据要用"余量"，不要用地址算术

首版按"最低局部地址 − 余量×4"估算栈底，再算注入深度。实测：估算栈底 `0x20000240`，
注入最低地址 `0x20000248`（+8 B），`[so] FAIL 切换后钩子未触发`。

这两个地址是**当时那版代码**的读数：源码已被替换，当前 ELF 不再复现它们（当前版本的
对照读数见§实测记录）。这里保留它们，是因为失败现象本身就是判据选择的证据。

排查顺序（不靠猜）：先确认检出宏真的被编进去（`nm ... tasks.c.obj` 里有
`U vApplicationStackOverflowHook`）、再读宏的判据（比较 4 个字是否仍为 `0xA5A5A5A5`）、
再读余量实现（从 `pxStack` 起扫 `0xA5`）。三者对照即可得出：估算差一个字的对齐，
注入点落在 16 B paint 之外。改成"余量归零"后同一份代码一次通过。

### 2. 归零的判据比"clamp 到恰好"更可靠，也更安全

逐级加深 + 归零即停，越界量上界由**步长**控制，而不是由估算精度控制。余量 > 8 字时用
4 帧步长快速逼近，接近后改成 1 帧，把越界压到 16 B。

### 3. 循环里每步打印是刻意保留的

首轮只在终点打印，结果"预测 52 / 实测 60"无法归因。加上每步读数后，衰减曲线直接说明：
稳态 16 B/帧没错，8 帧偏差来自 12→20 这段"不消耗余量"的深度。省这几行日志会让后面
所有偏差都变成猜。

### 4. 泄漏 ≠ 溢出：本实验不证明"栈够用"

`hwm == 0` 是**故意**造成的。它与 [`F103_13`](../F103_13_FreeRTOS_Timers/README.md) 的
"绝对 ≥32 字 / 相对 ≥25%"判据不冲突：那条判据针对常规任务，本次的任务就是用来溢出的。

## 常见错误和陷阱

1. **只设置钩子却从不实测**：`configCHECK_FOR_STACK_OVERFLOW` 与钩子函数可以同时存在而
   永远不触发，日志看起来"一切正常"——这正是本实验要消除的状态。
2. **在钩子里继续用栈**：此时栈已被破坏，`printf` 也可能写坏别人的数据；先
   `taskDISABLE_INTERRUPTS()`，再用最小代价输出。
3. **以为溢出会立刻停机**：最快也要下一次任务切换；不切换就看不见。
4. **用另一任务的视角读余量**：读数是当前扫描结果，任务若还在跑，读到的可能不是最低点。
5. **把 `= 2` 当成"能发现所有栈溢出"**：paint 只护住栈底 16 B；从中间某处跳跃式越界、
   或先越界再被复用覆盖，都可能漏检。
6. **注入不加步长上界**：一次加深几十帧，会先撞坏堆块，看到的现象就不再是"paint 被写穿"。

## 故障排查方法

| 现象 | 先查什么 | 判据 |
| --- | --- | --- |
| 钩子从不触发 | `nm <build>/.../tasks.c.obj \| grep vApplicationStackOverflowHook` | 有 `U` 说明钩子被引用，宏已编入 |
| 钩子触发但任务名不对 | 打印的 `pcTaskName` 与破坏者是否同一任务 | 检查是否在切换时才被检查（是），确认破坏者是谁 |
| 余量一直不小 | 递归是否被优化成循环 | 标定出的"每帧字节数"应为 0 → 代码里判 FAIL |
| 余量突然归零但没到预期深度 | 栈上是否有更深的调用（`printf`、库函数） | 打印每步读数看衰减是否线性 |
| 系统在钩子前就异常 | 是否越界写坏了栈块下方的堆控制区 | 缩小步长，看归零点是否提前 |

- **只验证了 paint 那一半**：SP 越过栈块的情形未构造（构造它必然先破坏相邻堆块，
  现象不再是"检出"而是"崩溃"，属于另一个实验）。
- **paint 只有 16 B**：越过 16 B 后继续写、或写后又被覆盖，都可能漏检；本实验不能推出
  "任何栈溢出都能被发现"。
- **QEMU 不建模 MPU/总线错误**：真板上越界写可能先触发 HardFault，而非走到钩子。
- **越界量依赖步长**：本次实测 16 B；改步长会改变这个上界，日志必须重新记录。
- 钩子内的 `printf` 在真板上可能因栈或串口状态而不可靠，生产代码应改成写固定 RAM 区。
