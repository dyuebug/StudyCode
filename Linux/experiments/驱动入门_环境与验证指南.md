# Linux 驱动入门：环境与验证指南

**适用范围**：Day2～Day14 的环境准备、最小模块和板级实验。  
**当前状态**：实验方案已编写；本文不代表任何命令已执行或实验已通过。

## 1. 学习目标

- 区分 Windows、Linux 用户态开发环境和可加载模块的目标内核环境。
- 在加载前检查架构、内核构建目录、配置、符号和签名要求。
- 用可恢复的最小实验取得证据，不直接在工作主机上试板级代码。

## 2. 环境与前置条件

| 环境 | 可以先做 | 不能默认做到 |
| --- | --- | --- |
| Windows PowerShell | 阅读、画调用链、审查 Makefile | 编译并加载 Linux `.ko` |
| WSL | Linux 用户态 C 编译、部分工具练习 | 存在匹配的模块构建树、允许加载任意模块 |
| Docker 容器 | 用户态构建；条件具备时交叉编译 | 拥有独立内核；容器内 `insmod` 安全隔离于宿主 |
| 可快照的 Linux 虚拟机 | 本机最小模块构建与加载 | 直接访问开发板的 GPIO、I2C、SPI |
| 课程开发板 | 对应 BSP 下的板级实验 | 旧模块可跨板、跨架构、跨内核直接加载 |
| QEMU | 被模拟硬件范围内的实验 | 自动复现未被模拟的传感器和电气时序 |

首次模块实验优先使用可快照、可重启的 Linux 虚拟机。不要为了学习给容器额外开放宿主模块加载权限。

## 3. 核心概念与入口

- **构建主机**：运行编译器的机器。
- **目标系统**：实际加载模块、运行测试程序的系统。
- **内核构建目录**：与目标内核匹配、已准备好的构建树，不是任意同名内核源码目录。
- **模块 ABI**：不仅取决于 `uname -r`，还涉及配置、符号版本、架构和构建结果。
- **验证层次**：源码分析 → 编译验证 → 加载/软件接口验证 → 仿真或真实硬件验证；前一层不能代替后一层。

完整讲义复用资料库中的 `StudyPlan/DailyDocs/`；本指南只补实验边界和证据要求。

## 4. 第一步：只采集环境，不加载模块


## 5. 最小可运行实验：只打印的模块

### 5.1 源码与构建前检查

从本指南所在目录出发，最小模块源码是：

[02_printk/hello_drv.c](../Linux_WEIDS/02_嵌入式Linux驱动入门直播/02_彻底分析第1个驱动程序/source/02_printk/hello_drv.c)

只选择该类不访问硬件的模块作为第一次加载对象。先读同目录 `Makefile`，确认 `obj-m`、架构和内核目录。建议复制到自己选择的 Linux 实验目录后构建，原始资料库不作批量修改。

示例构建命令在 **Linux 实验副本目录** 执行。这里直接调用目标内核的 Kbuild，不依赖课程顶层 `all` 目标；执行前仍需确认该目录的 Kbuild 规则只生成预期模块。

```bash
make -C "/lib/modules/$(uname -r)/build" M="$PWD" modules
file ./hello_drv.ko
modinfo ./hello_drv.ko
```

观察：编译是否退出成功；`file` 的机器架构是否正确；`modinfo` 中的 `vermagic` 是否与目标环境一致。匹配这些信息是必要检查，不是加载一定成功的保证。

### 5.2 加载、观察和卸载

仅在虚拟机快照已建立、没有其他同名模块、确认当前是目标系统后继续。两终端分别执行，保留观察窗口；日志跟随在实验结束后按 `Ctrl+C` 退出。

终端 A：

```bash
sudo dmesg --follow
```

终端 B：

```bash
sudo insmod ./hello_drv.ko
lsmod
sudo rmmod hello_drv
lsmod
```

每步成功后再执行下一步。预期看到初始化日志、模块出现、卸载日志和模块消失。`insmod` 本身无输出不能单独作为成功证据；还要记录退出状态与内核侧观测。

出现 Oops、卡死或新的严重内核告警时，停止继续加载，保存日志并恢复快照；不要强制卸载来“修复”。外部模块可能使内核带上 taint 标记，正常卸载不一定清除该标记。

### 5.3 最小字符设备实验的额外门禁

Day3 的原始 `05_transfer_data` 示例**不是开箱即用的字符串回显设备**：

- 驱动复制固定 4 字节整数，没有按请求长度和拷贝返回值完整处理。
- 测试程序打开 `/dev/xyz`，驱动本身只注册字符设备，没有自动创建设备节点。
- 测试程序把内容按字符串打印，数据格式与整数接口并不一致。

因此先做源码审查和接口约定，再在实验副本中修正；本材料不宣称这些问题已经修复。不要直接用 `cat` 读取一个始终返回数据而没有 EOF 语义的示例。

如果选择有 `class_create()` / `device_create()` 的另一个 hello 示例，也必须核对其版本接口、错误路径和用户态协议。需要手工设备节点时，只能在隔离环境中使用**本次实际分配**的主设备号和确定的次设备号，不能照抄别人的号码；本指南不批量创建设备节点或修改权限。

## 6. 板级构建与部署流程（Day5 以后）

先填写环境记录卡，特别区分主机 `uname -r` 和目标板 `uname -r`。交叉编译时不能用主机构建目录代替板卡内核树。

在 Linux 构建主机设置下列变量为已确认的实际值；变量未设置时命令应停止，而不是猜测路径。

```bash
make -C "${KERNEL_BUILD_DIRECTORY:?请先设置目标内核构建目录}" M="$PWD" ARCH="${TARGET_ARCHITECTURE:?请先设置目标架构}" CROSS_COMPILE="${TARGET_COMPILER_PREFIX:?请先设置交叉工具链前缀}" modules
```

- `ARCH` 使用内核接受的架构名称，如目标为 ARM32 时通常是 `arm`，ARM64 时通常是 `arm64`。
- `CROSS_COMPILE` 是工具链可执行文件前缀，不是单个 `gcc` 文件名。
- `modules_prepare` 不能替代所有内核构建准备；启用 `CONFIG_MODVERSIONS` 时尤其需要匹配的 `Module.symvers`，通常来自对应完整构建。
- 用户态测试程序还必须匹配目标架构、ABI 和根文件系统运行库。
- `M="$PWD"` 指向当前模块副本，路径尽量避免空格；课程旧构建脚本可能不能正确处理含空格路径。

部署前记录产物来源；传到目标板后先核对文件、架构与版本，再按课程板卡手册加载。GPIO、MMIO、IRQ、I2C、SPI 示例只能用于与接线、设备树和 BSP 匹配的目标。

**禁止把硬编码寄存器地址的板级驱动加载到普通 PC 上。** 没有板卡或接线图时，今天的成果是部署方案，不是硬件实验通过。

## 7. 命令与接口卡片

| 命令 | 作用、输入和返回 | 权限/副作用 | 常见误用 |
| --- | --- | --- | --- |
| `make -C ... M=... modules` | 进入内核构建目录，构建外部模块；非零退出表示失败 | 在模块目录生成文件；普通用户构建 | 把主机内核误当目标内核；忽略警告 |
| `modinfo ./模块.ko` | 读取文件中的模块元数据；不加载 | 只读检查 | 把元数据正确当成 ABI 已验证 |
| `insmod ./模块.ko` | 请求内核加载指定文件；失败为非零退出 | 需要目标系统授权；执行模块初始化 | 期待自动解析所有依赖；加载未知模块 |
| `lsmod` | 查看已加载模块；不执行测试 | 只读检查 | 名字相同就认定是刚编译的副本 |
| `dmesg` | 查看内核日志，可能受权限限制 | 普通查看不清除日志 | 日志不可读就认定模块没运行 |
| `rmmod 模块名` | 请求正常卸载；参数不是 `.ko` 路径 | 需要授权；模块被引用时可能失败 | 强制卸载，或忘记关闭测试进程 |

模块加载会修改运行内核状态，不是普通文件操作；所有加载/卸载动作应串行进行。`modprobe` 适合已正确安装到模块目录并建立依赖索引的模块，本轮不要求安装模块到系统目录。

## 8. 常见错误与故障排查

| 现象 | 先收集的证据 | 最小下一步 |
| --- | --- | --- |
| 构建目录不存在 | 目标内核版本、构建目录来源 | 准备匹配构建树，暂停模块实验 |
| `class_create` 参数错误或回调类型不符 | 完整编译诊断、目标头文件声明 | 按目标 API 在副本适配，不屏蔽类型检查 |
| `Invalid module format` | `modinfo`、目标 `uname -r`、内核日志 | 对照架构、配置、符号版本后重新构建 |
| `Unknown symbol` | 内核日志中的具体符号、依赖、`Module.symvers` | 核查依赖和构建来源，不随意复制符号文件 |
| 签名/密钥错误 | 原始错误、目标系统安全策略 | 使用合规签名或管理员批准的实验环境 |
| `/dev` 节点不存在 | 注册返回值、sysfs、devtmpfs/udev 状态 | 分别检查设备注册与节点创建，不能只改权限 |
| 打开设备失败 | 程序错误码、设备节点类型及设备号 | 区分不存在、权限、无对应驱动等原因 |
| 读取一直不退出 | 驱动返回值、偏移和协议、有限次数测试 | 停止无界读取，先明确 EOF/事件流语义 |
| `Module is in use` | 测试进程、打开文件和模块引用 | 正常停止消费者、释放资源后再卸载 |

一次只验证一个假设。不要清空内核日志、全局开放设备权限或跳过安全策略来掩盖问题。

## 9. 练习题与验收标准

- **基础题**：为何能运行 Linux 用户态应用，不代表能够加载 `.ko`？
- **改错题**：交叉编译时用主机 `uname -r` 选择构建目录，错在哪里？
- **综合题**：准备一个最小模块的环境卡、构建命令、观测计划、卸载与恢复方案。

验收分别填写，不能合并成一个“成功”：

- [ ] 环境信息与源码版本已记录。
- [ ] 模块已构建，命令、诊断和产物信息已保存。
- [ ] 加载和卸载均有真实证据。
- [ ] 用户态接口协议与错误路径已验证（只打印模块不适用）。
- [ ] 板级信号有目标板/仪器证据（无硬件则未执行）。
