# F103_14：FreeRTOS 心跳与看门狗（任务存活监督 / 停喂条件 / 阻塞检出与恢复）

> 结论先行：本实验在 QEMU 里**只能**证明"监督逻辑"这一半——心跳、超时判定、停喂、恢复动作、
> 恢复窗口与 IWDG 名义超时的比较。IWDG 计时与复位、`RCC->CSR` 复位标志在仿真环境中未建模
> （探针 `[11]`/`[12]` 实测读回全 0），"看门狗真的能把芯片复位"这一步**必须上真板**。

## 学习目标

1. 把"看门狗能救系统"拆成两个可分别验证的问题：软件侧是否按约定停喂，硬件侧是否真的复位。
2. 用任务心跳 + 时间戳把"任务卡死"变成可测量的事件，而不是靠人看现象。
3. 用"与"语义设计喂狗条件：任一被监控任务不健康就整体停喂，否则看门狗对卡死任务完全失效。
4. 把软件恢复窗口和 IWDG 超时窗口放在同一根时间轴上比较，让"真板会不会复位"成为可计算的结论。
5. 区分"代码编译通过""代码进入镜像""代码在目标上执行"三种不同强度的证据。

**时间数字口径**：本文件里所有 `t=`、`tick` 都是**固件毫秒**。QEMU 以 24 MHz 驱动 SYSCLK 而固件按

所以这些数字只能互相比较比例，**不能**当作实时性结论。

## 核心概念

### 1. 看门狗监控的是"有没有走到心跳点"，不是"任务对象还在不在"

任务被创建后，它的 TCB 一直在，`eTaskGetState()` 也可能一直是 `Blocked`——而"永久阻塞在某个
信号量上"和"正常周期性阻塞"在状态机里看起来完全一样。因此心跳必须由被监控任务**自己**在
主循环里打点；由监督任务替它打点，等于没监控。

### 2. 喂狗条件必须是"与"，不是"或"

| 方案 | 卡住一个任务时的行为 | 结论 |
| --- | --- | --- |
| 每个任务各自喂狗 | 卡住的任务根本不喂，看门狗照样被其它任务喂饱 | **失效** |
| 任一不健康即停喂（本实验） | 卡住的那一刻起，全系统停喂 | 有效 |

本实验的 `health` 任务持有唯一的 `watchdog_feed_if_enabled()` 调用点，两个通道全部健康才喂。

### 3. 检测延迟 = 心跳超时阈值 + 检查周期

`age > 400 ms` 才判 STALE，而检查每 `200 ms` 一次，所以最坏检测延迟约 `600 ms`（实测 409~410 ms，
因为注入时刻恰好落在两次检查之间）。这个延迟必须显式计入设计：它直接决定了喂狗窗口的下界。

### 4. 停喂窗口必须和 IWDG 超时窗口一起算

IWDG 参数（RM0008 第 19 章）：`PR = ÷64`、`RLR = 624`、LSI 名义 40 kHz → **名义超时 998 ms**。
LSI 在 F1 上容差极大（30~60 kHz），实际超时约 **665~1330 ms**。所以：

```text
软件停喂窗口 < 665 ms   → 任何 LSI 偏差下都是软件自愈先发生
软件停喂窗口 > 1330 ms  → 任何 LSI 偏差下都是看门狗先复位
介于两者之间            → 结果取决于芯片实际 LSI，必须上板确认
```

本实验用两轮注入正好跨过名义门限（819 vs 1424），把这条边界变成可复现的数字。

### 5. tick 比较必须用无符号差值

`xTaskGetTickCount()` 是 32 位、约 49.7 天回绕一次。`if (now > last)` 在回绕点会得到错误结论；
`(uint32_t)(now - last)` 在无符号语义下跨回绕仍然正确。本实验的 `hb_age()` 就是这一行。

## 接口卡片

### `BaseType_t xTaskCreate(TaskFunction_t fn, const char *name, uint16_t stack, void *arg, UBaseType_t prio, TaskHandle_t *out)`

作用：创建任务并记录句柄。**保存句柄**是本实验的硬需求——后面 `uxTaskGetStackHighWaterMark()`
要用它指定"查哪个任务"，传 `NULL` 只能查调用者自己。

返回值和错误：`pdPASS` / `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`。本实验未检查返回值（教学简化），
真实工程必须检查并按 §6.3 处理。

最小示例：`xTaskCreate( sensor_task, "sensor", 160, NULL, 3, &s_h_sensor );`

### `uint32_t uxTaskGetStackHighWaterMark(TaskHandle_t t)`

作用：返回任务自启动以来**最小**剩余栈（单位：字，不是字节）。

常见误用：在启动阶段读（此时很多代码路径还没跑过，读数偏大）；把"字"当"字节"；
用 `NULL` 读成了监督任务而不是目标任务（本实验第一版就犯了这个错，见"关键实现点 4"）。

### `TickType_t xTaskGetTickCount(void)`

作用：读调度器 tick。任务上下文可用；中断里应用 `xTaskGetTickCountFromISR()`。

### `SemaphoreHandle_t xSemaphoreCreateBinary(void)` / `xSemaphoreTake` / `xSemaphoreGive`

本实验只把二值信号量当作"故障注入用的卡住点"：`sensor` 在注入期间 `Take(1500 ms)`，
监督任务在恢复动作里 `Give`。**注意** `Give` 只是放行一次，不代表业务真的恢复了——
真实系统里这一步通常是重启子系统、切备份通道或进入安全模式。

### `RCC->CSR` / `RCC_CSR_IWDGRSTF` / `RCC_CSR_RMVF`

作用：读复位原因标志；`RMVF` 写 1 清除全部标志。**必须读完立刻清**，否则下次复位后分不清
是看门狗还是上电。本实验在 `main()` 里读并条件清除，QEMU 实测读回 `0x00000000`。

### IWDG 寄存器写序列（真板路径）

```c
IWDG->KR  = 0x5555U;   /* 解除 PR/RLR 写保护 */
IWDG->PR  = 0x04U;     /* ÷64 */
IWDG->RLR = 624U;      /* 名义 998 ms */
IWDG->KR  = 0xCCCCU;   /* 启动——此后只能靠复位停止 */
IWDG->KR  = 0xAAAAU;   /* 喂狗（重装计数器） */
```

**一旦启动无法关闭**：调试时若在 IWDG 启动后停在断点，芯片会被反复复位。标准做法是调试配置里
冻结 IWDG（`DBGMCU_CR` 的 `DBG_IWDG_STOP`）。

## 预期现象

1. 启动阶段打印 IWDG 路径状态（"未启用（QEMU 未建模 IWDG）"）、`RCC->CSR` 原始值、
   两个硬件路径函数的地址。
2. 前 4 次检查全部 `OK feed=ON`，随后 `R1 注入`。
3. `sensor age` 持续增长并带 `!`，`feed=OFF`；`io age` 始终远小于 400（**健康但不喂**）。
4. 连续 3 次 STALE 后 `R1 恢复动作`，下一拍 `恢复：…停止喂狗窗口 819 tick（…软件自愈先发生）`。
5. `R2` 重复同样过程，但窗口 1424 tick，标注"真板会先复位"。
6. 第 26 次检查打印汇总与三个任务的栈水位；之后每 20 次检查打一行，证明系统仍在运行。

| 指标 | R1 快恢复 | R2 慢恢复 |
| --- | --- | --- |
| 注入时刻（固件 ms） | 808 | 2847 |
| 首次判 STALE | 1217 | 3257 |

| 恢复动作时刻 | 1623 | 4267 |

补充观测：

- `io` 通道在两轮故障期间的 age 最大仅 122 / 112 tick，**始终健康**，但 `feed` 仍然是 `OFF`——
  这正是"与"语义的直接证据。
- 第 26 次检查时 `stale_total = 9 = blocked = 9`（3 + 6），`feeds = 17 = 26 - 9`，
  计数自洽；心跳次数 `sensor = 30`、`io = 35`（与各自的 `1/100 ms`、`1/150 ms` 比例一致）。
- 恢复后 `sensor age` 回到 0~15，`feed=ON` 连续 5 次，未见抖动性停喂。

| 任务 | 余量/总量（字） | 相对余量 | 判据（绝对 ≥32 / 相对 ≥25%） |
| --- | --- | --- | --- |
| `sensor` | 132/160 | 82% | 通过 |
| `io` | 106/128 | 83% | 通过 |
| `health` | 108/224 | 48% | 通过；按实测可下调到约 176 字仍有余量 |

读数时机是两轮注入全部走完之后（第 26 次检查），而不是启动阶段——否则打印路径还没跑过，

### 硬件路径的"构建级"证据

| 证据 | 结果 |
| --- | --- |
| `main.c.obj` 中有 `f103_watchdog_init` / `f103_watchdog_feed` | 有 |
| 最终 ELF 中有这两个符号（`nm`） | 有，`0x0800010C` / `0x08000130`（函数指针打印时为 Thumb 位加 1：`0x0800010D` / `0x08000131`） |
| `objdump -d` 中出现 IWDG 基址 `0x40003000` | 2 处 |
| 代码在真板上执行过 | **没有**（QEMU 未建模 IWDG，且 `F103_WATCHDOG_ENABLE = 0`） |

### 对这几个数字的正确读法

- `819` 与 `1424` 是**固件毫秒**，QEMU 下真实耗时约为其 1/2.90；比例关系可信，绝对值不可信。
- "真板会先复位"是**按名义 998 ms 折算的推论**，不是实测。LSI 若偏快到 60 kHz，超时降到 665 ms，
  则 R1 的 819 也会落入复位区；若偏慢到 30 kHz（超时 1330 ms），R2 的 1424 也仍然超过门限。
  只有 R1 的 819 介于两者之间——这一条必须上板确认。
- 本实验没有验证"复位后能否读到 `IWDGRSTF`"，因为 `RCC->CSR` 在 QEMU 读回 0。

## 关键实现点

### 1. 先写监督逻辑，再谈硬件看门狗

如果喂狗条件是错的，接上 IWDG 只会让系统更容易复位而不会更可靠。所以本实验把 IWDG 压到
`F103_WATCHDOG_ENABLE = 0`，先在仿真里把"什么时候该停喂"测清楚。

### 2. 故障注入必须能恢复，否则后面的计数全是垃圾

注入用二值信号量 `s_gate`：`sensor` 卡在 `Take(1500 ms)` 上且**本轮不踢心跳**。监督任务的
恢复动作 `Give` 它，`sensor` 立刻回到正常节奏。这样同一个二进制里能连续做两轮对照，
而不需要重新烧写。

### 3. 恢复门限写成参数，让两轮只差一个数字

`k_rounds[]` 把"何时注入"和"连续几次 STALE 才恢复"参数化。这不是过度设计：
只有让两轮唯一变量可控，819 与 1424 的差异才能归因到门限本身。

### 4. 我在这份测量代码里自己踩的两个坑（都靠日志发现）

| 缺陷 | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 恢复窗口恒为 0 | 日志打印 `窗口 0 tick` | 先覆盖 `s_last_feed_tick = now`，之后才做 `now - s_last_feed_tick` | 在覆盖**之前**取 `gap = now - s_last_feed_tick` |
| 恢复日志从不打印 | 只有 `STALE`，没有 `恢复` | 恢复动作里把 `stale_streak` 清零，而恢复日志的判据是 `stale_streak > 0` | 引入独立的 `degraded` 标志，与 streak 解耦 |

教训：**测量代码本身也是代码**，它的缺陷会以"数据看起来很合理"的形式出现。看到 0 或看到
"永远不触发"的分支，先怀疑测点，不要先怀疑结论。

### 5. `__attribute__((used))` 挡不住 `--gc-sections`（实测）

想让硬件路径"留在镜像里"，第一版加了 `used` 属性，结果：

- `main.c.obj` 里能 `nm` 到两个函数；
- 最终 ELF 里 `nm` 结果为空，`objdump` 里 `0x40003000` 出现 0 次。

原因是 `-ffunction-sections` 给每个函数单独成段，`--gc-sections` 把所有没被引用的段删掉，
`used` 只约束**编译器**不删、不约束**链接器**。最终改成在启动日志里打印两个函数地址，
让它们被真实引用，ELF 里才留下 `0x0800010D` / `0x08000131` 和两处 IWDG 写入。

### 6. 复位原因必须在启动早期读并清

`main()` 一进来就 `read_reset_flags()`，若 `IWDGRSTF` 置位则打印并写 `RMVF`。若放到后面清，
中间任何一次意外复位都会让原因丢失——故障排查最贵的成本就是"不知道上一次为什么重启"。

## 常见错误和陷阱

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 由监督任务代替业务任务踢心跳 | 看门狗对卡死完全失效 | 心跳点放在业务任务主循环里 |
| 每个任务各喂各的 | 卡住的任务不喂，其它任务喂饱看门狗 | 汇总后统一喂，"与"语义 |
| 用 `now > last` 比较 tick | 49.7 天回绕点误判超时 | `(uint32_t)(now - last)` |
| 检测阈值 = 心跳周期 | 一次调度抖动就误报 | 阈值 ≥ 2~3 倍周期，且检查周期 < 阈值 |
| 忘记把检查周期计入检测延迟 | 实际停喂窗口比设计值大一个检查周期 | 延迟 = 阈值 + 检查周期 |
| 软件恢复窗口落在 IWDG 最坏超时之外 | 想自愈却先被复位 | 让窗口 < 665 ms，或接受复位并设计好重启路径 |
| IWDG 启动后再写 `PR`/`RLR` | 写入被忽略（保护已生效） | 先 `KR=0x5555` 解锁再写 |
| 不读 `RCC->CSR` 或读完不清 `RMVF` | 复位原因丢失/一直被当成看门狗复位 | 启动早期读，条件清 |
| 以为 `used` 能让函数进镜像 | 链接期被 `--gc-sections` 删掉 | 真实引用（如打印地址），或链接脚本 `KEEP` |
| 在 IWDG 启动后设断点调试 | 芯片被反复复位，`continue` 都跑不完 | 调试配置里冻结 IWDG |

## 故障排查方法

1. **心跳不动**：先确认心跳点是否在被监控任务里；再看该任务的 `vTaskDelay` 是否被更长的阻塞
   覆盖（本实验注入的正是这种情况）。
2. **一直 STALE 但任务看着正常**：打印 `age` 的原始值与 `last` 值，确认不是 tick 回绕误判，
   也不是把"字/字节"或"秒/毫秒"搞混。
3. **应该停喂却还在喂**：检查是否有第二个 `xSemaphoreGive`/喂狗调用点绕过健康判定。
4. **应该恢复却一直不恢复**：确认恢复门限的取值来自本轮配置（`k_rounds[next_round-1]`），
   而不是硬编码；确认 `Give` 之后被阻塞的任务真的能拿到信号量。
5. **窗口数字不对**：确认 `gap` 在覆盖 `s_last_feed_tick` 之前计算；确认时间单位是 tick 不是秒。
6. **上真板后反复重启**：先看 `RCC->CSR` 是否 `IWDGRSTF`；再核对 LSI 实际频率下的超时窗口；
   最后确认喂狗周期在最坏阻塞路径下仍小于超时。
7. **QEMU 里看门狗"不生效"**：这不是 bug。IWDG 未建模（探针 `[11]`），必须上板。

## 练习题

**基础**

1. 把 `HB_TIMEOUT_MS` 改成 150 并重新运行：预测 `stale_total`、停喂窗口、以及是否会误报。
   跑完对比预测。
2. 把 `sensor` 的周期从 100 ms 改成 450 ms（大于超时阈值）：观察系统是否把"慢但正常"的任务
   误判为卡死，并说明该阈值应如何随周期调整。

**改错**

3. 把 `hb_age()` 改成 `if (now >= s_hb_last[idx]) return now - s_hb_last[idx]; else return 0;`，
   说明它在什么时刻给出错误结论，以及为什么无符号差值没有这个问题。
4. 把喂狗调用从 `health` 移到 `io` 任务里（让 `io` 自己喂）。运行后解释为什么 `sensor` 卡死时
   系统仍然在喂狗——这就是"或"语义的失效路径。

**综合**

5. 增加第三个通道 `comm`（200 ms 周期），并让它在 R2 期间与 `sensor` **同时**卡死。要求日志
   能区分"哪个通道先超时"和"整体何时恢复"。
6. 把恢复动作改成"不解除注入，而是记录一次故障并继续停喂"，让停喂窗口超过 2000 tick。
   说明此时真板上会发生什么，以及复位后应该靠什么信息判断原因。
7. 设计一个"启动自检"：复位原因若是 `IWDGRSTF`，则进入降级模式（例如只跑最小任务集）。
   写出状态转换条件和你需要的证据（真板）。

## 已知限制

- **IWDG 全程未在硬件上运行**：计时、复位、`SR` 更新标志、`RCC->CSR` 复位原因都是"仅构建"级别。
- QEMU 时基偏差 2.90 倍，所有毫秒数字只能作比例参考。
- 恢复动作是"解除注入 + 放行信号量"，不是真实的子系统重启；后者需要板上可复位的资源。
- `xTaskCreate` 返回值未检查（教学简化），真实工程必须检查并处理堆不足。
- 只有一个 `sensor` 通道参与注入，`io` 始终健康；多通道同时故障的场景留给练习题 5。
- QEMU 的 `-M stm32vldiscovery` 只有 8 KB SRAM，链接脚本 `STM32F100RB_qemu.ld` 与真板 F103C8T6
  的 20 KB SRAM 不同，堆/栈余量不能直接外推到真板。
