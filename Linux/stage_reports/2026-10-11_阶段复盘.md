# 驱动入门 14 天阶段复盘

**周期**：Day1–Day14（2026-09-28 ～ 2026-10-11，日期按任务顺序推定）
**累计时长**：22 小时（不含未计时的 Day1，按任务预计区间中值合计）
**记录性质**：时长与日期为推定；完成内容与验证结论来自实际编译输出和 QEMU 实测记录。

## 1. 建立了什么主线

14 天可以压成一条骨架，后续任何外设驱动都是替换其中的某一层：

```text
设备怎么被发现      → platform 匹配 / 设备树 compatible
probe 拿到了什么    → 资源、GPIO 描述符、i2c_client、spi_device
数据怎么进出        → file_operations / 子系统接口（i2c_transfer / SPI / fb_ops）
并发怎么处理        → 等待队列、poll、中断上下文划分
资源怎么有序退出    → 依赖顺序释放 + 版本差异适配
```

对应的迁移关系：

| 专题 | 替换的是哪一层 |
| --- | --- |
| 设备树 | 设备的描述方式（C 代码 → dtb） |
| pinctrl / GPIO | 硬件操作的抽象（寄存器 → gpiod） |
| I2C / SPI | 通信协议的承载（自定义字符设备 → 子系统） |
| framebuffer | 对上暴露的接口形态（自建 /dev → 标准 /dev/fb0） |

## 3. 哪些只是"见过"

- `request_threaded_irq` 的线程化中断：只在源码和课程示例里见过，没有真实中断源验证。
- framebuffer 的页寻址与 SSD1306 时序：`fb_ops` 只保证 `/dev/fb0` 可读写，屏上是否正确显示未验证。
- pinctrl 的设备树绑定：QEMU 用 `basic-mmio-gpio` 绕过了复用配置，真实 SoC 的 pinmux 未接触。
- 启动链、设备树编译进镜像的完整流程：只做过独立 dtb 加载。

## 4. 哪些代码能看懂

- `file_operations` 各回调的职责边界与返回值语义。
- platform 与 I2C/SPI 的 probe/remove 生命周期和 drvdata 用法。
- 设备树属性到驱动变量的读取路径（`device_property_read_*`）。
- 等待队列 + `poll` 的唤醒链，以及"先判条件再睡"的顺序要求。

## 5. 哪些代码敢改

- 在已有驱动上加一个 ioctl 或 sysfs 属性。
- 把手写字符设备换成子系统接口（例如用 `at24` 替代自写 EEPROM 驱动）。
- 调整资源释放顺序并验证 `rmmod` 可重复执行。

**仍不敢改**：中断上下文里的并发推理、framebuffer 与 fbcon 的交互、跨内核版本的子系统 API 迁移（需要逐项查证而非试错）。

## 6. 本轮暴露的问题类型

| 类型 | 实例 | 教训 |
| --- | --- | --- |
| 宏名冲突 | `key_init` 与 `<linux/key.h>` 宏 | 模块入口命名要避开内核头文件的宏 |
| API 重命名 | `from_timer` → `timer_container_of`、`del_timer_sync` → `timer_delete_sync` | 用 `container_of` 或版本分支 |
| 签名变更 | 6.11 起 `.remove` 返回 `void`；6.3 起 `i2c_driver.probe` 少了 `id` | 教材示例不等于当前内核可编译 |
| 用错子系统 API | I2C 设备调用 `platform_set_drvdata` | drvdata 必须走所属总线的接口 |
| 功能缺件 | 缺 `fb_ops` 导致 `/dev/fb0` 不可读写 | 文档写过的操作要回到代码确认支持 |
| 构建环境 | `ARCH` 未 export、`CONFIG_SPI` 是 bool | 交叉编译失败先查环境，不查代码 |

## 7. 下一阶段选择

| 方向 | 前置条件 | 建议 |

| 板级 BSP | 需要开发板 | 与目标岗位（嵌入式）最贴合，优先 |
